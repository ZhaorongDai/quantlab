<decisions>
Two calls the brief asked me to make explicitly.

**The `commit=` / step problem (facts 3 + 4) — resolved with an explicit `step`, never `commit=`.**
`_WandbEvalCallback` records the epoch it just logged on the head (`self._head._last_log_step = epoch`); `_record_feature_importance` then logs the chart payload with `step=self._last_log_step`. In wandb, logging at a step **equal to the current step** merges into that row; a bare `log(...)` with no step commits the row and advances the counter, which is exactly the desynchronisation fact 4 warns about. So the per-round step sequence stays `[0, 1, ..., N]` and the chart row lands *inside* step N. `commit=` is rejected on two independent grounds: it is not in this project's recorder protocol (`log(data, step=None)`, 11 call sites, both test doubles), so production code passing it would raise `TypeError` under every existing test; and `commit=False` parks a row waiting for a next `log` that never comes. **Neither `FakeRecorder` is modified — `tests/test_ml_models.py` is not touched at all.**

**Module-level vs deferred `import wandb` (fact 2) — module-level.**
Measured above: wandb is already in `sys.modules` by the time `xgb.py` finishes importing, because `quantlab/base/model.py` imports it at module scope, so the import cost of adding it here is a dictionary lookup. Module scope also matches the house style (`base/model.py:13`, `base/backtest.py:9`), and a deferred import buried inside best-effort telemetry is precisely where an `ImportError` would surface as a mid-training surprise instead of at startup.

**D-04 (top 30) is kept as given.** Nothing in the code fights it: the bar chart gets a 30-row table, the full table gets all of them, and with fewer than 30 factors the two are identical, which is what the 3-factor tests exercise.
</decisions>
