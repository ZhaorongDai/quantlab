<objective>
Make the dense full-US-equity panel materializable on a 16 GiB machine by
densifying and writing it one time window at a time, and make index-masking
alignment report the index members that market data does not cover.

Purpose: `--to-zarr` on the full 2006-today window is refused today (7.19 GiB
dense vs a 4.00 GiB budget) because `StockDataset._raw_data_to_xr()` holds the
~29.6M-row frame, the dense grid and conversion scratch at once. The guard is
correct; what is missing is a path that makes the full window achievable.

Output: a chunked densify-and-append ingestion path, a per-chunk sizing guard
with a whole-range advisory, a chunk-level resume ledger, and a
membership/market alignment component with an explicit missing-member report.

**Decision IDs used throughout.** D-01 time chunking is the mechanism; D-02 the
symbol axis is computed once over the whole range before any window; D-03
yearly default granularity, CLI-configurable; D-04 chunks are the resume unit;
D-05 `assert_dense_panel_fits()` stays, ahead of the download, applied
per-chunk with a whole-range advisory; D-06 missing constituents reported with
count and symbol list, timestamps inner-joined without reporting; D-07 Tiingo
is assumed to serve delisted history and the D-06 report is what makes that
assumption falsifiable — no fallback data source is designed.

<design_rationale>
## Where the chunked-write capability belongs (the argued choice)

The technical notes ask for `XrBackend` vs `StockDataset` to be argued rather
than picked silently. The answer is that "chunked writing" is not one
responsibility, it is three, and they land in three different places:

1. **Incremental bytes onto the medium — `XrBackend.append()`.**
   `DataBackend.write()` is already the storage-medium contract: "how the
   in-memory object reaches this medium". "How it reaches this medium
   incrementally" is the same concern at the same altitude, so it goes here.
   Every xarray-backed dataset gets it free — the membership panels today, an
   unstructured-source panel later. What must NOT move here is anything that
   needs `config`: the backend has no `raw_data_dir_path`, no `start_date`, no
   knowledge that its data came from parquet, and giving it any of those
   would break the medium-agnostic contract that lets `PlBackend` exist.

2. **Window boundaries and the resume ledger — `base/chunking.py`.**
   Both are pure functions of a timestamp axis and a JSON sidecar. They
   depend on no dataset, no backend and no config, so they are a leaf module
   (zero project-internal imports, the same rule `dataset/cleaning.py`
   follows) and are unit-testable without touching disk or a Dataset.

3. **The loop that ties them together — `BaseDataset.from_raw_data_chunked()`.**
   It needs `config.zarr_file_path`, `_clean()` and `data_backend` — all
   `BaseDataset` members — so it is the dataset layer's job. It reaches the
   raw source through TWO new overridable seams, and only those two are
   subclass business:
   - `_raw_axes_in_range()` — the pinned symbol axis AND the observed
     timestamp axis, from one scan.
   - `_raw_data_to_xr_window(start, end, symbols)` — densify ONE window onto
     the pinned axis.
   Both ship with a correct-but-unbounded default derived from the existing
   `_raw_data_to_xr()`, exactly the idiom `BaseDataset._reset_symbols()`
   already uses (a seam whose default is the historical behaviour, overridden
   where that behaviour is wrong). They are NOT `raise NotImplementedError`
   stubs — D-03 of Phase 03.1 split the hierarchy specifically to avoid those.
   `from_raw_data_chunked()` warns when `type(self)` has not overridden the
   windowed densifier, because for such a class chunking bounds the WRITE but
   not the DENSIFY and the memory win is absent.

`StockDataset` is the only class that overrides them today, because it is the
only one whose raw source (a polars `LazyFrame` over parquet) can push the
date filter down BEFORE materialisation. That is precisely why the
orchestration must not live on `StockDataset`: the ability to push a filter
down is per-source, the loop is not.

## Two chunk planners, one period rule

Sizing runs BEFORE the download, when no timestamp axis exists yet, so it can
only use calendar arithmetic — which is fine, because `estimate_dense_panel()`
is already a 252/365.25 approximation by design. The write loop runs after,
when the real axis exists, and MUST use it: calendar boundaries would produce
phantom rows for weekends and holidays. So `TimeChunkPlanner` exposes both,
sharing one private period-key function so their granularity definitions
cannot drift, with `plan_calendar`'s docstring stating it is sizing-only.
</design_rationale>
