<objective>
`BaseDataset` gains `update()` -- the automatic incremental entry point,
symmetric with the `Factor.update()` that landed hours ago -- and the choice
between `widen` and `rebuild` is made from raw-layer EVIDENCE rather than from
a caller-supplied flag.

Today the strategy is a command-line flag threaded straight through
(`ingest_us_equity.py:493` -> `from_raw_data_chunked(on_new_listing=...)`),
defaulting to `refuse`. The two strategies differ SEMANTICALLY, and
`quantlab/base/data.py`'s own warning says so: a widen does not re-read raw, so
history the vendor already has is not recovered.

- A **genuinely new listing** has no raw rows over the store's history. NaN is
  the CORRECT value; `widen` is right and cheap.
- A symbol **newly admitted to a widened roster** DOES have raw rows over that
  history. `widen` fills them with NaN and afterwards the store is
  indistinguishable from one where the data never existed.

That is a live condition in this repository, not a hypothesis. Measured at
planning time against `data/data/us_equity/1d/us_all.zarr` (21 timestamps x
7,700 symbols) and its real raw tier: **56 symbols are present in raw and absent
from the store, and exactly one of them -- `VSTD` -- carries 21 raw rows inside
the store's extent, which is every timestamp the store has.** A `widen` today
NaNs `VSTD` out completely, and nothing reports it.

Purpose: make the widen-vs-rebuild choice a fact read from the raw tier instead
of a parameter a user can get silently wrong, and close the `data_vars` axis gap
on the chunked path the way `260907-vyr` closed it on the factor path.
Output: `BaseDataset.update()`, an evidence probe seam with a hive-pruned
`StockDataset` override, a three-way resolver that speaks its decision, and a
three-axis reconciled per-window write.
</objective>

<decisions>
Recorded so a later reader does not "align" any of these away.

- **D-01 -- `update()` wraps, it does not duplicate.** `from_raw_data_chunked`
  already owns axis pinning, window planning, ledger consistency, resume, the
  per-window loop and rebuild-aside restoration. An update needs every one of
  them verbatim. `update()` is therefore a thin forwarding method, and the ONLY
  difference between the two entry points is where the strategy comes from.

- **D-02 -- the resolver lives in `_reconcile_new_listings`, not in
  `update()`.** Measured: hoisting it into `update()` costs a second
  `_raw_axes_in_range()` (4.51 s on the real tier) and, worse, creates a second
  place that decides whether the axes drifted. One drift-detection site.

- **D-03 -- the sentinel is `object()`, not a string.** A string sentinel would
  be a second public way to ask for automatic: reachable from
  `--on-new-listing`, from a config file, from a JSON round-trip. A non-string
  object is reachable only from code holding the private attribute, which makes
  `update()` the single public route STRUCTURALLY rather than by convention --
  the same reasoning the volume guard's structural arm follows (STATE.md,
  03.2).

- **D-04 -- `NEW_LISTING_STRATEGIES`, the CLI choices, and
  `from_raw_data_chunked`'s default are all UNCHANGED.** The design constraint
  is honoured literally: a caller passing an explicit strategy today sees
  byte-identical behaviour.
  `tests/test_ingest_tiingo_universe_wiring.py` (the `refuse`-default wiring
  assertion) and the five existing `on_new_listing` tests in
  `tests/test_chunked_ingest.py` stay green untouched.

- **D-05 -- a REMOVED symbol resolves to `refuse`, not to a strategy.** `widen`
  cannot express it (superset refusal, verified) and `rebuild` would drop the
  removed symbol's stored history. The automatic path is allowed to be
  conservative; it is not allowed to be destructive. The developer's decision
  text scopes the widen-vs-rebuild question to ADDED symbols, so this branch
  deliberately does not invent an answer.

- **D-06 -- the probe is a seam with a working default, not an abstract
  method.** Follows `_raw_axes_in_range` / `_raw_data_to_xr_window` exactly: a
  correct-but-not-memory-bounded default on `BaseDataset` derived from
  `_raw_data_to_xr_window`, with a run-time warning when it has not been
  overridden, so `SpotKlineDataset` and `IndexConstituentDataset` -- neither of
  which overrides the densify seams -- keep working unchanged.

- **D-07 -- the probe window is the STORE's append-dim extent.** Using the
  config's range instead would make every genuinely-new listing look like
  evidence and trigger a needless whole-store rebuild. Measured: on this repo's
  own store those two windows differ by eleven months.

- **D-08 -- the per-window write becomes `widen_and_append` for ALL chunked
  callers, and this is an argued behaviour change rather than an oversight.**
  Three grounds. (1) When the symbol axis and the variable set agree --
  every existing test and every existing production call --
  `widen_and_append` delegates to the identical `append()`, and an absent store
  delegates too, so existing behaviour is preserved by construction; applying
  the swap live left the suite at 568 passed. (2) `on_new_listing` expresses
  intent about the SYMBOL axis only, so no explicit caller's stated intent is
  being overridden on the variable axis. (3) The dangerous shape -- a vendor
  column RENAME -- presents as one variable missing plus one new, and the
  MISSING half is still refused unconditionally, so it still halts. The
  alternative, a conditional writer keyed on the sentinel, would put two write
  paths in one loop and give the guard ordering two places to drift.

- **D-09 -- the decision is logged, not gated behind a checkpoint.** The
  developer accepted the cost ("a wrong `widen` loses data invisibly while a
  `rebuild` is merely slow"), so the run proceeds; what it may not do is
  proceed silently. The report is bounded to the top 20 qualifying symbols by
  row count and states that it is truncated, so a 500-symbol admission does not
  produce 500 log lines.

- **D-10 -- no CLI flag is added, and this is recorded rather than dropped.**
  `Factor.update()` has no CLI either, so symmetry argues against one, and the
  operator-facing report the developer asked for already reaches the terminal
  through loguru from inside the library. A todo is filed so the question is
  the developer's to answer rather than silently decided:
  `.planning/todos/pending/2026-09-08-wire-dataset-update-into-the-ingest-cli.md`.

- **D-11 -- no gap guard is added anywhere.** Load-bearing, per the design
  constraint: `TimeChunkPlanner` builds windows whose edges are OBSERVED
  timestamps, so gapped appends are normal for market data and a gap check
  reddens 22 tests. Nothing in this plan reads or compares window adjacency.

- **D-12 -- overlap stays unconditionally refused.** `update()` reaches
  `XrBackend.append` through `widen_and_append` and inherits the 260907-uac
  refusal. No `mode`, `force` or `overwrite` parameter is introduced on any new
  method. Re-deriving a stored range remains the wholesale interface's job.
</decisions>
