# Quick Task 260908-0f4: Give Dataset an Automatic Update Interface — Summary

`BaseDataset.update()` now brings a store up to date and reads the
widen-vs-rebuild choice off the raw tier instead of taking it as a flag, and the
`data_vars` axis is reconciled on the chunked write path.

## What Was Built

**Task 1 — the evidence primitives** (`cad9fdb`)

- `BaseDataset._stored_append_extent(store_path, append_dim)` — the store's
  first and last append-dim label, or `None`. Coordinate-only and lazy like
  `_stored_symbol_axis`. Endpoints taken by **indexing after a length check**,
  never by reduction: this repo's own `stock_alpaca.zarr` carries a zero-length
  `timestamp` axis and a reduction over it raises.
- `BaseDataset._added_symbols_with_raw_history(added, start, end)` — an
  overridable seam returning `{symbol: in_window_row_count}`, with a
  correct-but-unbounded default and a run-time warning when it is the one
  running, so `SpotKlineDataset` and `IndexConstituentDataset` keep working.
- `StockDataset._added_symbols_with_raw_history` — the hive-pruned override,
  built on the existing `_scan_raw` so the `month=` pruning, the vendor
  assertion and the dedup come along rather than being re-derived.

**Task 2 — the resolver and the entry point** (`65dc287`)

- `BaseDataset.update(granularity, ledger_path, append_dim)`. No strategy
  parameter. Forwards everything else to `from_raw_data_chunked` verbatim.
- `_resolve_new_listing_strategy(added, removed, store_path, append_dim)`,
  wired into `_reconcile_new_listings` at exactly one point — after
  `added`/`removed` are computed, before the three untouched branches.
- `_AUTOMATIC = object()`, a non-string sentinel, plus
  `NEW_LISTING_REPORT_LIMIT = 20`.
- The rebuild decision is logged before the rebuild runs, naming qualifying
  symbols with their row counts, sorted by descending count, capped at 20 and
  saying so when it truncates.

**Task 3 — the third axis** (`c8bba70`)

- The single per-window write became
  `self.data_backend.widen_and_append(..., fill_values=self._widen_fill_values())`.
- `example/chunking.md` steps (4) and (6) re-pointed, plus a new section
  contrasting the two entry points.
- The no-CLI-caller question filed as a todo (D-10) rather than decided.

### The one real divergence: M9

The plan predicted that adding the sentinel to `NEW_LISTING_STRATEGIES` would
redden the CLI-choices assertion in `tests/test_ingest_tiingo_universe_wiring.py`.
It did not, and it **structurally cannot**. That test asserts

```python
assert list(action.choices) == list(BaseDataset.NEW_LISTING_STRATEGIES)
```

— a comparison against the **derivation**, not the contents. When the tuple grows,
the choices grow with it and the equality still holds. So it is blind to what
goes *into* the tuple; it only pins that the CLI does not restate it.

The protection the plan wanted does exist, and turned out to be broader than the
plan's own accounting: **three** tests redden under M9 — the new
`test_the_sentinel_is_absent_from_the_published_strategies`,
`test_no_string_reaches_the_automatic_branch`, and the pre-existing
`test_an_unknown_strategy_lists_the_accepted_values` in `test_chunked_ingest.py`
(which iterates the tuple asserting each member appears in the error message; an
`object()` does not). The threat T-0f4-04 is mitigated. Only the plan's
identification of the guardian was wrong.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] `XrBackend.widen_data_vars` corrupted the coordinate dtype, making variable widening unreachable for every real store**

- **Found during:** Task 3, immediately after swapping the per-window write.
- **Issue:** the filler was built with
  `coords={name: stored[name].values for name in dims if name in stored.coords}`
  and written with `to_zarr(mode="a")`. That is not a no-op. Measured live: zarr
  records `symbol` as `object`, `xr.open_zarr` **decodes** it to numpy's
  `StringDType()`, and writing the decoded array back raises
  `ValueError: Mismatched dtypes for variable symbol between Zarr store on disk
  and dataset to append` — **from inside `widen_data_vars`**, before the filler
  lands. Any store carrying a string coordinate could not be variable-widened at
  all, which is every real store in this project. Reachable from
  `Factor.update()` too, not just from this task's change; the existing
  `tests/test_variable_axis_widening.py` fixtures build their stores with a
  different encoding path and never surfaced it.
- **Fix:** the filler now carries only its dims. Zarr aligns it positionally
  against the arrays already on disk, so the coordinates stay exactly as
  written. Verified: stored values bit-identical, coordinates untouched, the new
  variable all-fill across the store's whole extent, and the following
  `append()` succeeds.
- **Files modified:** `quantlab/dataset/backend.py`
- **Commit:** `c8bba70`
- **Regression lock:** Task 3's tests are what found it and are what hold it;
  `tests/test_variable_axis_widening.py` and `tests/test_symbol_axis_widening.py`
  stay green untouched. No test was added for it, so the 592 total is unaffected.

**2. [Rule 3 — Blocking] `update()`'s docstring tripped the plan's own D-12 gate**

- **Found during:** Task 3's verification gate, which failed on its first run
  despite `592 passed`.
- **Issue:** the docstring promised "There is no `mode`, `force` or `overwrite`
  parameter". The gate greps non-comment lines for `\bforce\b`, and a docstring
  is not a comment — so prose *asserting the absence* of a loosening keyword read
  as its presence. Fail-closed: it would false-red a correct implementation,
  never pass an incorrect one.
- **Fix:** reworded to "no `mode` parameter, nothing named to loosen or bypass a
  guard", which states the same guarantee without the token. The gate was **not**
  edited. The structural version of the same claim is asserted by
  `test_update_exposes_no_strategy_parameter`, which pins the exact parameter set.
- **Commit:** `c8bba70`
