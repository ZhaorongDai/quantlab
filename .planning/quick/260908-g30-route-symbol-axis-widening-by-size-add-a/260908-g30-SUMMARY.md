# Quick 260908-g30: Route symbol-axis widening by size Summary

**`XrBackend.widen_symbol_axis` now sizes the widened panel before it writes anything and picks between the shipped whole-store rewrite and a new block-by-block one, so a 43.9 GiB allocation triggered by a single IPO becomes a bounded loop — behind an unchanged public signature, with the switch reported loudly and both paths measured to leave identical stores.**

## Accomplishments

- **The factor layer got the bound it had none of.** `Factor.update()` reaches `widen_symbol_axis` as its ONLY path — `Factor` has no raw tier, so `BaseDataset`'s `on_new_listing="rebuild"` escape does not exist for it. Routing arrived there for free: no call site in `quantlab/` changed, and `tests/test_factor_update.py` proves the chunked loop runs from the factor side rather than merely from the backend suite.
- **Both strategies ship behind one router**, decided on the brief's own timing table rather than on caution. Chunked runs 1.2x / 4.0x / 3.6x the whole-store wall clock on 0.2 / 34.6 / 137.3 MiB stores, so replacing the whole-store path outright would tax every routine widen ~4x to buy nothing.
- **The two paths are observationally identical**, and that is asserted rather than assumed: values element for element (`equal_nan=True`), both coordinates, the on-disk chunk grid, and the `symbol` coordinate's on-disk encoding — the last read straight off zarr, never through the decoded `xr.open_zarr` value that hid the 260908-dvv defect.
- **The block size is what makes the grids agree.** The first block carries `encoding=self._append_encoding(...)`, so the block length decides the store's append-dim chunk. Flooring the block onto `APPEND_DIM_CHUNK` and a multiple of it makes `min(APPEND_DIM_CHUNK, first_block_len) == min(APPEND_DIM_CHUNK, total_len)` identically — measured: a 100-row block leaves `(100, 3)` where 512 leaves `(512, 3)`.
- **The switch is not silent, and the routine path is not noisy.** Chunked logs a `warning` naming both symbol counts, the estimate and the budget in GiB, rows per block, block count, per-block size, the ~3.6–4.0x wall-clock cost (so a slow run reads as the strategy, not the machine), and how to opt back. Whole-store logs one `info` line.
- **Three now-false cost claims were retired** rather than left to age, each gated by a grep that fails today and passes only once the prose is actually rewritten.

## Decisions Made

All six settled decisions (D-1 … D-6) were implemented as written. Three implementation-level choices were made inside them:

1. **The plan-checker's advisory was resolved by hoisting the whole-store write inside `stored`'s lifetime**, which is what makes D-3 ("the chosen strategy runs INSIDE the `try:` whose `finally` closes `stored`") and Task 1's "carries the shipped body verbatim" both true — "verbatim" being about the write SEQUENCE (`reindex().load()` → `_append_encoding(...)` → one `to_zarr(mode="w", encoding=...)`), not the line position. Both `os.replace` calls still follow the close, in the shipped order. The third reading the advisory offered (router keeps the close outside and passes the handle explicitly) was NOT taken: `_widen_chunked` needs `stored` open for its whole loop, so the close has to move regardless, and moving it once for both strategies is one rule instead of two.
2. **The two strategies carry ONE signature, including a `block_rows` that `_widen_whole_store` accepts and ignores.** The router then selects by name and calls identically. The alternative — each strategy taking what it needs — gives the router two call sites to drift apart, which is the shape this repo has already been bitten by.
3. **The report was extracted into `_report_widen_strategy`** rather than inlined in the router. The router's job is the decision; a fifteen-line f-string in the middle of it obscures the four lines that actually branch. Private, single-caller, and the asymmetry is documented in one place.

## Deviations from Plan

**None** — plan executed as written. Three notes on judgement calls made inside the plan's own latitude:

- **`_widen_blocks` is an extra private helper the plan did not name.** It exists because the block offsets are needed in TWO places — the loop and the reported block count — and computing them twice is exactly how a report and a loop come to disagree. It also carries the `max(timestamps, 1)` guard so a zero-length append dim still writes one block rather than leaving no sidecar for the swap to rename in.
- **`test_the_block_size_rule_floors_onto_the_chunk_grid` takes no `symbol_encoding` fixture and is NOT in `_EXEMPT`.** It exercises `_widen_block_rows` as integer arithmetic — no panel, no store — so the family guard's store-touching detector never counts it and no exemption is needed. This is why the re-derived `checked` literal is 40 over 42 tests rather than 41; the distinction is written into the comment beside the literal so a future reader does not "fix" it.
- **`LONG` in `tests/test_factor_update.py` is HOURLY, not daily.** `Factor.update()` runs `_auto_filter()` first, which clips to the factor config's `2024-01-01..2024-12-31` window; a 600-DAY range would come back as 366 rows, below the 512-row block floor, and the multi-block assertion would then be vacuous — the exact failure mode the plan's 600-row rule exists to prevent. Hourly keeps all 600 rows inside the window. Still an argument to the existing `PanelFactor.cal()`, so `found` is unaffected.
