<objective>
Make the Tiingo bulk backfill range-aware and quota-aware.

Three defects, all observed in a real 14,674-symbol run on 2026-09-06:

1. **Watermarks record only the END date.** `_run` skips a symbol when
   `_read_watermark(symbol) != self.config.end_date`. Widening `--start-date`
   on a later run therefore silently skips every already-fetched symbol and
   yields a dataset with inconsistent per-symbol history depth, with no
   warning. This is the project's recurring silent-wrong-data failure mode.
2. **Quota exhaustion is treated as an ordinary per-symbol failure.** After
   4,638 successes Tiingo returned an over-allocation error; per-symbol
   failure isolation then caught it for every remaining symbol and continued
   at ~260 sym/s. Roughly 10,000 symbols were burned as fast-failing requests
   that may themselves have deepened the lockout.
3. **There is no way to wait out the window and resume.** The account's
   hourly allocation is empirically ~4,600 requests, so 14,674 symbols needs
   roughly three hourly windows.

Purpose: stop shipping a dataset whose per-symbol history depth is silently
inconsistent, and stop self-inflicting a deeper vendor lockout.

Output: a range-recording watermark schema with an explicit, user-supplied
migration; a global quota-abort path distinct from per-symbol failure; and an
off-by-default wait-and-resume switch.

**Why this plan has no `type="tracer"` task.** The architecture is already
proven and shipped — `ConcurrentTiingoAcquisition` runs end to end today, and
this plan changes three independent behaviours inside it. A thin vertical
slice through layers that already work would add no information. This is the
documented `--no-tracer` case: decompose by behaviour, not by layer.
</objective>

## Arguing D-04: what an un-stamped legacy watermark means

D-04 asks for the un-stamped case to be a deliberate, argued choice. Three
options exist and two of them are wrong:

- **(a) Assume the covered start was `2016-01-01`.** Forbidden outright by
  D-04. An assumed range that is wrong produces exactly the silent gap this
  change exists to prevent, and it produces it invisibly.
- **(b) Treat unknown coverage as "not covered" and re-fetch.** Correct for
  data integrity, and it violates D-01: it re-downloads 4,621 symbols and
  burns an entire hourly window for nothing.
- **(c) Treat unknown coverage as covering the request for SKIP purposes, and
  say so loudly on every run until stamped.**

**(c) is the default, and (b) ships as an opt-in escape hatch.**

The reasoning: what makes D-03's failure mode dangerous is *silence*, not the
skip. A run that skips 4,638 symbols while printing their exact count, the
fact that their covered start is unknown, and the one command that resolves
it, is not a silent gap — it is a reported one with a named cure. The user is
the only party who knows those symbols were fetched from `2016-01-01`, which
is precisely why D-04 makes stamping user-supplied.

Making it a knob (`legacy_watermarks`: `"warn"` default, `"refetch"`
alternative) is what turns this from an accident into a choice. Nothing here
invents a start date: `_read_coverage()` on a legacy file returns
`start_date=None`, and Task 1 pins that with a dedicated test so a future
"helpful" default cannot be added without turning the suite red.

<design>
## Watermark schema: purely additive

Current on-disk form, all 4,638 files: `{"last_date": "2026-09-06"}`.
New form: `{"start_date": "2016-01-01", "last_date": "2026-09-06"}`.

`last_date` is deliberately NOT renamed to `end_date`. Keeping the existing
key means new code reads old files and old code reads new files — the schema
is both backward and forward compatible, and no reader anywhere crashes. A
repo-wide grep confirms the only readers are `base/acquisition.py` and
`acquisition/tiingo.py`, both of which this plan owns.

`_read_watermark(symbol) -> str | None` keeps its exact current signature and
meaning (the last covered date). Both `base/acquisition.py`'s sequential
`refresh()` and `ConcurrentTiingoAcquisition._attempt()` call it to compute an
incremental start, and neither needs to change. Range awareness arrives as a
NEW sibling, `_read_coverage(symbol) -> dict | None`, returning
`{"start_date": str | None, "last_date": str | None}`.

## Coverage predicate

A symbol is covered by the requested window iff:
- its `last_date` equals `config.end_date`, AND
- its `start_date` is known AND is lexicographically `<=` `config.start_date`.

ISO-8601 `YYYY-MM-DD` strings order correctly under plain string comparison,
so no date parsing is needed and no timezone can creep in.

If `start_date` is unknown, the `legacy_watermarks` knob decides (see
`<decision_record>`).

If a stored `start_date` is LATER than the requested `config.start_date`, the
symbol is not covered and is re-fetched. That is the D-03 fix, and the run
reports the count under its own heading so widening the window has a visible,
countable consequence.

## Why recording the request window as coverage is truthful

`_fetch_and_write` writes with `data.write_parquet(out_dir / "data.pqt")` —
a whole-file overwrite, not an append. After a successful fetch the file
contains exactly the requested range and nothing else. Recording
`config.start_date` as the covered start after a successful `download()` is
therefore a true statement about the file, including in the narrowing case.

`refresh()` is different and must not overwrite the recorded start: it fetches
from the symbol's own `last_date` forward, so the covered start is whatever it
already was. If it was unknown, it STAYS unknown — refresh does not invent one
(D-04).

## Quota detection

Grounded in `<observations_at_planning_time>`, a helper walks the exception and
its `args` looking for an object exposing a `.response` with a `.status_code`,
because `RestClientError` does not expose `.response` directly but its
`args[0]` `HTTPError` does.

An error counts as quota exhaustion iff EITHER:
- **(A) structured:** the reachable status code is in `QUOTA_STATUS_CODES`, or
- **(B) textual:** a durable token appears, case-insensitively, in the
  reachable response body or in `str(exc)`.

`QUOTA_STATUS_CODES` is `frozenset({429})` only. `403` is deliberately
EXCLUDED: Tiingo also returns 403 for plan-restricted tickers, which is a
per-symbol condition, and treating it as global would let one restricted
ticker abort a 15k-symbol run. A 403 whose body carries the quota wording is
still caught by rule (B), so the strictly-safer status set costs nothing.

The textual token is `"request allocation"`, held in one class constant. The
observed body was `"Error: You have run over your hourly request allocation.
Contact us at support@tiingo.com to have these lifted."` A full-string match
would break the moment the vendor says "daily" or "monthly" instead of
"hourly", or edits its support address. `"request allocation"` survives all of
those. It is still text matching and it is still brittle — that brittleness is
a conscious choice, it lives in exactly one named constant, and Task 2 tests
it in both a 429-status form and a status-free textual form so either signal
alone is proven sufficient.

## Thread safety and clean termination

The abort flag is `threading.Event`. It is thread-safe by construction, needs
no surrounding lock, and its `wait(timeout)` is exactly the primitive the
resume delay wants. A fresh `Event` is created per pass of the resume loop so
a previous pass's trip cannot poison the next.

Stopping mid-stream interacts with `return_as="generator_unordered"` on two
levels, and only one of them is load-bearing:

- **Task level (load-bearing).** `_attempt` checks the event as its FIRST
  statement and returns a skipped marker immediately, issuing zero vendor
  requests. joblib cannot cancel work it has already queued, so this is the
  only mechanism that reliably stops the burn. Every remaining symbol becomes
  a no-op returning in microseconds.
- **Generator level (optimisation only).** The input generator also checks the
  event and stops yielding, so joblib stops queueing new batches. With
  `pre_dispatch` batching this helps but cannot be relied on alone, which is
  why it is not where the guarantee lives.

The result generator is **drained to completion, not abandoned**. Breaking out
of a joblib result generator mid-iteration leaves worker-thread teardown to
garbage collection; draining is deterministic, and it is now nearly free
because every remaining task is a no-op. The `tqdm` bar therefore terminates
by finishing normally rather than by being killed. To keep the racing bar from
reading as "all this work succeeded", its description is switched at abort
time to say the remainder is being drained, and the real completed/remaining
counts are reported from the results afterwards — never from the bar.

## Quota classification vs. per-symbol failure

`_attempt` currently returns `(symbol, message_or_None)`. It grows to
`(symbol, status, message)` with `status` in `{"ok", "failed", "quota",
"skipped"}` (private method, private call site, no external contract).

- `"failed"` → per-symbol manifest, no watermark, retried next run. Unchanged.
- `"quota"` → trips the abort event; **excluded from `_failures.json`**,
  because recording a global condition as one ticker's fault would defame a
  perfectly good symbol and make the manifest lie about what the last run did.
- `"skipped"` → never attempted; no watermark, not a failure, counted for the
  report only.

## Wait and resume

`_run` becomes a bounded loop. Each pass recomputes `pending` from the
watermarks on disk, which means the resume logic IS the existing skip logic —
no parallel bookkeeping that could drift. If a pass trips the abort and the
opt-in switch is on and waits remain, the run logs the delay and sleeps via an
overridable `_sleep()` seam (so tests patch it and assert call counts without
waiting), then loops.

**What is assumed and what is not.** Tiingo's reset semantics — fixed
top-of-hour bucket versus rolling window — are NOT established, and this plan
does not claim to know them. The design is therefore a configurable
`quota_wait_seconds` with a bounded `quota_max_waits`, not a computed
resume-at instant. The `3600` default is chosen because the observed message
said "hourly", and a full-hour delay measured from the moment of detection
covers a rolling one-hour window exactly and a fixed top-of-hour bucket
strictly. The `3` default for `quota_max_waits` comes from the observed
arithmetic: ~4,600 requests per window against 14,674 symbols is roughly three
windows. Both defaults are stated as assumptions in the docstring, not as
vendor facts.

## Knobs (all via the existing `_knob` idiom, D-06)

| Knob | Default | Meaning |
|------|---------|---------|
| `legacy_watermarks` | `"warn"` | `"warn"` = skip un-stamped legacy watermarks but report them every run; `"refetch"` = treat unknown coverage as uncovered |
| `wait_for_quota` | `False` | Opt-in wait-and-resume |
| `quota_wait_seconds` | `3600` | Delay between resume attempts |
| `quota_max_waits` | `3` | Bounded number of resume attempts |
</design>
