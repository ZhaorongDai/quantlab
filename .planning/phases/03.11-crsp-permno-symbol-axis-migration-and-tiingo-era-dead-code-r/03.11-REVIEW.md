## Summary

The axis migration itself holds up under attack. I traced every stringification /
sort / cross-dtype comparison site the phase touched and could not find a
remaining place where a symbol label is silently coerced on a data path:
`XrBackend.widen_symbol_axis` (backend.py:501-508), `widen_and_append`
(backend.py:1247-1271), `BaseDataset._stored_symbol_axis` (data.py:858),
`_raw_axes_in_range` on all three implementations, `BaseModel._save_model` /
`_read_trained_symbols` / `DLModel._align_prediction_symbols`, and
`UniverseMask.symbols` / `in_window_members` / `missing_members` all now speak
the store's own spelling, and the two `str()` casts that had to SURVIVE
(`_added_symbols_with_raw_history` in both `base/data.py:904` and
`dataset/stock.py:545`) are still there. Deletion completeness checks clean:
`exclude_non_common`, `is_common_ticker`, `NON_COMMON_TICKER_PATTERNS`,
`symbol_overrides`, `collision_universe`, `nan_adj_at_permno_seam`,
`CrspMembership.symbol_intervals`/`_symbol_frame` have zero live references in
`quantlab/`, and the prohibited-to-delete delisting **verdict** inheritance is
intact at `crsp.py:974-987` while the symbol carry is gone. I ran the 03.11 test
files (`test_symbol_axis_contract`, `test_symbol_axis_widening`,
`test_crsp_ticker_sidecar`, `test_universe_mask`, `test_constituent_panel`,
`test_crsp_identity`, `test_crsp_dataset`, `test_crsp_symbology`,
`test_crsp_membership`, `test_crsp_constituent`, `test_no_identity_residue`,
`test_universe_filtered_factor`): 241 passed, 0 failed.

What I did find clusters in the *new* display/readability layer added by plans
09-10 and in the new rebuild ABC — not in the axis migration. Two findings are
broken invariants the code states about itself in its own docstrings
(WR-01, WR-02), one is a layering violation the phase avoided in `base/factor.py`
and then committed in `base/backtest.py` (WR-03), one is an audit-artifact
regression whose handover was never closed (WR-04), and one is a silent-failure
path in the destructive half of the rebuilder (WR-05).

## Warnings

### WR-01: `CrspTickerLookup.label()` advertises "never raises" and raises on any structurally malformed sidecar

**File:** `quantlab/dataset/crsp_tickers.py:185-205` (and `as_of` at `:161-168`)

**Issue:** The class docstring (`:27-31`) and `label()`'s own docstring (`:186`,
"**Never raises.**") establish the safety invariant T-03.11-30: *"Breaking a
backtest because an audit sidecar is absent would make the readability layer
more fragile than the thing it annotates."* Three call sites depend on that
invariant — `VectorBtBacktester._forced_liquidations`
(`engine_vectorbt.py:303`), `UniverseMask._label` (`masking.py:262`), and
`DLModel._spell` (`model.py:1312`, invoked *while constructing a `ValueError`
message*).

The guard is too narrow. `label()` catches only `(FileNotFoundError,
ValueError)` and only around the `self.payload` access at `:186-188`. Every
subsequent field access is unguarded, and `as_of` indexes `span["start"]`,
`span["end"]`, `span["ticker"]` with no `.get`. Measured on this tree:

```
payload {"intervals": [1,2,3]}                    -> AttributeError: 'list' object has no attribute 'get'
payload {"intervals": {"13407": [{"ticker":"FB"}]}} -> KeyError: 'start'
payload []                                         -> AttributeError: 'list' object has no attribute 'get'
```

Failure scenario: a sidecar restored from a `BaseStoreRebuilder.backup()` copy
of an older schema (or hand-edited, or copied beside the wrong store) is valid
JSON but wrong-shaped. `_forced_liquidations` then aborts a completed
simulation with `KeyError: 'start'` at the moment it was only trying to make a
log line prettier — exactly the fragility the docstring says cannot happen. In
`DLModel._align_prediction_symbols` it is worse: the raise at `model.py:1264`
is *replaced* by the `KeyError`, so the operator loses the real diagnostic
("the feature panel lacks N of the M symbols this model was trained on").

Test coverage confirms the gap: `tests/test_crsp_ticker_sidecar.py:396-402`
covers only *unparseable* JSON (which lands in the `ValueError` arm) and
`:343-352` covers the missing file. Nothing covers a parseable-but-wrong shape.

**Fix:** widen the guard to cover the whole body and make `as_of` tolerant of a
missing key, since this entry point's contract is "produce a string, always":

```python
def label(self, permnos: Sequence, day: date) -> list[str]:
    try:
        payload = self.payload
        intervals = payload.get("intervals", {}) if isinstance(payload, dict) else {}
        if not isinstance(intervals, dict):
            intervals = {}
    except (OSError, ValueError):
        intervals = {}
    ...

def as_of(self, permno: int, day: date) -> str | None:
    spans = ...
    for span in spans:
        if not isinstance(span, dict) or "start" not in span or "end" not in span:
            continue          # `as_of` may still RAISE for the strict caller;
                              # if so, raise ValueError naming the bad span.
```

Add a test for `{"intervals": {"13407": [{"ticker": "FB"}]}}` asserting
`label()` returns `["13407"]` rather than raising.

### WR-02: `normalize_to_axis_dtype` silently coerces `float` and `bool` labels onto an int64 axis, contradicting its own refusal contract

**File:** `quantlab/utils/symbol_axis.py:143-168`

**Issue:** The docstring at `:130-133` is unambiguous: *"A label with no
spelling in the target dtype raises `ValueError` naming the offenders and the
dtype. It does NOT coerce to something, and it does NOT drop the label: either
would hand `reindex` a request that misses silently, which is the entire
failure this function was written to remove."* The implementation delegates to
`pd.Index(materialised).astype(dtype)`, which coerces rather than refuses for
any numeric-adjacent type. Measured on this tree:

```
normalize_to_axis_dtype([10107.9, 7000.2], pd.Index([1,2], dtype='int64')) -> [10107, 7000]
normalize_to_axis_dtype([True, False],     pd.Index([1,2], dtype='int64')) -> [1, 0]
normalize_to_axis_dtype([None],            pd.Index([1,2], dtype='int64')) -> ValueError  (correct)
```

The `bool` case is the sharper one, because the *same module* explicitly
excludes `bool` from `_is_integral` (`:51-52`) with the comment "a `[True,
False]` axis would otherwise sort 'numerically' and read as a legitimate
integer universe". The two halves of the module disagree about whether a bool
is an integer label.

Failure scenario: this repo has a live, documented case of a float64 symbol
coordinate —
`.planning/todos/pending/2026-09-08-an-empty-zarr-store-records-symbol-as-float64.md`,
cited by `tests/test_widening_fixture_realism.py`. A float label reaching
`widen_symbol_axis` is truncated rather than refused, the superset guard at
`backend.py:508` then compares truncated ints against the stored int64 index
and passes, and the rewrite is promoted by `os.replace` + `rmtree`
(`backend.py:594-596`) — the same promote-then-delete sequence the module's own
header (`:21-26`) documents as the path that destroyed 12 of 12 cells silently.

**Fix:** reject any label whose round trip is lossy, rather than trusting
`astype`:

```python
    try:
        index = pd.Index(materialised)
        converted = index.astype(dtype)
        if not (pd.Index(converted).astype(index.dtype) == index).all():
            raise ValueError("lossy")
        return converted.tolist()
    except (TypeError, ValueError) as error:
        ...
```

or, minimally, reject non-integral python types up front with the same
`_is_integral` predicate `sort_symbol_axis` already uses, so the two halves of
the module agree on what an integer label is.

### WR-03: `quantlab/base/backtest.py` hard-imports a concrete CRSP vendor module — the coupling `base/factor.py` went out of its way to avoid

**File:** `quantlab/base/backtest.py:15` (import), `:183-201` (property), `:1064`

**Issue:** `base/backtest.py` now does `from quantlab.dataset.crsp_tickers
import CrspTickerLookup` at module scope and unconditionally constructs one in
the `ticker_lookup` property, which is reached on every backtest through
`_align_and_predict` (`:1064`). This is the core/abstract backtester layer
naming a CRSP-specific class.

Two things make this a finding rather than a style quibble:

1. The same phase solved the identical problem *correctly* twice, and wrote
   down why. `base/factor.py:76-105` refuses to `isinstance`-check a vendor
   class and reads a declaration off `BaseDataset.REJECTED_FACTOR_CONFIG_FIELDS`
   instead, with the comment "an `isinstance` check against a concrete vendor
   class here would add a `base -> dataset` dependency on a specific subclass,
   against this repository's one-directional layering". `base/model.py:74-82`
   takes an *injected* `(symbols, day) -> list[str]` callable for the same
   reason — "模型层不该知道任何厂商". `base/backtest.py` then hardcodes the
   vendor class that both of those avoided.
2. The repo gate does not catch it. `tests/test_extensibility_contract.py:31-34`
   scans only `base/factor.py`, `base/model.py`, `base/backend.py` —
   `base/backtest.py` is outside `CORE_LAYER_FILES`, so the protection the
   phase context assumes ("the repo has a gate") is absent on exactly the file
   that broke the rule.

Failure scenario: a vendor with no CRSP tier (Alpaca, Binance) cannot import
the backtester base without pulling in `quantlab.dataset.crsp_tickers`, and the
next vendor that wants a display sidecar has to either reuse a class named
`Crsp*` or add a second branch here. The `ticker_lookup` property is also
unconditional: it is constructed for every panel regardless of vendor, and only
degrades at `label()` time.

**Fix:** the mechanism `base/model.py` already uses. Have the concrete
backtester (`quantlab/backtest/us_equity.py` or a `MarketSpec` field) supply the
labeller, and keep `base/backtest.py` holding only a
`Callable[[Sequence, date], list[str]] | None`:

```python
# base/backtest.py -- no CRSP import
self._symbol_labeller: "Callable[[Sequence, date], list[str]] | None" = None

@property
def symbol_labeller(self):
    if self._symbol_labeller is None:
        self._symbol_labeller = self._build_symbol_labeller()  # hook, default: identity str()
    return self._symbol_labeller
```

At minimum, add `quantlab/base/backtest.py` to `CORE_LAYER_FILES` and
`CrspTickerLookup`/`CrspStockDataset` to `FORBIDDEN_SUBSTRINGS` so the rule is
machine-checked wherever it is claimed to hold.

### WR-04: the D-17 filter report's per-PERMNO `symbol` field is now a verbatim copy of its own key — the audit trail lost its human-readable name and nobody picked up the handover

**File:** `quantlab/dataset/crsp.py:1226-1258` (esp. `:1239`, `:1248-1251`)

**Issue:** `_permno_breakdown` still renders `pl.col("symbol").last()` into the
report's `symbol` field. On the ticker axis that was the dropped security's
ticker. Since `_derivation` casts `symbol` to the Int64 PERMNO
(`crsp.py:568`), `record["symbol"]` is now the PERMNO, and the emitted JSON is:

```json
"dropped_permnos": {"86755": {"symbol": "86755", "types": [...], "rows": ..., ...}}
```

The key and the value are the same number. The field carries zero information
and the `{zarr}.crsp_filter_report.json` audit artifact — whose entire stated
purpose (`crsp.py:1054-1075`, `base/config.py:151`) is to let an operator see
what the filter removed, "never applied silently" — can no longer name what was
removed in the spelling an operator recognises.

This is a dropped handover, not an accepted trade-off.
`tests/test_crsp_identity.py:585-587` says so explicitly: *"`symbol` is read off
the derivation's `symbol` column, which IS the PERMNO now (D-01). Restoring a
human-readable ticker to the report is plan 09's ticker sidecar, not a thing to
reconstruct here."* Plan 09 then enumerated its display points
(`crsp_tickers.py:22-31`) and the filter report is not among them, so the
restoration never happened, and the test now *locks in* the degraded output
(`assert qqq["symbol"] == QQQ_PERMNO_TEXT`).

Failure scenario: an operator opens `crsp_filter_report.json` to find out which
S&P members `equity_common` dropped and gets a list of bare numbers with a
redundant field — while the sidecar that could spell them sits beside the same
store, written by the same conversion, from data
(`self._ticker_intervals`) the object already holds in memory at that point.

**Fix:** spell the field from the intervals the conversion already built, or
delete it. The data is in hand at `crsp.py:1234`:

```python
# _permno_breakdown, using the already-built self._ticker_intervals
spells = (self._ticker_intervals or {}).get("intervals", {})
def _name(permno: int, last_day: str) -> str | None:
    for span in spells.get(str(permno), []):
        if span["start"] <= last_day <= span["end"]:
            return span["ticker"]
    return None
...
"ticker": _name(record["permno"], str(record["last"])[:10]),
```

and update `tests/test_crsp_identity.py:585-587` / `:1097` to assert the ticker
rather than the digits. If the decision is "digits are fine", then drop the
`symbol` key entirely — a field that always equals its own key is dead weight in
an audit artifact.

### WR-05: `BaseStoreRebuilder.clear()` swallows deletion failures and then reports the undeleted paths as deleted in a frozen "evidence" object

**File:** `quantlab/base/rebuild.py:203-230` (esp. `:225`, `:229`), consumed at `:246-257`

**Issue:** `clear()` appends `str(store)` to `removed` *before* calling
`shutil.rmtree(store, ignore_errors=True)`. `ignore_errors=True` suppresses
every `OSError` — a permission problem, an open file handle, an NFS lock — so a
partially-deleted or wholly-undeleted store produces the same return value as a
clean deletion. The tuple then flows into `RebuildMeasurement.removed`, an
object whose own docstring (`:43-47`) says *"Frozen because it is evidence. A
caller that could mutate a field after the fact turns 'what the rebuild
measured' into 'what somebody last wrote here'."* A field that reports paths it
did not actually remove is that same failure by a different route.

The safety ordering (`:20-29`) is otherwise well argued, which is what makes
this the one soft spot: `assert_inputs_present` and `backup` are both strict,
and `clear` — the only irreversible step — is the one that cannot fail.

Failure scenario: `clear()` removes the sidecars (`sidecar.unlink` at `:229`
would raise loudly, but runs *after* the swallowed `rmtree`) while the store
directory survives. `_convert()` then reaches
`CrspStockDataset._assert_anchor_unchanged` (`crsp.py:1485-1499`), which sees a
store with no adjustment sidecar and raises "the store exists but its adjustment
sidecar is missing" — an error that blames the store's history rather than the
rebuild step that half-failed, and whose suggested remedy ("delete the store
together with its `.crsp_*.json` sidecars") is the step that just failed.

**Fix:** let the deletion fail loudly and record only what actually went:

```python
        if store.exists():
            shutil.rmtree(store)          # no ignore_errors: a failed clear
                                          # must not look like a clean one
            removed.append(str(store))
        for sidecar in self.sidecar_paths():
            if sidecar.exists():
                sidecar.unlink()
                removed.append(str(sidecar))
        if self.store_path.exists():
            raise OSError(
                f"{type(self).__name__}: {str(self.store_path)!r} still exists "
                f"after clear(); refusing to convert into a surviving store."
            )
```

### IN-03: `CrspSymbology`'s no-share-class sentinel is not case-normalised while its output is

**File:** `quantlab/dataset/crsp_symbology.py:56-58`, `:110-117`

**Issue:** `_NO_CLASS = ("", "None", "NONE")` is tested against
`pl.col("shareclass").str.strip_chars()` — stripped but *not* uppercased —
while the value that survives the test is uppercased on the next line
(`:116`). A `shareclass` of `"none"` or `"None "`-after-strip variants outside
the literal tuple therefore reads as a real class `NONE`, and if
`tradingsymbol == base + "NONE"` the symbol becomes `BASE.NONE`. Low
likelihood (the live tables are documented as writing `None`/`NONE` exactly),
but the asymmetry is gratuitous.

**Fix:** `pl.col("shareclass").str.strip_chars().str.to_uppercase().is_in(("", "NONE"))`.

### IN-05: `ChunkLedger.fingerprint` stringifies symbols, so an int64 axis and a digit-string axis hash identically

**File:** `quantlab/base/chunking.py:210`

**Issue:** `"\n".join(str(symbol) for symbol in symbols)` makes `[7000, 10107]`
and `["7000", "10107"]` produce the same digest. The ledger's symbol
fingerprint therefore cannot detect the very dtype flip this phase performed:
for the all-five-digit PERMNO universe (where numeric and lexicographic order
coincide, per `symbol_axis.py:76-81`) a pre-migration string-axis store and a
post-migration int64 store are indistinguishable to `assert_consistent`.

In practice `_reconcile_new_listings` and `widen_symbol_axis`'s superset guard
catch the mismatch loudly one step later, which is why this is Info and not a
Warning. But the ledger is the *first* consistency check on the append path and
it is blind to the axis property this phase changed.

**Fix:** include the dtype kind in the digest, e.g. prefix the join with
`np.asarray(symbols).dtype.kind`, so a dtype flip is a fingerprint change.
