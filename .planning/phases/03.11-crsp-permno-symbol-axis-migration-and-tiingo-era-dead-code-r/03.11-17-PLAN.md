<assumption_delta_decision>
与 03.11-15 同族的第二次：「payload 的顶层形状在哪里被检查」此前是**一处**（`_intervals()` 内联），
而实际上有**两个**读者（`_intervals()` 与 `product_end`），第二个读者绕开了那一处。

- **现在的主名词：** `_object_payload()` —— 「一份已确认是 JSON object 的 payload」。
- **决定：`promote`。** 把内联检查提升为共享 helper 并成为主路径，`_intervals()` 里那份内联判断降级为对它的调用。
  不是 add-alongside（在 `product_end` 里再写一份 `isinstance`），那只会把「唯一一处」这句话搬个家继续说假话。
- 代价：多一层函数调用（展示路径，每实例最多一次真读盘，可忽略）。
</assumption_delta_decision>
