本 phase 确实是一次身份模型变更，不是误报，因此按 checkpoint 的要求显式作答：

- **现在的主名词（generalized identity）：`permno` —— 一个 int64 的永久证券身份。**
  在此之前主名词是「在某个日期有效的 ticker」，它是一个**派生值**（由 `stksecurityinfohist` 的区间表按日期
  算出来），而且不是单射：一个 ticker 在时间上会被多家公司用过，一家公司在时间上会换多个 ticker。
- **决定：`promote`（提升），不是 `add-alongside`。**
  PERMNO 被提升为面板的主身份，ticker 被**降级**成「某一变体的一个细节」——具体而言降级成一个 as-of 查询：
  `{zarr}.crsp_tickers.json` sidecar + `CrspTickerLookup`（plan 09）。
  理由：`add-alongside`（面板里同时带 ticker 和 permno）在此之前正是现状，而现状可以无声地把两家公司拼成
  一列并伪造跨 seam 的收益。把两个身份并列保留，等于把「哪一个是真的」留给每个下游各自决定；D-03 又已锁定
  ticker 不能作为面板变量存在（2-D 字符串变量撞三道既有守卫，1-D coord 只能存「最后一个 ticker」而丢掉
  FB→META）。所以这是一次真正的提升，不是并列。
- **被降级但没有被删的：** `ticker` 仍然是唯一对人可读的标识，所以它活在 sidecar 里，并在 6 个人可见点

  CLI 的 `--symbols` 帮助文案）被还原。
- **接受的债与它的触发条件：** 非 CRSP vendor（Tiingo / Alpaca / Binance）保留 ticker 轴（D-02）。因此
  「本仓库的 symbol 维有两种语义」这件事是**接受的债**。强制它later 收敛的触发条件：出现第一个需要把

  `checkpoint:decision` 交给 operator（D-21）。

  B 在 2010 起用同一 ticker，断言面板里是两列两个 PERMNO 且没有任何跨公司的收益。未来任何一次把单数身份
  假设重新引入的改动，这条测试会立刻变红。
