## Decisions Made

1. **`_jsonable_symbol` 按元素类型分派而不是统一。** 它的存在是为了堵「面板不经 `collect()`、后端交回 `numpy.int64`」这一路（`numpy.int64` 不是 `int` 的子类，`json.dump` 直接 `TypeError`）。统一成 `str()` 正是本 plan 要拆掉的那行；统一成 `int()` 会在 ticker 轴上崩。`bool` 显式排除（它是 `int` 的子类，但一个布尔标的轴是上游缺陷，不是整数轴）。
2. **类型守卫比较的是「类别」，不是具体类型。** `_symbol_type_name` 把 `numpy.int64` 与 python `int` 都报成 `"int"`。二者在 `.sel()` 面前等价，报成两种只会制造一条假的不匹配，把一条本来能跑的链路拦死。
3. **`_read_trained_symbols` 归一顺序但不动元素类型。** 记录里只有**成员**是权威的（`_align_prediction_symbols` 的 docstring 早就这么写），顺序由数值序契约决定；而手改过或由别的生产者写出的记录可以是乱序的。既有的 `test_dl_predict_panel_is_correct_for_an_unsorted_training_record`（三种乱序参数化）仍然绿。
4. **`missing` / `extra` 列表现在打 PERMNO 数字，本 plan 不动。** 已在代码里写明这是 plan 09 的 ticker sidecar 负责的展示层；在这里各自查一次符号学就是把那份逻辑复制到第七个地方。
5. **端到端测 chunked 全流程，而不是只测 `_raw_data_to_xr_window`。** 计划的 behavior 第 3 条只说到 `reindex` 那一层。写成端到端是刻意的，也正是这一步把 `widen_and_append` 那个破坏点逼了出来——它在方法级测试里是看不见的。
