<objective>
Close UAT gap G-03.7-7. Every normal `run_cv` fold currently logs a spurious "config.model says ... using the
checkpoint's dates" warning, and date checks compare text instead of the training window the dates select.

Purpose: two causes act together (AND-gate, `.planning/debug/run-cv-spurious-checkpoint-date-warning.md`).
(1) `run_cv` reuses the run()-load-mode helper that compares every fold with config.model's single window.
Folds 1..N legitimately train on other windows, so they warn under any comparison. (2) Both date checks compare
string-converted tuples. train_cv writes np.datetime_as_string ns strings while config.model carries plain ISO
dates, so equal instants mismatch: fold 0, plus run() load-mode false positives. Fixing only one cause leaves
warnings (7 of 8, or the load-mode false positives). This plan fixes both.

Comparison semantics (see flagged assumptions): endpoints are compared by the bars they select on the price
calendar. This follows the orchestrator recommendation, which the user has not yet confirmed. It is not bare
Timestamp equality, because on intraday bars that would call '2024-02-09' and '2024-02-09T00:00' equal although
they select different end bars (verified in the UAT follow-up).

Output: a split helper and a calendar-resolved comparison in `quantlab/base/backtest.py`, regression tests in
two test files, and a dated correction paragraph in `example/backtest.md`.
</objective>

<flagged_assumptions>
- **Endpoint comparison uses slice semantics on the price calendar (orchestrator recommendation, not yet
  user-confirmed).** Rule: two (train_start, train_end) pairs describe the same training window iff (a) they
  are identical as given, or (b) neither has a None endpoint, both select the same (start, stop) bar positions
  via `pd.DatetimeIndex(calendar).slice_indexer(_slice_bound(start), _slice_bound(end))`, AND every endpoint
  lying outside the calendar's [first bar, last bar] span is pd.Timestamp-equal to its counterpart.
  Clause (b)'s last part is needed because the calendar in run() stops at the backtest end_date. Two
  genuinely different train_end dates that both lie past that end would otherwise both clip to the same stop
  and silence a stale config.model. An empty calendar falls back to pd.Timestamp equality of both endpoints.
  The alternative the user may prefer is plain pd.Timestamp equality everywhere. It is simpler, but it
  silences a real intraday difference. The choice only decides whether a warning appears, never which dates
  are used, so it is reversible and not gated behind a checkpoint.
- **The config.model comparison in run() moves from `_prepare_model` to just after `_price_calendar`.** The
  comparison needs the calendar, and run() computes it after `_prepare_model`. Moving the warning call leaves
  the order of data reads unchanged. Moving `_price_calendar` earlier would reorder reads in train mode, so it
  was rejected. The warning now appears after the price calendar read instead of before it. No test asserts
  warning order relative to reads.
- **The warning texts stay byte-identical**, including "(D-17, WR-01)" and "(D-16, WR-01)". tests/test_backtest_dates.py:642-647
  matches on "WR-01" plus both date strings.
</flagged_assumptions>
