## Summary

Scope: the phase 03.7 diff (`1bfc679^..HEAD`). That covers the new backtester layer (`quantlab/base/backtest.py`, `quantlab/backtest/*`), the model-layer additions (`predict_panel`, `cv_folds.json`), the config-rebuild fix (`config_cls` and `load_*_from_config`), the fingerprint, JSON and report utilities, and the docs and tests. Pre-existing code in `base/model.py` and `base/data.py` was read only to trace call chains.

These parts check out:
- **t+1 fill:** implemented correctly with `w.shift(1)`, and the last bar of every window is never a rebalance.
- **Weights contract:** enforced at both the base-class and engine boundaries.
- **Stitched CV curve:** one continuous simulation.
- **Delisting ffill and forced liquidation:** follow D-07.
- **Leakage checks:** DL early stopping uses the tail of the training segment, not the test segment. Neither the XGBoost/DL preprocessing nor the RNN recurrence (which runs over the symbol axis, not time) looks ahead in time.

Two defects produce wrong numbers silently:
1. **Intraday in-sample tail:** on intraday bars, the label-horizon bars after `train_end` are labelled out-of-sample. The docs claim the opposite ("偏保守").
2. **Annualization above daily:** annualization is wrong for any bar interval longer than one day. Weekly Sharpe, Sortino, Calmar, annualized return and turnover all use 36 bars/year instead of about 50.

The warnings are mostly reproducibility holes:
- A loaded checkpoint is never checked against the model config the backtester was given (features, symbols, train dates).
- Checkpoint paths in `cv_folds.json` are resolved against the working directory.
- A train-mode run does not record which checkpoint it trained.
- The fingerprint misses the data the predictions actually came from under `factor_data_strategy="read"`.
- Rebuilding a config that is missing a field silently takes today's defaults.
- `to_jsonable` silently drops or truncates data.

Self-reported executor items are assessed below:
- Missing `init_cash` in a rebuilt config: WR-06.
- Selector aligns by shape, not labels: WR-09.
- Intraday in-sample tails: CR-01, upgraded because the docs misstate the direction of the error.
- Stitched report has no shading, and a single-bar band has zero width: IN-04.
- Folds judged by day: IN-05.
- Constituent loader deepcopy untested: IN-09.

## Critical Issues

### CR-01: Intraday label-horizon bars after `train_end` are counted as out-of-sample (in-sample leakage into OOS metrics)

**File:** `quantlab/base/backtest.py:974-995` (`_training_window`), `quantlab/base/backtest.py:1020-1026` (`_split_window`), `example/backtest.md:307`
**Issue:**
- `_training_window` builds `end = np.datetime64(pd.Timestamp(self._iso_date(train_end)), "ns")`, which is **midnight** of the `train_end` day. It then does `searchsorted(calendar, end, side="right") - 1`.
- On intraday bars every bar of that day is later than midnight. `end_idx` therefore lands on the **last bar of the previous trading day**, and only then adds the horizon.
- The model layer trains on `data.sel(timestamp=slice(train_start, train_end))`, which includes the whole `train_end` day. Its last training label (for example, 16:00 on the `train_end` day) reads the next `h` bars, which fall on the **following** trading day.
- `_iso_date(calendar[end_idx])` resolves to the `train_end` day for `h < bars_per_day`, and `_split_window` compares by day. The result is that all of the `train_end` day is in-sample, but the `h` horizon bars on the next day are classified **out-of-sample**.
- A `train_end` given with a time of day is also truncated by `_iso_date`, with the same effect.
- These bars carry training-label information, so the `out_of_sample` metrics block, the `out_of_sample_ranges` and the stitched CV OOS ranges are contaminated. D-17 exists precisely to exclude them.
- `example/backtest.md:307` says "日内数据上 `train_end` 那一天的所有 bar 都算样本内，这是偏保守的方向". The error actually runs in the non-conservative direction.

For daily data the midnight timestamp equals the bar, so daily runs are correct.
**Fix:** Locate the last training bar as the last calendar bar on or before the **end** of the `train_end` day, then add the horizon. Split on the bar timestamps, not on days:
```python
day_after = np.datetime64(self._iso_date(train_end), "D") + np.timedelta64(1, "D")
end_idx = int(np.searchsorted(calendar, day_after.astype("datetime64[ns]"), side="left")) - 1 + horizon
window_end_ts = calendar[min(end_idx, last)]          # keep the full timestamp
# _split_window: in_sample = (timestamps >= window_start_ts) & (timestamps <= window_end_ts)
```
Return and persist full ISO timestamps (not dates) for `training_window`, `in_sample_range` and `out_of_sample_ranges`. Correct the doc sentence, and add an intraday test where `horizon` bars spill into the next session.

### CR-02: `MarketSpec.year_freq` mis-annualizes every bar interval longer than one day

**File:** `quantlab/base/backtest.py:49-57`, `example/backtest.md:182`
**Issue:**
- For `interval >= 1 day`, `bars_per_year = trading_days_per_year * (one_day / interval)`. This divides a **trading-day** count by a **calendar-day** interval.
- Checked with `US_EQUITY_MARKET` (`uv run`): `1D -> 252`, `7D -> 36.0`, `30D -> 8.4`, `31D -> 8.13`.
- A weekly US-equity bar series has about 50.4 bars/year (252/5) and a monthly one has 12. Weekly Sharpe and Sortino are therefore understated by about sqrt(50.4/36) ≈ 1.18x. Calmar and annualized return are wrong too, and so is `turnover.annualized` (`_turnover_summary`, line 1119).
- Nothing warns or fails.
- The only test (`tests/test_backtest_engine.py:486`) covers just `1D` and `1min`.
- The project is explicitly multi-frequency (D-18 calls rebalancing "frequency-agnostic"), so these are the headline metrics being reported wrong.
**Fix:** Count trading days per bar in trading days, not calendar days. For example:
```python
if interval >= one_day:
    # a 1D bar = 1 trading day; a 7D (weekly) bar = 5 trading days; ~30D (monthly) = 21
    trading_days_per_bar = max(1.0, round((interval / one_day) * 5 / 7))
    bars_per_year = self.trading_days_per_year / trading_days_per_bar
```
Alternatively, add explicit `bars_per_year` overrides for weekly and monthly on `MarketSpec`, or raise for intervals above 1 day until they are supported. Add weekly and monthly assertions to the test.

## Warnings

### WR-01: A loaded checkpoint is never checked against the model config it is loaded into, and in-sample detection trusts that config's dates

**File:** `quantlab/base/backtest.py:659-679` (`_load_model_checkpoint`), `quantlab/base/backtest.py:281-288` (`run` passes `model.config.train_start/train_end`)
**Issue:**
- `_save_model` writes a `config.json` beside every checkpoint with the real factor list, label list and train/test dates. `run()` in `load` mode ignores it.
- **Wrong or stale dates:** `config.model` might carry different or stale `train_start`/`train_end`, for example a model rebuilt by hand for backtesting. D-17 then classifies training bars as out-of-sample without any warning. If the dates are `None`, it only warns that every bar is OOS.
- **Different features:** a checkpoint trained on a different factor set or order with the same feature count (XGBoost only checks the count) predicts on permuted features without complaint.
- `run_cv` takes its dates from the manifest, which is correct, but it has the same feature-set blind spot.
**Fix:** In `_load_model_checkpoint`, read `Path(checkpoint).parent / "config.json"` when it exists. Compare `get_factor_names()`/`get_label_names()` with the saved `factor_names` (hard error on mismatch), and compare `train_start`/`train_end` (at least a `logger.warning`; better, use the checkpoint's dates for `_training_window`).

### WR-02: `predict_panel` does not check that the symbol universe matches training; RNN heads recur over the symbol axis

**File:** `quantlab/base/model.py:322-366`, `quantlab/dl_model/rnn.py:74-84,372-386`, `quantlab/dl_model/mlp.py:152-173`
**Issue:**
- `ModelRBaseCrypto.forward` receives `[T, S, F]` with `batch_first=True`, so the GRU/LSTM runs **across symbols**. A symbol's prediction therefore depends on every symbol sorted before it.
- A backtest feature panel whose symbol set differs from training accepts any `S` and shifts every prediction without complaint. That happens after tickers are appended to the store, a rebuild runs against an updated store, or a different price or factor dataset is used.
- The MLP bakes symbol position into `nn.Linear(num_symbols * num_features)`. It raises only if the **count** changes; the same count with different members is silently misaligned.
- `_load_model_checkpoint` rebuilds DL nets with `num_symbols` taken from the *current* panel, so the mismatch can never surface there either.
**Fix:** Persist the training symbol list in the checkpoint's `config.json` (or the state dict). In `DLModel._predict_panel_array`, or in `predict_panel` for DL heads, raise when `features.symbol` differs from it. At minimum, reindex the features onto the training symbols before prediction.

### WR-03: `cv_folds.json` checkpoint paths (and the backtest config's paths) are resolved against the process cwd

**File:** `quantlab/base/model.py:478-483`, `quantlab/base/backtest.py:355`, `quantlab/base/backtest.py:672`
**Issue:**
- `_train_one_fold` stores `str(Path(model_save_dir) / ...)` verbatim. With a relative `model_save_dir` (for example `"./models"`), the manifest holds relative paths.
- `run_cv` passes them straight to `Path(checkpoint)`, which resolves against the **current working directory**, not against `cv_project_dir`.
- Running `run_cv` from another directory, or after moving the project directory, fails with `FileNotFoundError`. Worse, it can load a same-named checkpoint from a different training run under the cwd.
- `config.checkpoint`, `cv_project_dir` and `output_dir` persisted in `config.json` have the same problem, which weakens D-25 reproducibility.
**Fix:** Write `Path(...).resolve()` into the manifest. In `run_cv`, resolve relative entries against the manifest directory:
```python
ckpt = Path(fold["checkpoint"])
if not ckpt.is_absolute():
    ckpt = Path(self.config.cv_project_dir).parent.parent / ckpt  # or store paths relative to cv_project_dir explicitly
```
Better still, store checkpoint paths relative to `cv_project_dir` and resolve them against it. Normalize the path fields of `BacktestConfig` to absolute paths in the setter.

### WR-04: Train-mode runs do not record the checkpoint they trained, and a same-second retrain crashes

**File:** `quantlab/base/backtest.py:644-657`, `quantlab/base/model.py:378-390`, `tests/test_backtest_rebuild.py:311`
**Issue:**
- `_prepare_model` calls `model.train()`, which writes `{model_save_dir}/{class}_trial_{%Y%m%d_%H%M%S}/...`. Neither `config.json`, `metrics.json` nor the `BacktestResult` records that path.
- A train-mode backtest therefore cannot be replayed in `load` mode against the exact model that produced it. The only way to rerun it is to retrain, which is not bit-reproducible for torch or GPU heads.
- The project directory name is only second-precise and `_save_model` raises `RuntimeError` when the directory exists. The backtester now makes this reachable: a train-mode run and its immediate rebuild collide.
- The test works around it with `time.sleep(1.1)`, a wall-clock dependency that can still flake on a slow or clock-adjusted CI host.
**Fix:**
- Have `BaseModel.train()` return (or store on `self`) the checkpoint path.
- Record it in the run's `config.json` as a new field (for example `trained_checkpoint`) and in `metrics.json`.
- Make the model project name collision-free (add `%f` or a uuid suffix, as `_run_dir_name` already does) and drop the `sleep`.

### WR-05: The fingerprint does not cover the data the predictions actually came from

**File:** `quantlab/base/backtest.py:793-807`, `quantlab/base/backtest.py:717-732`
**Issue:**
- **`read` strategy:** under `factor_data_strategy == "read"`, features come from the **factor store** (`factor.read(overwrite=True)`). `_record_factor_fingerprints` hashes `factor.config.dataset` (the raw data columns) instead.
- A recomputed or modified factor store therefore produces different predictions and weights with a matching fingerprint and no warning, which is exactly what D-27 is meant to catch.
- **`train` mode:** the training-window data and the label datasets are not fingerprinted at all (the docs note labels). A retroactive Tiingo re-base inside the training window silently changes the retrained model on rebuild.
**Fix:** For `read` strategy, fingerprint `factor.get_features()` (the factor names over the warm-up and window range) under its own key. In `train` mode, also fingerprint each factor and label dataset over the model's `start_date..end_date` before `model.train()`.

### WR-06: Rebuilding a config that lacks a field silently uses the current dataclass defaults

**File:** `quantlab/utils/module.py:156`, `quantlab/base/config.py:199-211`
**Issue:**
- `cls(_config_cls_of(cls)(**config))` fills any missing key (`fees`, `slippage`, `init_cash`, `score_label`, `use_wandb`, …) from the **current** defaults. This is the executor-reported `init_cash` gap.
- If a default changes later (for example `fees=0.0005` becomes `0.001`), an older or hand-edited `config.json` rebuilds into a different backtest with no warning and no failing test.
- That breaks D-25's "all parameters must be identical" guarantee.
**Fix:** In `load_backtester_from_config`, require every `fields(config_cls)` name (except `name`) to be present:
```python
missing = [f.name for f in fields(config_cls) if f.name not in config and f.name != "name"]
if missing:
    raise ValueError(f"backtest config is missing fields {missing}; refusing to fill them from current defaults")
```
Add a regression test that deletes `init_cash`.

### WR-07: `to_jsonable` silently truncates arrays and drops colliding keys in persisted artifacts

**File:** `quantlab/utils/jsonable.py:70-76`
**Issue:**
- **Arrays:** anything not special-cased falls through to `str(value)`. A numpy array, `pd.Series` or set becomes numpy's **abbreviated** repr; verified that `np.arange(2000.0)` becomes `'[0.000e+00 1.000e+00 2.000e+00 ... 1.999e+03]'`.
- **Keys:** dict keys are coerced with `str(key)` without checking for collisions. Verified that `{1: 'x', '1': 'y'}` becomes `{'1': 'y'}`, so `'x'` is lost.
- The function serializes `metrics.json`, `config.json`, `fingerprint.json` and `cv_folds.json` (whose fold dicts carry whatever `_fit` returns), so any array-valued metric or config value is persisted as unrecoverable text with no error. The docstring's "strictly standard JSON" promise holds only syntactically.
**Fix:**
- Convert `np.ndarray`, `pd.Series`, `pd.Index` and sets to lists (`to_jsonable(value.tolist())`).
- Raise `TypeError` on any other unknown type instead of calling `str()`, keeping explicit `Path`/`Decimal` cases.
- Raise on a key collision after `str()` coercion.

### WR-08: A failed persist leaves a run directory that looks like a completed run

**File:** `quantlab/base/backtest.py:1309-1332`, `quantlab/base/backtest.py:1407-1447`
**Issue:**
- `_report_and_persist` and `_persist_cv` create the run directory and write `config.json` first, then the zarr stores, `metrics.json`, the plotly report and the fingerprint.
- Any exception in a later step leaves `output_dir/{class}_{ts}/` holding a valid `config.json` (and possibly weights) but no metrics or fingerprint. This can come from a zarr write error, plotly, a disk-full condition, or a `KeyboardInterrupt`.
- No completion marker exists, so a downstream consumer or a human cannot tell a broken run from a good one.
- Because `config.json` is present, `load_backtester_from_config` will happily "reproduce" it.
**Fix:** Write everything into a `run_dir.with_suffix(".tmp")` sibling and `os.replace` it to the final name as the last step. Alternatively, write a `_SUCCESS` marker last and have the loader and consumers require it.

### WR-09: `CrossSectionTopNSelector.select` aligns scores and fill prices by shape, not by coordinate labels

**File:** `quantlab/backtest/selection.py:91-105`
**Issue:**
- `select` is documented as the reusable D-03 component that Phase 5 optimizers will sit beside. It converts both inputs to `.values` and checks only `fill_values.shape != score_values.shape`.
- `scores` and `next_fill_price` with the same shape but different symbol or timestamp order produce weights that pair each score with another symbol's price eligibility. Weights are labelled with the `scores` coordinates.
- Today `_backtest_window`'s `reindex` guards this (self-reported), but a direct caller or a future sibling backtester gets silent misalignment.
**Fix:** Align by label before extracting values and assert that the coordinates are identical:
```python
next_fill_price = next_fill_price.reindex(timestamp=scores.timestamp, symbol=scores.symbol)
# or: xr.align(scores, next_fill_price, join="exact")
```

## Info

### IN-01: Polars-factor fingerprint casts every dataset variable to float64

**File:** `quantlab/base/backtest.py:804-805`, `quantlab/utils/fingerprint.py:60-62`
**Issue:** For non-`FactorConfig` factors, `variables = list(ds.data_vars)`, and `dataset_fingerprint` does `np.asarray(..., dtype=np.float64)`. A string or datetime64 data variable in such a dataset would raise in `_redate_factors`, after training in `train` mode. Current stock stores were not verified to contain one.
**Fix:** Fingerprint non-numeric variables through a stable byte encoding (for example `values.astype(str)` joined), or restrict the list to numeric dtypes and record the skipped names.

### IN-02: `_training_window` can record an inverted window

**File:** `quantlab/base/backtest.py:985-995`
**Issue:** When `train_start` is after the calendar's last bar (a backtest window entirely before training), the result is `window_start = train_start` and `window_end = calendar[last]`, so `start > end`. The split is still correct (empty in-sample), but `metrics.training_window` persists a nonsensical pair.
**Fix:** Clamp both ends consistently, or record `training_window` from the raw `train_start`/`train_end + horizon` without calendar clamping.

### IN-03: `_log_to_wandb` leaves the run open on exception

**File:** `quantlab/base/backtest.py:1274-1285`
**Issue:** An exception from `run.log` or reading `report.html` skips `run.finish()`.
**Fix:** Wrap the body in `try: ... finally: run.finish()`.

### IN-04: Report shading gaps (self-reported)

**File:** `quantlab/utils/backtest_report.py:64-73`, `quantlab/base/backtest.py:1437-1443`
**Issue:**
- The stitched `run_cv` report never shades its multiple in-sample ranges.
- A single-bar in-sample range becomes a zero-width `add_vrect` (`x0 == x1`), so nothing is visible.
- The date-only bounds also cut intraday bands at midnight.

### IN-05: `run_cv` fold contiguity is judged by day (self-reported)

### IN-06: Misleading contract error for all-inf weight rows

**Issue:** A row of all `inf` is neither all-NaN nor all-finite, so it is reported as "mixes NaN and finite values".

### IN-07: `open_trade_count` double-counts across multiple ranges

### IN-08: Config loader imports the named module before the subclass check

**Issue:** `get_cls_from_path` runs `importlib.import_module` (executing module top-level code) before `issubclass(cls, BaseBacktester)` rejects it. The input is trusted by project stance; this is a hardening note only.

### IN-09: Constituent-dataset loader deepcopy is untested (self-reported)

### IN-10: `BacktestConfig` numeric fields are not type-validated

**File:** `quantlab/base/backtest.py:197-210`, `quantlab/backtest/selection.py:65`
**Issue:**
- `rebalance_periods=5.0` passes validation and then fails deep inside `rebalance_mask` (`mask[::5.0]` raises TypeError).
