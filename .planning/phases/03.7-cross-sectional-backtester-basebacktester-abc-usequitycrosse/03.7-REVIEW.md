## Critical Issues

### CR-01: XGBoost feature-importance recording crashes training before the checkpoint is written (BLOCKER)

**File:** `quantlab/ml_model/xgb.py:292-293`, `quantlab/ml_model/xgb.py:308-328`, `quantlab/base/model.py:1463-1477`

**Issue:**
- **When it runs:** `_record_feature_importance()` runs at the end of `_fit_model` whenever `_wandb_recorder is not None`.
  - `BaseModel.train()`/`_train_one_fold` always call `_init_wandb` first.
  - `wandb.init` returns a no-op Run, never None, even under `WANDB_MODE=disabled`. The 03.7-18 summary itself notes this.
  - In practice the step therefore runs on every XGBoost training.
- **Why it fails:** it unconditionally asks for `gain` and `total_gain` and does `float(score)`. Verified with xgboost 3.4.1 in this repo's venv:
  - `hyperparameters={"booster": "gblinear"}`: `get_score(importance_type="gain")` raises `XGBoostError: Check failed: importance_type == "weight" ... gblinear only has weight`.
  - gblinear with a multi-label `[T, S, L>1]` target: `get_score("weight")` returns lists (`{'f0': [0.028, -0.025], ...}`), so `float(score)` raises `TypeError`.
- **What is lost:** `MLModel._fit` calls `_fit_model` (line 1463) before `_save_model` (lines 1472-1477). The boosting work is already done, but:
  - no `.joblib` is written, and `_wandb_recorder.finish()` is skipped;
  - in `train_cv` the whole CV run aborts, and no `cv_folds.json` is written for folds that already finished;
  - a backtester `run()` in train mode fails after the full training cost.
- **Why it is a blocker:** `booster` passes through `hyperparameters` like any other key, so a valid (deprecated but supported) configuration loses its trained model to a best-effort telemetry step.

**Fix:** Make importance best-effort, restrict it to tree boosters, and record it after nothing else can be lost:
```python
def _record_feature_importance(self) -> None:
    booster_type = str((self._params or {}).get("booster", "gbtree"))
    if booster_type == "gblinear":
        logger.info(f"{self.class_name}: gblinear has no split importance; skipped")
        return
    names = [str(name) for name in self.get_factor_names()]
    for importance_type in _IMPORTANCE_TYPES:
        try:
            scores = self.model.get_score(importance_type=importance_type)
        except xgb.core.XGBoostError as exc:
            logger.warning(f"{self.class_name}: importance {importance_type!r} unavailable: {exc}")
            continue
        values = {name: 0.0 for name in names}
        for key, score in scores.items():
            ...  # keep the f<index> parse and the ValueError on a bad key
            if not np.isscalar(score):
                raise ValueError(...)  # or skip with a warning; never float() a list
            values[names[index]] = float(score)
        self._wandb_recorder.summary.update({...})
```
Add a regression test that trains `booster="gblinear"` (single-label and 2-label) with a recorder and asserts the checkpoint exists. Alternatively, move the importance call out of `_fit_model` into a post-`_save_model` hook, so an exception there can no longer cost the checkpoint.

### WR-01: The G-03.7-9 legacy fallback refuses a model's own pre-`trained_on` checkpoint whenever `factor_names` was user-ordered

**File:** `quantlab/base/model.py:420-444`, `quantlab/base/model.py:470-480`; contrast with `quantlab/base/backtest.py:906-909` and `quantlab/base/model.py:379-381`

**Issue:**
- **What the check compares:** when `trained_on` is absent, `_assert_trained_variables` compares the flattened legacy `factors[].factor_names` against `get_factor_names()`, which is built from `factor._get_factor_names()` (the derived names). A mismatch raises `ValueError`.
- **Why the legacy field is unreliable:** it is `config.factor_names` (`quantlab/base/factor.py:76-77, 186-187`). A user may supply it for a KunQuant factor in any order. Training builds its arrays from `BaseModel.get_factor_names()` (derived order), not from that field.
- **What happens:** a legacy checkpoint trained with `factor_names=("alpha003", "alpha001")` on a factor whose `_get_factor_names()` yields `("alpha001", "alpha003")` was trained in the derived order. It is now refused as "trained on factor variables ['alpha003', 'alpha001']", although it matches exactly.
- **The same defect already documented:**
  - This is the defect that `BaseBacktester._load_model_checkpoint`'s docstring (backtest.py:906-909) says plan 17 removed: the old check "会拒收模型自己的 checkpoint（该字段与训练真正用的名字顺序不同时）".
  - `_assert_trained_variables`' own docstring (model.py:379-381) says the config field "可以与训练真正用的名字顺序不同".
- **Net effect:** plan 17 moved the defect from the backtester into `load()`, where it now also blocks direct loads. The converse also holds: a legacy field that happens to equal the current derived list passes, even if training used another order. The weaker-record warning discloses that case but does not prevent it.

**Fix:** The legacy field cannot certify order, so compare it as a **set** and warn about order instead of raising:
```python
if source.startswith("legacy"):
    if sorted(recorded) != sorted(current):
        raise ValueError(...)            # different variables: still a hard refusal
    if recorded != current:
        self._warn_load_record_once(
            f"... legacy factor_names order {recorded} differs from the derived order "
            f"{current}; the legacy record cannot certify training order (G-03.7-9)")
    continue
```
Add a legacy-checkpoint test where the config field is a permutation of the derived names, and assert it loads with a warning.

### WR-02: `Alpha158Stock` still cannot compute on any stock store after 1f95940, and its `vwap` would mix adjusted and unadjusted scales

**File:** `quantlab/factor/alpha158.py:100-114`, `quantlab/factor/alpha158.py:142-157`, `tests/test_factor_kunquant.py:223-248`, `.planning/phases/03.7-.../03.7-baseline-gate.sh:48`

**Issue:**
- **Current inputs:** after 1f95940, `_get_func_names` reads `adjOpen`/`adjHigh`/`adjLow`/`adjClose`/`adjVolume`, but still `Input("amount")`.
- **`amount` never reaches the graph:**
  - No stock ingestion path writes an `amount` variable. The only producer is `quantlab/dataset/spot.py:174`, and the Tiingo columns are `enums/data.py:82-83`.
  - `StockDataset._to_kunquant` (`quantlab/dataset/stock.py:558-570`) now only copies the listed `data_columns`, with no `volume * close` synthesis.
- **Verified:** `uv run pytest tests/test_factor_kunquant.py -k "alpha158_stock or alpha101_stock_bugfix"` fails with `KeyError: "No variable named 'amount'..."`.
  - These failures are inside the gate's `test_factor_kunquant.py = 4` baseline, so no gate will ever report that the only US-equity Alpha158 path cannot run.
  - The test still passes raw `data_columns=["open","high","low","close","volume","amount"]`, so it would fail on the adjusted inputs even if `amount` existed.
- **Scale mismatch if `amount` is supplied:** `KunQuant.predefined.Alpha158.AllData` builds `vwap = amount / (volume + 1e-6)`.
  - With `volume=adjVolume` (split-adjusted) and a raw dollar-volume `amount`, `VWAP0..4` (vwap / close) and every VWAP-derived rolling feature jump at each split and drift with dividend adjustment.
  - The rest of the graph is on the adjusted scale.
- **Dead inputs:** `_get_func_stream` (lines 146-151) still declares raw `Input("close"/"low"/"high"/"open"/"volume")` and a second `Input("amount")`. KunQuant tolerates unused and duplicate inputs (verified with a probe), so they are harmless at runtime. They are misleading dead nodes that suggest raw columns are consumed.

**Fix:**
- **Build `vwap` on the adjusted scale** inside the graph and drop the `amount` input (or pass `vwap=` explicitly):
  ```python
  close, low, high, vopen, vol = (Input(c) for c in ("adjClose", "adjLow", "adjHigh", "adjOpen", "adjVolume"))
  vwap = Div(Add(Add(high, low), close), 3.0)   # or amount = Mul(close, vol) if a dollar-volume proxy is intended
  all_data = Alpha158.AllData(low=low, high=high, close=close, open=vopen, volume=vol, vwap=vwap)
  ```
- **Clean up the stream function:** remove the raw `Input(...)` lines from `_get_func_stream`.
- **Fix the test:** update `test_alpha158_stock_batch_cal_returns_xarray_dataset` to adjusted `data_columns`, so it leaves the baseline and actually guards the class.

## Info

### IN-01: `_same_training_bars` warns on endpoints that differ only outside the calendar but select identical bars

**File:** `quantlab/base/backtest.py:888-893`

**Issue:** The outside-span clause requires `pd.Timestamp` equality for any endpoint outside `[first bar, last bar]`. The cases differ:
- **`train_end` beyond the calendar:** equality is required, as intended (the `run()` calendar is truncated at the backtest end).
- **`train_start` before the calendar:** two dates that both fall before the price store's first bar (for example `"2015-01-01"` vs `"2016-01-01"` when the store starts in 2020) select exactly the same training bars and the same data, yet produce the WR-01 "using the checkpoint's dates" warning.

This is noise only; it never changes which dates are used.

**Fix:** Apply the Timestamp-equality requirement only to endpoints **after** the last bar, since that is where calendar truncation hides a difference. Before the first bar, treat slice equality as sufficient.

### IN-02: `to_jsonable` drops `pd.Series`/`pd.Index` labels despite the "lossless, or loud" contract

**File:** `quantlab/utils/jsonable.py:9-16`, `quantlab/utils/jsonable.py:113-114`

**Issue:** `pd.Series` becomes `to_jsonable(value.to_numpy())`, a bare list. A per-symbol Series (for example a turnover or stats Series keyed by symbol) silently loses its index. That is the same class of loss WR-07 set out to eliminate. No current caller passes one.

**Fix:** Convert a Series to a dict (`{str(k): to_jsonable(v) for k, v in value.items()}`, relying on the collision check), or raise `TypeError` for a Series with a non-default index.

### IN-03: A second checkpoint-sidecar parser contradicts "唯一解析入口"

**File:** `quantlab/base/backtest.py:934-955` vs `quantlab/base/model.py:358-372`

**Issue:**
- `BaseModel._read_checkpoint_sidecar` is documented as the only parser of a checkpoint's `config.json`.
- `BaseBacktester._read_checkpoint_config` re-implements the same read and non-object check.
- On every load the file is parsed three times (backtester, `_assert_trained_variables`, `_read_trained_symbols`), and the two error paths can drift.

**Fix:** Have `_read_checkpoint_config` call `self.config.model._read_checkpoint_sidecar(path)` and keep only its dates-specific warning.
