### CR-01: XGBoost feature-importance recording crashes training before the checkpoint is written

**Status:** fixed
**Files modified:** `quantlab/ml_model/xgb.py`, `tests/test_xgb_model.py`
**Commit:** a28a8e6

**Applied fix:**
- `_record_feature_importance` is now best-effort.
  - `booster="gblinear"` is skipped as a whole, with an info log.
  - For every other booster, an importance type that raises `XGBoostError`, or returns a non-scalar per-output score, is skipped with a warning. Only that type is skipped; the rest are still written.
  - `float()` is never applied to a list. The `ValueError` on a malformed `f<index>` key is kept, as the review asked.
- **Adapted beyond the review text:** the review's own regression test ("gblinear trains, checkpoint exists") exposed a second crash on the same path. `_forward` calls `Booster.inplace_predict`, which gblinear does not support (measured on xgboost 3.4.1: "Inplace predict is not supported by the current booster"). `MLModel._fit` calls `_evaluate` before `_save_model`, so the model was lost there as well.
  - `_forward` now falls back to `predict(DMatrix)` only on that exact error, and re-raises every other `XGBoostError`.
  - Probe on the fallback: gblinear returns shape `(n,)` / `(n, 2)`, and on a tree booster `inplace_predict` and `predict(DMatrix)` agree (`allclose`). The tree path is unchanged.
- Chinese docstrings were updated in both methods and in the class docstring.

**Regression tests:**
- `test_gblinear_trains_and_writes_its_checkpoint_with_a_recorder[single-label, two-label]` uses a recorder. It asserts the `.joblib` and `config.json` exist, `finish()` ran once, no `importance_*` keys were written, and prediction shape is `[T, S, L]`.
- `test_unavailable_or_non_scalar_importance_is_skipped_not_fatal` patches `Booster.get_score` so that `weight` raises and `gain` returns lists. The checkpoint is saved, only `total_gain` is written, and both skips are logged.

**Red evidence:** all 3 new tests failed on the pre-fix code in the worktree. The two-label gblinear test failed with `TypeError: float() argument must be ... not 'list'`; the other two failed with `XGBoostError`.
**Green:** `tests/test_xgb_model.py` plus `tests/test_ml_models.py` gave 48 passed.

### WR-02: `Alpha158Stock` still cannot compute on any stock store after 1f95940, and its `vwap` would mix adjusted and unadjusted scales

**Status:** fixed: requires human verification (the vwap construction is a semantic choice)
**Files modified:** `quantlab/factor/alpha158.py`, `tests/test_factor_kunquant.py`
**Commit:** f730dc8

**Applied fix:**
- `Alpha158Stock._get_func_names` drops `Input("amount")` and builds `vwap = (adjHigh + adjLow + adjClose) / 3.0` inside the graph.
- It assigns `all_data.vwap = vwap` explicitly after `Alpha158.AllData(...)`.
  - The installed KunQuant's `AllData.__init__` only sets `self.vwap` in its `if vwap is None:` derivation branch, and has no `else`.
  - So the review's literal `AllData(..., vwap=vwap)` would have left `vwap` unset.
  - `AllData` reads `amount` nowhere else, so dropping it is safe.
- The dead raw `Input("close"/"low"/"high"/"open"/"volume"/"amount")` lines were removed from `_get_func_stream`.
- `Output(v, k)` stays without `WindowedZScore`, so the D-09 matrix test is still green.
- The class docstring now documents the inputs and the vwap choice.

**Why typical price, not `amount = close * volume`:**
- **Scale consistency:** the typical price is built only from the adjusted series, so every VWAP-derived feature (`VWAP0..4` and the rolling windows) stays on the adjusted scale, like the rest of the graph.
- **The proxy is degenerate:** with `amount = adjClose * adjVolume`, `AllData` computes `vwap = amount / (volume + 1e-6)`, which is about `adjClose`.
  - `VWAP0 = vwap / close` would then be a near-constant 1.0.
  - `VWAP1..4` would duplicate `CLOSE1..4`.
  - That adds features with no information.
- **Nothing to read:** Tiingo supplies no dollar volume, so there is no true VWAP or amount on either scale.
- **For the human reviewer:** the typical price is a proxy, not a traded VWAP. If a true dollar-volume VWAP is ever ingested, it must be adjusted to the same scale before it replaces this.

**Test changes:**
- `test_alpha158_stock_batch_cal_returns_xarray_dataset` now uses adjusted `data_columns` (`adjOpen/adjHigh/adjLow/adjClose/adjVolume`) and adds `VWAP0`.
  - The store is rewritten with `adjHigh = 1.10 * adjClose`, so the typical price differs from close, and with the raw columns rescaled.
  - It asserts `VWAP0 == ((adjH + adjL + adjC) / 3) / adjC` at `rtol=1e-5`, and that `VWAP0` is not about 1.0 (which is what the dollar-volume proxy would produce).
- New `test_alpha158_stock_graph_reads_only_adjusted_inputs` asserts that the `Input` names of the compiled graph are exactly the five adjusted columns.
  - `Function` prunes inputs that no output reaches, so the test requests `KMID` + `VWAP0` + `VOLUME0` to reach all five.

**Red evidence:** both tests failed on the pre-fix `alpha158.py`. The input-set test's diff showed `'amount'` among the graph inputs.
**Green:** `tests/test_factor_kunquant.py` went from 4 failed / 5 passed to 3 failed / 7 passed.
- The Alpha158 stock batch test has **left the baseline**.
- The 3 remaining failures predate this round and are outside WR-02: `test_stock_to_kunquant_synthesizes_amount_as_adjusted_dollar_volume`, `test_stock_to_kunquant_without_amount_leaves_arrays_unchanged` and `test_alpha101_stock_bugfix_batch_cal_returns_xarray_dataset`.

**Left as-is and noted, not fixed:**
- `quantlab/config/__init__.py:stock_alpha158_config` still lists `"amount"` in `data_columns`, and `test_stock_alpha158_config_wires_amount_and_a_derived_path` asserts it.
  - A config built by that factory would still raise `KeyError: 'amount'` at `to_kunquant`.
  - It was left alone because of the standing decision not to fix config factories: construct configs directly.
- `Alpha101Stock` has the same `Input("amount")` problem. It was outside this finding and stays in the baseline.
- `example/dataset.md` / `example/factor.md` still describe the retired `amount = volume * close` synthesis.
