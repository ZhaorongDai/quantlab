# Phase 03.7 Plan 10: run_cv, the Model-CV Backtest Summary

**`run_cv()` replays a `train_cv` run. It reads and version-checks `cv_folds.json` and refuses a gap or overlap between fold test segments before loading anything. Each fold is backtested on its own test segment with its own checkpoint and in-sample rule, then one continuous stitched simulation is run over the concatenated fold weights. The run directory holds the stitched curve at top level and each fold under `folds/fold_{i}/`. 14 new locks and an extended D-02 lock cover it. All 10 mutations run went red.**

## Accomplishments

- **Manifest reader (D-36).**
  - `_read_cv_folds` refuses a missing file with `FileNotFoundError` naming the path.
  - It raises `ValueError` for:
    - a payload without `format_version`;
    - any version other than `BaseModel.CV_FOLDS_FORMAT_VERSION` (`True` is refused even though `True == 1`);
    - a non-list or empty `folds`;
    - a fold entry missing one of `fold`, the four dates, or `checkpoint`;
    - a test segment whose start is after its end.
  - Dates go through `_iso_date`, and folds are returned sorted by `fold`.
- **Load-mode rule (D-13, D-16).**
  - The setter now requires `checkpoint` or `cv_project_dir`, at least one.
  - `run()` refuses when load mode has no checkpoint; `run_cv()` refuses when there is no `cv_project_dir`.
  - `run_cv()` also refuses when `model_mode` is not `load`.
- **Contiguity before anything runs (D-35).**
  - `_select_folds` keeps folds whose whole test segment lies inside the config window.
  - `_assert_contiguous_folds` maps each segment onto the price calendar (first bar on or after `test_start`, last bar on or before `test_end`'s day). The next fold's first bar must be exactly one past the previous fold's last bar.
  - If it is further, the error reports a gap and how many bars belong to no fold. If it is not further, the error reports an overlap and how many bars two models would trade. Either way it names both folds and both boundary dates.
  - The assertion runs before any model load or simulation.
- **One per-window pipeline.**
  - `_backtest_window` holds the steps that used to sit inline in `run()`: align and predict, load prices, reindex onto the price axes, split, generate signals, check the weights contract, simulate, benchmark and metrics.
  - `run()` calls it once with the model config's train dates; `run_cv()` calls it per fold with that fold's train dates, so D-17 applies per fold.
  - `_load_model_checkpoint` (existence check, DL feature collection, `load`) and `_redate_factors` (warm-up, refreshed reads, factor fingerprints) are shared the same way.
- **Stitched curve (D-35).**
  - The fold weights are concatenated along `timestamp` and checked against the stitched price bars and the weights contract, then simulated once.
  - Capital therefore carries across fold boundaries, while each fold's own simulation starts at `init_cash`.
  - `_stitched_split` builds `in_sample_ranges` from every fold's non-empty `in_sample_range`, and the unshaded remainder becomes `out_of_sample_ranges`. `_compute_metrics` slices in-sample over that list.
- **Fingerprints over the union window (D-27).** After the folds, factors are re-dated to the first fold's warm-up start through the last `test_end` and their reads refreshed. Price fingerprints come from the stitched `_load_prices`, then the record is compared once.
- **Run directory.** `_persist_cv` writes the files below, and `_log_to_wandb` receives the stitched metrics when `use_wandb` is on:

  | Location | Contents |
  |---|---|
  | `config.json` | `get_config()`, including `data_fingerprint` |
  | `weights.zarr`, `equity.zarr` | stitched weights; stitched value and returns |
  | `folds/fold_{i}/weights.zarr`, `folds/fold_{i}/equity.zarr` | each fold's own weights and simulation |
  | `metrics.json` | `stitched`, `folds` (the six manifest fields plus that fold's metrics) and `notes` |
  | `liquidations.json` | `stitched` and per-fold `folds` |
  | `fingerprint.json` | the union-window fingerprints |
  | `report.html` | the stitched curve with the notes |

  `_new_run_dir` (refuse if the directory exists) and `_write_weights_and_equity` are shared with `_report_and_persist`.
- **D-02 lock.** `test_run_lives_only_on_base_backtester` now forbids `run_cv` above the base. It also pins the public callables `BaseBacktester` itself defines to exactly `run`, `run_cv` and `get_config`.

## Decisions Made

See `key-decisions` in the frontmatter. The two with visible consequences:

- **Stitched metrics shape.** The stitched block has `training_windows`, `in_sample_ranges` and `out_of_sample_ranges`, not `in_sample_range`: a single date pair cannot hold one in-sample band per fold. The per-fold metrics keep exactly `run()`'s shape.
- **Stitched report shading.** The stitched report is unshaded, and its note names where the in-sample bars are recorded. Drawing several bands would need `quantlab/utils/backtest_report.py`, which is outside this plan's files.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing validation] run_cv refuses model_mode='train'**
- **Found during:** Task 1
- **Issue:** The plan only makes `run_cv()` refuse a missing `cv_project_dir`. With `model_mode="train"`, `run_cv()` would silently ignore the mode and load checkpoints, while a user expecting training would get a replay.
- **Fix:** `run_cv()` raises `ValueError` naming `model_mode` when it is not `load`.
- **Files modified:** quantlab/base/backtest.py
- **Committed in:** `79e342d`

**2. [Rule 3 - Interface fit] Multi-segment in-sample split for the stitched curve**
- **Found during:** Task 2
- **Issue:** The plan says to build the stitched split "from the union of the per-fold in-sample ranges", with `in_sample_range` being None when none overlap. A union of per-fold bands is several disjoint ranges and does not fit one date pair or the one-band report.
- **Fix:**
  - `_stitched_split` returns `in_sample_ranges`, which is an empty list when no fold overlaps.
  - `_compute_metrics` uses that list when it is present and copies every split key into metrics. `run()`'s split has exactly the old three keys, so its metrics are unchanged; the metrics and persistence suites stayed green.
  - The stitched report passes `in_sample_range=None`, and a note explains why.
- **Files modified:** quantlab/base/backtest.py
- **Committed in:** `4596c6f`

**3. [Rule 2 - Lock strength] Capital lock catches rescaled chaining too**
- **Found during:** Task 2 test design
- **Issue:** The planned assertion (stitched value at fold 1's first bar != `init_cash`) stays green for per-fold values rescaled to the previous end value, which is also a glued curve.
- **Fix:** The lock also asserts that the stitched value moves across the boundary bar, and that the stitched path equals fold 0's path until the first boundary. M5 proves the addition.
- **Files modified:** tests/test_backtest_run_cv.py
- **Committed in:** `19ff854`

**4. [Rule 3 - Refactor, no behaviour change] Shared helpers and one ordering move in run()**
- `_redate_factors` was extracted from `_align_and_predict`, and `_new_run_dir` and `_write_weights_and_equity` from `_report_and_persist`. Each is now also called by `run_cv` rather than duplicated.

- **Files modified:** quantlab/base/backtest.py
- **Committed in:** `79e342d`, `4596c6f`

## Issues Encountered

- **Day granularity.** Fold dates are normalized to ISO days, as the plan requires, so contiguity, fold selection and the in-sample split are all judged per day. For intraday bars, two folds whose segments meet within one day would be reported as an overlap. That is the same day-level rule `_split_window` already uses, recorded here as a limitation rather than solved.
- **Per-fold DL collection.** For a `DLModel`, `_load_model_checkpoint` collects the feature panel before every fold's load, so DL run_cv pays one feature collection per fold. ML heads skip that step. No DL run_cv test exists yet.
- **Manual report check (D9): not performed.** A human should open a run_cv report.html and judge whether the unshaded stitched page and its note read clearly.
- Spec-less probe fallback: skipped (no requirement IDs to probe), recorded here as the plan asks.
