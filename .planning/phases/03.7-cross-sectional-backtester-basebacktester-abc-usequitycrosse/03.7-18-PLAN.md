<objective>
Deliver the user's additions to UAT gap G-03.7-9. XGBoost DMatrix receives feature_names, so the Booster itself
knows its inputs and W&B can record feature importance by factor name.

Purpose: the diagnosis (`.planning/debug/model-load-skips-variable-order-check.md`, XGBoost addendum) measured
that `XGBoostRegressor` trains on nameless DMatrix and predicts through `inplace_predict(numpy)`, which checks
only the column count. Passing names alone does NOT make `_forward` validate, because inplace_predict on numpy
ignores names. `_forward` therefore compares the Booster's names with the declared factor names explicitly. That
path is cheaper than a named DMatrix, gives a clearer message, and brings no DataFrame into the layer (project
constraint). The check complements the trained_on load check from plan 03.7-17. It also covers `.joblib` files
copied without their config.json, and it keys importance by factor name.

Output: `quantlab/ml_model/xgb.py` changes, tests in `tests/test_xgb_model.py`, and a dated doc paragraph.
</objective>

<flagged_assumptions>
- **Explicit name comparison in `_forward`, not a named DMatrix + Booster.predict.** Both validate. The explicit
  comparison keeps today's `inplace_predict` numbers bit-identical (tests/test_model_predict_panel.py
  `test_xgboost_regressor_predict_panel_matches_predict` compares to 1e-12), avoids building a DMatrix per
  prediction, and names both lists in the error.
- **Importance types are weight, gain and total_gain.** Summary keys are `importance_{type}/{factor}`, so W&B
  groups them by the slash. For a multi-output Booster, xgboost aggregates across outputs, and the doc says so.
- **Importance is written only when a recorder exists**, after the best_iteration/best_score update. It is never
  written in `MLModel._evaluate`, which would break tests/test_ml_models.py:281.
- **Name validation raises in `_fit_model`** before any DMatrix is built. All shipped names comply (82
  Alpha101, 169 Alpha158Stock, and the repo Polars/label names, per diagnosis), so only arbitrary user
  FactorPolars columns can hit it.
</flagged_assumptions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.joblib` Booster on disk -> XGBoostRegressor._forward | May be copied without config.json, or trained before names existed |
| model config factor list -> Booster | A reordered factor list silently permutes columns under count-only validation |
| training metadata -> W&B | Importance values leave the machine only when the user enables W&B |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.7-18-01 | Tampering | permuted factor list against a named Booster without config.json | high | mitigate | `_forward` compares Booster.feature_names with get_factor_names() and raises (Test T). |
| T-03.7-18-02 | Tampering | legacy nameless Booster | medium | accept | No names to compare. The load()-level trained_on check (03.7-17) still applies when config.json exists. Documented as unvalidated (Test U). |
| T-03.7-18-03 | Denial of Service | a user factor name xgboost rejects, failing deep in xgb.train | low | mitigate | Pre-validated in `_fit_model` with a named ValueError before any DMatrix (Test V). |
| T-03.7-18-04 | Information Disclosure | factor names and importances sent to W&B | low | accept | Same channel and opt-in as the existing metrics and resolved_hyperparameters. The test suite runs with WANDB_MODE=disabled. No credential is involved. |
