## Summary

三个实测结论决定了本 phase 的全部形状。

**第一，逐位不变是可证的，而且证据已经在手。** 我在本机真实 store（`data/data/us_equity/1d/wrds_crsp_sp500_1d.zarr`，252×520）上用 numpy 从 `close`/`ret`/`cumfacshr`/`open`/`high`/`low`/`volume` 七个**已落盘**的原始列重算了五个 `adj*` 列，结果与 store 里存的值**逐位相等**（`==` 精确比较，130,276 个非 NaN 格子全等，NaN 位置也完全一致），耗时 **3.8 ms**。这意味着：(a) D-03「下游逐位不变」不是希望而是已验证的事实；(b) store 今天就已经携带了派生所需的全部原料，改造是**只删不加**；(c) Still open #3 的缓存问题消失——派生成本在存储读取成本面前是噪声。

**第二，`"last"` 锚必须定义在 STORE 的完整跨度上，而不是读窗口上。** 这是本研究最重要的发现。回测层会用**三个不同的窗口**反复重读同一个价格数据集（`_price_calendar` 用 `[START_DATE, end]`、`_load_prices` 用 `[start, end]`、`run_cv` 每折各用一段），如果 `"last"` 在读窗口内解释，同一个 `(t, symbol)` 会在一次 run 内拿到不同的 `adjClose`。更硬的证据：把本机 store 切成一个月的窗口，520 个标的里有 **3 个**在窗口内没有任何可用锚行——`_assert_anchor_usable` 会直接 `ValueError` 拒绝整次读取。把派生放在 `read()` 里、`data_backend.read()` 之后、`_filter()` **之前**，锚的作用域就等于 store 的完整跨度，而 store 的跨度恰好等于今天的转换窗口，于是「逐位不变」「切片不变」「守卫作用域不变」三件事同时成立，一分钱不用多花。

**第三，`anchor="listing"` 在本机根本算不出来，必须具名拒绝。** 本机 raw tier 只覆盖 `2019-01-02..2025-12-31`（132 个 `.pqt`，138,893 行，539 个 PERMNO），而这 539 个 PERMNO 里有 **512 个**（95%）的 `securitybegdt` 早于 2019-01-02，最早的是 1925-12-31。D-02 的前缀标量 `cum_to_<start>` 要求收益链从上市日累起，raw 里根本没有那段历史。所以 `cum_to_<start>` 的写入器必须先比对 `stksecurityinfohist.securitybegdt` 与 raw tier 的每 PERMNO 首行日期，缺一段就按 PERMNO 报错，而不是从 2019 开始累乘然后声称那是「上市以来」。好消息是：**默认锚 `"last"` 完全不需要这张表**（`G_t/G_A` 把前缀整除掉了），所以 D-03 的零回归路径与这张表解耦，表可以按需、后补、甚至本 phase 只写拒绝逻辑不写计算逻辑。

**Primary recommendation:** 在 `CrspStockDataset.read()` 里、`data_backend.read()` 与 `_filter()` 之间做 eager numpy 派生（作用域 = store 完整跨度），`anchor` 作为 `CrspDatasetConfig` 的新字段随 `config.json` 往返；`_reference/_derived/anchor/{product_end}/` 目录名承载 vintage 失效；`_assert_anchor_usable` 原样搬到读侧；`cum_to_<start>` 只服务非默认锚，且以「raw 不到上市日 → 具名拒绝」开路。

## 2.1 Still open #1 —— `cum_to_<start>` 的缓存键与失效策略

### 现状测绘

D-02 提到的「`crsp_reference.py:261-329` 的写入器」在 03.11 的搬迁后拆成了两半：

| 角色 | 真实路径 | 关键坐标 |
|---|---|---|

| **写入器**（要 WRDS session） | `quantlab/acquisition/wrds/crsp_reference.py` | `CrspReferenceTables.pull()`（`:143-224`）、`read_manifest()`（`:106-128`）、`_write_parquet_atomically`、manifest 最后写（`:222`） |

vintage 戳的比对惯例，共**三处**，全部以 `product_end` 为键：

1. `_reference/manifest.json` → `{"product_end", "pulled_at", "tables": {...}}`。本机实测内容：`product_end = "2025-12-31"`，三张表。[VERIFIED: `data/downloads/us_equity/1d/wrds_crsp/_reference/manifest.json`]
2. `pull()` 的 skip 判定：`str(existing.get("product_end")) == product_end.isoformat()`（`crsp_reference.py:170-173`）。**vintage 不同 → `entries` 从空 dict 重新开始，每张表重拉。**
3. raw tier 侧的 `_vintage/wrds.json`，内容就是 `{"product_end": "2025-12-31"}`，由 `quantlab/acquisition/wrds/crsp.py:590-629` 的 `_assert_one_vintage` 写与比。[VERIFIED: 本机 `data/downloads/us_equity/1d/wrds_crsp/_vintage/wrds.json`]

**第三处是最贴切的先例**：它把 vintage 当成一个独立的小 JSON 戳，而不是往 `manifest.json` 里塞。

### 两个落盘方案

#### 方案 A：单文件 + 宽表 + 自带 manifest（字面照抄 D-06）

```
_reference/_derived/adjustment_anchor.parquet
    permno | anchor_date | close_A | cumfacshr_A | cum_to_2000-01-01 | cum_to_2019-01-02 | ...
_reference/_derived/manifest.json
    {"product_end": "2025-12-31", "built_at": "...", "prefixes": ["2000-01-01", ...]}
```

- **失效**：读时 `derived_manifest["product_end"] != CrspReference(...).product_end` → 当作不存在，整体重建。
- **补算一个新 `start_date`**：read-modify-write 整个 parquet（`pl.read_parquet` → `with_columns` → `_write_parquet_atomically`）。
- 优点：一个文件、一次 join、字面符合 D-06 的五列形状。
- 缺点：(a) 列名里带日期，schema 随用随变，`ReferenceTableSpec` 那套「列序即契约」的校验完全用不上；(b) 每加一个 start 就重写全表，两个进程并发补算会互相覆盖；(c) 必须自己维护一个 manifest，多一个可以和 `_reference/manifest.json` 漂移的真相源。

#### 方案 B：vintage 目录 + 每 start 一个文件（**推荐**）

```
_reference/_derived/anchor/{product_end}/base.parquet         # permno | anchor_date | close_A | cumfacshr_A
_reference/_derived/anchor/{product_end}/cum_to/{start}.parquet  # permno | cum
```

- **失效**：vintage 是**路径的一部分**。新 vintage = 新目录，旧目录里的东西不可能被误读。不需要 manifest，不需要比对逻辑，失效是构造性的而非检查性的 —— 这正是 raw tier 的 `subdir='wrds_crsp_{product_end:%Y}'`（`acquisition/wrds/crsp.py:622`）已经在用的招。
- **补算**：append-only，写一个新文件，无 read-modify-write，无并发覆盖。
- **清理**：旧 vintage 目录整目录删，一行 `shutil.rmtree`。
- 优点：失效逻辑为零行代码；写入是原子 `os.replace` 单文件；`cum_to` 的 key 就是文件名。
- 缺点：目录里文件数随 start_date 增长（实践中是个位数）；与 D-06 字面写的「一个 parquet 五列」不同 —— **但 D-06 的实质是「前四列 vintage 级、第五列 (vintage,start) 级」，方案 B 把这个区分变成了目录结构，比塞在一张表里更忠实。**

**推荐 B。** 建议 plan 在任务描述里明确记「D-06 的五列被拆成 `base.parquet` 四列 + `cum_to/{start}.parquet` 一列，语义不变，vintage 失效由路径承载」，这样不算偏离决策。

### ⚠️ 两条必须写进 plan 的硬约束

**(a) 不要把派生产物写进 `_reference/` 的根目录。** `CrspReferenceTables.pull()` 在 vintage 变更时会把 `entries` 清空重建（`crsp_reference.py:169-173`），一个不在 `entries` 里的 parquet 会**静默留在原地**而 manifest 不再提它 —— 正是 03.12 要消灭的那种「文件在、账不在」。放进 `_derived/` 子目录（或干脆一个 `_reference/` 的兄弟目录）就没这个交集。

**(b) `cum_to_<start>` 在本机根本算不出来，必须具名拒绝。** 实测：
- 本机 raw tier 覆盖 `2019-01-02 .. 2025-12-31`，132 个 `.pqt`，138,893 行，539 个 PERMNO。
- 这 539 个 PERMNO 里，`stksecurityinfohist.securitybegdt` 早于 2019-01-02 的有 **512 个**；最早 **1925-12-31**。
[VERIFIED: 本会话 polars 实测，`data/downloads/us_equity/1d/wrds_crsp/`]

所以写入器必须：对每个 PERMNO 比对 `securitybegdt` 与它在 raw tier 里的首行日期，凡 raw 首行晚于上市日的，**按 PERMNO 报错并给出两组日期**，绝不从 raw 的第一行开始累乘然后把结果叫作「上市以来」。那会静默产出一个错的后复权序列，而没有任何下游会报警 —— 与 CR-01 同型的故障。

**由此得出一条排期建议**：`anchor="last"`（默认）与 `anchor="first"` 都在窗口内完成，**不需要这张表**（`G_t/G_A` 把前缀整除掉）。`anchor="listing"` 与固定日历日才需要。plan 可以把「派生下沉 + 删机械 + 默认锚零回归」作为本 phase 的主线（本机可完整验证），把 `cum_to` 的**计算**降级成「写拒绝路径 + 留接口」，或拆成独立的后续任务。这不违反 D-02/D-06 —— 它们规定的是**怎么做**，不是**这次必须全做完**。

### 因子层怎么拿 `adjClose`

不是「直接从 zarr 读」，而是经 `Dataset`：

- `base/factor.py:324-346` `FactorKunQuant.cal()` → `:325` `self.config.dataset.to_kunquant(data_columns=self.config.data_columns)`
- → `base/data.py:1204-1208` `to_kunquant()` → `self.read().get_xarray_dataset()` → `self._to_kunquant(data, data_columns)`
- → `dataset/stock.py:578-590` `_to_kunquant()`：`data.sortby(["timestamp","symbol"])`，逐列 `np.ascontiguousarray(data[col].to_numpy().astype(np.float32))`
- 输入名在 `quantlab/factor/alpha101.py:83-87`（`Input("adjClose")` 等五个）与 `quantlab/factor/alpha158.py:108-112`，标签在 `quantlab/label/fret.py:18`、`:48`。

所以派生只要在 `read()` 里做，因子层零改动。[VERIFIED: 逐文件 `Read`]

### 一次因子计算触发几次派生、成本多少

一次 `cal()` 触发 **1 次** `read()` → 1 次派生。回测一次 `run()` 里，`_price_calendar` / `_load_prices` / 每个因子的 `_refresh_factor_reads` 各触发一次（都是 `overwrite=True`），量级是个位数。

**实测成本**（本机，真实 store 252×520 = 131,040 格）：

```
一次 cumprod + 一次锚点归约 + 五列派生 = 3.8 ms
```
[VERIFIED: 本会话 `uv run python` 计时]

计算量口径：`O(T×S)` 一次 `cumprod`（沿 timestamp）、`O(T×S)` 一次 argmax 归约取锚行、`5 × O(T×S)` 逐元素乘除。内存：5 个 float64 dense 数组 = `T×S×8×5` 字节。

外推（**本机只有 539 PERMNO / 2019-2025 的合成规模真实数据；训练服务器的真实 store 规模未知，以下为估算口径而非实测**）：

| 场景 | T×S | 五列内存 | 估算耗时 |
|---|---|---|---|
| 本机 store（实测） | 252 × 520 = 131k | 5 MB | 3.8 ms |
| S&P500 全历史（1960-2025，成员并集 ~1500） | 16k × 1500 = 24M | ~960 MB | ~0.7 s |
| CRSP 全市场全历史 | 25k × 30k = 750M | ~30 GB | 不可行 |

### 结论与建议

**不需要缓存。** 理由：

1. 3.8 ms 对比一次 zarr 读取（本机 10 MB store）是噪声；对比 KunQuant 的 `cal()`（本机 CRSP 测试套件 34 个用例跑 27.9 s）更是噪声。
2. `read()` 里派生天然已经是「每次 `read()` 一次」，而 `XrBackend` 的读缓存（`overwrite=False` 早返回）已经把重复 `read()` 挡住了 —— **缓存层已经存在，只是它缓存的是 `self.data`，而派生结果就挂在 `self.data` 上。** 再加一层是重复。
3. 落盘缓存会把 `(anchor, window)` 变成一个新的失效维度 —— 正是本 phase 在删的那类税。

**但必须写一条规模守卫。** 全市场全历史面板下 30 GB 的 eager 派生会 OOM。建议：派生前算 `T*S`，超过阈值（比如 2e8 格）时报错，消息里写明「用 `config.permnos` 或 `roster_universe` 收窄，或给出一个窗口」。这比默默 OOM 或默默换成 dask 好。

**不要用 dask / 分块 cumprod。** dask 的 `cumprod` 在分块边界上用的是不同的结合顺序，**会破坏逐位相等**（IEEE 乘法不满足结合律）。`np.cumprod` 沿一个未分块的时间轴是唯一能保证逐位复现今天数值的写法 —— 这点已在 §5 实测中验证。

# 5. 关键实测证据：逐位相等

这是本研究为 D-03 提供的**可执行证据**，plan 应把它变成一个真实的回归测试。

**做法**：从本机真实 store 里**只读原始列**（`close` / `ret` / `cumfacshr` / `open` / `high` / `low` / `volume`），用 numpy 复刻 `_derivation()` 的算术，与 store 里存的五个 `adj*` 做**精确 `==` 比较**。

```python
# 复刻 quantlab/dataset/crsp/__init__.py:591-639 + 1386-1389 的算术，
# 但输入是 DENSE 的 [timestamp, symbol] 面板而非 raw polars frame。
G = np.cumprod(1.0 + np.nan_to_num(ret, nan=0.0), axis=0)          # :591-594 的 fill_null(0.0).cum_prod().over("permno")
usable = (~np.isnan(close)) & (close > 0.0) & (~np.isnan(cumfacshr))  # :609-611 的三条谓词（D-05 / K2）
idx = np.where(usable, np.arange(G.shape[0])[:, None], -1).max(axis=0)  # :615-617 的 .last()，三个量取自同一行
closeA, GA, cfsA = close[idx, col], G[idx, col], cumfacshr[idx, col]
adjClose = np.where(np.isnan(close), np.nan, closeA * G / GA)        # :625-634（含 close 为 null 时的 NaN mask）
factor   = adjClose / close                                          # :637
vfac     = cumfacshr / cfsA                                          # :638-639
adjOpen, adjHigh, adjLow = open_*factor, high*factor, low*factor     # :1386-1388
adjVolume = volume * vfac                                            # :1389
```

**结果**（`data/data/us_equity/1d/wrds_crsp_sp500_1d.zarr`，252×520）：

| 变量 | 逐位相等 | NaN 位置相同 | 比较格子数 |
|---|---|---|---|
| `adjClose` | ✅ True | ✅ True | 130,276 |
| `adjOpen` | ✅ True | ✅ True | 130,276 |
| `adjHigh` | ✅ True | ✅ True | 130,276 |
| `adjLow` | ✅ True | ✅ True | 130,276 |
| `adjVolume` | ✅ True | ✅ True | 130,276 |

耗时 **3.8 ms**。[VERIFIED: 本会话 `uv run python`，2026-09-22]

**为什么 dense 面板上的 cumprod 等于 sparse per-PERMNO 的 cumprod**：稠密化引入的「该标的当天不存在」格子在 `ret` 里是 NaN，`nan_to_num(...,0.0)` 后贡献因子恰为 `1.0`，而 IEEE 下 `x * 1.0 == x` 是精确的。所以前缀积在每个真实行上逐位相同。这也正是 `:591-594` 里 `fill_null(0.0)` 的语义（「null 贡献因子 1」，模块 docstring `:47-50`）。

**推论（对 plan 极其重要）**：store 今天就已经携带了派生所需的全部原料。所以

- 逐位对比测试**可以在改造前就写出来并变绿**（对着现有 store）；
- 改造后它仍必须绿 —— 只是这次左边是 store 里的列，右边是读侧派生的列；
- **数据重建对正确性不是必需的**（现有 store 的原始列没变）。重建是为了让 store 的列构成符合 D-01 的「只存原始」，以及让 `.crsp_adjustment.json` 消失。这给了 plan 一个安全的分步顺序：先改代码 + 验证逐位，再重建。

## 6.4 逐位对比测试的设计（D-03 的核心验收）

**现有测试里没有能承担这个角色的。** 现有的全是「某个具体日子的 `adjClose` ≈ 某个手算值」（`pytest.approx`），不是「读侧派生 ≡ 今天的落盘值」的全面板精确比较。`tests/test_crsp_dataset.py:1049-1088` 的 `xr.testing.assert_identical` 最接近，但它比的是 year vs month granularity 两个**新**面板，不是新旧两代。

**建议新建 `tests/test_crsp_read_side_adjustment.py`，三个用例：**

1. **`test_read_side_derivation_reproduces_a_stored_panel_bit_for_bit`**（合成，进常规回归）
   用 `mock_crsp_session` 建一个含拆股 + 分红 + 退市哨兵的合成 store（复用 `tests/test_crsp_dataset.py:980` 的 `_anchor_series_rows()` 与 `tests/crsp_fixtures.py:dsf_row`），把**改造前**的五列 `adj*` 数值作为 golden 数组硬编码进测试文件（或用 `_convert` 在旧代码上跑一次导出），然后断言读侧派生 `np.array_equal(..., equal_nan=True)` 与 **`==` 精确相等**。⚠️ 用 `==` 不用 `approx` —— 「逐位」是字面要求。
2. **`test_a_narrow_read_window_gives_the_same_levels_as_the_full_store`**（合成）
   `store[2020-01-01..2020-12-31]` 读出后切 3 月，与直接把 config 定到 3 月再 `read()`，两边 `adjClose` 必须 `==`。**这条用例把 §2.2 的「`_filter()` 之前」钉死**：任何窗口级锚的实现都会红。
3. **`test_the_real_store_reproduces_its_adjusted_columns`**（真实数据，进 `test_crsp_rebuild_measurements.py` 或新的同类门，不进常规回归）
   就是 §5 的脚本：对着 `QUANTLAB_DATA_ROOT` 下的真实 store，重算五列、`==` 比较。**这是唯一能在真实 CRSP 数据分布（含真实退市、真实 0.0 哨兵、真实 NULL `cumfacshr`）上证明 D-03 的用例。** 注意它必须在重建**之前**跑一次（对着旧 store 的 `adj*`）——重建之后 store 里就没有 `adj*` 可比了。**这决定了 plan 的任务顺序：golden 快照必须在重建任务之前固化。**

**建议的 golden 固化方式**：在重建任务之前加一个任务，把真实 store 的五列 `adj*` 用 `np.save` 或一个小 zarr 存进 `.planning/phases/03.12-.../evidence/`（或 `data/_snapshot_pre_03.12/`），并把 sha256 写进 plan 的 verification 证据。之后的逐位比较对着这份快照，永久可复查。

# 9. Common Pitfalls / 风险与坑

### R-01（最高）：`_assert_anchor_usable` 换了作用域就会变成常态化拒绝
**现象**：窄窗口读取抛 `ValueError` 列出 3 个 PERMNO（实测：本机 store 切 1 个月，520 标的里 3 个无可用锚行）。
**根因**：守卫的作用域跟着锚走。
**避免**：派生 + 守卫都放在 `_filter()` **之前**，作用域钉在 store 完整跨度。
**预警信号**：任何一个跑 1 个月窗口的回测测试突然红。

### R-02（最高）：CR-01 / CR-02 的哨兵谓词必须完整复刻
D-05 的三条谓词 **必须同时满足且来自同一行**：
```
close.is_not_null() & (close > 0.0) & cumfacshr.is_not_null()
```
- 「同一行」= 一次归约取出 `close_A` / `G_A` / `cumfacshr_A` 三个量的**同一个索引**（现行 `:613-618` 用一次 `group_by().agg(last())` 实现；numpy 侧用一个 `idx` 向量同时索引三个数组，见 §5 的写法）。**先按 `close` 选行、再回去读那行的 `cumfacshr`，就是 CR-02 本体。**
- `close > 0.0` 不能省：CRSP 的无价格哨兵是**数字 `0.0`**，`is_not_null()` 放它过（CR-01）。
- 读侧的 `close` 已经是转换时哨兵守卫过的（`:573-590` 的 `dlyprcflg ∈ ("DA",) | dlyprc == 0.0 → None`，再 `abs()`），所以读侧直接用 store 的 `close` 是**安全的**；但 D-05 那句「不能直接用 `dlyprc > 0`」仍然适用于任何**从 raw 重算**的路径（例如 `cum_to` 的写入器，它读的是 raw）。**plan 必须在 `cum_to` 写入器的任务里重述这条。**
- 第二个拒绝（`G_A == 0.0 | isinf | isnan`，`:721-741`）同样要搬，理由不变：`dlyret == -1.0` 是合法的 CRSP 全损。

### R-03（高）：派生的中间变量泄漏进 `data_vars` 会改指纹
今天靠 `_finalise` 的 `select(columns)` 一刀切（`:1455-1465`）。读侧没有这道闸。派生完必须断言 `set(ds.data_vars)` 恰好等于预期的 27 个名字。**建议写成一条测试**。

### R-04（高）：`anchor="last"` 若用 `C` 前缀标量乘法实现，会破坏逐位相等
`(a*c)/(b*c) != a/b` 在 IEEE 下一般不成立。默认锚路径必须**短路**：锚在窗口内 ⇒ 完全不碰 `cum_to` 表，直接 `G_t/G_A`。若实现图省事「统一走 global G」，D-03 立刻失守而且很难察觉（相对误差 ~1e-16，`approx` 测不出来，只有 `==` 能抓）。

### R-05（中）：`CRSP_SIDECAR_SUFFIXES` 里的 `.crsp_adjustment.json` 不能直接删
`rebuild.py:49-53` 的注释已经写了这条规则的判例：`.crsp_symbology_report.json` 停止生成后**仍留在清理清单里**，因为「suffix 从这里删掉，会让一个描述已删机制的文件留在它从未描述过的 store 旁边」。同理，`.crsp_adjustment.json` 应当：
- **留在 `CRSP_SIDECAR_SUFFIXES`（清理清单）**，并把注释改成「不再生成；留在这里是为了清掉旧 store 旁的遗留」；
- **从 `tests/test_crsp_rebuild_measurements.py:117-127` 的 `EXPECTED_WRITTEN_SIDECARS`（必须写出清单）里移除**。
两张清单答的是不同问题 —— 那段注释（`:113-119`）自己就是这么说的。

### R-06（中）：`head()` 拿不到派生列
`XrBackend.head()`（`backend.py:1616-1652`）按路径独立 open，不碰 `self.data`（RV-01 修复的结果，故意如此）。CRSP 的 `head()` 将不含 `adj*`。**不要为此破 RV-01**，只在 docstring 里说明。

### R-07（中）：`_dataset_variables_fingerprint` 不先 `read()`
`backtest.py:1150` 直接 `factor.config.dataset.get_xarray_dataset()`，依赖 `:1075` 的 `_refresh_factor_reads` 已经读过。如果派生放在 `get_xarray_dataset()` 而不是 `read()`，这里会拿到没派生的面板 → `dataset_fingerprint` 的 `ValueError: cannot fingerprint variables ['adjClose']`（`fingerprint.py:48-54`）。又一条指向 `read()` 的证据。

### R-08（中）：`XrBackend.read` 的读缓存 + 派生 = 重复派生风险
`overwrite=False` 且 `self.data` 已存在 → 早返回（`backend.py:21-22`），此时面板可能**已收窄且已派生**。派生前必须幂等判断（`"adjClose" in data_vars` 则跳过）。

### R-09（中）：stale `.pyc` 会让已删函数继续可导入
03.11-14 的原始教训（`STATE.md:309-310`，`tests/test_stale_bytecode_lesson.py`）。本 phase 删 6 个方法 + 2 个类常量，风险高于平均。verify 前清 `__pycache__`。

### R-10（低）：`cum_to` 的 parquet 若写进 `_reference/` 根目录会被 vintage 换代静默遗弃
见 §2.1(a)。用 `_derived/` 子目录。

### R-11（低）：规模守卫
全市场全历史 eager 派生 ~30 GB。加一条 `T*S` 上限报错。

## 9.1 Anti-Patterns to Avoid

- **把 `anchor` 做成 `read()` 的 kwarg**：破坏 `config.json` 复现（CLAUDE.md 硬约束「全流程参数通过配置文件驱动」）。
- **为旧 store 写兼容读路径**（「store 里有 `adjClose` 就用，没有就派生」）：违反 `project_no_backward_compat`，也让「store 只存原始」这条不变量永远无法断言。
- **让 `_derivation()` 同时吃 raw frame 和 dense 面板**：两个契约焊死。新起一个函数（如 `_derive_adjusted(panel, anchor)`）。
- **顺手把 `_compare_fingerprints` 的 warning 改成 raise**：不在 D-01..D-09 范围内。
- **把 `adjustment_anchor` 塞进 `REFERENCE_TABLES_BY_NAME`**：那是 server 表的闭集，混入派生物会让 `CrspReferenceTables.pull()` 尝试去服务器上 `COUNT` 一张不存在的表。
