# Phase 03.10: CRSP Stock v2 Daily Data via WRDS - Context

**Gathered:** 2026-09-19
**Status:** Ready for planning (depends on Phase 03.9's WRDS session infrastructure being merged)

<domain>
## Phase Boundary

CRSP US Stock Database **Version 2 (CIZ format), annual-update product** on WRDS becomes a drop-in
`us_equity` / `1d` data source: daily security data, security information / ticker history, and
delisting & distribution events are acquired into raw parquet shards by a new WRDS CRSP provider,
and a Dataset converts them into the canonical `[timestamp, symbol]` Zarr panel carrying the same
variables as `StockDataset` (OHLCV + adjusted columns) plus CRSP-specific extras, so factors,
labels, models and the backtester can switch vendor without code changes.

Out of scope: CRSP monthly data; a standalone CRSP-native dataset (follow-up phase); CCM/Compustat
linking; monthly/quarterly-update CRSP products (not entitled — see D-03).

</domain>

<decisions>
## Implementation Decisions

### Source (from live check `03.10-LIVE-CHECK.json`, 2026-09-19)
- **D-01:** Read from schema **`crsp_a_stock`** (annual update; entitled). Coverage 1925-12-31 →
  **2025-12-31** (annual refresh — a request past the product's last date must be refused/clipped
  with a clear message, never silently return nothing). `crsp.*` exposes same-named views;
  `crsp_m_*` / `crsp_q_*` (monthly/quarterly update) are **not entitled**.
- **D-02:** Tables (CIZ names, verified columns in the live check):
  - daily: `stkdlysecuritydata` (110M rows; `permno, dlycaldt, dlyprc, dlyprcflg, dlyret, dlyretx,
    dlyreti, dlyretmissflg, dlyopen, dlyhigh, dlylow, dlyclose, dlyvol, dlybid, dlyask, dlynumtrd,
    dlycap, dlyfacprc, dlyorddivamt, dlynonorddivamt, dlydelflg, …`) — or the pre-joined
    `dsf_v2` (adds per-day `ticker`, `sharetype`, `securitytype`, `securitysubtype`,
    `primaryexch`, `shrout`, `dlycumfacpr`, `dlycumfacshr`, `siccd`, `permco`). Which one (or
    `wrds_dsfv2_query`, 98 cols incl. distributions + market returns) is the researcher's call,
    judged on correctness (no row duplication on multi-distribution days) and pull cost.
  - security info / ticker history: `stksecurityinfohist` (and/or `stocknames_v2`).
  - events: `stkdelists` (29.8K rows, `delret`, `delactiontype`, …), `stkdistributions` (1.1M).
  - index membership: `crsp_a_indexes.dsp500list_v2` (`permno, indno, mbrstartdt, mbrenddt,
    mbrflg, indfam`).
- **D-03:** Reuse Phase 03.9's WRDS infrastructure unchanged: psycopg2 session (host
  `wrds-pgdata.wharton.upenn.edu:9737`, `sslmode=require`, `WRDS_USERNAME` + `~/.pgpass`, one
  connection per run, never `wrds.Connection`), schema-entitlement probe, SQL-shaped volume
  guard (`SqlVolumeGuard`), credential scrubbing, the test tripwire. Server SQL stays
  `SELECT … WHERE` + `COPY … TO STDOUT` (daily data has a unique `(permno, dlycaldt)` key, so
  ordering is not an issue here, but keep the no-aggregation shape).

### Identity & universe
- **D-04:** Panel `symbol` dimension = the **ticker valid on each date** (period-correct, from
  CRSP's own per-day ticker / security-info history), in the universe notation (`BRK.B`).
  **PERMNO (and PERMCO) are kept as data variables.** The planner must handle: a PERMNO whose
  ticker changes (it moves between symbol labels over time — acceptable, matches the
  period-correct universes), and two PERMNOs sharing one ticker on the same date (must be detected
  and resolved deterministically or refused, never silently merged).
- **D-05:** Universe = **CRSP's own point-in-time S&P 500 membership** (`dsp500list_v2`, by PERMNO
  with start/end dates), mapped to period-correct tickers. The existing Wikipedia-based universes
  remain available for other vendors. (The CRSP universe should be usable as a universe source by
  this vendor's CLI; whether it also becomes a general `UniverseCatalog` category is the planner's
  call — keep the change minimal.)
- **D-06:** Securities: **common stocks only** by default (filter on CRSP `securitytype` /
  `securitysubtype` / `sharetype` — exact codes from research; excludes ETFs, ADRs, funds, units,
  etc.); the filter is configurable.

### Prices & returns
- **D-07:** Variables match `StockDataset` so the swap is drop-in: `open, high, low, close, volume`
  (raw, from `dlyopen/dlyhigh/dlylow/dlyclose` or `dlyprc`, volume `dlyvol`) and
  `adjOpen, adjHigh, adjLow, adjClose, adjVolume`. CRSP extras as additional variables (at least
  `permno`, `permco`, `ret` (=`dlyret`), `retx`, `shrout`, `market_cap`, bid/ask, delisting flag).
  Exact names follow existing `StockDataset` naming (research confirms the Tiingo-side names).
- **D-08:** **Adjusted prices are total-return adjusted** (splits + dividends), built by chaining
  CRSP `dlyret` backward from the most recent date in the pulled window (latest adjusted close =
  latest raw close), same semantics as Tiingo `adjClose`; `adjOpen/High/Low` scale by the same
  per-day factor; `adjVolume` uses the share-adjustment factor (`dlycumfacshr`-based). Research
  must note the implication that the adjustment anchor moves when the window is extended (same as
  Tiingo) and how incremental refresh handles it.
- **D-09:** CRSP negative `dlyprc` (bid/ask midpoint when no trade) → absolute value for price,
  with a flag variable; missing-return codes (`dlyretmissflg`) → NaN return, never 0.
- **D-10:** **Delisting returns are incorporated** into the return series and the total-return
  adjusted prices on the delisting date, so labels and backtests include delisting losses
  (no survivorship bias). Research must verify whether CIZ `dlyret` already includes the
  delisting return (if so, do not double count); `stkdelists` fields are also kept as event data.

### Events
- **D-11:** Delisting and distribution events are acquired and stored (raw), and surfaced in the
  panel at least as: delisting flag/return on the delisting date; distribution amounts/factors on
  ex-dates. Exact panel representation is the planner's call.

### Infrastructure / integration
- **D-12:** Register as a `SourceDescriptor` for `us_equity` / `1d` with vendor `"wrds"` (a second
  capability of the existing wrds vendor, or a distinct vendor key if the registry cannot hold two
  WRDS providers — planner decides), `required_env=("WRDS_USERNAME",)`, config via a provider
  classmethod (no `quantlab/config` factory — user memory), CLI `scripts/ingest_wrds_crsp.py`
  following `scripts/ingest_wrds_taq.py`.
- **D-13:** Test gate = no new failures vs the pre-existing baseline list (same approach as 03.9).
  No test may connect to WRDS.

### Claude's Discretion
- Table choice within D-02; batching (by year × PERMNO batch is natural for 110M rows); raw hive
  layout (`1d` → `month=` key exists); variable names for CRSP extras; chunk granularity.

</decisions>

<code_context>
## Existing Code Insights

- The Acquisition/Dataset/registry/volume-guard stack built for WRDS TAQ in Phase 03.9 is the
  template; the CRSP provider differs in frequency (`1d`), table shape (one row per permno-day,
  unique key), and identity mapping (PERMNO → period-correct ticker).
- `StockDataset` builds the panel from observed timestamps; daily CRSP data aligns with that.
- Factor/label code reads adjusted columns only, so D-07/D-08 are what make the vendor drop-in.

</code_context>
