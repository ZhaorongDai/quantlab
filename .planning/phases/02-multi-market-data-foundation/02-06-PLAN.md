<objective>
Provide the automated proof for ROADMAP Phase 2 Success Criterion 4 and CONTEXT.md/REQUIREMENTS.md DATA-03: "adding a new market or frequency only requires a new `Dataset` subclass + config -- no changes needed in factor/model/backtest code." This plan does NOT build a real third market or frequency (CONTEXT.md's domain boundary explicitly says this phase does not need to) -- it builds a minimal, test-only `FakeDataset` subclass exercising the full `from_raw_data()` -> `save()` -> `read()` lifecycle, plus an automated grep-based check that the three core layers (`base/factor.py`, `base/model.py`, `base/backend.py`) contain no market-specific branching or concrete-subclass references.

ROADMAP Phase 2 Success Criterion 4 literally requires "a design/code review" confirming this, not an automated check alone (02-VALIDATION.md's Manual-Only Verifications table lists the human review as a required row ALONGSIDE the automated `FakeDataset` proof, not instead of it). A literal-substring grep catches accidental references to concrete class names but cannot catch structural coupling such as `isinstance`/`hasattr` dispatch on a `Dataset` subclass or branching on `self.config.market`/`self.config.frequency` string values. This plan therefore closes with a `checkpoint:human-verify` task asking a human to read the three core files and confirm no such coupling exists -- the automated proof and the human review are complementary, not substitutes for each other.

Purpose: Turns what 02-VALIDATION.md calls a "manual design/code review" into an automated, repeatable, CI-enforceable check wherever mechanically possible (per the automation-first rule), while still honoring the ROADMAP's explicit requirement for a human-confirmed design/code review for the structural coupling a grep cannot see.
Output: `tests/test_extensibility_contract.py` with both the `FakeDataset` lifecycle test and the core-layer purity grep check, plus a human-verify checkpoint confirming no structural coupling remains.
</objective>

<interfaces>
`base/data.py:Dataset(ABC)` requires three abstract methods to be implemented by any
subclass: `_to_kunquant(self, data: xr.Dataset, data_columns: tuple[str, ...]) -> tuple[dict,
np.ndarray, np.ndarray]`, `_raw_data_to_xr(self) -> xr.Dataset`, `_to_nautilus(self, data:
xr.Dataset, venue: str, n_jobs: int) -> tuple[list[list], list[Instrument]]`. A test-only
`FakeDataset` only needs `_raw_data_to_xr()` to return a real, small, valid `[timestamp,
symbol]`-indexed `xr.Dataset` (hand-built directly, no file I/O needed since this is testing
the abstraction, not real ingestion); `_to_kunquant`/`_to_nautilus` can `raise
NotImplementedError` since the lifecycle under test (`from_raw_data`/`save`/`read`) never
calls them.

`DatasetConfig` (from `base/config.py`, landed by `02-02`) requires `market`/`frequency` as
Literal-typed fields, but Python does not enforce `Literal` values at runtime -- passing a
novel string like `market="fake_market"` for this test is valid Python and is the correct way
to prove genuine novelty (a real third market/frequency is out of this phase's scope per
CONTEXT.md's domain boundary; this test only needs to prove the CONTRACT holds for an
arbitrary new value, not register a fourth real market in the `Market` Literal).
</interfaces>
