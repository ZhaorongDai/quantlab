## Area 1 — Batching / pagination abstraction shape

### Q1.1 — Where does the batching seam go?

| Option | Description | Selected |
|--------|-------------|----------|
| Add `_fetch_batch` with a looping default | `download`/`refresh` call `_fetch_batch`; base default loops the existing `_fetch_and_write`. Tiingo untouched. Cost: two adjacent abstractions on the base. | |
| Invert: batch is the primitive | `_fetch_batch` becomes the only abstract method; Tiingo loops its own single-symbol call. Cleanest, one abstraction. Cost: edits `TiingoAcquisition` and the 674-line `ConcurrentTiingoAcquisition`, contradicting its "does NOT touch base" docstring. | ✓ |
| Separate `BatchedAcquisition(Acquisition)` | New intermediate base; full isolation. Cost: two parallel `download`/`refresh` implementations that will drift. | |
| You decide | Constraints only. | |

**User's choice:** Invert — batch as primitive.
**Notes:** Annotated at ask time with the codebase's two prior forks (03-02's
narrow `Factor(ABC)`, 03.1 D-03's `BaseDataset`), both of which chose
seam-extraction over stub-forcing.

### Q1.2 — Refactor depth on `ConcurrentTiingoAcquisition`

| Option | Description | Selected |
|--------|-------------|----------|
| Minimal: Tiingo keeps its own orchestration | Tiingo's `_fetch_batch` just loops; `ConcurrentTiingoAcquisition` keeps overriding `download`/`refresh`. Lowest risk. Cost: Alpaca reimplements concurrency/resume. | |
| Unified: lift concurrency/resume/quota to the base | One shared batched orchestration for both vendors. Cost: touches production logic just fixed by 260906-26o. | ✓ |
| You decide | Non-regression constraint only. | |

**User's choice:** Unified orchestration in the base.
**Notes:** Recorded as D-02 with an explicit non-regression checklist drawn
from 260906-26o (`QUOTA_STATUS_CODES == {429}`, abort Event as `_attempt`'s
first statement, drained result generator, legacy-watermark skip-and-report).

### Q1.3 — Pagination failure mid-run

| Option | Description | Selected |
|--------|-------------|----------|
| Page-level resume: shard to disk + record `next_page_token` | Restart continues from the token. Cost: raw layout changes; token may expire. | ✓ |

| Write what you have + narrow the watermark | Most consistent with the coverage-range semantics. Cost: requires strict time-ordered pages. | |
| You decide | Research first. | |

**User's choice:** Page-level resume.

## Area 2 — Watermark and failure semantics under batching

## Correction round — Q3.2 reversed

**User's message (verbatim):** "raw 布局不是用 HIVE 吗"

The record was stated plainly: hive was option 2 and was not selected; the
first-pass answer was the symbol-directory layout. But the challenge was
directionally right, and the reason was given: Q3.2 was answered *before*
Q5.3/Q6.1 established that undownsampled tick would stop at the raw tier,
which makes raw the largest-volume tier in the phase and makes date-level
pruning matter. A symbol-only tree can prune by symbol but not by date.

### Q7.1 — Re-decide the raw layout

| Option | Description | Selected |
|--------|-------------|----------|
| Hive partitioning | Date and symbol predicates prune at the directory level; batch responses can be written by date without splitting per symbol. Cost: `_scan_raw` rework; Tiingo daily paths change too (migration cost is zero given D-13). | ✓ |
| Keep the symbol-directory layout | `_scan_raw` untouched. Cost: "one day across the market" opens every shard; 03.3 would likely force the change anyway. | |
| Split by frequency | Daily keeps today's layout; minute/tick go hive. | |
| You decide | Let research measure it. | |

**User's choice:** Hive partitioning. Recorded as D-08 (revised), with the
reversal and its reasoning written into the decision so a later reader does
not "restore" the simpler layout.
