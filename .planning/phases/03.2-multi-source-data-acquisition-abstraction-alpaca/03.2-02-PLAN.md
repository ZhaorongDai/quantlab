<objective>
Prove the phase's spine end to end on the thinnest real path: one Alpaca symbol, one timeframe,
fetched through the new batched base-class primitive, landing at a vendor-namespaced hive shard with
a page ledger written and read back through the reworked `_scan_raw` — then expand that proven slice
with page-level resume (SC-3) and the structural vendor isolation SC-7 needs.

Purpose: the two highest-risk changes in this phase are relocations whose failure mode is silent
behavioural drift, not a crash. Proving the whole vertical on one symbol first means an architectural
dead-end surfaces after one commit rather than after ten already-committed layers.

Output: `_fetch_page` as the sole abstract fetch primitive, a concrete paginating `_fetch_batch`, the
`PageLedger` leaf module, a `requests`-based Alpaca client, the vendor dimension on the config and
path factories, and a hive-aware `_scan_raw` that cannot silently merge two vendors.
</objective>

CONTEXT.md rates three of this phase's decisions **one-way**: D-08 (the raw hive layout), D-11 (the
vendor path segment) and D-13 (existing Tiingo raw data and watermarks are discarded rather than
migrated). Undoing any of them after data has landed means physically relaying the raw tier and
re-burning Tiingo quota — the account's allocation was observed to run out after ~4,600 requests on
2026-09-06. A fourth contract, D-04's `no_data` marker encoding, is rated costly for the same
reason: it lands in on-disk sidecars.

Research settled the shape but two details are the planner's call and are cheap now, expensive later.
The concrete proposal follows; it is what 03.2-02 through 03.2-07 are written against.

**Proposal 1 — path layout.** Under the existing `downloads/{market}/{frequency}/` root
(02-CONTEXT.md D-02, unchanged; `QUANTLAB_DATA_DIR` remains the only path knob per 260906-0iy D-04):

- raw hive root: `downloads/{market}/{frequency}/{subdir}/{vendor}/` — the basename IS the vendor, so
  `StockDataset._scan_raw` can assert `Path(raw_data_dir_path).name == config.vendor` and make an
  accidentally-one-level-up scan unreachable rather than merely unlikely.
- watermark root: `downloads/{market}/{frequency}/{subdir}/_watermarks/{vendor}/` — a SIBLING of the
  vendor directory, deliberately NOT inside it. A polars directory scan walks every file beneath the
  root it is given; a `.json` sidecar inside the raw tree would break the scan outright. This is a
  change from today's `{subdir}/_watermarks/`, and D-13 already discards those sidecars.
- page ledgers: `{watermark_path}/_pages/{batch_key}.pages.json`.
- hive keys by frequency (RESEARCH Pattern 5's file-count arithmetic): `1d` -> `month=YYYY-MM`
  (~130 leaf dirs over 2016-2026 vs ~41 million for the illustrative `date=/symbol=`); `1m` ->
  `date=YYYY-MM-DD`; `tick` -> `data_type=quotes|trades/date=YYYY-MM-DD/symbol=XXX`. Declared once in
  `enums/data.py` as `RAW_HIVE_KEYS` so the writer and the reader cannot drift. The leading
  `data_type=` key for tick is a planner refinement of RESEARCH's recommendation: quotes and trades
  have DIFFERENT column sets, so without it a directory scan of one tick root would hit two schemas
  and raise. Making it a hive key rather than a new `Frequency` token keeps `enums/data.py`'s locked
  literal set untouched (02-RESEARCH.md Assumptions Log A2) and keeps the two prunable.
- shard filename: `part-{batch_key}-{page_index:05d}.pqt` — deterministic, so re-fetching a page
  overwrites rather than duplicates, which is what makes the crash window between shard write and
  ledger record cheap.
- **the leading `data_type=` key for tick** is a planner refinement of RESEARCH's recommended layout.
  Quotes and trades carry DIFFERENT column sets, so without it a directory scan of one tick root
  would meet two schemas and raise. Expressing the distinction as a hive key rather than as two new
  `Frequency` tokens leaves `enums/data.py`'s locked literal set untouched (02-RESEARCH.md
  Assumptions Log A2) and keeps both prunable.
- **the intraday `date=` key is the US/EASTERN SESSION date, not the naive-UTC date** (RESEARCH
  Assumption A8, which the researcher flagged for exactly this decision rather than resolving). Every
  timestamp in this codebase is a naive `pl.Datetime` carrying UTC wall time, so a UTC-derived day key
  files the last ~4 hours of each US session (20:00-24:00 UTC) under the FOLLOWING day. A
  "give me one trading day" query would then be silently wrong at both edges — missing data at the
  close, phantom data at the open. The timestamp VALUES stay naive UTC and unchanged; only the derived
  partition key is converted. Consumed by 03.2-06's minute and tick writers and readers.

**Proposal 2 — `no_data` marker.** One additive boolean key on the existing watermark sidecar,
written ONLY when true and omitted entirely when false, so every sidecar written before this phase
reads back as not-no-data. Same absence-means-unknown discipline `start_date` already follows
(260906-26o D-04). Payload becomes `{"start_date": ..., "last_date": ..., "no_data": true}`.

written. Existing Tiingo raw parquet and watermarks on the Linux workstation become unreadable by the
new hive-aware `_scan_raw` and are re-fetched under the new path, as a separate, resumable,
optional invocation that cannot block the rest of the phase from verifying.
