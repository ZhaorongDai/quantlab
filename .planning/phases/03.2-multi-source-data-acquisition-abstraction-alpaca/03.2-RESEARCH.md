### Locked Decisions

Copied verbatim from `03.2-CONTEXT.md` `<decisions>`. Rationale and reversibility notes
are in that file; only the binding statements are reproduced here.

- **D-01: Invert the primitive.** `_fetch_batch(symbols, start_date, end_date)` becomes the
  single abstract fetch method on `Acquisition`; a single-symbol vendor is the degenerate
  case (Tiingo's implementation loops its own per-symbol call internally). Rejected: adding
  `_fetch_batch` alongside `_fetch_and_write` with a looping default, and a separate
  `BatchedAcquisition` sibling base.
- **D-02: Unify orchestration in the base class.** Concurrency
  (`joblib.Parallel(backend="threading")`), resume/skip-already-covered, failure isolation,
  and the global quota abort move UP out of `ConcurrentTiingoAcquisition` into the base's
  batched `download()`/`refresh()`, so Tiingo and Alpaca share one implementation.
  **Hard non-regression constraint:** every behaviour 260906-26o locked must survive the
  lift, specifically: `QUOTA_STATUS_CODES == frozenset({429})` (403 deliberately excluded),
  the abort `threading.Event` checked as `_attempt`'s FIRST statement with the result
  generator drained rather than abandoned, un-stamped legacy watermarks
  SKIPPED-but-loudly-reported with the exact stamping command, and `refresh()`'s
  end-date-only rule (D-06).
- **D-03: Page-level resume.** Pagination is checkpointed: fetched pages are written to disk
  as shards and the vendor's `next_page_token` is recorded, so an interrupted multi-hour job
  resumes at the failed page rather than at page 1 or at the top of the batch. Rejected:
  batch-atomic and write-what-you-have + narrowed-watermark.
  **Open for research:** `next_page_token` lifetime/expiry semantics, and whether Alpaca
  returns pages in a stable order. If tokens expire, the ledger must record enough to
  re-derive a resume point without one.
- **D-04: A symbol absent from a batch response gets a third state.** Not "failure" and not
  a bare successful advance. The sidecar records an explicit "queried, no data" marker
  alongside the coverage range, the watermark advances, and the state stays distinguishable
  at read time. Schema extension must stay **additive**: old readers must tolerate new files
  and new readers must tolerate old ones.
- **D-05: Two layers of state, separate responsibilities.** The per-symbol watermark sidecar
  keeps its exact current semantics (`{start_date, last_date}`, unknown start = key ABSENT,
  never invented) and gains nothing about pagination. Pagination progress goes into a
  **task-level ledger**, built in the same shape as the already-proven
  `base/chunking.py:ChunkLedger`. Rejected: cramming page tokens into the per-symbol
  sidecar, and collapsing 15.4k sidecars into one manifest.
- **D-06: `refresh()`'s end-date-only rule carries over verbatim to the batch path.**
  `refresh` fetches `[symbol watermark, config.end_date]` and does NOT honour a widened
  `config.start_date`; back-filling earlier history is `download()`'s job.
- **D-07: Delivered this phase:** daily bars, minute bars, quotes/trades.
  **Abstraction-only, not implemented:** corporate actions.
- **D-08 (REVISED during discussion): Raw data lands in a hive-partitioned layout**, e.g.
  `.../{market}/{frequency}/{vendor}/date=YYYY-MM-DD/symbol=XXX/*.pqt` (exact partition keys
  and their order are the researcher's call). Read via
  `pl.scan_parquet(..., hive_partitioning=True)` so date and symbol predicates prune at the
  directory level. **Do NOT "restore" the simpler `raw/{symbol}/{part}.pqt` layout.**
  **Consequence to plan for:** `dataset/stock.py:_scan_raw` must be reworked onto hive
  scanning. The `diagonal_relaxed` concat is also the exact mechanism by which two vendors'
  differently-shaped parquet would merge *without erroring* — which is why D-11's vendor
  partition is structural rather than conventional.
- **D-09: The volume guard is a pre-flight estimate that refuses, with an explicit
  override.** Before issuing requests, estimate volume from symbol count × date span ×
  frequency; over threshold it raises with a concrete narrowing suggestion. Same shape as
  the project's existing `assert_dense_panel_fits` / `MAX_DENSE_PANEL_BYTES`. This guard is
  also the enforcement mechanism for the `<domain>` scope fence.
- **D-10: Alpaca and Tiingo coexist as parallel alternative sources, selected by config.**
  Not a replacement, and not cross-validation/reconciliation.
- **D-11: The path convention gains a vendor segment:** `data/{market}/{frequency}/{vendor}/…`,
  for both `raw_data_dir_path` and `watermark_path`. Structural isolation, not conventional.
  Every factory function in `config/__init__.py` must derive the vendor segment rather than
  have it passed in ad hoc.
- **D-12: Alpaca subscription tier is undecided.** Design the feed level (SIP vs IEX) as a
  **config parameter**, so upgrading is a config change and not a code change.
  **Required of research:** enumerate concretely what differs between the free (IEX) and
  paid (SIP) tiers for the three delivered data types — historical depth, rate limits,
  available fields, and any delay. If quotes/trades on the free tier are IEX-only, that
  limitation must be documented on the class itself, not just in research.
- **D-13: Existing Tiingo raw data and watermarks are NOT migrated and NOT read via a
  fallback path — they are re-fetched under the new vendor path.** Plan the re-fetch as a
  resumable run that respects the quota-abort path, and as an *optional/separate* invocation
  so a failed re-fetch does not block the rest of the phase from verifying.
- **D-14: One top-level script per source** — add `ingest_alpaca.py`, matching the existing
  `ingest_tiingo.py` / `ingest_us_equity.py` / `ingest_binance_spot.py` /
  `refresh_us_equity_universe.py` shape. **Constraint:** do not copy-paste a third
  implementation of the shared `--universe` / `--as-of-date` / `--chunk` argument parsing.
  Factor it into something both scripts call.
- **D-15: Market-data endpoints only. No trading/broker API this phase.** Credentials are
  market-data credentials only, read from environment variables in `__init__` and never
  assigned to a config dataclass.
- **D-16: Raw tick is not downsampled.** Quotes/trades are fetched and landed at full
  resolution; no resampling or aggregation step in this phase.
- **D-17: Run 03.2 before closing Phase 3's outstanding gaps.** **Known conflict:**
  `03-07-PLAN.md` modifies `dataset/stock.py` and `config/__init__.py`; D-08 and D-11 modify
  both of those same files. The 03.2 plans MUST record this overlap explicitly. Before
  running `/gsd-execute-phase 3 --gaps-only`, `03-06`/`03-07`'s `read_first` lists and file

- **D-18: The tick → Zarr conversion is a separate follow-up phase (03.3).** This phase stops

## Summary

This phase has three independent technical problems wearing one coat, and the research
splits cleanly along them.

**First, the vendor.** Alpaca's Market Data API is genuinely batched and genuinely
paginated, and both behaviours are documented precisely enough to design against: one
request takes a comma-separated `symbols` list, returns a `{"bars": {SYMBOL: [...]},
"next_page_token": ...}` envelope capped at 10,000 rows, and orders results **by symbol
first, then timestamp**. That ordering is what makes D-03's page-level resume coherent — a
resume point is a monotone `(symbol, timestamp)` position, and the `next_page_token` is a
base64 encoding of exactly that (verified by decoding Alpaca's own documented example
token). There is no evidence of token expiry and no session state behind it. The one
genuine surprise is the **official Python SDK cannot express this phase's core requirement**:
`alpaca-py`'s `_get_marketdata()` loops every page internally into one in-memory dict and
discards `next_page_token` before returning, and `StockBarsRequest` has no `page_token`
field — so page-level resume is unreachable through its public API (read from the 0.44.0
sdist this session). The recommendation is therefore a thin `requests`-based client, not the
SDK.

**Second, the storage layout.** D-08's hive partitioning was validated empirically against
polars 1.44.1 in a scratch venv, and it works — but with three sharp edges that would each
have shipped as a silent bug. Filtering on the `timestamp` *data* column produces **zero**
directory pruning (measured: 5 of 5 files opened); only a predicate on the hive *key* column
prunes (measured: 2 of 5 files, at plan time). `dataset/stock.py:_scan_raw` currently filters
on `timestamp` alone, so a mechanical port to hive scanning would deliver the new directory
tree and none of its benefit. Separately, scanning a root that sits *above* two vendor
directories **silently merges both vendors** into one frame with no error and no provenance
column when their schemas happen to match — meaning D-11's vendor path segment is necessary
but not sufficient, and needs an explicit invariant assertion plus a `vendor` column to
become the structural guarantee SC-7 asks for.

**Third, the orchestration lift.** D-02 moves the quota abort into the base class to drive
both vendors, and the trap is that `429` does not mean the same thing to the two vendors.
For Tiingo it is hourly *allocation* exhaustion — global, recoverable in ~an hour, correctly
handled by aborting the run. For Alpaca it is a per-minute *rate limit* (200/min on Basic),
recoverable in under sixty seconds and expected during normal operation. Hoisting
`QUOTA_STATUS_CODES` as a shared constant would abort a full-market Alpaca run within
seconds of starting it. The mechanism hoists; the classification must stay a per-vendor
policy method.

**Primary recommendation:** Make `_fetch_page(symbols, start, end, page_token) ->
(frame, next_token)` the single abstract method, give each vendor class a
`DEFAULT_BATCH_SIZE` (Tiingo `1`, Alpaca `100`) so Tiingo's degenerate case is behaviourally
identical to today, hoist the orchestration *mechanism* while keeping error *classification*
per-vendor, drive Alpaca through `requests` rather than `alpaca-py`, partition raw data by a
frequency-dependent date key with `vendor` as a plain path segment plus a written `vendor`
column, and filter `_scan_raw` on both the hive key (for pruning) and `timestamp` (for exact
edges).

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Raw `requests` client | `alpaca-py` `StockHistoricalDataClient` high-level methods | **Structurally incompatible with D-03.** `_get_marketdata()` loops `while True:` over every page into one in-memory dict and returns only `response[selected_key]` — `next_page_token` is discarded and never reaches the caller; `StockBarsRequest` has no `page_token` field `[VERIFIED: alpaca_py-0.44.0/alpaca/common/rest.py:367-407 and alpaca/data/requests.py:86-107, read from sdist this session]`. | `date=YYYY-MM-DD` hive key for daily bars | `month=YYYY-MM` | See Pattern 5's file-count arithmetic. `date=` for daily produces ~2,520 directories holding ~1-row files per batch; `month=` produces ~120. Both prune correctly (measured) |
| Frequency-dependent partition keys | One scheme for all frequencies | One scheme cannot serve both: daily wants coarse (few files), tick wants fine (one day of full-market quotes is larger than the free disk). Each frequency already has its own scan root, so per-frequency schemes never collide |
| Per-batch ledger files | One ledger file + `threading.Lock` | Both correct. Per-batch files avoid the lock entirely and degrade gracefully (a corrupt file loses one batch's resume, not the run's); they also match the existing per-symbol sidecar idiom already proven at 15.4k scale |

### Pagination — the D-03 answer

The exact wording, which is the design constraint:

> "The returned results are sorted by symbol first, then by bar timestamp. This means that
> you are likely to see only one symbol in your first response if there are enough bars for
> that symbol to hit the limit you requested. In these situations, if you keep requesting
> again with the `page_token` from the previous response, you will eventually reach the
> other symbols if any bars were found for them."
> `[CITED: docs.alpaca.markets/us/reference/stockbars]`

**Ordering: symbol-major, then timestamp.** With `sort=asc` this is a total, monotone order,
so a resume point is a well-defined `(symbol, timestamp)` position. `sort` must be pinned to
`asc` explicitly — a `desc` request inverts the resume semantics and would make the ledger's
"furthest position reached" meaningless.

**Token opacity and lifetime.** Alpaca's own documented example token decodes to a plain
positional tuple:

```
base64d("QlRDL1VTRHxNfDIwMjMtMDMtMTdUMDg6MDA6MDAuMDAwMDAwMDAwWg==")
  == b'BTC/USD|M|2023-03-17T08:00:00.000000000Z'
```

`[VERIFIED: base64 decode executed this session of the token published at
alpaca.markets/docs/api-documentation/api-v2/market-data/alpaca-crypto-data/historical]`

That is `SYMBOL|TIMEFRAME|TIMESTAMP` — **positional, not a server-side session cursor.** The
practical consequences:

- **No expiry mechanism is documented, and none is implied by the encoding.** A token stored
  in the ledger overnight is a position, not a lease. There is no documented TTL
  `[ASSUMED — Alpaca publishes no statement about token lifetime either way; this is an
  inference from the encoding, not a vendor guarantee]`.
- **Do NOT re-derive tokens by encoding your own `symbol|timeframe|timestamp`.** The encoding
  is undocumented and can change without notice. Record the token *verbatim*.
- **Do record a token-free fallback anyway.** Alongside the verbatim token, record the last
  written row's `(symbol, timestamp)` per page. If a stored token is ever rejected, the
  resume degrades to re-issuing the batch with `start` narrowed to that timestamp and the
  symbol list trimmed to those at-or-after that symbol — a correct, if slightly wasteful,
  recovery. This is what CONTEXT.md's D-03 asks for ("If tokens expire, the ledger must
  record enough to re-derive a resume point without one") and it costs one extra field.

### Pattern 1: Batched primitive with a class-level batch size (D-01, SC-1)

**What:** One abstract method, `_fetch_page`, expressing "one vendor request". Batching and
pagination are both concrete base-class behaviour above it.

**When to use:** This is the phase's central inversion. Everything else hangs off it.

**Why this shape rather than `_fetch_batch` as the abstract method:** D-01 names
`_fetch_batch(symbols, start_date, end_date)` as the abstract primitive, but a method with
that signature cannot express D-03's page-level resume — it has nowhere to accept an
incoming `page_token` and nowhere to hand back an outgoing one, so the pagination loop would
have to live *inside* each vendor implementation and every vendor would re-implement the
ledger. Making `_fetch_page` the abstract method and `_fetch_batch` a concrete base method
that loops it keeps D-01's guarantee exactly (`_fetch_batch` is still the batched primitive;
a single-symbol vendor is still the degenerate case; there is still no stub) while putting
the resume machinery in one place, as D-02 requires. **Flag this refinement at plan review**
— it honours D-01's intent and its stated rejections, but it is not D-01's literal signature.

```python
# base/acquisition.py
class Acquisition(ABC):
    #: Symbols per vendor request. A vendor whose API takes one symbol per call
    #: sets 1, which makes the batched path behaviourally identical to the
    #: per-symbol path it replaces -- the degenerate case, not a special case.
    #: Overridable per run via config.kwargs["batch_size"].
    DEFAULT_BATCH_SIZE: int = 1

    @abstractmethod
    def _fetch_page(
        self,
        symbols: list[str],
        start_date: str,
        end_date: str,
        page_token: str | None = None,
    ) -> tuple["pl.DataFrame", str | None]:
        """Issue ONE vendor request and return `(rows, next_page_token)`.

        `rows` carries the vendor's raw columns plus `timestamp` and `symbol`.
        A `None` token means this was the last page for `symbols`.
        A vendor with no pagination returns `None` on every call -- that is a
        complete implementation of this contract, not a stub.
        """
        ...

    def _fetch_batch(self, symbols, start_date, end_date, ledger) -> "BatchOutcome":
        """Drive `_fetch_page` to exhaustion, checkpointing each page (D-03).

        Concrete, shared, and the only place pagination is implemented.
        """
        page_index, page_token = ledger.resume_point(...)
        seen: set[str] = ledger.symbols_seen(...)
        while True:
            frame, next_token = self._fetch_page(
                symbols, start_date, end_date, page_token=page_token
            )
            # Shard write BEFORE the ledger record, and idempotent by filename,
            # so a crash between the two costs a re-fetch and an overwrite --
            # never a duplicate row and never a lost page.
            self._write_shard(frame, page_index=page_index)
            seen.update(frame["symbol"].unique().to_list())
            ledger.record_page(page_index, next_token, rows=frame.height, seen=seen)
            if next_token is None:
                break
            page_index, page_token = page_index + 1, next_token
        return BatchOutcome(symbols=symbols, symbols_with_data=seen)
```

Tiingo's degenerate implementation — a real implementation, not a placeholder:

```python
# acquisition/tiingo.py
class TiingoAcquisition(Acquisition):
    #: Tiingo's EOD endpoint takes ONE ticker per call, so a "batch" is one
    #: symbol and every batch is exactly one page. Every property the
    #: concurrent path relies on (per-symbol watermarks, per-symbol failure
    #: isolation, per-symbol resume) then falls out of the shared batched
    #: orchestration unchanged.
    DEFAULT_BATCH_SIZE = 1

    def _fetch_page(self, symbols, start_date, end_date, page_token=None):
        frames = [self._fetch_one(s, start_date, end_date) for s in symbols]
        frames = [f for f in frames if f is not None and not f.is_empty()]
        empty = pl.DataFrame(schema=self.RAW_SCHEMA)
        return (pl.concat(frames) if frames else empty), None  # never paginates
```

**Why `DEFAULT_BATCH_SIZE = 1` is load-bearing.** With any other value, Tiingo's
`_fetch_page` would issue N sequential requests inside one unit of work, and the existing
guarantees would degrade: a failure mid-batch would fail N symbols instead of one, the abort
check (which runs once per batch, as `_attempt`'s first statement) would let N-1 extra
requests through, and the resume granularity would coarsen from one symbol to N. At 1, every
260906-26o behaviour maps one-to-one. The batch size is the single knob that makes the
degenerate case *exact* rather than merely *similar*.

### Pattern 2: Hoist the mechanism, keep the classification per-vendor (D-02, SC-2)

**What:** Move `_run`, `_run_once`, `_partition_by_coverage`, `_report_coverage`, `_attempt`,
`_write_failure_manifest`, `_scrub`, `_knob`, `_abort`/`_reset_abort`, `_sleep` and the
resume loop into `Acquisition`. Leave error *classification* — which exception means what —
as an overridable method.

**When to use:** This is the whole of D-02, and the classification split is the one place a
literal reading of D-02 produces a broken system.

```python
# base/acquisition.py
class Acquisition(ABC):
    def _classify_error(self, exc: BaseException) -> Literal["failed", "quota", "rate_limited"]:
        """How this vendor's failures map onto the shared orchestration.

        - "failed"       -> per-symbol; manifest, no watermark, retried next run.
        - "quota"        -> GLOBAL and slow to clear; trips the abort Event.
        - "rate_limited" -> transient and fast to clear; backoff inside the
                            worker, no global abort, no manifest entry.

        The default is conservative: everything is per-symbol. A vendor that
        has a global condition says so by overriding.
        """
        return "failed"

# acquisition/tiingo.py -- behaviour identical to today, relocated verbatim
class TiingoAcquisition(Acquisition):
    QUOTA_STATUS_CODES = frozenset({429})   # 403 excluded; see 260906-26o D-05
    QUOTA_MESSAGE_TOKEN = "request allocation"

    def _classify_error(self, exc):
        return "quota" if self._is_quota_error(exc) else "failed"

# acquisition/alpaca.py -- the OPPOSITE mapping for the same status code
class AlpacaAcquisition(Acquisition):
    #: 429 is a PER-MINUTE rate limit (200/min on Basic), not an allocation
    #: exhaustion. It clears in under a minute and is EXPECTED during a large
    #: run. Alpaca publishes no request-allocation concept at all, so this
    #: class has no "quota" state -- see the class docstring.
    RATE_LIMIT_STATUS_CODES = frozenset({429})

    def _classify_error(self, exc):
        status = self._status_of(exc)
        if status in self.RATE_LIMIT_STATUS_CODES:
            return "rate_limited"
        return "failed"
```

**Why this is not optional.** `QUOTA_STATUS_CODES = frozenset({429})`
`[VERIFIED: acquisition/tiingo.py:158 — `QUOTA_STATUS_CODES = frozenset({429})`]` is currently
a class attribute on `ConcurrentTiingoAcquisition`, and 260906-26o's rationale for it is
Tiingo-specific: 429 there means the hourly allocation is gone, empirically after ~4,600
requests, and the correct response is to stop dispatching for an hour. Alpaca returns the
same status for a 200-requests-per-*minute* ceiling that a healthy full-market run will hit
repeatedly and recover from in seconds. Hoisting the constant would make a batched Alpaca
run abort within seconds of starting, every time, and the failure would look exactly like
Tiingo's quota exhaustion in the logs. The `"rate_limited"` third outcome is what keeps the
shared `threading.Event` abort meaning "stop the world" for both vendors while letting each
decide what deserves it.

**Non-regression: `QUOTA_STATUS_CODES` must remain reachable at its current name on the
Tiingo class.** `tests/test_tiingo_quota.py:401` asserts
`ConcurrentTiingoAcquisition.QUOTA_STATUS_CODES == frozenset({429})` by direct equality
`[VERIFIED: tests/test_tiingo_quota.py:401]`, and line 463 parameterises over it

### Pattern 3: The page ledger as a per-batch sidecar (D-03/D-05, SC-3)

**What:** One JSON sidecar per batch under `{watermark_path}/_pages/{batch_key}.json`,
modelled on `base/chunking.py:ChunkLedger` — atomic `os.replace` flush, missing file means
empty, sha256 fingerprint of the roster rather than the roster itself.

**When to use:** Any vendor whose `_fetch_page` can return a non-`None` token.

```python
# base/pageledger.py  -- LEAF module: stdlib only, ZERO project imports,
# exactly like base/chunking.py, so it is unit-testable without an Acquisition
# and structurally incapable of introducing an import cycle.

class PageLedger:
    SUFFIX = ".pages.json"

    @staticmethod
    def batch_key(vendor, frequency, start_date, end_date, symbols) -> str:
        """Stable across runs, so a resume finds the same batch.

        Symbols are SORTED before hashing -- a batch is a set, unlike
        ChunkLedger's pinned symbol AXIS, which is ordered and hashes in
        order because two orderings there produce two different stores.
        """
        payload = "|".join([vendor, frequency, start_date, end_date,
                            ",".join(sorted(symbols))])
        return hashlib.sha256(payload.encode()).hexdigest()[:16]
```

Schema (Claude's discretion per CONTEXT.md):

```json
{
  "batch_key": "3f2a91c04e6b7d18",
  "vendor": "alpaca", "frequency": "1m",
  "start_date": "2024-01-01", "end_date": "2024-12-31",
  "symbol_count": 100,
  "symbol_fingerprint": "<sha256 of the sorted roster>",
  "complete": false,
  "pages": [
    {"index": 0, "next_token": "QUFQTHwx...", "rows": 10000,
     "last_symbol": "AAPL", "last_timestamp": "2024-03-14T15:30:00Z",
     "shard": "date=2024-03-14/part-3f2a91c0-00000.pqt"},
    {"index": 1, "next_token": null, "rows": 4210, "...": "..."}
  ],
  "symbols_with_data": ["AAPL", "MSFT", "..."]
}
```

**Three design points worth defending at review:**

1. **Per-batch files, not one manifest, because the writers are threads.**
   `ChunkLedger` is written from a single sequential loop; this ledger is written from N
   worker threads at once. `ChunkLedger._flush()` is atomic *per file* (temp file +
   `os.fsync` + `os.replace` `[VERIFIED: base/chunking.py:_flush]`), but the preceding
   `self._payload["windows"].append(...)` is an unguarded in-memory mutation — two threads
   interleaving would silently lose one record, and the loss would only surface as a
   re-fetched page much later. One file per batch means one writer per file and no lock at
   all. It also fails small: a corrupted sidecar costs one batch's resume, not the run's.
   (If a single manifest is chosen instead, a `threading.Lock` around append-plus-flush is
   mandatory, not optional.)
2. **Shard write strictly before ledger record — the same ordering `ChunkLedger` uses, but
   the crash window is cheap here and expensive there.** For the Zarr append, a crash between
   write and record forced `assert_consistent`'s four-case refusal, because an append cannot
   be validated after the fact. Here the shard filename is deterministic
   (`part-{batch_key}-{page_index:05d}.pqt`), so re-fetching the page **overwrites** rather
   than duplicates — idempotent by construction. And even if a duplicate did land,
   `_scan_raw` already runs `dedup_raw_frame(keep="last")`
   `[VERIFIED: dataset/stock.py:60 — `return dedup_raw_frame(data, keep="last")`]`. That is
   why this ledger needs no `assert_consistent` equivalent, and should not grow one.
3. **`symbols_with_data` accumulates across pages and is only read when the batch
   completes.** See Pitfall 4 — reading it per page produces a false "no data" verdict for
   most of the batch.

### Pattern 4: The "queried, no data" third state (D-04, SC-4)

**What:** One additive boolean key on the existing watermark sidecar. Four read-time states
from three storage facts.

```python
# base/acquisition.py  -- extends _write_watermark's payload, additively
payload: dict = {"last_date": last_date}
if start_date is not None:
    payload["start_date"] = start_date
if no_data:                      # key OMITTED when False -- absence is the default
    payload["no_data"] = True
```

| Read-time state | On disk |
|-----------------|---------|
| Never fetched | no sidecar, no manifest entry |
| Fetch failed | no sidecar, **plus** an entry in `_failures.json` |
| Fetched, data landed | sidecar `{start_date, last_date}`, `no_data` **absent** |
| **Queried, vendor returned nothing** | sidecar `{start_date, last_date, "no_data": true}` |

**Why `no_data` is omitted rather than written as `false`:** it makes absence the default, so
every sidecar written before this phase reads back as "not no-data" — which is correct, since
the old code only wrote a watermark after a successful fetch. That is the same
absence-means-unknown discipline `start_date` already follows
`[VERIFIED: base/acquisition.py:_write_watermark — "`start_date=None` omits the key ENTIRELY
rather than writing a null -- an unknown covered start is represented by absence, so it
cannot be mistaken at read time for a recorded value"]`, and it satisfies D-04's additivity
requirement in both directions: old readers ignore the key, new readers tolerate its absence.

**Extend `_read_coverage`, do not add a second read path.** `_read_sidecar` is documented as
"the single tolerant read both `_read_watermark` and `_read_coverage` share, so there is
exactly ONE failure policy for a corrupt sidecar rather than two that could drift apart"
`[VERIFIED: base/acquisition.py:_read_sidecar docstring]`. `_read_coverage` returns a dict
that gains a third key; nothing else changes.

**Interaction with `_coverage_status` — the point of the whole thing.** A `no_data` symbol
whose `last_date == config.end_date` and whose `start_date <= config.start_date` classifies
as `"covered"` and is skipped on re-run. That is what prevents the re-fetch storm across
thousands of delisted tickers that D-04 exists to avoid. It needs an explicit test, because
it is the behaviour that would silently regress.

### Pattern 5: Hive layout, vendor isolation, and the pruning predicate (D-08/D-11, SC-7)

**What:** Frequency-dependent hive key; `vendor` as a plain path segment *and* a written
column; `_scan_raw` filtering on both the hive key and `timestamp`.

**Recommended partition keys** (this is CONTEXT.md's explicit "researcher's call"):

| Frequency | Layout under `downloads/{market}/{frequency}/{vendor}/` | Leaf dirs over 2016-2026, `us_all` |
|-----------|--------------------------------------------------------|-----------------------------------|
| `1d` | `month=YYYY-MM/part-{batch}-{page}.pqt` | ~130 |
| `1m` | `date=YYYY-MM-DD/part-{batch}-{page}.pqt` | ~2,690 |
| `tick` | `date=YYYY-MM-DD/symbol=XXX/part-{batch}-{page}.pqt` | per fetched slice only |

**The arithmetic that drives this, and why D-08's illustrative `date=/symbol=` is wrong for
daily bars.** With 15,424 symbols and ~2,690 trading days
`[VERIFIED: acquisition/universe.py:1389-1396 — "the full `us_all` roster over
2006-01-01..today is 15,424 symbols x ~5,215 trading days"; trading-day count for
2016-2026 derived from `TRADING_DAYS_PER_YEAR = 252` at acquisition/universe.py:1385]`:

- `date=/symbol=` for daily → 2,690 × 15,424 ≈ **41 million leaf directories**, each holding
  a one-row file. A single `scan_parquet` would stat and open 41M files; the directory tree
  alone would exhaust inodes on most filesystems.
- `date=` alone for daily → 2,690 dirs × ~155 batches ≈ **417,000 files**. Survivable but
  pathological: each file holds ~90 rows.
- `month=` alone for daily → ~130 dirs; one batch's whole-range frame splits into ~130 files,
  so ~155 batches × 130 ≈ **20,000 files** of ~800 rows each. This is the right size.
- For `tick`, the calculus inverts: one symbol-day of quotes is large enough to justify its
  own directory, and `symbol=` pruning genuinely pays.

Since each frequency already has its own scan root, per-frequency schemes never meet. Declare
the key as a class attribute on the acquisition/dataset pair so the writer and the reader
cannot drift.

**Measured hive behaviour** (all executed this session against polars 1.44.1 in a scratch
venv — commands and outputs reproduced in Common Pitfalls):

| Behaviour | Result |
|-----------|--------|
| `scan_parquet(dir)` on `.pqt` files | Works; hive partitioning auto-enabled for a directory argument |
| Hive keys in the frame | Appear as columns; `date=` parses to `Date`, `month=` stays `String` (`try_parse_hive_dates=True` default) |
| Filter on hive key | **Prunes at plan time** — 2 of 5 files in the scan list |
| Filter on `timestamp` data column | **No pruning** — 5 of 5 files |
| Hive key colliding with a real column of the same name | File column wins for the value; **pruning still applies** via the path |
| Numeric-looking hive value (`symbol=8686`) | Inferred as `Int64`; pin with `hive_schema={"symbol": pl.String}` |
| Two vendors, **different** schemas, one root | Raises `SchemaError` (default `extra_columns='raise'`) |
| Two vendors, **same** schema, one root | **Silently merges. No error. No provenance.** |

**That last row is why D-11's vendor path segment is necessary but not sufficient for SC-7.**
A plain `…/{vendor}/…` segment stops nothing on its own: `pl.scan_parquet(".../1d/")` walks
into both `tiingo/` and `alpaca/`, and because the segment carries no `=` it is not a hive
key, so the merged frame does not even record which vendor each row came from. Measured:

```text
### scan rooted ABOVE both vendors, same schema ###
shape: (2, 4)
│ timestamp           ┆ symbol ┆ close ┆ month   │
│ 2024-01-02 00:00:00 ┆ AAPL   ┆ 9.9   ┆ 2024-01 │   <- alpaca
│ 2024-01-02 00:00:00 ┆ AAPL   ┆ 1.0   ┆ 2024-01 │   <- tiingo
```

`dedup_raw_frame(keep="last")` would then collapse these two to one, arbitrarily. Three
mutually reinforcing measures make SC-7 structural:

1. **`AcquisitionConfig` and `DatasetConfig` carry an explicit `vendor` field**, and the
   config factories build `raw_data_dir_path` so it *terminates* at the vendor segment.
2. **`_scan_raw` asserts the invariant**: `Path(config.raw_data_dir_path).name == config.vendor`,
   raising a legible error if a caller ever points the root one level up. One line, and it
   makes the merge unreachable by accident.
3. **Every raw shard carries a literal `vendor` column** (as Tiingo already writes a literal
   `symbol` column `[VERIFIED: acquisition/tiingo.py:71 — `data = data.with_columns(pl.lit(symbol).alias("symbol"))`]`).
   Provenance then survives even a merged read, so the condition is *detectable* as well as
   prevented. `_scan_raw` asserts `n_unique(vendor) == 1` and then drops the column.

**`_scan_raw`'s new shape:**

```python
def _scan_raw(self, start_date=None, end_date=None) -> pl.LazyFrame:
    root = Path(self.config.raw_data_dir_path)
    if root.name != self.config.vendor:      # (2) above
        raise ValueError(...)
    lf = pl.scan_parquet(root, hive_partitioning=True, hive_schema=self.HIVE_SCHEMA)

    start, end = self._as_datetime(...), self._as_datetime(...)
    # BOTH filters. The hive predicate prunes DIRECTORIES at plan time; the
    # timestamp predicate trims the window's exact edges. Dropping the hive
    # filter opens every file (measured); dropping the timestamp filter
    # over-includes rows from the partially-covered edge partitions.
    lf = lf.filter(self._hive_window_predicate(start, end))
    lf = lf.filter(pl.col("timestamp") >= pl.lit(start), pl.col("timestamp") <= pl.lit(end))

    # Provenance asserted, then dropped, so the frame handed to
    # _raw_data_to_xr_window has EXACTLY its pre-refactor column set and every
    # existing assertion in tests/test_stock_dataset.py stands untouched.
    lf = self._assert_single_vendor_and_drop(lf).drop(self.HIVE_KEY)

    return dedup_raw_frame(lf.sort(by=["timestamp", "symbol"]), keep="last")
```

**`extra_columns` and `missing_columns` must stay at their defaults.** The `SchemaError` a
mixed-schema scan raises is a *feature* here — it is the structural half of D-11. Setting
`extra_columns='ignore'` / `missing_columns='insert'` "to make the scan work" would reopen
precisely the silent merge D-11 exists to prevent, and would do it while looking like a bug
fix. Worth a comment in the source, not just here.

### Pattern 6: Pre-flight volume guard (D-09, SC-6)

**What:** A sizing method on `UniverseCatalog`, a refusal at the CLI before any client is
constructed, and an explicit override. Shaped on `assert_chunked_panel_fits`, which already
establishes the "estimate, refuse per unit, advise on the total, name the remedy" idiom
`[VERIFIED: acquisition/universe.py:1543 — `def assert_chunked_panel_fits(`]`.

**What differs from the existing guard, and why it cannot just be reused.**
`assert_dense_panel_fits` bounds *RAM for a dense `[timestamp, symbol]` panel*
`[VERIFIED: acquisition/universe.py:1406 — `MAX_DENSE_PANEL_BYTES = 4 * 1024**3`]`. This
phase never densifies (D-18 fences the conversion out), so RAM is not the binding
constraint. Three other quantities are: **bytes on disk**, **request count**, and **wall
clock** — and on the Basic tier wall clock binds first.

```python
def estimate_acquisition_volume(self, category, start_date, end_date, *,
                                frequency, batch_size, page_limit=10_000,
                                rate_limit_per_min=200,
                                rows_per_symbol_day=None) -> dict:
    """Rows / bytes / requests / wall-clock a fetch would cost. Zero requests issued."""
```

**Volume Arithmetic.** Request and wall-clock columns follow arithmetically from the
verified 10,000-row page cap and the verified rate limits; row counts rest on
`bars_per_day` assumptions flagged below.

| Scenario | Symbols | Rows | Requests | Wall clock @200/min | Wall clock @10k/min | Raw bytes |
|----------|---------|------|----------|---------------------|---------------------|-----------|
| `us_all` daily, 2016-2026 | 15,424 | ~15.3M | ~1,530 | **~8 min** | <1 min | ~0.9 GB |
| S&P 500 minute, 1 year | 500 | ~49M | ~4,900 | **~25 min** | ~30 s | ~3 GB |
| `us_all` minute, 2016-2026 | 15,424 | ~6.0B | ~597,000 | **~50 hours** | ~60 min | **~358 GB** |
| S&P 500 trades, 1 day | 500 | ~50M | ~5,000 | **~25 min** | ~30 s | ~3 GB |
| S&P 500 quotes, 1 day | 500 | ~0.5–1B | ~50–100k | **~4–8 hours** | ~5–10 min | **~30–60 GB** |

Row-count inputs: daily density 0.368
`[VERIFIED: acquisition/universe.py:1390-1393 — "80.4M dense cells, of which only ~29.6M are
real observations (density 0.368)"]`; 390 regular-session minute bars per day `[ASSUMED —
9:30–16:00 ET; extended hours would raise it to ~960]`; ~100k trades and ~10–20× that in
quotes per liquid symbol-day `[ASSUMED — order-of-magnitude only, from general market
microstructure knowledge; NOT measured against Alpaca and NOT verified this session]`.

**The two rows in bold are the scope fence made arithmetic.** A full-market minute backfill
needs 358 GB against ~120 GiB free on the target volume
`[CITED: acquisition/universe.py:1400-1402 — "Disk is not the binding constraint: 120 GiB is
free on the target volume"]`, and 50 hours on the Basic tier. One day of full-market quotes
is likewise larger than the free disk. This is exactly what CONTEXT.md means by "the volume
guard is the mechanism that keeps that distinction enforceable rather than merely stated" —
and it is why the guard must be denominated in **bytes**, not row counts, or a tick request
would pass a row-count check and fill the disk anyway.

**Recommended thresholds and knobs** (Claude's discretion; all via `config.kwargs`):

| Knob | Suggested default | Rationale |
|------|-------------------|-----------|
| `max_raw_bytes` | `20 * 1024**3` (20 GiB) | Comfortably under 120 GiB free while admitting every "capability" scale in the table and refusing every v2-scale one |
| `max_requests` | `50_000` | Admits S&P-500-minute-per-year (~4,900); refuses `us_all` minute (~597,000) |
| `max_wall_clock_hours` | `4.0` | Derived from `max_requests / rate_limit_per_min`; the knob a user actually feels |
| `force_volume` | `False` | The explicit override. CLI: `--force-volume` |
| `rows_per_symbol_day` | required for `tick` | Tick volume is not derivable from a calendar. **Refuse rather than guess** — an invented figure would make the guard confidently wrong in exactly the regime it exists for |

The refusal message must name a concrete narrowing, the way `assert_dense_panel_fits` does
("Narrow the date window or the symbol set, or raise `MAX_DENSE_PANEL_BYTES` deliberately if
this machine has the RAM." `[VERIFIED: acquisition/universe.py:1536-1540]`) — e.g. "this is
597,000 requests / 358 GB / ~50h at 200 req/min; `--category sp500_constituent` over one year
is 4,900 requests / 3 GB / ~25 min, or pass `--force-volume` to proceed."

**Placement.** Before the client is constructed and before a single request — the same
position `ingest_us_equity.py` already chose for `assert_chunked_panel_fits`, and for the
same reason it documents: sparing the user "a multi-hour backfill that ends in a refusal they
could have been told about immediately".

### Pattern 7: Shared CLI argument groups (D-14)

**What:** Argument-group builders plus a resolver, in `utils/cli.py`, called by all three
ingest scripts.

```python
def add_window_args(parser)              # --start-date / --end-date
def add_universe_args(parser)            # --universe/--category + --as-of-date
def add_chunk_args(parser)               # --chunk (TimeChunkPlanner.GRANULARITIES)
def add_concurrency_args(parser)         # --max-workers / --limit
def resolve_symbols(args, catalog, *, mode: Literal["as_of", "in_range"]) -> tuple[str, ...]
```

**The one thing that must not be unified.** `ingest_tiingo.py` resolves membership on a
single day (`get_symbols_as_of`) while `ingest_us_equity.py` resolves interval overlap
(`get_symbols_in_range`) — and that is a deliberate semantic difference, not duplication:

> "Interval OVERLAP, deliberately NOT `get_symbols_as_of()`: a backfill wants every symbol
> that traded at ANY point in the window, including the ~6.9k that delisted inside it.
> Resolving membership on a single day here would reintroduce exactly the survivorship bias
> this roster exists to remove."
> `[VERIFIED: ingest_us_equity.py, comment above the `symbols = tuple(catalog.get_symbols_in_range(...))` call]`

A shared resolver must therefore expose **both** modes explicitly (hence the `mode`
parameter) and must never pick one as a default. Collapsing them is the single highest-cost
mistake available in D-14's refactor, because the resulting bias is invisible in every test
that does not specifically look for delisted tickers.

### Anti-Patterns to Avoid

- **Hoisting `QUOTA_STATUS_CODES` to the base class.** Aborts every Alpaca run within seconds.
  See Pattern 2 / Pitfall 1.
- **Porting `_scan_raw` to hive scanning while keeping only the `timestamp` filter.** Delivers
  the directory tree and none of the pruning. Measured: 5 of 5 files opened. See Pitfall 2.
- **"Fixing" a `SchemaError` with `extra_columns='ignore'`.** Re-opens the silent cross-vendor
  merge that D-11 exists to prevent, while looking like a bug fix.
- **Concluding "no data" from a symbol's absence on a single page.** Alpaca is symbol-major;
  most of the batch is legitimately absent from page 1. See Pitfall 4.
- **Calling `alpaca-py`'s `get_stock_bars()`.** Materialises every page in memory and discards
  the resume token — structurally incompatible with both D-03 and D-09.
- **Letting the hive key or the `vendor` column reach `to_xarray()`.** They become junk data
  variables in the Zarr store. Drop them at the end of `_scan_raw`.
- **Re-deriving `next_page_token` by encoding your own `symbol|timeframe|timestamp`.** The
  encoding is undocumented; record the token verbatim and keep a positional fallback.
- **Adding a `NotImplementedError` stub for corporate actions (D-07).** The codebase has
  refused this fork twice (03-02's `Factor(ABC)`, 03.1 D-03's `BaseDataset`). Corporate
  actions are accommodated by the abstraction *not precluding* them, which requires no code.
- **Defaulting `feed` in code before the SIP-access checkpoint resolves.** D-12 wants it a
  parameter; the documentation conflict makes an in-code default a guess with a 50% chance of
  being silently wrong about data coverage.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic JSON sidecar writes | A fresh temp-file-and-rename | Copy `base/chunking.py:ChunkLedger._flush` (`NamedTemporaryFile` in the same dir → `flush` → `os.fsync` → `os.replace`, with `unlink(missing_ok=True)` on any `BaseException`) | Already field-proven in this repo. D-05 explicitly says the page ledger is ChunkLedger's sibling, "rather than a new invention" |
| Roster-change detection between runs | Storing the symbol list in the ledger | `ChunkLedger.fingerprint()`'s sha256-over-newline-joined idiom | 15,000 tickers would dominate the sidecar; the only question a resume asks is "same roster?", which a fingerprint answers exactly |
| Time-window splitting for large fetches | New window arithmetic | `base/chunking.py:TimeChunkPlanner` | Already splits at year/quarter/month through ONE `_period_key`, and `plan_calendar()` is explicitly the sizing-time planner — exactly what D-09's estimate needs |
| Thread pool over batches | `concurrent.futures` directly | `joblib.Parallel(backend="threading", return_as="generator_unordered")` | Already in use and its subtleties are already documented in place: the generator form is what makes `tqdm` tick per completed unit rather than rendering nothing for hours |
| Corrupt-sidecar tolerance | A second read path | Extend `_read_sidecar` | It is documented as the single chokepoint so there is "exactly ONE failure policy for a corrupt sidecar rather than two that could drift apart" |
| Duplicate-row handling in raw parquet | Dedup inside acquisition | `dataset/cleaning.py:dedup_raw_frame(keep="last")` in `_scan_raw` | Already applied there; a second vendor's overlapping rows flow through unchanged. This is also what makes idempotent shard rewrites safe |
| Dense-panel sizing | New estimator | `UniverseCatalog.estimate_dense_panel` | The catalog is the only object that knows per-symbol listing intervals — which is exactly why dense ≫ observed. The new volume estimator should be its sibling, sharing `_validate_category` / `_validate_iso_date` |
| Ticker syntactic validation | A new regex | `_WELL_FORMED_TICKER` from quick task 260906-eme | Already admits digits (`[A-Z0-9]`) for a documented reason; a second, stricter regex would reject the repo's own synthetic fixture symbols |
| Credential scrubbing in logs/manifests | New redaction | `_scrub` (extend to both Alpaca env values) | Single chokepoint every captured message already passes through; this repo has already leaked one real key |
| HTTP retry/backoff | A bespoke retry decorator | `requests` + an explicit, configurable backoff in `_classify_error`'s `"rate_limited"` path | Not a "don't build" so much as "don't build it twice": the base class already owns the resume loop and the `_sleep` seam that tests substitute |

**Key insight:** almost every collaborator this phase needs already exists in the repo, built
for a neighbouring problem and already hardened in the field. The genuinely new code is small:
one leaf ledger module, one vendor client, one sizing method, one CLI helper. The *risk* is
concentrated somewhere else entirely — in the two relocations (orchestration lift, `_scan_raw`
rework), where the failure mode is silent behavioural drift rather than a crash. Budget review
effort accordingly.

## Common Pitfalls

### Pitfall 1: 429 means opposite things to the two vendors

**What goes wrong:** The D-02 lift hoists `QUOTA_STATUS_CODES = frozenset({429})` to the base
class. Every Alpaca run aborts within seconds and the log says "Vendor request allocation
exhausted -- STOPPED dispatching".

**Why it happens:** Tiingo's 429 is hourly *allocation* exhaustion — global, ~an hour to
clear, empirically after ~4,600 requests. Alpaca's 429 is a per-*minute* rate limit
(200/min on Basic `[CITED: docs.alpaca.markets/us/docs/about-market-data-api]`) that a healthy
batched run is *expected* to hit. Same status code, opposite correct response.

**How to avoid:** Pattern 2 — hoist the mechanism, keep `_classify_error` per-vendor, add the
`"rate_limited"` outcome that backs off inside the worker without touching the global abort.

**Warning signs:** an Alpaca run that "completes" in under a minute with most symbols
unattempted; the word "allocation" in a log line from a vendor that has no allocation concept.

### Pitfall 2: Filtering on `timestamp` gives zero directory pruning

**What goes wrong:** `_scan_raw` is ported to hive scanning, the directory tree is correct,
and every query still opens every file. The phase ships its headline storage benefit with the
benefit missing, and nothing fails.

**Why it happens:** the hive key and the `timestamp` data column are different columns.
Polars prunes on the former at plan time and cannot prune on the latter at all.

**Measured this session** (polars 1.44.1, five single-day partitions, filtering for the last two):

```text
=== filter on HIVE date column ===
Parquet SCAN [hive2/date=2024-01-04/symbol=AAPL/part-a.pqt,
              hive2/date=2024-01-05/symbol=AAPL/part-a.pqt]
ESTIMATED ROWS: 2

=== filter on TIMESTAMP column ===
Parquet SCAN [hive2/date=2024-01-01/symbol=AAPL/part-a.pqt, ... 4 other sources]
ESTIMATED ROWS: 5
```

**How to avoid:** apply **both** predicates — the hive key for pruning, `timestamp` for exact
edges. Never one alone.

**Warning signs:** `.explain()` listing every partition; a conversion whose runtime does not
change when the window narrows. **Make `.explain()` string-assertion a test** — it is the only
cheap way to keep this property from rotting, and it fails loudly rather than slowly.

### Pitfall 3: A vendor path segment does not prevent a cross-vendor merge

**What goes wrong:** SC-7 is assumed satisfied by D-11's path segment. A caller points a scan
one directory up — or a config factory is edited to return the frequency root — and two
vendors' rows merge into one xarray with no error and no way to tell afterwards.

**Why it happens:** a plain path segment is not a hive key, so it neither partitions the scan
nor records provenance. `SchemaError` only fires when the two vendors' *schemas differ*;
identical schemas merge silently. Measured output is in Pattern 5.

**How to avoid:** the three measures in Pattern 5 — explicit `vendor` config field with the
path terminating at it, a basename assertion in `_scan_raw`, and a written `vendor` column
asserted-then-dropped.

**Warning signs:** duplicate `(timestamp, symbol)` rows surviving into `_raw_data_to_xr`; a
row count that roughly doubles after a second vendor is fetched.

### Pitfall 4: "Absent from this page" is not "absent from the batch"

**What goes wrong:** the D-04 no-data marker is computed per page as
`requested_symbols - response.keys()`. Because Alpaca is symbol-major, page 1 of a
100-symbol batch legitimately contains one symbol — so 99 symbols are stamped "queried, no
data", their watermarks advance, and they are skipped forever. A silent 99% data loss that
looks like a successful run.

**Why it happens:** the ordering guarantee that makes resume tractable ("sorted by symbol
first, then by bar timestamp… you are likely to see only one symbol in your first response")
also makes per-page absence meaningless.

**How to avoid:** accumulate `symbols_with_data` across every page of the batch and evaluate
`batch_symbols - symbols_with_data` **only after** `next_page_token is None`. If the batch
aborts before completion, write no no-data markers at all — an incomplete batch has no
opinion about absence, and absence-means-unknown is the house rule (260906-26o D-04).

**Warning signs:** a no-data count that scales with batch size; `no_data: true` on a
liquid mega-cap.

### Pitfall 5: `asof` defaults to today and quietly reintroduces survivorship bias

**What goes wrong:** a `us_all` backfill including ~6.9k delisted tickers is issued without
`asof`. Alpaca maps each symbol to the entity that holds it *today*, so a recycled ticker
returns the *current* occupant's history under the delisted company's name.

**Why it happens:** the documented default:

> "asof — The as-of date of the queried stock symbol(s). Format: YYYY-MM-DD. **Default:
> current day.** This date is used to identify the underlying entity of the provided
> symbol(s), so that name changes for this entity can be found. Data for past symbol(s) is
> returned if the query date range spans the name change. The special value of `-` means
> symbol mapping is skipped."
> `[CITED: docs.alpaca.markets/us/reference/stockbars]`

**How to avoid:** make `asof` an explicit, required-by-convention parameter threaded from the
roster resolution, never left to the default. Two defensible choices — `asof` = the
`--as-of-date` the roster was resolved at (keeps symbol identity consistent with the roster),
or `asof="-"` (raw symbol, no mapping). They differ in *meaning*, so pick one deliberately,
document it on the class, and surface it as a `config.kwargs` knob. This is directly adjacent
to the survivorship-bias reasoning `get_symbols_in_range` already encodes, and it deserves
the same standard of explicitness.

**Warning signs:** a delisted ticker returning bars after its delisting date; two tickers
returning identical price series.

### Pitfall 6: Intra-vendor schema drift breaks the entire raw tier

**What goes wrong:** Alpaca adds a field, or one code path writes a column another omits. The
next `_scan_raw` raises `SchemaError` and *no* data is readable — not just the new shards.

**Measured this session:** two shards in one partition, one with an extra `vw` column:

```text
ERR: SchemaError extra column in file outside of expected schema: vw,
hint: specify this column in the schema, or pass extra_columns='ignore' in scan options.
```

**Why it happens:** hive/directory scanning derives one schema from the first file and
enforces it across all of them — unlike the current per-file `pl.concat(how="diagonal_relaxed")`,
which tolerates differing column sets by design
`[VERIFIED: dataset/stock.py:47 — `data = pl.concat(stock_dfs, how="diagonal_relaxed")`, with
the comment "raw parquet files may come from different acquisition sources/vendors with
columns in a different order (or a differing but compatible column set)"]`.

**How to avoid:** pin the projection at *write* time. Each vendor class declares an explicit
ordered `RAW_COLUMNS` tuple and every shard is written through `frame.select(RAW_COLUMNS)`, so
shards are schema-stable by construction. Do **not** reach for `extra_columns='ignore'` —
that is Pitfall 3's silent merge wearing a different hat. Assert the written schema in a test.

**Warning signs:** a `SchemaError` naming a column you recognise as a legitimate new vendor
field; a scan that works on a fresh directory and fails on an incrementally grown one.

### Pitfall 7: Scanning an empty or absent raw root raises rather than returning empty

**What goes wrong:** a first run, a not-yet-fetched frequency, or a fully-pruned window hits
`pl.scan_parquet` on a directory with no files and gets a `ComputeError`, not an empty frame.

**Measured this session:**

```text
ERR: ComputeError failed to retrieve first file schema (parquet): expanded paths were empty
(path expansion input: 'paths: [PlRefPath { inner: "h5" }]', glob: true).
Hint: passing a schema can allow this scan to succeed
```

**Why it happens:** polars infers the schema from the first file; with no files there is no
schema.

**How to avoid:** keep an existence check equivalent to `get_pqt_files`'s current
`assert Path(dir_path).exists()` `[VERIFIED: utils/file.py:get_pqt_files]`, and raise a
message naming the vendor, frequency and expected path — "no raw data for
`alpaca`/`1m` under …; run `ingest_alpaca.py` first" beats a schema-inference error. Note
this also fires on a *legitimately* empty window; distinguish "root absent" from "root
present but pruned to nothing".

**Warning signs:** `ComputeError` mentioning "expanded paths were empty" from a code path a
user reached by asking a reasonable question.

### Pitfall 8: Numeric-looking hive values change dtype

**What goes wrong:** `symbol=8686` is inferred as `Int64`, and a downstream `pl.col("symbol") == "8686"`
silently matches nothing.

**Measured this session:** `Schema({'close': Float64, 'symbol': Int64})`, fixed by
`hive_schema={"symbol": pl.String}` → `symbol` as `str`.

**How to avoid:** always pass an explicit `hive_schema`. Note the interaction with quick task
260906-eme, which established that `_WELL_FORMED_TICKER` admits digits (`[A-Z0-9]`) precisely
because digit-bearing tickers are legitimate — so this is a live case, not a hypothetical.

**Warning signs:** a symbol filter that returns zero rows for a ticker you can see on disk.

### Pitfall 9: `alpaca-py`'s built-in 429 retry silently swallows the signal

**What goes wrong:** the SDK path is chosen, and `_classify_error` never sees a 429 because
the SDK already retried it three times internally — so the base class's rate-limit backoff
never engages and the run just gets mysteriously slow.

**Why it happens:** `DEFAULT_RETRY_EXCEPTION_CODES = [429, 504]`, `DEFAULT_RETRY_ATTEMPTS = 3`,
`DEFAULT_RETRY_WAIT_SECONDS = 3`
`[VERIFIED: alpaca_py-0.44.0/alpaca/common/constants.py:11-13]`, applied in `_request`'s
`while retry >= 0:` loop.

**How to avoid:** if the SDK is used at all, construct it with `retry_exception_codes=[504]`.
Note `retry_attempts=0` does **not** work — the guard is `if retry_attempts and retry_attempts > 0`
`[VERIFIED: alpaca_py-0.44.0/alpaca/common/rest.py:76-77]`, and `0` is falsy, so the default
of 3 survives. This asymmetry is exactly the kind of thing that makes the raw-`requests`
recommendation cheaper than it looks.

### Reading a page and its resume token, without the SDK

```python
# acquisition/alpaca.py
import os
import requests

class _AlpacaMarketDataClient:
    """Thin, single-page Alpaca Market Data transport.

    Deliberately NOT alpaca-py's StockHistoricalDataClient: its
    `_get_marketdata()` loops every page into one in-memory dict and discards
    `next_page_token` before returning, so page-level resume (D-03) is
    unreachable through its public API, and a whole batch materialises in RAM
    before the volume guard could ever see it (D-09).

    Credentials are read from os.environ HERE and are never assigned to
    AcquisitionConfig, which is asdict-serialized -- the same rule
    TiingoAcquisition follows for TIINGO_API_KEY.
    """

    BASE_URL = "https://data.alpaca.markets/v2"   # pinned; never config-overridable
    KEY_ENV, SECRET_ENV = "APCA_API_KEY_ID", "APCA_API_SECRET_KEY"

    def __init__(self) -> None:
        key, secret = os.environ.get(self.KEY_ENV), os.environ.get(self.SECRET_ENV)
        if not key or not secret:
            raise RuntimeError(
                f"{self.KEY_ENV} and {self.SECRET_ENV} must be set. Alpaca "
                f"market-data credentials are read from the environment and "
                f"are never stored on the config (see D-15)."
            )
        self._session = requests.Session()
        self._session.headers.update({
            "APCA-API-KEY-ID": key,
            "APCA-API-SECRET-KEY": secret,
        })

    def get_page(self, path: str, params: dict) -> dict:
        """ONE request. Returns the raw envelope INCLUDING next_page_token."""
        response = self._session.get(f"{self.BASE_URL}{path}", params=params, timeout=60)
        response.raise_for_status()
        return response.json()
```

Header names, base URL and the envelope shape are all verified above; the class structure
follows this repo's own `TiingoAcquisition.__init__` credential pattern
`[VERIFIED: acquisition/tiingo.py:33-42]`.

### The vendor's `_fetch_page`

```python
    #: Pinned projection and ORDER. Every shard is written through
    #: frame.select(RAW_COLUMNS), so the raw tier is schema-stable by
    #: construction -- a hive/directory scan derives one schema from the first
    #: file and enforces it across all of them (Pitfall 6).
    RAW_COLUMNS = ("timestamp", "symbol", "vendor", "open", "high", "low",
                   "close", "volume", "trade_count", "vwap")

    _FIELD_MAP = {"t": "timestamp", "o": "open", "h": "high", "l": "low",
                  "c": "close", "v": "volume", "n": "trade_count", "vw": "vwap"}

    def _fetch_page(self, symbols, start_date, end_date, page_token=None):
        params = {
            "symbols": ",".join(symbols),
            "timeframe": self._TIMEFRAME_MAP[self.config.frequency],  # "1Day" / "1Min"
            "start": start_date,
            "end": end_date,
            "limit": self._knob("page_limit", 10_000),   # vendor max
            "adjustment": self._knob("adjustment", "raw"),
            "sort": "asc",          # PINNED: desc would invert resume semantics
            "asof": self._knob("asof"),   # explicit; never the vendor default (Pitfall 5)
        }
        feed = self._knob("feed")          # no in-code default until the SIP checkpoint clears
        if feed:
            params["feed"] = feed
        if page_token:
            params["page_token"] = page_token

        payload = self._client.get_page("/stocks/bars", params)

        # {"bars": {SYMBOL: [ {...}, ... ]}, "next_page_token": ...}
        rows = [
            {"symbol": symbol, "vendor": self.VENDOR,
             **{self._FIELD_MAP[k]: v for k, v in bar.items() if k in self._FIELD_MAP}}
            for symbol, bars in (payload.get("bars") or {}).items()
            for bar in bars
        ]
        frame = pl.DataFrame(rows, schema=self.RAW_SCHEMA) if rows else pl.DataFrame(schema=self.RAW_SCHEMA)
        return frame.select(self.RAW_COLUMNS), payload.get("next_page_token")
```

### Timestamp normalisation — match the existing convention exactly

Alpaca returns RFC-3339 with a `Z` suffix, the same shape Tiingo does. The existing
normalisation and its rationale transfer verbatim:

```python
        # Alpaca's `t` is RFC-3339 with a trailing `Z` (UTC). Parse as UTC then
        # drop the tz so the dtype is a naive pl.Datetime, matching every other
        # timestamp in this codebase -- StockDataset's filter bounds are naive,
        # and parsing without an explicit time zone raises on tz-aware strings.
        frame = frame.with_columns(
            pl.col("timestamp").str.to_datetime(time_zone="UTC").dt.replace_time_zone(None)
        )
```

`[VERIFIED: acquisition/tiingo.py:60-73 — the identical transformation and its comment,
applied to Tiingo's `date` field]`

**One genuine divergence to decide deliberately:** Tiingo daily timestamps are midnight-UTC
date stamps; Alpaca daily bars are also date-stamped, but *minute* bars carry true intraday
UTC instants that are **not** naive-local. Dropping the zone on minute data yields naive UTC,
which is self-consistent but is *not* US/Eastern market time — a 09:30 ET bar reads as 14:30.
That is fine as long as it is consistent and documented, and it must be, because the `date=`
hive key is derived from it and a UTC-vs-ET day boundary would put the last ~4 hours of each
session in the wrong partition. Recommend: derive the hive `date=` key from the **US/Eastern
session date**, not the UTC date, and state it in the class docstring. Flag at plan review.

## Security Domain

`.planning/config.json` does not set `security_enforcement`, so it is enabled by default.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | Vendor API-key auth via `APCA-API-KEY-ID`/`APCA-API-SECRET-KEY` headers. Keys read from `os.environ` in `__init__`, never assigned to `AcquisitionConfig` (which is `asdict`-serialized and lands in persisted configs) |
| V3 Session Management | no | No user sessions; `requests.Session` is connection pooling, not identity |
| V4 Access Control | no | Single-user local research pipeline; no authorization surface |
| V5 Input Validation | yes | `symbols` are interpolated into a query string. Validate against the existing `_WELL_FORMED_TICKER` from 260906-eme; reject on failure rather than silently correcting. Validate `feed`, `adjustment`, `sort`, `timeframe` against closed literal sets |
| V6 Cryptography | no | No cryptographic operations. HTTPS is delegated to `requests`/OpenSSL — never hand-rolled |
| V7 Error Handling & Logging | yes | Extend `_scrub` to both Alpaca env values before any message is logged or written to the failure manifest. This repo has already leaked one real Tiingo key |
| V9 Communication | yes | Base URL pinned to `https://data.alpaca.markets`; never accept a scheme or host from config. TLS verification left at `requests`' default — never `verify=False` |
| V12 Files & Resources | yes | Shard paths are derived from vendor/frequency/date/symbol. A symbol containing `/` or `..` would escape the raw root — the same ticker validation that guards V5 guards this |
| V14 Configuration | yes | No credential field on any dataclass; `.env` files are not read; the two new env vars are documented but never defaulted |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Credential echoed in a vendor exception or the failure manifest | Information Disclosure | `_scrub` at the single chokepoint, extended to both Alpaca values. Alpaca sends credentials in *headers* rather than the URL, so URL echo is a smaller vector than Tiingo's `?token=` — but `requests` exception chains can reach `request.headers`, so scrub both regardless |
| Credential persisted into a saved config JSON | Information Disclosure | Never assign to `AcquisitionConfig`; `test_stock_acquisition_config_has_no_credential_field` is the existing lock and needs an Alpaca sibling |
| Malicious/malformed ticker escaping the raw directory root (`../`, `/`) | Tampering | `_WELL_FORMED_TICKER` validation before path construction **and** before query-string interpolation |
| Query-parameter injection via a `,`-bearing symbol | Tampering | Same validation; `symbols` is a comma-joined list, so an embedded comma silently changes the request |
| Cross-vendor data merge producing an untraceable blended series | Tampering | Pattern 5's three measures. This is SC-7 and it is a *data-integrity* control as much as a storage one |
| Silent partial data presented as complete (Pitfall 4's false no-data) | Repudiation / Integrity | Batch-completion gating on the no-data marker; never write markers for an aborted batch |
| Slopsquatted dependency | Tampering | `alpaca-py` rated `SUS`; the recommended design does not install it, and a `checkpoint:human-verify` gates it if the SDK path is chosen |
| Unbounded resource consumption filling the disk | Denial of Service | D-09's volume guard, denominated in bytes as well as requests |
