# Phase 03.2: Code Review Report

**Reviewed:** 2026-09-06
**Depth:** standard (per-file, with targeted empirical verification)
**Files Reviewed:** 27
**Status:** issues_found

## Summary

The phase's *stated* structural guarantees mostly hold and I could not break them:
credentials are read from `os.environ` only, `CREDENTIAL_ENV_VARS` really are module-level
constants that a patched transport cannot disable, the 429 asymmetry is correctly split
(`QUOTA_STATUS_CODES` exists only on `TiingoAcquisition`; `RATE_LIMIT_STATUS_CODES` only on
`AlpacaAcquisition`; neither is a base attribute), SC-7's three parts are all present in
`dataset/stock.py`, `acquisition/universe.py` still imports no acquisition module, shard names
carry no timestamp/uuid/counter, and the `no_data` / `start_date` absence-means-unknown discipline
is consistent in both directions. The declared subset of the suite is green (112 passed).

What the review found is a different class of defect: **four places where a documented guarantee
is asserted in the code and in a test, but is not actually true at the boundary that matters.**
Three of the four are silent — they produce plausible-looking data or plausible-looking success.

The most serious is CR-01: `asof` is documented, threaded, and *tested* as "explicitly passed,
including as `None`" — but `requests` drops `None`-valued params before the wire, so the parameter
is never sent and Alpaca's current-day default applies. That is exactly the survivorship bias the
point-in-time roster exists to remove, arriving as clean data. The test passes because it asserts
on the dict handed to `get_page`, not on the request. This is failure shape "proved directly but
never proved through its real call site" — a seventh instance of the pattern the SUMMARYs record
six of.

CR-02 (polars' 100-row schema inference silently dropping fields) and CR-04 (tick shard duplication
across runs, in the one tier that deliberately never dedups) are the other two silent ones. CR-03
is loud but fatal: `ingest_alpaca.py` adds a `--frequency 1m` front door and then densifies the
result with no dense-panel guard in front of it, after a fetch the volume guard explicitly admits.

## Critical Issues

### CR-01: `asof` is never sent to Alpaca — the survivorship-bias guard is a no-op

**File:** `acquisition/alpaca.py:601-622` (the `params` dict; `"asof": self._knob("asof", None)` at
line 621), reaching `_AlpacaMarketDataClient.get_page` at `acquisition/alpaca.py:82-95`.

**Issue:** The code, its comment, the class docstring, `ingest_alpaca.py`'s module docstring and
two tests all assert that `asof` is "passed EXPLICITLY, including as `None`, and never left to the
vendor's default of today". It is not. `requests` omits any param whose value is `None` when it
builds the query string. Verified in this repo's own environment:

```
>>> requests.Request('GET', url, params={'symbols':'AAPL','start':'2024-01-01',
...     'end':'2024-01-02','limit':10000,'sort':'asc','asof':None}).prepare().url
'https://data.alpaca.markets/v2/stocks/bars?symbols=AAPL&start=2024-01-01&end=2024-01-02&limit=10000&sort=asc'
```

`asof` is absent from the URL. Alpaca therefore applies its documented default (the current day),
which maps every requested ticker onto whatever entity holds that symbol *now*. A delisted ticker
in the `us_all` roster silently returns the current occupant's history. The output is
indistinguishable from correct data, and it is exactly the bias
`get_symbols_in_range`/`UniverseCatalog` exists to eliminate — reintroduced one layer down.

**Why the tests do not catch it:** `tests/test_alpaca_acquisition.py:1475-1476` and `:277` assert
`"asof" in call and call["asof"] is None`, where `call` is the params **dict** recorded by
`FakeAlpacaClient.get_page` (`tests/conftest.py:925-932`). The dict is not the request. The only
boundary at which this claim is falsifiable is `requests`' URL encoding, and no test crosses it.
This is the recorded failure shape "proved as a function is not proved to be wired", one indirection
further out than the six already logged.

**Fix:** Do not rely on a `None` param reaching the wire. Send the vendor's documented
"no symbol mapping" sentinel, and omit the key only when a caller deliberately wants the vendor
default:

```python
# acquisition/alpaca.py
#: What Alpaca's `asof` takes to mean "do not map this symbol onto today's
#: occupant". A `None` value is NOT this: `requests` drops None-valued params,
#: so `asof=None` sends nothing and the vendor's current-day default applies.
ASOF_NO_MAPPING = "-"

...
params = {
    ...,
    "asof": self._knob("asof", self.ASOF_NO_MAPPING),
}
```

and re-point the test at the URL rather than the dict:

```python
prepared = requests.Request("GET", url, params=call_params).prepare()
assert "asof=" in prepared.url, "asof must survive query-string encoding"
```

Confirm the sentinel against a live one-request probe before shipping — the fix must not swap one
unverified claim for another.

### CR-02: polars infers the page schema from 100 rows, silently dropping later fields

**File:** `acquisition/alpaca.py:668` (`frame = pl.DataFrame(rows)`), consumed by the
`missing`/`unexpected` check at `:680-694`.

**Issue:** `pl.DataFrame(list_of_dicts)` infers its schema from the first `infer_schema_length`
rows (default 100) and **silently discards** keys that first appear later. Verified:

```
>>> rows = [{'a':1}]*150 + [{'a':2,'b':9}]
>>> pl.DataFrame(rows).columns
['a']            # 'b' is gone, no error, no warning
```

A page carries up to `limit=10_000` rows, ordered symbol-major. Alpaca omits absent fields from a
row rather than nulling them (`n`/`vw` on thin or OTC bars; `c`/conditions on quotes and trades).
So whenever the first 100 rows of a page happen to lack a field that later rows carry, one of two
things happens, and both are wrong:

1. **Silent data loss.** If the field is in `OPTIONAL_COLUMNS_BY_DATA_TYPE` (`conditions` for
   quotes and trades), the `if missing:` branch at `:695-698` null-fills it — discarding the
   conditions data that *was* on the page for rows 101..N. This is precisely the "null-filling
   convenience converts a mapping error into silent data loss" shape the constant's own comment
   says it exists to prevent; the guard fires on the wrong side because the column was removed by
   inference, not by the vendor.
2. **Spurious whole-batch failure.** If the field is not optional (`vwap`, `trade_count`,
   `price`, `bid_price`...), `:687` raises, `_attempt_batch` classifies it `failed`, and **all 100
   symbols in the batch** land in `_failures.json` with a message accusing the field map of being
   out of date. It will keep failing every run, and the diagnostic points at the wrong cause.

**Fix:** Infer over the whole page, or construct against the declared schema:

```python
# Never the default 100: a page carries up to `limit` rows and the vendor omits
# absent fields per row, so a field first appearing at row 101 would be dropped
# with no error -- which the `missing` check below would then read as vendor
# absence and null-fill.
frame = pl.DataFrame(rows, infer_schema_length=None)
```

Add a regression test whose page has >100 rows and introduces `conditions` (and separately
`vwap`) only after row 100, asserting the column survives with its real values.

### CR-03: `ingest_alpaca.py` densifies minute bars with no dense-panel guard in front of it

**File:** `ingest_alpaca.py:310-326` (the `else:` branch calling
`StockDataset(ds_config).from_raw_data().save()` at line 325).

**Issue:** This phase adds a second US-equity front door that, unlike `ingest_tiingo.py`, offers
`--frequency 1m`. The pre-flight guard it wires (`assert_acquisition_volume_fits`) bounds **raw
disk bytes, request count and wall clock** — its own docstring says so, twice, and calls
`assert_dense_panel_fits` / `assert_chunked_panel_fits` its "siblings, never a replacement".
`ingest_alpaca.py` wires the new one and neither sibling.

The consequence is reachable through the guard's own admitted scenario.
`tests/test_volume_guard.py:548` pins "S&P-500 minute for one year" as *admitted* (~4,900 requests,
~3 GB). Running `ingest_alpaca.py --universe sp500 --as-of-date ... --frequency 1m` over that same
window then reaches line 325, where `_raw_data_to_xr_window` does
`.to_pandas().set_index(["timestamp","symbol"]).to_xarray()` — a dense
`[timestamp, symbol]` cartesian product of ~500 symbols x ~98,000 minute stamps x ~10 variables
x 8 bytes ≈ **4 TB in RAM**, on a machine whose `MAX_DENSE_PANEL_BYTES` is 4 GiB. The process dies
*after* a successful ~25-minute fetch, with the raw shards on disk and nothing having warned.

`ingest_us_equity.py` already solved this shape for daily (`assert_chunked_panel_fits` at two call
sites, one of them before a byte is downloaded). The new door inherited none of it, and
`test_the_chunked_panel_guard_keeps_both_of_its_call_sites` scopes itself to
`ingest_us_equity.py` only, so nothing catches the gap.

**Fix:** Either refuse the densification up front or route it through the chunked path. Minimum:

```python
# ingest_alpaca.py, alongside the volume guard and BEFORE the fetch --
# a sibling of it, not a replacement: that one bounds raw disk/requests/hours,
# this one bounds the RAM of the dense [timestamp, symbol] panel line 325 builds.
if args.frequency != "tick":
    pricing.assert_dense_panel_fits(category, guard_start, guard_end)
```

and extend `test_the_chunked_panel_guard_keeps_both_of_its_call_sites` (or add a sibling) to assert
the RAM guard exists at every entry point that reaches `from_raw_data()`. Note that
`assert_dense_panel_fits` currently sizes in trading **days**; for `1m` it must be multiplied by
`BARS_PER_DAY_BY_FREQUENCY[frequency]` or it will admit the same fetch it is meant to refuse.

### CR-04: tick rows are duplicated across runs — deterministic filenames do not cover a changed window

**File:** `base/acquisition.py:780-792` (`_shard_path`), `base/acquisition.py:866-880`
(`_ledger_for`, `batch_key` includes `start_date`/`end_date`), read by
`dataset/stock.py:365-374` (tick returns **without** `dedup_raw_frame`).

**Issue:** Shard determinism is scoped to *one* `(vendor, frequency, start, end, symbols)` tuple,
because `batch_key = sha256(vendor|frequency|start|end|sorted(symbols))` and the filename is
`part-{batch_key}-{page:05d}.pqt`. Change the window and the same rows land under a **different
filename in the same partition directory**:

- `ingest_alpaca.py --frequency tick --data-type trades --refresh` requests
  `[watermark_last_date, end_date]`. `last_date` is inclusive, so the final session is re-fetched.
  Its `batch_key` differs from the original `download()`'s (different `start_date`), so the
  overlap session's trades are written a **second** time under a second part file.
- The same happens for a plain re-`download()` with any widened `--end-date`, and again on every
  subsequent refresh as the watermark advances.

For `1d`/`1m` this is absorbed: `dataset/stock.py:374` runs `dedup_raw_frame(data, keep="last")`.
For **tick it is not** — `:365-373` deliberately returns undeduped, on the correct grounds that
genuine quotes and trades share `(timestamp, symbol)`. That correct decision is exactly what makes
the duplicates undetectable: a doubled trade tape is indistinguishable from a busy one. Volume,
VWAP and any microstructure statistic computed off this tier are silently wrong, permanently.

The D-19 contract-4 reasoning ("a re-fetched page OVERWRITES rather than duplicating") is true only
within a fixed window; nothing in the code or the tests states or enforces that scope.

**Fix:** Make the shard path deterministic over the *content coordinates* rather than the request
coordinates for the tick tier — e.g. drop `start_date`/`end_date` from the identity used in the
filename and key the shard on `(vendor, frequency, symbols, page_index)` plus the partition it
lands in; or, more simply, delete the existing part files in a partition before writing a
re-fetched one:

```python
# base/acquisition.py:_write_shard, before write_parquet
# The window is part of `batch_key`, so a re-fetch over a DIFFERENT window
# writes a second file rather than overwriting the first. `1d`/`1m` absorb that
# in dedup; tick deliberately does not dedup (D-16), so the duplicate is
# permanent and invisible. Clear the partition's prior shards for this page.
for stale in path.parent.glob(f"part-*-{page_index:05d}.pqt"):
    if stale != path:
        stale.unlink()
```

Whatever the chosen mechanism, add a test that runs `download()` then `refresh()` over an
overlapping tick window and asserts the row count of the overlap session is unchanged.

### WR-01: Alpaca tick timestamps are truncated from nanoseconds to microseconds

**File:** `acquisition/alpaca.py:708-712` (`str.to_datetime(time_zone="UTC")` with no `time_unit`),
schema declared at `:358-396` (`"timestamp": pl.Datetime`, i.e. microseconds).

**Issue:** Alpaca's trades and quotes carry nanosecond RFC-3339 timestamps. polars parses to
microseconds here (verified: `2024-01-02T14:30:00.123456789Z` → `2024-01-02 14:30:00.123456`,
dtype `datetime[μs]`). D-16 and the `_fetch_page` docstring state tick rows are landed "at FULL
resolution ... no resampling, no bucketing and no dedup". Sub-microsecond ordering is lost, and it
is lost in the one tier that *deliberately* never dedups on `(timestamp, symbol)`, so the
truncation manufactures ties that downstream code cannot tell from real simultaneity.

**Fix:** Declare and parse nanoseconds for the tick data types:

```python
RAW_SCHEMA_BY_DATA_TYPE = {
    "bars":   {"timestamp": pl.Datetime("us"), ...},
    "quotes": {"timestamp": pl.Datetime("ns"), ...},   # vendor sends ns
    "trades": {"timestamp": pl.Datetime("ns"), ...},
}
...
frame = frame.with_columns(
    pl.col("timestamp")
    .str.to_datetime(time_zone="UTC", time_unit=self.RAW_SCHEMA["timestamp"].time_unit)
    .dt.replace_time_zone(None)
)
```

Assert the round trip in a test with a nine-fractional-digit timestamp.

### WR-02: `_fetch_batch` has no guard against a repeated page token

**File:** `base/acquisition.py:944-984` (the `while True:` page loop).

**Issue:** The loop terminates only on a falsy `next_token`. If a vendor ever echoes the token it
was handed (a mis-implemented `page_token`, a proxy replaying a response, a partial outage), the
loop runs forever: `page_index` increments each iteration, so shard filenames keep changing, the
ledger's `pages` list grows without bound, and the raw root fills the disk. Nothing bounds it —
not a page cap, not an "identical token" check, not a zero-rows check.

**Fix:**

```python
if next_token and next_token == page_token:
    raise ValueError(
        f"{self.class_name}: the vendor returned the SAME page token it was "
        f"given ({next_token!r}) on page {page_index} of batch {batch_key}. "
        f"Continuing would loop forever, writing a new shard per iteration. "
        f"Refusing rather than filling the raw root."
    )
```

Optionally also cap pages per batch via a `_knob("max_pages", ...)`.

### WR-03: the failure manifest loses failures recorded by earlier resume passes

**File:** `base/acquisition.py:1069-1104` (`failures` is *reassigned* by each pass at `:1077`;
`_write_failure_manifest(failures)` runs once at `:1104`).

**Issue:** `_run`'s quota resume loop can execute several passes. `failures` is overwritten each
time rather than merged. Sequence: pass 1 fails 40 symbols (real 404s) and then trips the global
abort; the run waits; pass 2 re-derives `pending` from disk, aborts again on the first batch and
returns `{}`. `_write_failure_manifest({})` then writes an **empty** manifest. The docstring at
`:1576-1584` claims "an empty one is a meaningful statement that the last run was clean" — here it
is a false statement about a run that had 40 failures. The symbols are still retried (no watermark
was written), so this is a reporting defect rather than data loss, but the manifest is the artefact
the operator is told to trust.

**Fix:** accumulate across passes:

```python
failures: dict[str, str] = {}
while True:
    ...
    aborted, pass_failures = self._run_once(pending, from_watermark)
    # Merged, not replaced: a pass that aborts before re-reaching an earlier
    # pass's failures must not erase them from the manifest.
    failures.update(pass_failures)
```

(Entries for symbols that later succeed should be dropped in the same update; the succeeding pass
returns them as `ok`, so remove them explicitly.)

### WR-04: symbols reach filesystem path construction before `_validate_symbols` runs

**File:** `base/acquisition.py:627-644` (`_validate_symbols`, docstring claims it is "Called BEFORE
path construction"), versus `:141` (`_watermark_path`) reached from `:1373-1383`
(`_partition_by_coverage`), `:838-851` (`_refresh_batches`) and `:1458-1460` (`_attempt_batch`).

**Issue:** The ordering claim is false. `_run` calls `_partition_by_coverage` first, which calls
`_read_coverage(symbol)` → `_watermark_path(symbol)` → `self._watermark_root / f"{symbol}.json"`,
for every symbol in the roster, before any validation happens. Validation only runs later, inside
`_fetch_batch`. A roster entry of `"../../../../etc/hosts"` (from a hand-written `--symbols`, a
corrupted `universe.parquet`, or a future roster source) produces a path outside the watermark
root, which is then `exists()`-checked and `json.load`ed. Reads only — no write path is reachable
before validation — so the blast radius is bounded, but the security control does not run where
its own docstring says it does.

**Fix:** validate once at the top of `_run` (and of `coverage_report`/`stamp_watermarks`), so every
downstream path builder is behind the check:

```python
def _run(self, symbols, from_watermark):
    # Validated HERE, not only in `_fetch_batch`: `_partition_by_coverage`
    # below turns every symbol into a filesystem path before any batch exists.
    requested = self._validate_symbols(list(symbols or self.config.symbols))
```

Add a test that a `../`-bearing symbol raises before any sidecar is opened.

### WR-05: Tiingo shards pin column names but not dtypes, unlike Alpaca's

**File:** `acquisition/tiingo.py:176-215` (`_fetch_one` — `pl.DataFrame(response)` then
`select(RAW_COLUMNS)`, with **no** cast), versus `acquisition/alpaca.py:713-720` (`frame.cast(...)`
against `RAW_SCHEMA`).

**Issue:** `Acquisition.RAW_COLUMNS`' own docstring claims "the raw tier is schema-stable BY
CONSTRUCTION ... a single shard written with an extra column, or with the same columns in a
different order, makes the whole vendor root unreadable". Column set and order are pinned; **dtype
is not.** `pl.DataFrame(json_rows)` infers per response, so one symbol whose `divCash` is all
integer `0`, or whose `volume` is all `null` over the requested window, yields a shard with
`Int64`/`Null` where its siblings have `Float64`. `dataset/stock.py:317-327` deliberately leaves
`extra_columns`/`missing_columns` at their raising defaults, so the whole `month=` directory scan
then fails with a `SchemaError` naming a file, not a cause — and it will look intermittent, because
which file polars opens first is filename-ordering dependent (the same shape as the tick
`data_type` bug the SUMMARYs record as mutation #6).

Alpaca already does the right thing; the two vendors implement the same stated contract differently.

**Fix:** give `TiingoAcquisition` a `RAW_SCHEMA` and cast on the way out of `_fetch_one`, mirroring
`_empty_frame`'s existing dtype map:

```python
return data.select(self.RAW_COLUMNS).cast(
    {name: dtype for name, dtype in self.RAW_SCHEMA.items() if name != "timestamp"}
)
```

### WR-07: `test_the_estimate_is_printed_whether_or_not_it_refused` cannot fail for the reason it names

**File:** `tests/test_volume_guard.py:1072-1115`; the behaviour it claims to cover lives at
`ingest_tiingo.py:117-132`, `ingest_us_equity.py:426-444`, `ingest_alpaca.py:281-296`.

**Issue:** The test calls `print_volume_estimate(...)` directly with a hand-built dict and
`forced=True` / `forced=False`. It never exercises a refusal. In all three scripts the call is
structured as `print_volume_estimate(pricing.assert_acquisition_volume_fits(...), ...)` — the guard
is an *argument*, so when it raises, `print_volume_estimate` is **never invoked**. The estimate is
therefore *not* "printed whether or not it refused"; on refusal only the exception message is
shown. `print_volume_estimate`'s own docstring (`utils/cli.py:511-515`) repeats the same false
claim. The test passes for a different reason than its name asserts, and would stay green if the
refusal path stopped printing anything at all — which it already does.

**Fix:** either rename the test to what it proves (`test_the_forced_line_distinguishes_overridden_from_clean`)
and correct both docstrings, or make the claim true and test it at the call site:

```python
estimate = None
try:
    estimate = pricing.assert_acquisition_volume_fits(...)
finally:
    if estimate is not None:
        print_volume_estimate(estimate, ...)
```

with a test that runs the `__main__` body against a refusing scenario and asserts the numbers were
printed before the raise propagated.

### WR-08: a page ledger with pages but no fingerprint is resumed onto by any roster

**File:** `base/pageledger.py:180-184` (`if self.symbols is not None and
payload["symbol_fingerprint"] is not None:`), and `:248-270` (`describe` does not flush).

**Issue:** The roster-mismatch guard is skipped entirely when the stored `symbol_fingerprint` is
`None`. `describe()`'s own docstring states the reason this must not happen — "a ledger with pages
but no fingerprint could be resumed onto by a different roster" — and then the loader tolerates
exactly that state. Reaching it requires a ledger written without `describe()` having run, which is
possible because `describe()` **mutates `_payload` without flushing**: identity only reaches disk on
the first `record_page`. Any hand-edited, externally produced, or partially-restored ledger with a
`pages` array and no fingerprint is silently resumed onto, skipping pages that were fetched for a
different symbol set.

**Fix:** treat a missing fingerprint on a ledger that has pages as a mismatch:

```python
if self.symbols is not None and payload["pages"]:
    if payload["symbol_fingerprint"] != self.fingerprint(self.symbols):
        return self._empty()   # covers None as well as a genuine mismatch
```

and flush in `describe()` so identity is on disk before the first request.

### WR-09: `start`/`end` are sent as bare dates for intraday, while the watermark claims the whole day

**File:** `acquisition/alpaca.py:604-605` (`"start": start_date, "end": end_date`), with
`base/acquisition.py:1541-1547` writing `last_date = self.config.end_date` unconditionally and
`base/acquisition.py:1354-1362` (`_classify_coverage`) treating `last_date == end_date` as
`covered`.

**Issue:** For `1d` a date-only bound is unambiguous. For `1m` and `tick` it is not: Alpaca
documents these as RFC-3339 instants, and a bare `YYYY-MM-DD` end most plausibly resolves to
`00:00:00Z` — which excludes the entire final trading session (the US regular session is
14:30–21:00 UTC). Regardless of how Alpaca resolves it, the bookkeeping is unconditional: on a
successful batch `_attempt_batch` stamps `last_date = config.end_date` whether or not any row for
that date arrived, and `_classify_coverage` then marks the symbol `covered`. A missing final
session is therefore never re-fetched, and reads as sparse data rather than as a gap.

This is stated as a warning rather than a blocker because Alpaca's date-only parsing is not
established in the repo and I could not verify it without credentials — but that is itself the
problem: nothing in the code or the tests records which reading is assumed.

**Fix:** send explicit instants for intraday and pin the assumption:

```python
#: Intraday windows are sent as explicit RFC-3339 INSTANTS, not bare dates: a
#: date-only `end` resolves to 00:00Z and would exclude the whole final US
#: session (14:30-21:00 UTC) while the watermark stamps that date as covered.
params["start"] = start_date if self._data_type == "bars" and freq == "1d" else f"{start_date}T00:00:00Z"
params["end"]   = ... f"{end_date}T23:59:59.999999999Z"
```

and add a test asserting the wire-level `end` for `1m`/`tick` covers the session close.

## Info

### IN-01: `AlpacaAcquisition._classify_error` duplicates the base implementation verbatim

**File:** `acquisition/alpaca.py:568-577` versus `base/acquisition.py:608-617`.

Both bodies are `if self._status_of(exc) in self.RATE_LIMIT_STATUS_CODES: return "rate_limited"` /
`return "failed"`. The override adds documentation but no behaviour, and it means every Alpaca
classification test exercises the copy — a mutation of the base's version would leave those tests
green. Either delete the override and move its docstring onto `RATE_LIMIT_STATUS_CODES`, or keep it
and add one assertion that the base's default is itself covered by a subclass that does not
override.

### IN-02: `ingest_alpaca.py` writes every roster into the `nasdaq_data` subdirectory

**File:** `ingest_alpaca.py:160-177` — neither factory call passes `subdir`, so the default
`"nasdaq_data"` applies. `ingest_alpaca.py --universe us_all` lands its raw shards under
`downloads/us_equity/{freq}/nasdaq_data/alpaca/`, a directory named for a different roster;
`ingest_us_equity.py` uses `DEFAULT_SUBDIR = "us_all"` for exactly this reason. Vendor isolation is
unaffected (the vendor segment still terminates the path), but the tree is misleading and the two
Alpaca rosters share one watermark root, so their coverage bookkeeping is entangled. Suggest a
`--subdir`/roster-derived default mirroring `ingest_us_equity.py`.

### IN-03: a lowercase or malformed `--symbols` entry produces a "successful" run with an all-failed manifest

**File:** `utils/cli.py:281-283` (symbols split verbatim, no normalisation) →
`base/acquisition.py:627-644` (raises) → `base/acquisition.py:1494-1512` (caught, classified
`failed`).

`--symbols aapl,msft` does not match `_TICKER_PATTERN` (uppercase only). Every batch raises inside
`_attempt_batch`, is caught, and lands in `_failures.json`; the script prints its success lines and
exits 0. A CLI-level normalisation (`token.strip().upper()`) or an up-front validation in
`resolve_symbols` would turn a typo into an immediate, legible error.

### IN-04: `_assert_single_vendor_and_drop` forces an extra eager collect of the whole filtered scan

**File:** `dataset/stock.py:257-262`.

`data.select(pl.col("vendor").unique()).collect()` materialises a pass over every matching shard
before the real collect. Correctness is fine (and the ordering before `dedup_raw_frame` is right),
but the cost is a full second scan of the window. `.select(...).unique().limit(2).collect()` would
prove the same thing — one vendor versus more than one — while letting polars stop early.

### IN-05: `AcquisitionConfig` gained a required field in a positional dataclass

**File:** `base/config.py:150-153` — `vendor: Vendor` inserted as the third field of a plain
`@dataclass` (not `kw_only=True`, unlike `DatasetConfig`).

All in-repo constructions are keyword-based, so nothing breaks today, and a five-positional call now
raises `TypeError` loudly. But a six-positional external call would silently misbind
`raw_data_dir_path` → `vendor`. Adding `kw_only=True` to match `DatasetConfig`/`BaseDatasetConfig`
would make the class structurally immune.
