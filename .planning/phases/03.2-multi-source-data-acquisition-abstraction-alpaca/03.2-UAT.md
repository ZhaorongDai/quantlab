### 1. Free-tier SIP access (open question O-1)

test: |
  Issue ONE historical SIP quotes request older than 15 minutes with a free (Basic)
  tier key pair:

  ```bash
  curl -i -H "APCA-API-KEY-ID: $APCA_API_KEY_ID" -H "APCA-API-SECRET-KEY: $APCA_API_SECRET_KEY" \
    'https://data.alpaca.markets/v2/stocks/quotes?symbols=AAPL&start=2024-01-02T14:30:00Z&end=2024-01-02T14:31:00Z&feed=sip&limit=1'
  ```
expected: |
  200 → Basic tier reaches historical SIP.
  403 → IEX is the only usable feed.
  Either answer is a result; there is no wrong outcome here.
why_human: |
  Alpaca's own documentation self-conflicts — three sources say Basic reaches historical
  SIP, one says IEX-only. No `feed` default was baked into code precisely because this is
  unresolved: `acquisition/alpaca.py:773` reads `feed` from kwargs defaulting to `None` and
  omits the key when unset (confirmed live — no request carried a `feed=` param), and
  `ingest_alpaca.py` registers no `--feed` flag.
resolves: RESEARCH Assumption A7, open question O-1
result: pass
finding: |
  ANSWERED YES — the Basic (free) tier DOES reach historical SIP.
  Three independent observations, all required for the conclusion:
    - `X-Ratelimit-Limit: 200`  -> Basic tier (Algo Trader Plus is 10,000)
    - historical SIP (2024-01-02, >15 min old) -> 200 with real consolidated
      quotes (`ax:"P"`, tape `z:"C"`, two-sided); IEX for the same window is
      one-sided with ask 0 (`ax:"V"`) — genuinely different sources
    - recent SIP (last 2h, inside the 15-minute embargo) -> 403
  So: historical SIP is available on Basic, subject to a 15-minute embargo on
  recent data. The three documentation sources saying so were right; the fourth
  (IEX-only) was wrong.
  Consequence: a `feed` default MAY now be written into code. Not done in this
  phase — it is a code change beyond 03.2's scope.

### 3. Real maximum symbols per request (RESEARCH Assumption A2)

test: |
  Probe upward from the 100-symbol default in a single `symbols=` param — e.g. 100 → 200
  → 500 — recording the status code at which the vendor rejects.
expected: |
  The empirical ceiling. `AlpacaAcquisition.DEFAULT_BATCH_SIZE = 100` is a conservative
  working value until this is known.
why_human: |
  Requires live vendor responses; the limit is not authoritatively documented.
resolves: RESEARCH Assumption A2
result: pass
finding: |
  ANSWERED — but the limit is not a symbol count. Probed with distinct real
  tickers from `data/data/reference/universe.parquet`, padded with well-formed
  synthetic tickers to isolate the REQUEST limit from data availability:
    n=6,632  url 45,074 B -> 200
    n=8,000  url 54,650 B -> 200
    n=10,000 url 68,650 B -> 414 Request-URI Too Large
  The binding constraint is URL LENGTH (~64 KB, a standard nginx header-buffer
  limit), not a documented per-request symbol ceiling. Because ticker lengths
  vary, a fixed symbol count is the wrong way to express it.

  `AlpacaAcquisition.DEFAULT_BATCH_SIZE = 100` is therefore roughly two orders of
  magnitude more conservative than necessary. Raising it is a real optimisation
  (it divides the request count, and the volume guard's request/wall-clock
  estimates with it) but is a design change, NOT part of this phase. Logged for
  follow-up rather than changed here.

  An earlier probe of mine was invalid — it repeated 20 tickers, so `symbols` had
  only 20 distinct values regardless of n, and `limit=1` capped returned rows.
  It proved nothing; re-run with a real distinct roster.
