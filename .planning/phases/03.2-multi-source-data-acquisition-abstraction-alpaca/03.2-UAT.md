### 1. Free-tier SIP access (open question O-1)

test: |
  Issue ONE historical SIP quotes request older than 15 minutes with a free (Basic)
  tier key pair:

  ```bash
  curl -i -H "APCA-API-KEY-ID: $APCA_API_KEY_ID" -H "APCA-API-SECRET-KEY: $APCA_API_SECRET_KEY" \
    'https://data.alpaca.markets/v2/stocks/quotes?symbols=AAPL&start=2024-01-02T14:30:00Z&end=2024-01-02T14:31:00Z&feed=sip&limit=1'
  ```
expected: |
  200 → Basic tier reaches historical SIP.
  403 → IEX is the only usable feed.
  Either answer is a result; there is no wrong outcome here.
why_human: |
  Alpaca's own documentation self-conflicts — three sources say Basic reaches historical
  SIP, one says IEX-only. No `feed` default was baked into code precisely because this is
  unresolved: `acquisition/alpaca.py:773` reads `feed` from kwargs defaulting to `None` and
  omits the key when unset (confirmed live — no request carried a `feed=` param), and
  `ingest_alpaca.py` registers no `--feed` flag.
resolves: RESEARCH Assumption A7, open question O-1
result: [pending]

### 2. Real Alpaca round-trip — SC-5's manual half

test: |
  With credentials exported, run one symbol over one trading day, three ways:

  ```bash
  uv run python ingest_alpaca.py --symbols AAPL --start-date 2024-01-02 --end-date 2024-01-02
  uv run python ingest_alpaca.py --symbols AAPL --start-date 2024-01-02 --end-date 2024-01-02 --frequency 1m
  uv run python ingest_alpaca.py --symbols AAPL --start-date 2024-01-02 --end-date 2024-01-02 \
    --frequency tick --data-type quotes --rows-per-symbol-day 1000000
  ```
expected: |
  Each run lands a parquet shard at the hive path the verifier already reproduced offline:
    1d          → data/downloads/us_equity/1d/nasdaq_data/alpaca/month=2024-01/part-*.pqt
    1m          → data/downloads/us_equity/1m/nasdaq_data/alpaca/date=2024-01-02/part-*.pqt
    tick/quotes → data/downloads/us_equity/tick/nasdaq_data/alpaca/data_type=quotes/date=2024-01-02/symbol=AAPL/part-*.pqt
  plus a watermark sidecar under `_watermarks/alpaca/`.

  **The vendor must accept `asof=-`.** A 4xx on every batch means the sentinel is wrong.
why_human: |
  No credentials on this machine, so the live transport cannot be exercised. Every
  offline-provable half of SC-5 was independently verified at the prepared-HTTP-request
  boundary — the field maps, endpoint map, session-date hive key and query-string encoding
  were all exercised against the real `_AlpacaMarketDataClient` with only
  `requests.Session.send` patched. Only the vendor's actual response is unobservable.

  `ASOF_NO_MAPPING = "-"` is an unverified sentinel, labelled as such in code. If it is
  wrong it fails LOUD — 4xx per batch, isolated to that batch, recorded in the failure
  manifest — rather than silently. That is the direction to be wrong in, but it is still
  unverified.
resolves: SC-5 live half; the `ASOF_NO_MAPPING` sentinel
result: [pending]
