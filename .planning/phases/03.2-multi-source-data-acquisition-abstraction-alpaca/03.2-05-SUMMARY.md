# Phase 03.2 Plan 05: The "queried, no data" third state Summary

**One additive `no_data` boolean on the watermark sidecar — omitted when false, computed once per completed batch, never per page — turning three storage facts into four distinguishable read-time states.**

## Performance

- **Duration:** 25 min
- **Started:** 2026-09-06T21:14:00Z
- **Completed:** 2026-09-06T21:38:32Z
- **Tasks:** 2 (both TDD)
- **Files modified:** 3

## Accomplishments

- **A fourth read-time state that costs one key.** `_write_watermark` gained
  `no_data: bool = False`; the key reaches disk only when true. Four states now
  read out of three storage facts: no sidecar and no manifest entry = never
  fetched; no sidecar plus a `_failures.json` entry = fetch failed; sidecar with
  the key absent = fetched and data landed; sidecar with the key = queried and
  the vendor returned nothing. `_read_coverage` returns the third key through the
  *unchanged* `_read_sidecar`, so a corrupt sidecar still has exactly one failure
  policy.
- **The marker can only be written about a batch the vendor finished answering.**
  `_attempt_batch` takes `set(batch_symbols) - outcome.symbols_with_data` once,
  behind two gates: `outcome.complete` and a clear global abort. A batch that
  raised never reaches the write loop at all. This is RESEARCH Pitfall 4 closed:
  Alpaca is symbol-major, so page 0 of a 100-symbol batch legitimately carries
  one symbol, and a per-page difference would have stamped the other 99 "no
  data", advanced their watermarks and skipped them forever.
- **A marked symbol is skipped, not re-asked — and is not a tombstone.** The
  classification rule stayed deliberately blind to the marker, so a marked symbol
  still covering the request is `covered` (zero vendor calls next run: the
  re-fetch storm across thousands of delisted tickers that D-04 exists to
  prevent), while a marked symbol whose coverage is narrower than a later,
  deeper request is still `widened` and re-fetched.
- **Every new gate was mutated against its own tests before being claimed.** Nine
  mutations run; one (`outcome.complete` removed) survived and exposed a real
  hole, which is now locked by an injected incomplete `BatchOutcome`.

## Decisions Made

- **`no_data` omitted when false, never written as `false`** (implements the
  encoding confirmed at 03.2-02 Task 1's `checkpoint:decision`). Absence is the
  default, so the ~4,600 sidecars already on the user's volume read back
  correctly as not-no-data — true because the old code only ever wrote a
  watermark after a successful fetch. Writing `false` would have put a positive
  claim in new files that older files cannot make, leaving those older files
  ambiguous between "had data" and "never said".
- **The classification rule stays blind to the marker.** No branch was added to
  `_coverage_status`/`_classify_coverage`; the absence of a special case *is* the
  design, and two tests (covered-and-skipped, widened-and-re-fetched) exist to
  keep someone from adding one later as a plausible-looking optimisation.
- **A refresh may clear a marker but never assert a new one.** Not in the plan
  text; see deviation 2.
- **The per-vendor 429 asymmetry was left untouched.** No `QUOTA_STATUS_CODES` or
  `QUOTA_MESSAGE_TOKEN` was hoisted to the base; classification stays behind
  `_classify_error`, and the comment explaining why the attribute deliberately
  does not exist at that level is unchanged.

**1. [Rule 3 - Blocking] `_read_coverage`'s exact-equality assertion in the D-02 gate suite**

- **Found during:** Task 1 (GREEN)
- **Issue:** The plan requires `_read_coverage` to gain a third key, but
  `tests/test_tiingo_acquisition.py::test_read_coverage_on_a_new_format_watermark_returns_both_components`

  test red, which would have broken D-02's per-commit gate at the very commit
  the plan mandates.
- **Fix:** Extended the expected dict with `"no_data": False` rather than
  loosening the comparison to a subset check — the point of that test is that
  `_read_coverage` returns the whole recorded coverage and nothing invented, and
  a subset check would have silently stopped proving it. A comment records why
  the `False` is the correct reading of a sidecar whose key is absent.
- **Files modified:** `tests/test_tiingo_acquisition.py` (7 lines, one assertion)
- **Verification:** `uv run pytest tests/test_tiingo_acquisition.py tests/test_tiingo_quota.py -q` → 48 passed
- **Committed in:** `abd666d`

**2. [Rule 2 - Missing Critical] A refresh must not newly assert absence**

- **Found during:** Task 2 (GREEN)
- **Issue:** The plan specifies the marker set as
  `set(batch_symbols) - outcome.symbols_with_data` with no `download`/`refresh`
  distinction. Applied literally on the refresh path this records a *false*
  claim: a refresh queries `[watermark, end_date]` while the sidecar it stamps
  records `[covered_start, end_date]`, a strictly wider window. A routine refresh
  that returns no new rows (market closed, symbol already current) would have
  stamped `no_data: true` onto a symbol with years of history — laundering "no
  new rows this week" into "nothing since 2020", and inflating the reported
  count with symbols the vendor has plenty of data for. That is precisely the
  T-03.2-23 shape (a partial answer recorded as a complete one) the plan exists
  to close, arriving through the other entry point.
- **Fix:** On the refresh path the marker is carried through rather than
  computed: it may be CLEARED (rows arriving anywhere in the window do prove the
  symbol has data in it) but never newly asserted. Exactly mirrors the
  `covered_start` carry-through two lines above it, which follows the same D-04
  discipline for the same reason.
- **Files modified:** `base/acquisition.py` (3 lines plus comment)
- **Verification:** `test_a_refresh_may_clear_a_no_data_marker_but_never_assert_a_new_one`;
  mutated in both directions (allow a new assertion / drop an existing marker),
  each caught.
- **Committed in:** `1542d55`

**3. [Rule 1 - Bug] `stamp_watermarks` would have dropped the marker**

- **Found during:** Task 1 (GREEN)
- **Issue:** `stamp_watermarks` rewrites a whole sidecar via `_write_watermark`.
  With the new default it would have silently dropped an existing marker,
  downgrading a confirmed absence to "fetched, data landed". Invisible: the file
  still parses and the start is now correctly recorded.
- **Fix:** Pass `no_data=coverage["no_data"]` through, with a docstring paragraph
  stating that stamping knows which window a file covers and nothing about
  whether the vendor had rows in it. The plan named this constraint
  ("`stamp_watermarks` … must not touch the marker") but listed no test for it;
  one was added (`test_stamping_a_legacy_sidecar_carries_its_no_data_marker_through`,
  the 8th Task-1 test) because the drop is otherwise silent.
- **Files modified:** `base/acquisition.py`, `tests/test_acquisition_batching.py`
- **Verification:** Mutation (drop the carry-through) → test red.
- **Committed in:** `abd666d`

**4. [Rule 1 - Bug] `_partition_by_coverage` would have read each sidecar twice**

- **Found during:** Task 1 (GREEN)
- **Issue:** Counting the marker alongside the status meant calling both
  `_coverage_status` (which reads) and `_read_coverage` (which reads again),
  falsifying that method's documented "One pass, so each sidecar is read exactly
  once" invariant and doubling I/O on a ~15.4k-symbol partition pass that runs at
  least twice per run.
- **Fix:** Split the classification RULE into `_classify_coverage(coverage,
  from_watermark)`, with `_coverage_status` reading and delegating.
  `_partition_by_coverage` now reads once and classifies from the dict. This is a
  split of read from rule, **not** a second read path — `_read_sidecar` is still
  the only place a sidecar is opened, and the acceptance criterion asserting
  exactly one `def _read_sidecar` passes.
- **Files modified:** `base/acquisition.py`
- **Verification:** `uv run pytest -q` → 305 passed; the `_read_sidecar` source
  assertion passes.
- **Committed in:** `abd666d`

**5. [Rule 2 - Missing Critical] The completion gate had no test and survived mutation**

- **Found during:** Task 2 (post-GREEN mutation pass)
- **Issue:** Removing `outcome.complete` from the marker gate left the entire
  suite green. `_fetch_batch` returns normally only after the vendor hands back a
  null page token, at which point it has already set `complete=True` — so the
  flag is always true where the gate reads it and no end-to-end test can move it.
  A gate no test can fail is a gate a future refactor deletes, and the first
  `_fetch_batch` that *can* return early (a page budget, the token-free
  degradation D-03 sketches) would then mark every symbol whose rows were on a
  page it never fetched. This is the same class as the three carry-over findings
  from Waves 2-4.
- **Fix:** Added `test_an_incomplete_batch_outcome_writes_zero_no_data_markers`,
  which injects a `BatchOutcome(complete=False)` at the `_fetch_batch` seam. This
  is the one place a seam substitution is the honest test: the property is
  `_attempt_batch`'s *contract with* `_fetch_batch`, not the page loop's
  behaviour.
- **Files modified:** `tests/test_acquisition_batching.py`
- **Verification:** Re-ran the same mutation → test red.
- **Committed in:** `1542d55`

## Issues Encountered

- **The scale-guard test was initially wrong, not the code.** Its first form ran
  both batch sizes against one `tmp_path` and with the default 8 workers. The
  shared `mock_alpaca_client.pages` queue is global, so concurrent batches popped
  each other's pages and every batch "saw" symbols it never requested — marking
  all 12. Fixed by isolating each size under its own `subdir` (otherwise run 2
  skips everything run 1 covered and reports zero for the wrong reason) and
  pinning `max_workers=1` so the queue is deterministic. The test now also
  asserts the queue was fully consumed, so it cannot pass by not fetching.
- **Five of the six Task-2 RED tests passed before the implementation**, because
  they are negative assertions (zero markers) that "no feature at all" trivially
  satisfies. The positive-direction test was the genuine RED driver; the
  negatives earned their keep in the mutation pass afterwards.
