# Phase 03.2 Plan 02: Batched Fetch Primitive and Vendor-Namespaced Hive Tier Summary

**`_fetch_page` replaces `_fetch_and_write` as the sole abstract fetch primitive, with a concrete paginating `_fetch_batch`, a per-batch `PageLedger` resume sidecar, a dependency-free `requests` Alpaca client, and a hive-aware `_scan_raw` that cannot silently merge two vendors — proved end to end on one Alpaca symbol over one month.**

## Accomplishments

- **The primitive is inverted.** `Acquisition.__abstractmethods__` is exactly `{"_fetch_page"}`; `_fetch_and_write` is gone with no transitional alias, retired in the same commit that landed its replacement (03.1 D-03 precedent). `_fetch_batch` is concrete on the base and is the only place pagination exists.
- **The whole vertical works on one symbol.** An Alpaca daily batch fetches through the batched primitive, writes a shard at `{raw}/alpaca/month=2024-01/part-{batch_key}-00000.pqt`, records a page ledger at `{watermark}/_pages/{batch_key}.pages.json` and a watermark sidecar, and reads back through the reworked `_scan_raw` with neither the `vendor` column nor the `month` hive key present.
- **Page-level resume is real.** A client failing on page 3 of 5 leaves pages 0–2 recorded; the second run's *first* request carries the token page 2 recorded, and exactly two further requests complete the batch.
- **Hive pruning is measured against a query plan**, 2 of 5 files versus 5 of 5 for a timestamp-only predicate, with the negative control inside the same test so the assertion cannot rot into a tautology.
- **No new dependency.** The Alpaca transport is ~40 lines of `requests`. `alpaca-py` was rejected on design grounds and no `uv add` was run.
- **D-02 held at every commit.** The Tiingo suites were run before each of the three code-touching commits, not once at the end.

## Decisions Made

- **D-19 recorded in `03.2-CONTEXT.md`** — all nine contracts confirmed `as-proposed`, with `date-key-for-daily`, `utc-day-key` and `watermarks-inside-vendor-dir` and their reasons recorded so the rejections are durable rather than re-litigated.
- **A completed page ledger is not a veto.** See Deviations #1. The ledger answers "where within this batch do I resume", never "should this batch run"; that second question is the per-symbol watermark layer's (D-05's two layers).
- **Credential env-var names are module-level constants.** See Deviations #2. A security control must not be reachable through an indirection whose entire purpose is to be replaced by a test double.
- **`vendor` is a market-only `DatasetConfig` field.** It names *whose* raw market files the directory holds, so a dataset with no such directory — an index-membership panel — has no vendor either. Putting it on the shared base would hand every non-market dataset a provenance field none of them can fill.
- **`ConcurrentTiingoAcquisition` was left in place**, its `_attempt` re-pointed at a one-symbol `_fetch_batch` so it inherits the ledger and the write ordering rather than carrying a second write path. It collapses in 03.2-03; no permanent alias was introduced.
- **The page ledger DOES get an `assert_consistent`**, against 03.2-RESEARCH.md Pattern 3's advice that it "should not grow one". The plan's Task 3 explicitly required it and specified its shape. Research's argument covers only the shard-write ordering (deterministic names make a re-fetch an overwrite); it does not cover the ledger being *ahead* of the disk, which is a genuine hole a resume would skip. Only that direction is checked.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A completed page ledger silently vetoed an explicitly requested re-fetch**

- **Found during:** Task 2 (running the D-02 gate)
- **Issue:** `_fetch_batch` returned early when `ledger.is_complete()`. That made `download()` with `kwargs={"resume": False}` issue **zero** vendor requests — `test_resume_false_re_fetches_symbols_already_at_the_watermark` failed with `0 == 5`. The within-batch resume mechanism was overriding a symbol-level policy the user had set explicitly, which is exactly the layer confusion D-05 separates.
- **Fix:** Added `PageLedger.reset()` (discards recorded pages, keeps batch identity) and called it instead of returning early. Reaching `_fetch_batch` at all means the caller's symbol-level policy already decided this batch should run. Re-fetching is safe precisely because shard filenames are deterministic, so a redo overwrites rather than duplicating.
- **Files modified:** `base/pageledger.py`, `base/acquisition.py`
- **Verification:** `uv run pytest tests/test_tiingo_acquisition.py tests/test_tiingo_quota.py -q` → 44 passed.
- **Committed in:** `d0f1345`

**2. [Rule 2 - Missing Critical] `_scrub` read its credential env-var names through a patch target**

- **Found during:** Task 2 (first run of the credential-safety tracer test)
- **Issue:** `AlpacaAcquisition._scrub` read `_AlpacaMarketDataClient.KEY_ENV` / `.SECRET_ENV`. `tests/conftest.py:mock_alpaca_client` replaces that class wholesale, so the call raised `AttributeError: type object 'FakeAlpacaClient' has no attribute 'KEY_ENV'`. The visible symptom was a crash, but the underlying defect is worse: any substituted client that *did* happen to define those names differently — or a future double that defines them as empty — would silently disable credential redaction rather than crash. A security control was reachable through an indirection whose entire purpose is to be swapped out.
- **Fix:** Moved `KEY_ENV` / `SECRET_ENV` to module-level constants in `acquisition/alpaca.py` and had `_scrub` read them from there. `_AlpacaMarketDataClient` re-exposes both as class attributes because they are part of its own published contract (and the plan's acceptance criteria assert them there), but the definition no longer lives on the patchable class.
- **Files modified:** `acquisition/alpaca.py`
- **Verification:** `tests/test_alpaca_acquisition.py` 7 passed, including the assertion that neither credential appears in `cfg.to_dict()` and that both are redacted from a message.
- **Committed in:** `d0f1345`

**3. [Rule 3 - Blocking] Two test files outside `files_modified` had to be updated for the plan's own acceptance criteria to hold**

## Issues Encountered

- **The pruning assertion is easy to write backwards, and nearly was.** polars abbreviates a long scan source list as `[first.pqt, ... 4 other sources]`, so `explain().count(".pqt")` returns **1** for an unpruned five-file scan and **2** for a pruned two-file one. The obvious implementation would have asserted the exact opposite of the intended property and passed. Caught by measuring real `.explain()` output in a scratch tree before writing the test; the resulting `_scan_source_count` helper parses both renderings and carries its own self-test.
- **The Tiingo raw layout changed, so four path assertions in `test_tiingo_acquisition.py` had to move** from `{raw}/{symbol}/data.pqt` to the hive tree. They now assert on the symbols readable back out of the tree rather than on a filename containing a content-derived hash, so the tests pin behaviour rather than pinning a hash.
