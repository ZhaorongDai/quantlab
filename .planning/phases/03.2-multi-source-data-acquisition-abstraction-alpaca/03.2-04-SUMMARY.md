# Phase 03.2 Plan 04: Pre-flight Acquisition Volume Guard Summary

**A zero-request `UniverseCatalog` estimator that prices a fetch in rows, GiB, requests and hours, and a three-ceiling refusal that names every crossed ceiling and a re-estimated narrowing that would fit — so `--frequency 1m --universe us_all` fails in milliseconds instead of after 50 hours and 333 GiB.**

## Accomplishments

- `estimate_acquisition_volume()` prices a fetch in four quantities before it starts, issuing zero vendor requests. It delegates the roster, the trading-day count and the measured 0.368 density to `estimate_dense_panel()`, so the two estimators cannot disagree about the window they both size — and it uses `observed_cells`, never `dense_cells`, because a dense count overstates a full-market daily backfill by ~2.7x.
- `assert_acquisition_volume_fits()` refuses over three **independent** ceilings — 20 GiB on disk, 50,000 requests, 4.0 wall-clock hours. Any one alone lets a real scenario through: a request-count check passes a tick fetch that fills the volume, a byte check passes a small, slow, many-request fetch that runs overnight.
- The refusal message names what is refused, the full arithmetic, **every** crossed ceiling with the constant to edit, a concrete narrowing **re-estimated** for the shorter window with its own request/GiB/hour figures, and `force=True` / `--force-volume` by name. When no window is short enough (the batch floor alone is over), it says so and points at the roster instead.
- The ROADMAP scope fence is now arithmetic, at the real thresholds: `us_all` minute 2016-2026 (595,973 requests / 333.03 GiB / 49.7 h) is REFUSED; S&P-500 minute for a year (4,911 requests / 2.74 GiB / 24.6 min) and `us_all` daily 2016-2026 (1,529 requests / 0.85 GiB / 7.6 min) are ADMITTED.
- `tick` without `rows_per_symbol_day` refuses rather than guessing — the available ~100k-trades-per-symbol-day figure is flagged unmeasured against Alpaca (RESEARCH A4), and encoding it as a default would make the guard confidently wrong in exactly the regime it exists for.
- The test harness builds a synthetic catalog at the **measured** scale (15,424 `us_all` symbols shaped to the measured 0.368 density), so every scenario reproduces a row of RESEARCH's Volume Arithmetic table offline, in milliseconds, with no network call. A toy fixture would have left every default threshold untested because nothing could reach one.

## Decisions Made

- **The ordering claim is structural, not procedural.** SC-6 requires the refusal to happen before the client is constructed. Rather than relying on call order (which a later refactor can silently invert), the guard lives in a module that imports no acquisition module and binds no `Acquisition` subclass — there is nothing here that *could* be constructed. That is asserted directly, alongside a socket tripwire and the removal of every vendor credential from the environment.
- **`observed_cells`, never `dense_cells`.** The measured 0.368 density is the whole reason a dense count would be wrong. A guard that overstates by 2.7x refuses fetches that would have been fine, which is how a guard gets deleted rather than obeyed.
- **The narrowing is a second real estimate.** `requests` carries a `ceil` and a batch floor, so dividing the original figures by the overshoot ratio would print a plausible-looking number that is not what the narrowed fetch actually costs. `_narrowing_that_fits` re-estimates (still zero requests) and halves further, bounded, until it fits — and reports honestly when no window is short enough because the per-batch floor alone is over.
- **`MAX_ACQUISITION_WALL_CLOCK_HOURS` stays a literal `4.0`, pinned to `round(50_000 / 200 / 60)`.** Kept as its own constant because it is the knob a user actually feels (nobody has an intuition for 50,000 requests; everybody has one for "four hours") and because it must stay independently raisable — on the paid tier the same request count takes ~5 minutes, so the two genuinely diverge. Pinning the rounding rather than the exact quotient means they cannot decouple silently.
- **Only the crossed ceilings' keywords are offered in the cure.** Listing all three every time tells a user to raise a ceiling they are nowhere near, which teaches the habit of raising everything.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] Degenerate knobs raised `ZeroDivisionError` instead of refusing**

- **Found during:** Task 1
- **Issue:** The plan's signature takes `batch_size`, `page_limit` and `rate_limit_per_min`, all of which arrive off a CLI flag or `config.kwargs`. `--batch-size 0` would have surfaced as `ZeroDivisionError` from inside a sizing method. A guard that crashes on a typo'd flag has failed at being a guard, and an unknown `frequency` would have raised a bare `KeyError`.
- **Fix:** Added `_resolve_volume_knobs`, which validates all four and returns the resolved rate limit, with a named `ValueError` per knob.
- **Files modified:** `acquisition/universe.py`, `tests/test_volume_guard.py`
- **Verification:** `test_degenerate_knobs_refuse_instead_of_dividing_by_zero` (an eighth test in Task 1, over the plan's seven)
- **Committed in:** `de91397` / `00f8d20`

**2. [Rule 1 - Bug] `str.capitalize()` corrupted the unit and the constant name in the refusal**

- **Found during:** Task 2
- **Issue:** The joined reasons string was rendered with `.capitalize()`, which lowercases everything after the first character — printing `23.07 gib > 20.00 gib` and `max_raw_bytes` where the message is supposed to name `GiB` and the `MAX_RAW_BYTES` constant a reader is meant to go and edit. Caught by the three-independent-ceilings test asserting on the constant name.
- **Fix:** Build the leading `"Over the "` explicitly and join the rest, with a comment naming the trap. Also replaced the ad-hoc constant→keyword string munging with the `ACQUISITION_CEILINGS` single declaration, so the constant named in the message and the keyword offered in the cure cannot drift from the value being checked.
- **Files modified:** `acquisition/universe.py`
- **Verification:** `test_each_of_the_three_ceilings_raises_independently`; sample refusals printed and read end to end
- **Committed in:** `16fd7ce`

**3. [Rule 1 - Bug] Only the first crossed ceiling was reported (found by mutation, not by the suite)**

- **Found during:** Task 2, post-GREEN mutation testing
- **Issue:** `_crossed_ceilings`' own docstring claimed "all crossings are reported, so a refusal names every reason rather than only the first". Truncating the returned list to its first entry (`[:1]`) left the **entire suite green** — the three isolating scenarios each cross exactly one ceiling by construction, and the only multi-crossing scenario was asserting on the arithmetic rather than on the ceiling list. This is the Wave-3 failure mode exactly: a mechanism proved in one place and not proved where it matters.
- **Fix:** `test_full_market_minute_backfill_is_refused_by_the_default_ceilings` now asserts all three ceiling names and all three constants appear in the message, with a comment recording that the mutation escaped and why the name is load-bearing.
- **Files modified:** `tests/test_volume_guard.py`
- **Verification:** re-ran the `[:1]` mutation — now fails; restored — 17 passed
- **Committed in:** `16fd7ce`

**4. [Rule 1 - Bug] Two assertions I wrote were false, not the code**
