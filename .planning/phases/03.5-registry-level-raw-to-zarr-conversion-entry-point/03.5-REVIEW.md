# Phase 03.5: Code Review Report

**Reviewed:** 2026-09-11
**Depth:** standard
**Files Reviewed:** 22
**Status:** issues_found

## Summary

The phase ships a genuinely clean design surface: `Capability.dataset_cls` as data-not-branch,
the estimate/assert split, `ConversionResult` in `base/`, and the reporter/cancel pair threaded
through the chunk loop. The 775-test suite passes. None of that helps with the three defects
below, all of which are reproducible on this checkout and all of which the suite is blind to for
the same structural reason: the tests drive `convert()` and `from_raw_data_chunked()` through
happy and cancel paths against a *real* `UniverseCatalog`-free fixture, and never drive the
three ingest shells' actual guard objects, the exception path, or the repo-root scripts.

Two of the three are user-facing on the *documented* usage line of a shell; one is silent data
loss on a path this phase itself created (cancel + rebuild).

No hardcoded credentials, API keys or absolute developer paths were found in any in-scope file
(`grep -nE "(api[_-]?key|secret|token|password)\s*[=:]\s*['\"][A-Za-z0-9]{8,}"` and
`grep -nE "/Users/|/home/[a-z]"` both empty across the 13 source files).

Known-context items 1, 2 and 4 were re-checked and are as logged; item 3 is confirmed false and
is reported below as WR-02 because it is now provable rather than merely unverified.

## Critical Issues

### CR-01: A cancelled `on_new_listing="rebuild"` permanently deletes the previous Zarr store

**File:** `quantlab/base/data.py:705` (the `break`) with `quantlab/base/data.py:870-872` (the
`else:` arm) and `quantlab/base/data.py:1255-1258` (`_discard_rebuild_asides`)

**Issue:** `_reconcile_new_listings` implements `rebuild` by *renaming the existing store and
ledger aside* (`.superseded.tmp`) rather than deleting them, precisely so a failure halfway
through a multi-hour re-densify has a way back — the comment at `data.py:864-866` says so.
That safety net is keyed on the `try/except/else` split: an exception restores the asides, a
completed loop discards them.

Plan 06 introduced a **third** exit from the loop — `break` on cancel at `data.py:705` — and it
lands in the `else:` (success) arm. So a cancelled rebuild discards the only surviving copy of
the pre-rebuild store. Verified on this checkout:

```
# 4-year store, 2 symbols, 4 year-windows; then a new listing "C" appears in raw
BEFORE: 8 timestamps, symbols ['A', 'B']
# rebuild, cancelled after ONE of four windows
RESULT: ConversionResult(..., windows_planned=4, windows_written=1, rows_written=2,
                         resumed=False, cancelled=True)
AFTER:  2 timestamps, symbols ['A', 'B', 'C']
ASIDE EXISTS: False
```

Six of the eight converted timestamps are gone and the `.superseded.tmp` backup was `rmtree`'d.
The degenerate case is worse — a token already cancelled before the first window:

```
RESULT: ConversionResult(..., windows_written=0, rows_written=0, cancelled=True)
STORE EXISTS: False | ASIDE EXISTS: False | LEDGER EXISTS: False
```

The complete store, its ledger, and the backup are **all** removed and nothing is written in
their place. `convert()` then returns a `ConversionResult` whose `zarr_path` names a directory
that no longer exists, and `print_conversion_result` prints `Zarr store written at: <that
path>` (see WR-02).

This also contradicts the loop's own cancel log line — *"Every recorded window stays
resumable"* (`data.py:687-691`) — which is true of the ledger and false of the data the rebuild
was standing on.

**Why it matters:** silent, unrecoverable data loss on a path the caller was told was safe.
Recovery depends entirely on the raw tier still holding everything the old store held, which is
exactly the assumption `rebuild` exists *because* the operator cannot make (symbols removed
from the roster have no raw rows in the current window).

**Fix:** a cancelled run is not a completed rebuild. Treat it like the exception arm:

```python
        else:
            if rebuild_asides is not None:
                if cancelled:
                    # A cancel is a halfway exit, not a landing: the rebuild has
                    # NOT re-densified every window, so the superseded copies are
                    # still the authoritative ones.
                    self._restore_rebuild_asides(rebuild_asides)
                else:
                    self._discard_rebuild_asides(rebuild_asides)
```

(If restoring is judged too aggressive because partial progress is resumable, the minimum
acceptable behaviour is to *keep* the asides — never `rmtree` them — and say so in the result.)
Add a test: complete a store, drift the roster, run `on_new_listing="rebuild"` with a token
cancelled after N windows, assert the pre-rebuild store is still reachable.

### CR-02: `--symbols` / `--limit` plus `--to-zarr` now aborts on every run for Tiingo and Alpaca

**File:** `quantlab/acquisition/universe.py:1918` (`self._validate_category(category)` in
`estimate_chunked_panel`), reached from `ingest_tiingo.py:241` and `ingest_alpaca.py:445`

**Issue:** D-07 switched `ingest_tiingo.py` and `ingest_alpaca.py` from `assert_dense_panel_fits`
to `assert_chunked_panel_fits`. The object those two shells call the guard on is *not* always a
`UniverseCatalog`: `volume_pricing` (`quantlab/utils/cli.py:696-706`) substitutes
`_explicit_symbol_catalog(len(symbols))` whenever `--symbols` is given or `--limit` truncates a
category, and reports the category as the sentinel `EXPLICIT_SYMBOLS_CATEGORY =
"(explicit --symbols list)"` (`cli.py:543`).

`_ExplicitSymbolCatalog` (`cli.py:587`) overrides **exactly one** method — `estimate_dense_panel`
— which is why the old `assert_dense_panel_fits` path worked: it never validates the category.
The new `estimate_chunked_panel` opens with `self._validate_category(category)`, which the
subclass does not override. Verified:

```
$ uv run python -c "... c = _explicit_symbol_catalog(3) ..."
--- old path (assert_dense_panel_fits) ---   OK
--- new path (assert_chunked_panel_fits) ---
ValueError : Unknown universe category '(explicit --symbols list)'; known categories are
['nasdaq100_constituent', 'nasdaq_all', 'sp500_constituent', 'us_all'].
```

Bypassing only `_validate_category` makes the rest of the method work
(`max_chunk_bytes = 72864`), confirming this is the sole blocker.

**Why it matters:** the failing invocation is the documented one. `ingest_tiingo.py:47` reads
`uv run python ingest_tiingo.py --symbols AAPL,MSFT --to-zarr`. That, and every `--limit N
--to-zarr` run of either shell, now dies with a nonsense "unknown universe category" message
*before a single byte is fetched*. SC-6's "all three shells share one conversion path" is
delivered in a shape where two of the three cannot reach it on their primary usage.

**Fix:** teach the explicit-symbol view to accept its own sentinel, beside the
`estimate_dense_panel` override it already carries:

```python
        class _ExplicitSymbolCatalog(UniverseCatalog):
            def _validate_category(self, category: str) -> None:
                # This view resolves no roster from the reference table, so
                # `EXPLICIT_SYMBOLS_CATEGORY` is the only token it can be asked
                # about and there is nothing to validate against.
                if category != EXPLICIT_SYMBOLS_CATEGORY:
                    super()._validate_category(category)
```

Add a test that calls `assert_chunked_panel_fits` on `_explicit_symbol_catalog(n)` with the
sentinel — the one assertion that would have caught this and that
`tests/test_volume_guard.py` does not make.

### CR-03: Reinstating `DatasetConfig.market` as a required field breaks `main.py` and `cal.py`

**File:** `quantlab/base/config.py:43`

**Issue:** D-02 restores `market: Market` with no default. `BaseDatasetConfig` is `kw_only`, so
there is no positional-shift hazard — but every construction site must now pass it. The phase
walked `441e630` backwards through `quantlab/config/__init__.py`, `tests/conftest.py` and the
test files, and missed the two repo-root scripts that commit also touched. Verified:

```
$ uv run python -c "import runpy; runpy.run_path('main.py',  run_name='__not_main__')"
TypeError DatasetConfig.__init__() missing 1 required keyword-only argument: 'market'
$ uv run python -c "import runpy; runpy.run_path('cal.py',   run_name='__not_main__')"
TypeError DatasetConfig.__init__() missing 1 required keyword-only argument: 'market'
```

`main.py:7` and `cal.py:22` both construct a `DatasetConfig` without `market`.

**Why it matters:** two tracked entry points (one of them the project's nominal `main.py`) are
dead on this commit, and the 775-test suite cannot see it because neither file is imported by
any test. A secondary instance of the same break is `quantlab/utils/module.py:49`
(`DatasetConfig(**config)`), which will `TypeError` on any `config.json` serialised while
`market` was absent; that set is believed empty per `get_cls_from_path`'s own evidence, so it is
noted rather than counted separately.

**Fix:** add `market='us_equity'` to both call sites (both point at
`data/data/us_equity/1d/us_all.zarr`, so the value is not a guess):

```python
ds_cfg = DatasetConfig(
    zarr_file_path='.../data/us_equity/1d/us_all.zarr',
    raw_data_dir_path='',
    catalog_path='',
    market='us_equity',
    frequency='1d',
)
```

Better still, add a smoke test that imports every top-level `*.py` entry point, so the next
required-field addition fails in CI rather than on a developer's next run.

## Warnings

### WR-01: The chunk loop emits `conversion_started` with no matching `conversion_finished` on the exception path, and never calls `reporter.close()`

**File:** `quantlab/base/data.py:662-678` (start event), `:830-848` (finish event), `:863-872`
(the `try/except/else` that the finish event sits *inside*)

**Issue:** the finish event is emitted at `data.py:830`, inside the `try:` block, after the
window loop. Any exception raised in the loop — the pinned-axis `ValueError` at `:737`, a disk
error inside `widen_and_append`, a `_raw_data_to_xr_window` failure — skips it and re-raises at
`:869`. The docstring directly above the emit claims the opposite: *"After the loop DRAINED,
whether it ran to the end or stopped on a cancel — a stopped conversion still finished the
call, and a reporter that only ever saw a finish event on the happy path would have no way to
release what it opened on the other."* Verified with a reporter that records kinds, against a
monkeypatched `_raw_data_to_xr_window` that raises:

```
EXC kinds: ['conversion_started']   closed: 0
```

Separately, `reporter.close()` is **never** called by this loop, on any path — happy included
(`closed: 0` on a successful two-window conversion). `ProgressReporter.close`'s own docstring is
"Release whatever `emit` acquired."

This is a straight divergence from the precedent one layer up:
`quantlab/base/acquisition.py:1681-1692` puts `run_finished` in a `finally:` *and* calls
`self._close_reporter()`, with a comment explaining exactly this hazard.

**Why it matters:** the console's reporter is the consumer this phase was built for. A bar or a
Textual widget opened on `conversion_started` is orphaned by any conversion that fails, which is
the case an operator most needs the UI to report honestly. `tests/test_registry_convert.py`
covers happy, cancel, and exploding-reporter, but never an exception *inside the loop*.

**Fix:** mirror the acquisition loop.

```python
            finally:
                self._emit_progress(
                    reporter,
                    ProgressEvent(kind="conversion_finished", ...),
                )
```

Move the emit into a `finally:` nested around the window loop (and decide deliberately whether
the loop should also `reporter.close()`; the acquisition side does, and consistency across the
two loops is what an out-of-repo consumer will assume).

### WR-02: `print_conversion_result` never renders `cancelled`, and headlines a cancelled run as a completed write

**File:** `quantlab/utils/cli.py:846-897`

**Issue:** this confirms known-context item 3 and upgrades it from unverified to false. The
renderer branches on `resumed` and `peak_window_bytes` and never reads `result.cancelled`.
Verified against a genuinely cancelled conversion:

```
ConversionResult(..., windows_planned=2, windows_written=0, rows_written=0, cancelled=True)
->
Zarr store written at: /.../out.zarr
  windows:           0 written, 0 skipped of 2 planned (year)
  symbols pinned:    2
  rows appended:     0
  chunk ledger:      /.../out.zarr.chunks.json
```

Nothing distinguishes that from a run whose planner simply found no work. The first line
asserts a write that did not happen — and after CR-01 the path it names may not exist at all.
The field's own docstring in `quantlab/base/data.py` argues that `cancelled=True` with
`windows_written=2 / windows_planned=4` is *"the honest description of a stopped run; without
this flag it would be indistinguishable"* — and the only renderer in the repo drops it.

**Why it matters:** all three shells call `print_conversion_result` (`ingest_tiingo.py:299`,
`ingest_alpaca.py:529`, `ingest_us_equity.py:572`) and then exit 0. A partial conversion reads
as a finished one in the terminal and in the exit code.

**Fix:** render it, and demote the headline when the run did not complete.

```python
    if result.cancelled:
        print_fn(
            f"Conversion CANCELLED at a window boundary; the store at "
            f"{result.zarr_path} holds {result.windows_written} of "
            f"{result.windows_planned} planned window(s). Re-run to resume."
        )
    else:
        print_fn(f"Zarr store written at: {result.zarr_path}")
```

Consider also having the shells exit non-zero on `result.cancelled`.

### WR-03: `TqdmProgressReporter` handles none of the four conversion event kinds

**File:** `quantlab/base/progress.py:190-236` (`emit` matches only `run_started`,
`batch_completed`, `quota_exhausted`, `run_finished`)

**Issue:** plan 06 added `conversion_started`, `window_written`, `window_skipped` and
`conversion_finished` to `EVENT_KINDS` (`progress.py:71-83`) and documented them at length on
`ProgressEvent`, but did not extend the repository's only rendering reporter. Passing
`TqdmProgressReporter()` into `convert()` or `from_raw_data_chunked()` therefore renders
absolutely nothing — every event falls through the `elif` chain. Worse in a mixed session: the
bar this reporter opened on `run_started` is not closed by `conversion_finished`, only by
`run_finished`, so a conversion following an acquisition on the same reporter leaves a stale bar
on the terminal.

**Why it matters:** the class's docstring calls it "the DEFAULT reporter", and a caller reading
`EVENT_KINDS` reasonably concludes both loops are renderable by the shipped reporter. It is a
silent no-op instead. This is not covered by any test — `tests/test_registry_convert.py` uses
only bespoke recording reporters.

**Fix:** either add a `conversion_started` / `window_*` / `conversion_finished` arm to
`TqdmProgressReporter.emit` (a window bar with `unit="window"`), or state explicitly in the
class docstring that it renders acquisition events only and that a conversion needs
`CallbackProgressReporter`. Silence with neither is the worst of the three.

### WR-04: Existing Tiingo/Alpaca Zarr stores become unconvertible after this change, with no migration note

**File:** `ingest_tiingo.py:290`, `ingest_alpaca.py:520` (the switch from
`from_raw_data().save()` to the chunked `convert()`)

**Issue:** before this phase both shells wrote with `from_raw_data().save()`, i.e.
`XrBackend.write(mode="w")` — a full overwrite, no chunk ledger. They now go through
`from_raw_data_chunked()`, whose `ChunkLedger.assert_consistent`
(`quantlab/base/chunking.py:340-346`) refuses outright:

> `ChunkLedger: a store exists at <path> but there is no chunk ledger at <path>.chunks.json, so
> there is no record of which windows it already holds. Appending blind would duplicate or skip
> windows with no way to tell afterwards. Delete the store to rebuild it, or restore the
> ledger.`

Every store either shell produced before this commit has no `.chunks.json` sidecar, so the first
post-upgrade `--to-zarr` run refuses. The second half of the change is just as consequential and
also unmentioned: these two doors lost their re-derive semantics. `--to-zarr` used to be
idempotent-by-overwrite; it is now append-only with an unconditional overlap refusal, which is a
deliberate property for `ingest_us_equity.py` and a **new** constraint for the other two.

Neither shell's module docstring, nor any of the six SUMMARY.md files, mentions either. (`grep
-n "no ledger\|existing store\|migration\|overwrite" *SUMMARY.md` returns nothing.)

**Why it matters:** the refusal message names a remedy ("delete the store"), so this is not
silent corruption — but an operator upgrading is told to delete a multi-hour artifact by an
error they were never warned about, and the loss of re-derive is a contract change on a public
entry point.

**Fix:** add a paragraph to both shells' module docstrings stating (a) a store written before
03.5 must be deleted once, and (b) `--to-zarr` no longer re-derives a range the store already
holds — use a fresh `zarr_file_path` or delete the store. If a smoother path is wanted, a
one-shot "adopt an unledgered store" flag is the follow-up, but the documentation is the
blocking half.

## Info

### IN-01: `MarketDataset._raw_data_to_xr_window`'s abstract stub shadows `BaseDataset`'s working default in the MRO

**File:** `quantlab/base/data.py:1359-1365`

**Issue:** the re-declaration at `MarketDataset` has an `...` body, so it sits *between* a
concrete subclass and `BaseDataset`'s real implementation. A subclass that writes
`return super()._raw_data_to_xr_window(start, end, symbols)` — the natural way to express "I
inherit the default" — silently gets `None` back instead of a `xr.Dataset`, and the failure
surfaces later as an attribute error on `None`. `SpotKlineDataset` sidesteps this by copying the
five-line body verbatim (`quantlab/dataset/spot.py:105-109`), which is correct but is now a body
that can drift from the base's.

**Fix:** make the abstract stub delegate rather than return `None`, so `super()` stays usable:

```python
    @abstractmethod
    def _raw_data_to_xr_window(self, start_date, end_date, symbols=None) -> xr.Dataset:
        # Abstract for the obligation (D-08), but with the shared base's working
        # body, so a subclass that genuinely wants the unbounded default can say
        # so with `super()` instead of copying five lines that then drift.
        return BaseDataset._raw_data_to_xr_window(self, start_date, end_date, symbols)
```

`SpotKlineDataset` then becomes a one-line `return super()._raw_data_to_xr_window(...)` and its
D-09 docstring keeps its whole point.

### IN-02: `convert()` returns a `ConversionResult` that disagrees with `dataset.last_chunk_result`

**File:** `quantlab/acquisition/registry.py:580-582`

**Issue:** `dataclasses.replace(result, predicted_peak_bytes=predicted_peak_bytes)` produces a
*new* object; the one still published on `dataset.last_chunk_result` keeps
`predicted_peak_bytes=None`. Two objects describe the same run and differ. Harmless today
because `convert()` drops the dataset, but the asymmetry is a trap for anything that later
reaches the dataset directly (e.g. an in-process caller that wants the dataset too).

**Fix:** assign the replaced object back before returning, or set `predicted_peak_bytes` by
passing it down into `from_raw_data_chunked()` so there is only ever one result object.

### IN-03: `ingest_us_equity.py` sizes its chunk guard on the full category, ignoring `--limit`

**File:** `ingest_us_equity.py:507-510`

**Issue:** it calls `catalog.assert_chunked_panel_fits(args.category, ...)` while the other two
shells call `pricing.assert_chunked_panel_fits(category, guard_start, guard_end, ...)`, where
`pricing`/`category` come from `volume_pricing` and already account for `--limit` and explicit
rosters. So `ingest_us_equity.py --limit 5 --to-zarr` sizes the conversion against the *entire*
`us_all` category (~15k symbols) rather than the 5 that will exist in the raw tier, and can be
refused for a conversion that would fit trivially.

Pre-existing (the same call shape is at `dbd6d0c:ingest_us_equity.py:513`), so it is not a
regression — but SC-6 now asserts the three shells share one conversion path and one guard, and
this is the one place they demonstrably do not. It is also the mirror image of CR-02: us_equity
uses the object that validates categories and gets the wrong roster; the other two use the
object that has the right roster and cannot validate the category.

**Fix:** route it through the same helper the other two use:

```python
        chunk_report = print_chunk_report(
            pricing.assert_chunked_panel_fits(
                category, guard_start, guard_end, granularity=args.chunk
            )
        )
```

This depends on CR-02 being fixed first, since `--limit` makes `pricing` the explicit-symbol
view.
