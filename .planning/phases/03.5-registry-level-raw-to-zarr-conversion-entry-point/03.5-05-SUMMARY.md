# Phase 03.5 Plan 05: The three US-equity shells become the entry point's callers Summary

**`ingest_us_equity.py`, `ingest_tiingo.py` and `ingest_alpaca.py` stopped being three implementations of a conversion and became three callers of one: each now sizes with `assert_chunked_panel_fits`, calls `registry.convert()`, and renders the `ConversionResult` it gets back — which made `--chunk` / `--on-new-listing` uniform as a consequence rather than as new surface, and forced two AST suites to learn that the densification now lives one frame down.**

## Accomplishments

### The entry point has real callers

`convert(SOURCE, ds_config, granularity=args.chunk, on_new_listing=args.on_new_listing, predicted_peak_bytes=chunk_report["max_chunk_bytes"])` is now the conversion in all three shells. No shell names `from_raw_data` or `from_raw_data_chunked` any more — asserted by AST, not by substring, because all three module docstrings still discuss those methods in prose.

That is the half of DATA-07 a signature cannot deliver. `03.5-01` built `convert()` and proved it against a synthetic store; this plan put it on the path a user actually runs, and the `ConversionResult` it returns is now printed by three programs rather than only asserted by one test.

### The prediction and the outcome ended up in the same place

Each shell binds its guard's own report to a local and forwards `max_chunk_bytes` as `predicted_peak_bytes`. `convert()` echoes it back untouched (03.5-01, D-11: the entry point runs no guard of its own), so `print_conversion_result` prints `peak window: 3.00 GiB (predicted 3.40 GiB)` — the number the guard promised beside the number the run actually hit, in the one place a user looks after a multi-hour job. Neither was reachable from the other before.

The renderer prints the predicted figure ONLY when there is an observed peak to put it beside: a fully-resumed run materialises no window, so it has no measurement, and `0.00 GiB` would claim one nobody took.

### The divergence disappeared rather than being papered over

`add_chunk_args(parser)` is one line in each of two shells, and it is the whole of SC-6's flag half. That is the point: the flags became shareable because the conversion became shared, so the edit is one line rather than a reimplementation of chunking in two more scripts.

### Alpaca's minute sizing crossed intact

`bars_per_day=pricing.BARS_PER_DAY_BY_FREQUENCY[args.frequency]` and `num_variables=len(RAW_COLUMNS_BY_DATA_TYPE["bars"]) - 3` were carried across to the chunked guard verbatim. `T-03.5-15` is the threat that this argument gets quietly dropped in the switch, and dropping it would not raise, would not warn, and would not have failed any test written before this phase — the call would keep working and keep reporting a number 390x too small. Two runnable checks now stand against that: an AST check that reads the keyword's EXPRESSION (not a grep for a name that could appear in a comment), and an end-to-end check that a 1000-symbol single-year window the guard *returns from* at the default *raises* at `bars_per_day=390`, with the finer-chunk remedy still in the message.

### Two AST suites kept their teeth, and a third one nearly did not

`tests/test_volume_guard.py::test_every_entry_point_that_densifies_guards_the_dense_panels_ram` detects a densification by AST. After delegation no shell names a densify method, so its counter would have reached 0 and its `assert densifying >= 2` would have gone red — which is the test doing exactly what its own message says it should ("if a door stopped densifying, say so here rather than letting this test silently cover nothing"). `_is_densify` now returns `True` for a bare `Name` call to `convert`, the two attribute arms stay beside it, and the threshold was not touched.

`estimate_chunked_panel` joined the guard-siblings tuple — the addition `03.5-02` was deliberately barred from making, because two plans half-owning one test file is what produces a task whose verify contradicts its own action. Everything else in that test is byte-identical, pinned by a runnable check.

## Findings reported, not acted on

The plan asked for these to be REPORTED rather than decided by this task.

### 1. The `symbols=None` argument's original rationale is dead, and a different one survives

`df7bfe9` deleted `BaseDataset._reset_symbols` outright. The config setter (`quantlab/base/data.py:239-263`) now assigns `name`, normalises `start_date`/`end_date`, and stops — it touches no symbol axis, reads no store and raises nothing. **Construction no longer densifies for ANY config**, so "keeps the construction from densifying" is no longer what `symbols=None` buys, in any of the three shells or in `tests/test_ingest_shells.py`'s assertion.

A surviving reason WAS found, and the comments now state it: the conversion resolves its symbol axis from the RAW DATA, through `_raw_axes_in_range()` inside the chunked loop, pinned once over the whole range before any window is materialised. A roster named in the dataset config would be a second, competing answer to the same question — and the two genuinely differ, because `mode="in_range"` resolves membership from the universe table while the raw tree holds only what actually downloaded. The probe, the argument and the assertion are all unchanged; **only the justification was rewritten.** If the developer disagrees that this is reason enough, removing the argument is their call, not this plan's.

### 2. `quantlab/base/data.py` still documents the deleted mechanism, and one of its stated invariants may no longer hold

Not fixed — that file belongs to the concurrently-running plan 04, and this plan is scoped out of it.

`BaseDataset.__init__` (around `quantlab/base/data.py:166-173`) carries a comment block whose whole argument is the deleted method:

> "Ordering is load-bearing … Here the config property setter below DOES reach the storage backend -- through `_reset_symbols()` -> `read()` -- so the backend must already exist by the time the setter fires. Do not 'harmonize' the two hierarchies: reversing these two lines raises `AttributeError` on every dataset construction."

The setter reaches no backend any more. So the comment is false in its premise, and its conclusion ("reversing these two lines raises `AttributeError`") is a claim about the CURRENT code that is worth re-testing before anyone relies on it — if it no longer holds, `tests/test_dataset_hierarchy.py`'s source-introspection of that ordering is pinning a rule whose reason has gone. `03.5-01-SUMMARY.md` already reported the neighbouring stale `#:` block above `__init__`; this is a second, sharper instance in the same file.

### 3. `tests/test_ingest_conversion_gate.py::test_refusal_precedes_every_symbol_bearing_dataset_construction` now covers nothing

Its loop finds no bare `StockDataset(...)` construction in any shell (they hold only the `replace(..., symbols=None)` probe) and falls through on every iteration. Kept deliberately as a regression guard, and its docstring now says so out loud. Logged to `.planning/WINDOWS.md` as `unrun-verify` so it is visible at ship time rather than passing quietly forever.
