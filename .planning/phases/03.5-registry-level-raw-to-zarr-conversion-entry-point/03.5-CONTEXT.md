# Phase 03.5: Registry-level raw→Zarr Conversion Entry Point - Context

**Gathered:** 2026-09-11
**Status:** Ready for planning

<domain>
## Phase Boundary

A caller that is not one of quantlab's own scripts — the out-of-repo `quantlab-console` first,
but the contract is not written for it — converts an acquired raw parquet tier into the Zarr tier
through the registry, without naming a vendor class, a `Dataset` subclass, or an `ingest_*.py`
script at the call site, and can ask what peak RAM that conversion predicts BEFORE anything is
allocated.

The conversion call is SEPARATE from `registry.run()`, never a flag on it (03.4 D-14).
`registry.run()` stays acquisition-only.

**OUT of this phase:** the `quantlab-console` repository itself; tick→Zarr conversion (03.3);
a registry-level incremental `update()`; crypto spot joining the entry point.

</domain>

<decisions>
## Implementation Decisions

### Entry point signature and addressing

- **D-01:** `dataset_cls: type[MarketDataset] | None` is a field on **`Capability`**, NOT on
  `SourceDescriptor`. This follows the rule `Capability`'s own docstring already states — *"Per-capability
  data goes HERE, never on `SourceDescriptor`. … A field only some rows can populate is a signal to move
  the field down, not to widen the container."* `dataset_cls` is exactly such a field: Alpaca's `1d`/`1m`
  capabilities map to `StockDataset`, while its `tick` capabilities (`quotes`/`trades`) have no Dataset
  subclass that can express an irregular event axis until Phase 03.3.

  Two consequences the planner gets for free:
  - **SC-7 becomes data, not a branch.** The tick capability rows carry `dataset_cls=None`, so the
    refusal IS the absence of a conversion target. No vendor literal, no `if frequency == "tick"`.
    When 03.3 lands a tick Dataset, the change is filling two fields.
  - **The vendor/market mismatch dissolves.** `SourceDescriptor` is keyed by vendor (03.4 D-01) while
    Dataset subclasses are keyed by market — `StockDataset` serves both Tiingo and Alpaca. `Capability`
    is already keyed by `(market, frequency, data_type)`, which is precisely the axis Dataset subclasses
    divide on. `StockDataset` appearing on three capability rows across two vendors is one correct answer
    to three different questions, not a duplicated decision — and it is a direct class reference (03.4
    D-03), so there is no copy that can drift.

  Accepted cost, recorded deliberately: `Capability` widens from "what the vendor serves" to "what the
  vendor serves and what materialises it". `SourceDescriptor` already reaches across the same seam
  (`config_factory` is a construction concern, not a "who am I" fact).

  **NOTE FOR PLAN-CHECKER — do not flag:** a second `market → Dataset` registry was considered and
  REJECTED because ROADMAP 03.4 explicitly forbids inventing a second registry style.
  — **Reversibility:** costly — once `quantlab-console` reads `dataset_cls` off capabilities,
  relocating the field changes enumeration call sites in a second repository.

- **D-02:** **`DatasetConfig.market` is reinstated.** It was dropped in commit `441e630`
  (`drop the unused market field from DatasetConfig and every call site`) as housekeeping, not as a
  design decision — nothing read it. This phase creates its first reader: without it the capability
  lookup key is only `(frequency, data_type)`, which resolves ambiguously the day one vendor serves
  two markets at the same frequency. Restoring it makes the lookup key exactly `Capability`'s own key.

  Mechanical scope: walk `441e630`'s diff backwards — `quantlab/config/__init__.py` factories plus the
  `market=` lines in `tests/conftest.py` and the test files that commit touched.

- **D-03:** The entry point is a **module-level `convert()` in `quantlab/acquisition/registry.py`**,
  inserted AFTER `run()` (`registry.py:302`) and BEFORE the bottom vendor-import block. That is the
  only position both adjacent to `run()` — which is what makes 03.4 D-14's "two calls, never a flag"
  visible while reading — and compatible with 03.4 D-07's imports-must-be-last constraint.

  **Verified, no new dependency direction:** `quantlab/acquisition/inspector.py:71` already does
  `from quantlab.dataset.stock import StockDataset` and subclasses it at `:75`, while
  `quantlab/dataset/stock.py` imports nothing from `quantlab.acquisition`. So descriptors referencing
  Dataset classes introduces no cycle and no new edge.

  Shape (parameter names and defaults are the planner's to finalise; `granularity` and `on_new_listing`
  mirror `from_raw_data_chunked()`'s):
  ```
  convert(descriptor, dataset_config, *, granularity="year", on_new_listing="refuse",
          reporter=None, cancel=None) -> ConversionResult
  ```

- **D-04:** `convert()` returns a **`ConversionResult` dataclass defined in `quantlab/base/data.py`**,
  not in `registry.py`. This follows the direction `AcquisitionResult` already argues at
  `quantlab/base/acquisition.py:113-118`: the base layer must not import the acquisition package, so a
  result type living beside the registry would have to be imported backwards or duplicated.

  It carries at least: windows written / skipped, the pinned symbol count, the predicted peak, the Zarr
  path, the ledger path, and whether the run resumed or was cancelled — so an in-process caller renders
  the outcome without reading disk. Exact field set is the planner's.

  The entry point also **normalises a real asymmetry** that is half its reason to exist:
  `from_raw_data()` returns `Self` and leaves writing to a separate `.save()`, while
  `from_raw_data_chunked()` writes inside its loop via `widen_and_append()` + `ledger.record()`.
  `convert()` writes, period.

- **D-05:** `convert()` carries **`reporter` and `cancel`**, keyword-only with `None` defaults, word
  for word symmetric with the adjacent `run()`. 03.4 D-17's argument — cancellation cannot be added by
  the console from outside because the loop lives in quantlab — applies identically to the chunk loop.
  `cancel` is checked at window boundaries; `ChunkLedger` already supplies the
  completed-work-stays-resumable precondition that acquisition had to retrofit via atomic sidecars.

### Conversion mode — CONTRACT CHANGE

- **D-06:** **There is no `mode` parameter. Not a defaulted one — an absent one. `convert()` does
  chunked conversion and only chunked conversion.**

  **This supersedes ROADMAP Success Criteria 2 (second half) and 3 entirely.** SC-2's first half — that
  conversion is a SEPARATE call and never a flag on `run()` — still stands and still matters. What
  loses its object is "the three modes carry three differently-sized RAM guards": there is one mode and
  one guard.

  Why the roadmap's "three" did not survive contact: it was **stale arithmetic**. 03.4 D-14 counted
  three *scripts* (tiingo unconditional whole-window, alpaca per-frequency, us_equity opt-in chunked),
  and `G-03.4-1b`'s unification of `--to-zarr` already collapsed the first two onto one whole-window
  path. The repo's own vocabulary had already settled at **two**, not three:
  `quantlab/utils/cli.py:92` reads `ConversionMode = Literal["whole-window", "chunked"]`. The developer
  then removed the second.

  **ACTION REQUIRED OUTSIDE THIS DOCUMENT:** ROADMAP 03.5's SC-2 and SC-3 must be **rewritten**, not
  left standing in contradiction — the same handling 03.4 D-12 prescribed for the superseded boundary
  contract.
  — **Reversibility:** costly — reintroducing a mode parameter after `quantlab-console` calls
  `convert()` changes a published signature in a second repository, and the whole-window guard call
  would have to be restored in three shells.

- **D-07:** Consequences of D-06 that the planner must carry out rather than rediscover:
  - `ConversionMode` (`utils/cli.py:92`), the two-arm `_TO_ZARR_HELP` dict (`:94-106`), and
    `add_to_zarr_arg`'s `mode` parameter (`:195`) all **collapse**. `--to-zarr` becomes one uniform
    boolean flag with one help text.
  - **SUPERSEDED within this discussion:** an earlier answer moved `ConversionMode` to
    `quantlab/enums/data.py` beside `Market`/`Frequency`/`Vendor`, with a `CONVERSION_MODES` tuple
    per the `ROSTER_MODES` precedent. That decision is moot — the type ceases to exist. **Do not
    implement it.**
  - ROADMAP SC-6's "the `--chunk` / `--on-new-listing` divergence disappears" is no longer a design
    choice but an automatic consequence: all three US-equity shells go through the one chunked path, so
    both flags appear on all three.
  - `ingest_tiingo.py:210` and `ingest_alpaca.py:384` currently call the whole-window
    `assert_dense_panel_fits`; they switch to `assert_chunked_panel_fits`.

- **D-08:** **`_raw_data_to_xr_window` becomes an abstract method declared on `MarketDataset`** — NOT
  on `BaseDataset`, which keeps its concrete default at `base/data.py:429` for non-market datasets such
  as the constituent panels.

  Driver: the developer's requirement that chunked-only must make onboarding a NEW data source easy.
  That seam is already the single entrance ticket to chunked conversion, but its ABSENCE today is only
  a `logger.warning` (`base/data.py:578-586`) followed by silent degradation to whole-range densify +
  slice. For onboarding, a warning is the worst possible shape: the newcomer sees their source *work*,
  and discovers the missing method months later as an OOM at production roster size.

  **Two pinned assertions must be updated deliberately** — this is the test doing its job, not an
  obstacle:
  - `tests/test_dataset_hierarchy.py:135` — `BaseDataset.__abstractmethods__ == frozenset({"_raw_data_to_xr"})`
    forbids putting the abstract on `BaseDataset`.
  - `tests/test_dataset_hierarchy.py:136-138` — an exact `==` on
    `set(MarketDataset.__abstractmethods__) - set(BaseDataset.__abstractmethods__) == {"_to_kunquant", "_to_nautilus"}`
    becomes a three-element set. Update the docstring above it too.

- **D-09:** `SpotKlineDataset` gains an **explicit `_raw_data_to_xr_window` whose body is today's
  inherited one** (whole-range densify, `.sel()` slice, `.reindex()`), with a docstring stating plainly
  that it is a known non-memory-bounded implementation and that the binance date pushdown is pending.
  Behaviour is unchanged; `ingest_binance_spot.py:111` is untouched.

  **VERIFIED FACT that forced this decision:** `StockDataset` DOES override the seam
  (`quantlab/dataset/stock.py:477`), so chunked gives US equity a genuine memory win.
  `SpotKlineDataset` does NOT — under chunked-only it would densify the whole range once per window:
  identical peak RAM, plus a ledger sidecar, plus N redundant densifications. Chunked is therefore
  **not** a free superset of whole-window for crypto spot.

  Crypto spot stays OUT of the entry point, and that costs nothing: **binance is not a registered
  source at all** — `registry.py`'s bottom imports only `alpaca` and `tiingo`, and no binance
  descriptor exists. `ingest_binance_spot.py` cannot reach `convert()` regardless.

  **Scope honesty for CONTEXT.md readers:** ROADMAP SC-6 says "all three ingest shells", but
  `ingest_binance_spot.py:111` is a **fourth** converting shell the roadmap never names. "One
  conversion entry point" is therefore INCOMPLETE this phase, by decision. Say so; do not paper over it.

### Estimate vs guard

- **D-10:** Split "ask" from "refuse" by **copying the pair that already exists one screen up in the
  same class**: a new `estimate_chunked_panel(...)` that NEVER raises, mirroring
  `estimate_dense_panel` (`quantlab/acquisition/universe.py:1743`); and `assert_chunked_panel_fits`
  keeping its current signature and becoming a thin wrapper that calls the estimator and then raises,
  mirroring `assert_dense_panel_fits` (`:1785`). One copy of the arithmetic; existing callers and
  tests unchanged.

  **Implementation note the planner must not miss:** today's `assert_chunked_panel_fits` raises
  INSIDE the per-chunk loop (`universe.py:1907`), so it never builds the full chunk list when one
  window overflows. The estimator must complete the loop and mark every over-budget chunk together
  with its remedy, or SC-4's "ask without starting" cannot be answered for the case that matters.

  SC-5 is preserved rather than built: the existing refusal message already names the fitting remedy
  (`Pass a finer --chunk (year -> quarter -> month)`).

  Note SC-4's "ask which guard a given (mode, roster, window) selects" also loses half its object
  under D-06 — with one mode there is one guard. SC-4 reduces to "what peak does it predict".

  **AMENDED 2026-09-11 — "keeping its current signature" above is now FALSE, deliberately.** D-10 as
  written has two halves in tension. One orders the new estimator to MIRROR `estimate_dense_panel`;
  the other says `assert_chunked_panel_fits` keeps its current signature. But `estimate_dense_panel`
  **already carries `bars_per_day: int = 1`** (`quantlab/acquisition/universe.py:1674`) — the
  parameter that makes a `1m` window size 390x the same `1d` window instead of being silently sized
  as daily. Mirroring it and freezing the signature cannot both be done. The developer resolved the
  tension **in favour of the mirroring half**:

  - `estimate_chunked_panel` takes a **keyword-only `bars_per_day: int = 1`**, forwards it to its
    whole-range advisory call, and multiplies each chunk's timestamp axis by it.
  - `assert_chunked_panel_fits` gains the same keyword-only `bars_per_day: int = 1` and forwards it.
  - `ingest_alpaca.py` passes `BARS_PER_DAY_BY_FREQUENCY[args.frequency]`, exactly as its
    whole-window call does today (`ingest_alpaca.py:419`).

  **The identity default is what preserves D-10's "existing callers and tests unchanged" reason.**
  That clause is qualified in D-10's own text by its reason, and a keyword-only parameter whose
  default `1` is the arithmetic identity satisfies that reason exactly: every existing call site and
  every assertion in `tests/test_volume_guard.py` computes byte-identical numbers to today's.

  Why this could not be left alone: D-07 moves `ingest_alpaca.py` off `assert_dense_panel_fits` —
  and the guard it leaves behind is the one that takes `bars_per_day`. Without this amendment, D-07
  would silently downgrade alpaca's minute sizing by 390x, which is the exact CR-03 failure that
  guard exists to refuse (`T-03.5-15`). Compensating by inflating `num_variables` or
  `bytes_per_value` was considered and **REJECTED**: it would make the refusal print a false
  decomposition and break SC-5's "the refusal names the fitting remedy honestly".
  — **Reversibility:** costly — `quantlab-console` calls these methods (its `CVT-02`), so narrowing
  the signature back later changes a published signature in a second repository; and removing the
  parameter would silently restore the 390x understatement rather than fail loudly.

- **D-11:** **`convert()` does NOT run the guard itself — it trusts the caller.** The shells and the
  console call `assert_chunked_panel_fits` before calling `convert()`, exactly as
  `ingest_us_equity.py:513` already does. This reads the ROADMAP's own wording literally: the RAM guard
  is *answerable* before the run (SC-4), not *enforced* by the run.

  **RISK, developer-accepted and recorded plainly:** the entry point is not self-protecting. A new
  integrator who forgets to ask goes straight to OOM, and the guarantee lives at every call site rather
  than at the one place that allocates. Revisit if that failure is observed.

- **D-12:** `estimate_chunked_panel` returns a **dict**, copying the existing shape
  (`{"granularity", "advisory", "chunks", "max_chunk", "max_chunk_bytes"}` plus the per-chunk verdict
  fields D-10 adds). Having chosen to copy the estimate/assert pair, copying its return shape is the
  consistent move — `estimate_dense_panel` and `assert_chunked_panel_fits` both return dicts and
  existing callers index them.

  Deliberately different from D-04's `ConversionResult`, which IS a dataclass: different layers. The
  estimator is a `UniverseCatalog` method where dicts are the established shape; `ConversionResult` is
  the entry point's return type in `base/`. Accepted cost: the console receives an untyped dict.

- **D-13:** `_print_chunk_report` (`ingest_us_equity.py:160`) is **hoisted to
  `quantlab/utils/cli.py` as `print_chunk_report`**, beside `print_volume_estimate`
  (`utils/cli.py:735`), and shared by all three US-equity shells. This is the mechanism that makes
  SC-4's "the estimate is a value the caller can render, not a line this layer prints" true:
  `quantlab/acquisition/` and `quantlab/base/` produce report objects only, every print lives in
  `utils/cli.py`, and the console renders the same object its own way.

  fragments and the established home for rendering.
- `StockDataset._raw_data_to_xr_window` (`dataset/stock.py:477`) — the working reference
  implementation any new dataset author copies the shape of.

### Established Patterns
- Guards are a class constant plus a check method (`MAX_DENSE_PANEL_BYTES` +
  `assert_chunked_panel_fits`; `MAX_WIDEN_BYTES` + its router).
- An estimator returns a dict the caller can print without recomputing; the asserting sibling calls it
  and raises.
- Keyword-only, no-default arguments where a wrong choice would be silent (`resolve_symbols(mode=...)`,
  `cli.py:397`) — double-guarded by a runtime membership check with a message explaining why there is
  no default.
- Result types live in `quantlab/base/`, never beside the registry, so the base layer never imports
  the acquisition package.
- Empty `__init__.py`, full dotted imports, no re-exports (with `quantlab/config/__init__.py` as the
  pre-existing exception).

### Integration Points
- `registry.py` gains one function and `Capability` gains one field; `tiingo.py`/`alpaca.py` gain one
  line each.
- The three US-equity shells delegate conversion instead of performing it; `ingest_binance_spot.py`
  does not change.
- `quantlab-console` (separate repo) calls `convert()` in-process for writes, and
  `estimate_chunked_panel()` for its CVT-02 "show the guard and the predicted peak" requirement.
- `MarketDataset` gains an abstract method; `SpotKlineDataset` gains a concrete implementation of it.

<specifics>
## Specific Ideas

- The developer's framing that drove D-06 and D-08: **"chunked-only 要方便接入新的数据"** — collapsing
  to one conversion mode is only worth it if joining that one mode is easy for a new data source. That
  is why the seam became abstract rather than merely warned about: the contract for joining must be
  impossible to satisfy by accident.
- **"mode 的选择不能自动吗"** — the developer pushed back on requiring an explicit mode, citing (in
  effect) the precedent of `BaseDataset.update()`, whose docstring argues a strategy that is a FACT
  should be read rather than asked for. The resolution went further than automatic selection: with one
  mode there is nothing to select.
- The estimator/guard split was accepted specifically because the in-repo pair already exists — the
  developer chose "照搬现有的 estimate/assert 对" over inventing a `raise_on_overflow` flag.

</specifics>

## Deferred Ideas

- **A genuinely memory-bounded `SpotKlineDataset._raw_data_to_xr_window`** — the binance raw tier is
  monthly CSV and `quantlab/utils/file.py:file_date_filter` already has the date pushdown, so the

  point, and before a binance descriptor would be worth registering. Not this phase (D-09).
