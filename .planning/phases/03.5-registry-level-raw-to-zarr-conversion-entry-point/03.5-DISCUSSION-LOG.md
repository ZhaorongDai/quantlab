## Entry point signature & addressing

### Q1 — How does the conversion entry point address the Dataset subclass?

| Option | Description | Selected |
|--------|-------------|----------|
| `Capability.dataset_cls` | Per-capability field; tick rows carry `None` so SC-7 is data, not a branch | ✓ (after clarification) |
| `SourceDescriptor.dataset_cls` | Top-level, one per vendor; forces one answer across Alpaca's 1d/1m/tick | |
| DatasetConfig-only signature | `convert(dataset_config, *, mode)`, reverse-lookup by `vendor` | |
| Second `market → Dataset` registry | Rejected up front: ROADMAP 03.4 forbids a second registry style | |

**User's first response:** asked for a recommendation rather than choosing. Claude recommended
`Capability.dataset_cls`, citing `Capability`'s own docstring rule ("a field only some rows can
populate is a signal to move the field down"), and flagged one limitation: `DatasetConfig.market`
had been dropped in `441e630`, leaving the lookup key as only `(frequency, data_type)`.

**User's counter:** "把 market 补回去" — reinstate the field, which removes that limitation entirely.
Verified in-session that `441e630`'s commit message calls it `the unused market field`, i.e. it was
housekeeping, not a design decision.

**User's choice after re-asking:** `Capability.dataset_cls` **plus** reinstating `DatasetConfig.market`.

### Q2 — What does `convert()` return?

| Option | Description | Selected |
|--------|-------------|----------|
| `ConversionResult` dataclass | Defined in `base/data.py` per `AcquisitionResult`'s stated direction | ✓ |
| Return the `Dataset` instance | Matches `from_raw_data() -> Self` chaining; no home for windows-skipped/peak | |
| Return `None` | Side-effect only; asymmetric with `run()` | |

**Notes:** Claude surfaced that `from_raw_data()` and `from_raw_data_chunked()` have asymmetric write
semantics (the former needs a separate `.save()`), and that normalising this is half the entry point's
reason to exist.

### Q3 — Which module does `convert()` live in?

**User interjected first:** "convert()和 run()分别在哪里" — asked for the concrete location of both.
Claude answered `run()` is at `quantlab/acquisition/registry.py:302` (a module-level function, not a
`DataSourceRegistry` method), gave the file's full layout table, and verified no import cycle
(`inspector.py:71` already imports `quantlab.dataset.stock`).

| Option | Description | Selected |
|--------|-------------|----------|
| `registry.py`, after `run()` | The ROADMAP's literal "beside `run()`"; before the bottom vendor imports | ✓ |
| New `quantlab/acquisition/conversion.py` | Same package, separate file; loses adjacency | |
| Under `quantlab/dataset/` | Would invert the dependency direction | |

### Q4 — Does `convert()` carry `reporter` / `cancel`?

| Option | Description | Selected |
|--------|-------------|----------|
| Both, keyword-only | Symmetric with the adjacent `run()`; 03.4 D-17's argument applies to the chunk loop | ✓ |
| `reporter` only | No cancel channel; kill + ledger resume deemed enough | |
| Neither this phase | Minimal surface; both are backward-compatible to add later | |

**Notes:** Claude named the honest asymmetry — whole-window mode has no interior boundary, so cancel
could only be checked before starting. (Moot once mode was removed.)

## Mode vocabulary

### Q1 — What values does the mode enum take?

| Option | Description | Selected |
|--------|-------------|----------|
| Two, reuse `ConversionMode` | `utils/cli.py:92` already reads `Literal["whole-window", "chunked"]` | ✓ (later superseded) |
| Three, add `update` | Would make SC-2's "three guards" literally true and close a matched todo | |
| Three, third is `tick` | Duplicates the `dataset_cls=None` refusal; a never-selectable enum value | |

**Notes:** Claude opened by reporting that the ROADMAP's "three modes" is **stale arithmetic** — 03.4
D-14 counted three *scripts*, and `G-03.4-1b`'s unification of `--to-zarr` had already collapsed two of
them onto one whole-window path.

### Q2 — Where does the `ConversionMode` vocabulary live?

| Option | Description | Selected |
|--------|-------------|----------|
| Move to `enums/data.py` | Beside `Market`/`Frequency`/`Vendor`; add `CONVERSION_MODES` tuple | ✓ (later moot) |
| Leave in `cli.py` | Drags `argparse` + `BaseDataset` into the registry's import chain | |
| Redefine in `registry.py` | Two live copies of one vocabulary | |

**Notes:** Claude also settled SC-3's enforcement without asking — `resolve_symbols` (`cli.py:397`)
already demonstrates the double guard (keyword-only with no default, plus a runtime membership check).

### Q3 — How is the mode expressed on the shells?

**Not answered as posed.** Options offered were `--to-zarr` as a value flag, a separate `--mode`, or
per-shell hardcoding. **User's response:** "mode 的选择不能自动吗".

Claude answered at length: automatic selection has an in-repo precedent (`BaseDataset.update()` derives
its strategy from evidence rather than asking), but the two modes differ in *durable side effects* —
ledger sidecar, resumability, and append-dim overlap refusal vs `.save()` overwrite semantics — so
auto-picking would let a store's behaviour change silently with roster size. Claude recommended a middle
path: explicit mode, with the estimate returning a `recommended_mode` field.

### Q4 — Should the mode be chosen automatically?

| Option | Description | Selected |
|--------|-------------|----------|
| No auto, estimate recommends | Explicit mode; suggestion is a value, not a behaviour | |
| True auto, mode omittable | Best ergonomics; overrides SC-3 | |
| **Keep only chunked** | Mode parameter ceases to exist; SC-2/SC-3 lose their object | ✓ |

**Notes:** The cost — that SC-2 and SC-3 lose their object and the ROADMAP must be rewritten — was
stated in the option text before selection.

### Q5 — chunked-only's premise fails for `SpotKlineDataset`

Claude verified its own claim ("chunked can do everything whole-window can") and found it **false for
crypto spot**: `StockDataset` overrides `_raw_data_to_xr_window` (`dataset/stock.py:477`) but
`SpotKlineDataset` does not, so chunked would densify the whole range once per window — identical peak
RAM plus a ledger plus N redundant densifications. Also surfaced that `ingest_binance_spot.py:111` is a
**fourth** converting shell the ROADMAP's SC-6 never names.

| Option | Description | Selected |
|--------|-------------|----------|
| Implement the window seam for spot this phase | Makes the premise true; extra work unrelated to the registry | |
| **Spot stays out of the entry point** | Smallest change, no regression; "one entry point" stays incomplete | ✓ |
| Keep two modes after all | Reverts the previous answer | |

### Q6 (user-initiated) — "chunked-only 要方便接入新的数据"

User sent this requirement mid-turn. Claude connected it to the Q5 finding: the seam is already the
single entrance ticket to chunked, but its absence is only a `logger.warning` followed by silent
degradation — the worst shape for onboarding, since a newcomer sees their source *work* and discovers
the gap months later as an OOM.

| Option | Description | Selected |
|--------|-------------|----------|
| Refuse at `convert()`, naming what to implement | Runtime check; keeps the warning path intact | |
| **Make the seam an abstract method** | Earliest possible failure; can't join by accident | ✓ |
| Keep the warning | "Easy to onboard" becomes "looks easy to onboard" | |

### Q7 — Abstracting the seam breaks `SpotKlineDataset`

Claude surfaced the collision between Q5's and Q6's answers: an abstract seam makes
`SpotKlineDataset` non-instantiable, breaking `ingest_binance_spot.py:111`. Also identified the two
exactly-pinned assertions at `tests/test_dataset_hierarchy.py:135-138`, and the fact that **binance is
not a registered source at all**, so "spot stays out" is automatic and costless.

| Option | Description | Selected |
|--------|-------------|----------|
| **Write today's behaviour explicitly** | Spot implements the seam with the inherited body + honest docstring | ✓ |
| Do the real date pushdown this phase | Binance reaches chunked standard; extra scope | |
| Put the abstract somewhere narrower | Back to a runtime check, not the abstract method chosen | |

## Estimate vs guard split

### Q1 — How is "ask" split from "refuse"?

Claude opened with the blocking fact: `assert_chunked_panel_fits` raises *inside* the per-chunk loop, so
it can never serve as the question — and with the observation that `UniverseCatalog` already contains
the answer shape one screen up (`estimate_dense_panel` / `assert_dense_panel_fits`).

| Option | Description | Selected |
|--------|-------------|----------|
| **Copy the existing estimate/assert pair** | New non-raising estimator; assert becomes a thin wrapper | ✓ |
| Add a `raise_on_overflow` parameter | Smallest diff; a method named `assert` that might not assert | |
| Make it never raise | Cleanest conceptually; changes `ingest_us_equity.py:513`'s contract | |

### Q2 — Does `convert()` run the guard itself?

| Option | Description | Selected |
|--------|-------------|----------|
| Assert internally, unconditionally | Guard becomes unforgettable; double arithmetic when asked first | |
| **Trust the caller** | Zero duplication; matches SC-4's "answerable", not "enforced" | ✓ |
| Accept a pre-computed estimate | Caller could pass a stale or forged report | |

**Notes:** Claude recorded the accepted risk plainly — a new integrator who forgets to ask goes
straight to OOM — and noted the consequence that `ingest_tiingo.py:210` and `ingest_alpaca.py:384`
switch from the whole-window guard to the chunked one.

### Q3 — dict or dataclass?

| Option | Description | Selected |
|--------|-------------|----------|
| **dict, copy existing shape** | Consistent with both existing estimators in the same class | ✓ |
| dataclass, align with `ConversionResult` | Typed for the console; splits the class's own convention | |

### Stated, not asked — where rendering lives

`_print_chunk_report` (`ingest_us_equity.py:160`) hoists to `utils/cli.py` as `print_chunk_report`,
beside `print_volume_estimate` (`utils/cli.py:735`). The precedent was exact enough not to warrant a
question.
