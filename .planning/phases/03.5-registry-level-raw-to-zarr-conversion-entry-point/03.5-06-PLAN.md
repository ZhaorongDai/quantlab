<objective>
Give the conversion the two handles the acquisition already has.

03.4 D-17's argument — cancellation cannot be added by the console from outside, because the loop
lives in quantlab — applies identically to the chunk loop, and a chunked conversion of a
full-market panel is the longest-running operation this project has. D-05 therefore puts `reporter`
and `cancel` on `convert()`, word for word symmetric with the adjacent `run()`.

The chunk loop is the easier of the two cases: `ChunkLedger` already supplies the
completed-work-stays-resumable precondition that acquisition had to retrofit via atomic sidecars,
so cancelling at a window boundary is already safe by construction.

This plan also closes the last stale-docstring obligation the phase carries: `run()`'s docstring at
`quantlab/acquisition/registry.py:328-331` still describes three genuinely different conversion
modes with three differently-sized RAM guards. D-06 killed that sentence.

Purpose: DATA-07's "whether it resumed or was cancelled" half, and the out-of-repo console's
ability to render and stop a multi-hour conversion.

Output: `reporter` / `cancel` on both `convert()` and `from_raw_data_chunked()`, conversion event
kinds, and a de-staled `run()` docstring.
</objective>

## Planner notes carried forward

- **`quantlab/base/progress.py` is a LEAF by contract** — its module docstring says so, and
  `tests/test_acquisition_progress.py` asserts it structurally by walking the file's AST. It
  imports stdlib plus `tqdm` and nothing from quantlab, so `quantlab/base/data.py` importing it
  introduces no cycle. Do not add any quantlab import to `progress.py` while adding event kinds.
- **`EVENT_KINDS` is advisory, not enforced** — `ProgressEvent` is a frozen dataclass with no
  validation, deliberately, so an out-of-repo consumer's forward compatibility does not depend on
  quantlab shipping first. Adding kinds is therefore safe; the tuple is documentation plus
  something a reporter can match against instead of hard-coding literals. Verified at plan time:
  no test asserts `EVENT_KINDS`'s exact contents.
- **Why this plan is Wave 3 rather than Wave 1.** It edits `quantlab/base/data.py`, which Plan 01
  and Plan 04 both edit. The ordering is a file-conflict consequence, not a design dependency.
- **Scrubbing asymmetry, stated so it is not read as an oversight.** `Acquisition._emit` scrubs the
  reporter's exception text with the vendor's `CREDENTIAL_ENV_VARS` before logging it, because
  vendor error strings reach that layer and Tiingo's echo back a request URL carrying the API
  token. The conversion loop constructs no vendor client and sees no vendor response text, so its
  emit wrapper logs without scrubbing. Say this in the wrapper's docstring — an unexplained
  difference between two never-raises wrappers reads as a bug.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| out-of-repo reporter callback → quantlab's conversion loop | The console's `emit` runs INSIDE the chunk loop. Code this repository does not control executes between two appends. |
| out-of-repo cancel token → the chunk loop | A `threading.Event` the caller owns decides whether the loop continues. |
| `ProgressEvent` strings → the caller's UI | A new egress path for text out of quantlab. |
