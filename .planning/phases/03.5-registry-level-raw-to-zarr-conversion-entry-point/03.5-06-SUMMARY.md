# Phase 03.5 Plan 06: Conversion reporter and cancel handles Summary

**The raw→Zarr chunk loop now takes the same `reporter` / `cancel` pair the acquisition loop takes: a conversion emits per-window events to an in-process caller, stops at a window boundary on a `CancelToken`, and reports `cancelled` on its `ConversionResult` — and a reporter that throws cannot end it.**

## Accomplishments

- `BaseDataset.from_raw_data_chunked()` gained `reporter` and `cancel` as keyword-only parameters with `None` defaults, appended after the existing ones so `update()`'s `_AUTOMATIC` call and every other caller is untouched.
- The cancel token is read at the TOP of each window iteration and nowhere else. A cancel therefore lands between two appends, never between an append and its `ledger.record` — the T-03.5-19 tampering case where the store and the ledger would disagree about one window. The placement is pinned by a source-structure assertion, not by a comment.
- `BaseDataset._emit_progress` gives the chunk loop the never-raises delivery contract `Acquisition._emit` already holds one layer up (T-03.5-18). Its docstring states why it does **not** scrub: this loop constructs no vendor client and sees no vendor response text, so no credential-bearing string is in scope. An unexplained difference between two never-raises wrappers would read as a bug.
- Four conversion event kinds joined `EVENT_KINDS` with a docstring bullet each, grouped and explained beside the acquisition kinds. `cancelled` is deliberately shared between the two loops.
- `ConversionResult.cancelled` went from declared-and-always-`False` to live, and its comment now explains what the flag distinguishes (a stopped four-window run from a run that only had two windows of work).
- `registry.convert()` carries both handles, word-for-word symmetric with the adjacent `run()` — same names, kinds, defaults and annotations — and forwards them. The forwarding is proved behaviourally, because a signature-only assertion would pass against a `convert()` that accepted both and dropped them.
- `run()`'s stale paragraph was rewritten. D-06 falsified every clause of the three-genuinely-different-modes / differently-sized-RAM-guards reasoning; the surviving claim (acquisition-only, conversion is a separate call) stays, with the contract argument beneath it: folding conversion into `run()` would turn an acquisition-only contract into a conversion-sometimes one, and the two-call shape is what lets a caller acquire without converting and convert without acquiring.

## Decisions Made

- **`conversion_finished` is emitted on the cancelled path too.** A reporter that only ever saw a finish event on the happy path would have no way to release what it opened on the other. `cancelled` arrives immediately before it, so the two are still distinguishable.
- **The seven new Task-1 tests reach `from_raw_data_chunked` directly**, breaking this module's otherwise-strict "everything through `convert()`" rule. The contract under test is the chunk loop's; a test that only ever went through `convert()` could not tell "the loop never checks the token" from "`convert()` drops the argument". The forwarding gets its own test instead, and the exception is argued in a section comment above them.
- **`window_skipped` and `window_written` both report `completed = written + skipped`** — "windows resolved so far", so the number rises monotonically across a mixed resume rather than restarting per category.
