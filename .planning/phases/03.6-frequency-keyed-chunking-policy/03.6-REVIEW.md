## Warnings

### WR-01: `--chunk day` / `--chunk hour` 把 Zarr store 的 append 维 chunk 压成首窗口长度

**File:** `quantlab/base/chunking.py:70`（新 rung 来源）、`quantlab/dataset/backend.py:868-893`（`_append_encoding`）

**Issue:** `XrBackend._append_encoding` 用 `max(min(self.APPEND_DIM_CHUNK, size), 1)` 决定 append 维 chunk，而 `size` 取自**首次写入的那一块**。分块转换的首块就是第一个窗口，所以窗口越细、store 的 on-disk chunk 越小。本阶段新增的两级把这一点推到病态：`day` rung 在日频轴上首窗口只有 1 行 → chunk = 1。

实测复现（以 `tests/test_chunked_ingest.py` 的 `three_year_stock_config` 夹具跑 `granularity="day"` 与非分块路径各一次，读回 `encoding["chunks"]`）：

```
day-chunked  {'close': (1, 3), 'anomaly_flag': (1, 3), ... }   # 13 个变量全部 (1, 3)
unchunked    {'close': (9, 3), 'anomaly_flag': (9, 3), ... }
```

生产尺度下的后果：十年日频 `--chunk day` ≈ 2,500 个窗口 × 13 个变量 = 约 32,500 个单行 chunk 对象；`--chunk hour` 在 1m 轴上每块约 60 行、约 16,000 个窗口 → 约 208,000 个 chunk 对象。append 是不可逆的，修正只能删库重建。这一点在 `add_chunk_args` 的 `--chunk` 帮助文本、`example/chunking.md` 的新增小节、以及三个 shell 的 docstring 里都没有任何提示——帮助文本只说「more append round trips」。

注意：`year`/`month` 早已有同类弱化（日频 `year` 首窗 ≈252 行 → chunk 252 而非 512），所以成因不是本阶段引入的；但 `day` 把它从「略次优」变成「单行 chunk」，量级不同，而且正是本阶段交付的那两级触发它。

**Fix:** 让分块写入路径显式传入期望的 chunk，而不是让首块长度决定它。`_append_encoding` 已经接受 `data` 参数，最小改法是让 `from_raw_data_chunked` 的首次写入按**整段轴长**而不是窗口长度来选 chunk：

```python
# quantlab/dataset/backend.py
def _append_encoding(
    self, append_dim: str, data=None, *, append_dim_size: Optional[int] = None
) -> dict:
    ...
    size = int(panel.sizes[dim]) if append_dim_size is None else int(append_dim_size)
    chunks.append(max(min(self.APPEND_DIM_CHUNK, size), 1))
```

首窗口写入时由 `from_raw_data_chunked` 传 `append_dim_size=len(pinned_timestamps)`，使分块路径与整段路径落在同一格网上（这正是 `backend.py:420-431` 对 widen 路径已经论证过的「两种策略必须在 grid 上一致」）。若判定为纯性能问题而不修，至少要在 `--chunk` 帮助文本与 `example/chunking.md` 写明「窗口行数低于 512 时 store 的 chunk 会随之变小」。

**File:** `tests/test_chunked_ingest.py:1087-1090`
