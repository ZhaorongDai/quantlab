## Summary

Plan 03.6-07 把 `append_dim_size` 关键字接到了 widen 改写路径上的四个落盘点。
**惰性（inertness）与签名一致性两项都成立**，我逐条验证过：

- `_widen_whole_store` 与 `_widen_chunked` 的签名逐字符相同（`inspect.signature` 比对），
  router 按名字选分支不会产生潜伏 `TypeError`；
- 不传该关键字的调用方行为逐字节不变——`Factor.update()` → `widen_and_append` →
  `widen_symbol_axis` 走 `kwargs.get(...)` 得到 `None`，`_append_encoding` 回落到面板自身长度；
  `tests/test_factor_update.py` + `test_symbol_axis_widening.py` +
  `test_variable_axis_widening.py` + `test_dataset_update.py` 共 93 项全绿；
- `widen_and_append` 的 GET-not-POP 是对的：`append()` 把 `append_dim_size` 声明为
  keyword-only 形参，所以它被吃掉而不会漏进 `to_zarr(**kwargs)`；三个消费者都拿得到；
- 全量 `uv run pytest` 796 passed。

但**这次改动引入了一处真实回归**，而且它恰好违反本阶段自己写在文档里的不变量。
`from_raw_data_chunked` 把 `len(timestamps)`（**本次运行 config 日期区间内**的原始时间轴长度）
当作 `append_dim_size` 传给 reconciliation 的 widen 分支，而 `XrBackend` 对这个参数的契约是
「**store 的总 extent**」。当 config 区间窄于 store 已有历史时，`mode="w"` 改写会把
on-disk append-dim chunk **改小**——Zarr 建好的 grid 无法再修，只能删库重建。这是 CR-01。

另有 6 处 WARNING：其中 WR-01 证明 `widen_and_append` 新加的那句「a store cannot come out of
here carrying one grid per axis」是**假的**（`save()` 建的库 + 一次变量 widen 就出两套 grid）；
WR-03 是 `.superseded.tmp` 目录残留会把 widen 路径永久卡死的 crash 缺口，且
`BaseDataset` 与 `XrBackend` 在同一个 store path 上用了**同名后缀**。

## Critical Issues

### CR-01: 窄区间 update/widen 会不可逆地把已完成 store 的 chunk grid 改小

**File:** `quantlab/base/data.py:672-678`（以及 `quantlab/base/data.py:1310-1316`、
`quantlab/dataset/backend.py:1145-1161`）

**Issue:**

`XrBackend._append_encoding` 的文档把 `append_dim_size` 定义为
「the store's TOTAL extent along `append_dim`」，`widen_symbol_axis` 的文档也说传它是为了拿到
「the grid a whole-range write would have left」。但唯一的生产调用点传的不是 store 的总 extent：

```python
# quantlab/base/data.py:672-678
ledger, rebuild_asides = self._reconcile_new_listings(
    symbols, ledger, append_dim, on_new_listing,
    append_dim_size=len(timestamps),      # ← 这是 CONFIG 区间内的原始时间轴长度
)
```

`timestamps` 来自 `self._raw_axes_in_range()`，而 `StockDataset._raw_axes_in_range` →
`_scan_raw()` 会套用 `self.config.start_date` / `self.config.end_date`
（`quantlab/dataset/stock.py:361-366`）。所以只要 config 区间**窄于 store 已持有的历史**，
`len(timestamps)` 就小于 store 的真实 extent，而 `_append_encoding` 对它**不做任何钳制**：

```python
# quantlab/dataset/backend.py:1152-1157
if dim == append_dim and append_dim_size is not None:
    size = int(append_dim_size)          # 直接采信，不与 panel/store 的实际长度取 max
else:
    size = int(panel.sizes[dim])
if dim == append_dim:
    chunks.append(max(min(self.APPEND_DIM_CHUNK, size), 1))
```

`widen_symbol_axis` 是 `mode="w"` 全量改写，它**重新钉** grid，于是 chunk 被改小。
Zarr 在写入时固定 grid、事后无法修改（这正是本模块 `APPEND_DIM_CHUNK` 注释自己说的），
所以损坏是**不可逆**的，只能 delete-and-rebuild。

**端到端实测**（`APPEND_DIM_CHUNK` 调到 4，走生产入口 `from_raw_data_chunked`）：

```
after full backfill  (12 行, roster {A,B}, 整区间):  close.chunks = (4, 2)   ← 正确
after narrow-range widen (config 只覆盖最后 2 天, roster 增长到 {A,B,C}):
                                                     close.chunks = (2, 3)   ← 被改小
store rows: {'timestamp': 12, 'symbol': 3}
```

改动前 `_reconcile_new_listings` 不传该关键字，`_widen_whole_store` 用
`_append_encoding(append_dim, data=widened)`，得到 `min(4, 12) = 4`——**正确**。
所以这是 plan 03.6-07 引入的回归，方向与本阶段目标相反。

加重两点：

1. widen 在 `ledger.assert_consistent()` **之前**提交。上面那次运行其余窗口全被 ledger 跳过、
   整个 run 实际上是 no-op，却照样把 grid 砍了一半，且日志里没有任何一行提到 grid。
2. 同一个值还会流到 `widen_data_vars`（`quantlab/dataset/backend.py:1091-1097`）
   和 `_widen_chunked` 的首块编码，所以三条 widen 路径同时被同一个错值污染。

现有测试全部只覆盖「stated extent ≥ store 现有 extent」这一侧
（`_incomplete_store` 造的是 stated 9 / 持有 3），**没有任何一条断言 widen 不得把 grid 改小**。

**Fix:**

在 `_append_encoding` 里把 stated extent 当作**下界而非替换值**，这样错误的窄值最多是不生效、
不会造成不可逆损坏：

```python
# quantlab/dataset/backend.py:1152-1157
if dim == append_dim:
    size = int(panel.sizes[dim])
    if append_dim_size is not None:
        # STATED extent 只能把 grid 往上抬（朝 min(APPEND_DIM_CHUNK, total) 靠），
        # 永远不能把一个已经写宽的 store 重新钉窄 —— Zarr 无法回滚 grid。
        size = max(size, int(append_dim_size))
    chunks.append(max(min(self.APPEND_DIM_CHUNK, size), 1))
else:
    chunks.append(max(int(panel.sizes[dim]), 1))
```

注意 `_widen_*` 传给 `_append_encoding` 的 `data=` 是**被改写的 store 面板**（或首块），
所以 `panel.sizes[append_dim]` 在 whole-store 分支上就是 store 现有 extent，`max()` 正好
把 CR-01 堵死；chunked 分支上首块长度受 `_widen_block_rows` 的 `APPEND_DIM_CHUNK` 下限保护，
也不会被 `max()` 反向拉低。

并补一条红→绿测试：完整 12 行 store + `append_dim_size=2` 的 widen，断言 grid 仍是
`min(APPEND_DIM_CHUNK, 12)`。

（可选、正交的第二道保险：让 `from_raw_data_chunked` 传
`max(len(timestamps), 已存 store 的 append 长度)`，而不是裸的 `len(timestamps)`。
但上面的 `max()` 是单点修复，优先。）

## Warnings

### WR-01: `widen_and_append` 新写的「不可能出现一库两 grid」是假的，实测可复现

**File:** `quantlab/dataset/backend.py:1026-1031`

**Issue:** 本次新增的文档段落断言：

> All three read `append_dim_size` from the SAME `kwargs` entry, so a store cannot come
> out of here carrying one grid per axis.

这只覆盖了「本次调用写的三样东西」，没有覆盖**store 里早就存在的变量**——它们的 grid 是更早
一次写入钉的，可能来自完全不同的 `append_dim_size`，或者根本没有 encoding。
`XrBackend.write()`（即 `BaseDataset.save()` / `Factor.save()` 的落盘路径，
`quantlab/dataset/backend.py:125-130`）**完全不传 `encoding`**，所以 `save()` 建出来的库走的是
Zarr 默认 grid。实测：

```
save()-created grid:        {'close': (10, 2)}
after widen_and_append(append_dim_size=15):
                            {'close': (10, 2), 'newvar': (4, 2)}   SINGLETON? False
```

这直接违反本阶段声明的不变量「`set(_chunk_grid(store).values())` 对本项目写出的每一个 store
都必须是单元素集合」，且 `save()` → `update()` 是文档明确支持的工作流
（`Factor.save()` 的报错信息就在推荐 `update()`）。

**Fix:** 二选一——(a) 把这句话降级为「本次调用写入的三样东西彼此一致」，并在
`widen_data_vars` 里加一条「新变量的 chunk 与 store 现有变量不一致时 `logger.warning`」；
或 (b) 见 WR-02，从源头让 `write()` 也钉 grid。推荐 (b) + 收窄措辞。

### WR-02: `XrBackend.write()` 不钉 encoding，整个「grid 是 store 的属性」论断在批量写路径上不成立

**File:** `quantlab/dataset/backend.py:125-130`

**Issue:**

```python
def write(self, path: str, **kwargs) -> Self:
    if not Path(path).exists():
        Path(path).parent.mkdir(parents=True, exist_ok=True)
    kwargs.setdefault("mode", "w")
    self.data.to_zarr(path, **kwargs)     # 没有 encoding
    return self
```

`append()` / `widen_*` 三条路都费尽力气让 grid 落在
`min(APPEND_DIM_CHUNK, total)` 上，唯独 `save()` 这条**最常用的批量写路径**不管。
`APPEND_DIM_CHUNK` 那 65 行注释开头就说「A fixed value makes the layout a property of the
store rather than of whichever window happened to be written first」——这句话对 `write()`
建出来的 store 从来没有成立过。后果就是 WR-01。

**Fix:**

```python
kwargs.setdefault("mode", "w")
if kwargs["mode"] == "w":
    kwargs.setdefault("encoding", self._append_encoding("timestamp"))
self.data.to_zarr(path, **kwargs)
```

（append 维名要么参数化，要么复用 `append()` 的默认值；请顺带补一条断言
`save()` 与 `from_raw_data_chunked()` 落在同一 grid 的测试。）

### WR-03: 残留的 `.superseded.tmp` 目录会把 widen 路径永久卡死，且与 rebuild 的 aside 同名同路径

**File:** `quantlab/dataset/backend.py:386-405`、`498-500`；
`quantlab/base/data.py:994`、`1374-1377`

**Issue:** `widen_symbol_axis` 的 crash guard 只处理
`superseded.exists() AND NOT target.exists()`（第 390 行）。**两者同时存在**的情况没有守卫，
而收尾的交换是：

```python
os.replace(target, superseded)   # ← superseded 若是非空目录，POSIX 上必抛 ENOTEMPTY
os.replace(widening, target)
shutil.rmtree(superseded, ignore_errors=True)
```

实测：`os.replace` 到一个**非空目录**上抛 `OSError: [Errno 66] Directory not empty`。
而残留是可达的，至少两条路：

1. 收尾的 `shutil.rmtree(superseded, ignore_errors=True)` 静默失败（权限 / NFS / SIGKILL），
   或进程在 rmtree 中途被杀；
2. **命名碰撞**：`BaseDataset.SUPERSEDED_SUFFIX`（`data.py:994`）与
   `XrBackend.SUPERSEDED_SUFFIX`（`backend.py:277`）是**同一个字符串**，且都拼在**同一个
   store path** 后面。一次被 SIGKILL 的 `on_new_listing="rebuild"` 会留下
   `store.zarr.superseded.tmp`（`_restore_rebuild_asides` 只在异常/取消时跑，SIGKILL 跑不到；
   续跑时 `_reconcile_new_listings` 看到部分 store 的 roster 已是新并集，直接 fall through，
   `rebuild_asides` 为 `None`，`_discard_rebuild_asides` 永不执行）。此后**任何一次 widen**
   都会在把整个 sidecar 写完之后才炸 `ENOTEMPTY`，且错误信息里没有一个字提到该怎么办。

`widening` 侧有 `shutil.rmtree(widening, ignore_errors=True)` 的自愈（第 400-403 行），
`superseded` 侧没有对称处理——而 `superseded` 恰恰是那个「可能装着真数据」的目录，
所以既不能盲删，也不能不管。

**Fix:** 在 guard 区加第四种状态，明确拒绝并给出人工指令：

```python
if superseded.exists() and target.exists():
    raise ValueError(
        f"XrBackend.widen_symbol_axis: refusing to widen {path} -- a superseded "
        f"sidecar already exists at {superseded} while {path} is also present. "
        f"It is either a crashed widen's leftover or a SIGKILLed "
        f"on_new_listing='rebuild' aside (both use '{self.SUPERSEDED_SUFFIX}'). "
        f"Renaming {path} aside would fail with ENOTEMPTY after the whole rewrite "
        f"has been done. Decide by hand which directory is authoritative, remove "
        f"the other, and re-run."
    )
```

并把两个 `SUPERSEDED_SUFFIX` 改成不同字符串（例如 dataset 侧用 `.rebuild.tmp`），
或让 `BaseDataset` 直接引用 `XrBackend.SUPERSEDED_SUFFIX` 并在文档里承认这是共享命名空间。

### WR-04: `_restore_rebuild_asides` 可能在 `except BaseException` 处理器内部抛出，吞掉原始失败

**File:** `quantlab/base/data.py:1359-1366`（调用点 `934-940`、`963-966`）

**Issue:**

```python
if Path(asides["store"]).exists():
    shutil.rmtree(asides["store"], ignore_errors=True)   # 静默失败 → 目录还在且非空
os.replace(asides["store_aside"], asides["store"])       # → ENOTEMPTY
```

它跑在 `except BaseException: ... raise` 里面。一旦这里抛 `OSError`，
**原始异常被替换掉**（只留在 `__context__` 里），操作者看到的是一个与真实故障无关的
「Directory not empty」，同时 store 停在「部分重建 + aside 仍在」的中间态。

**Fix:** 去掉 `ignore_errors=True`（让删除失败可见），或把整段包起来：

```python
try:
    ...
except OSError as exc:
    logger.error(
        f"{self.class_name}: could not restore the pre-rebuild store at "
        f"{asides['store']}; the complete copy is still at "
        f"{asides['store_aside']} -- recover it by hand. {type(exc).__name__}: {exc}"
    )
    # 不再抛出，让原始异常继续传播
```

### WR-05: `append_dim_size` 与 `_widen_block_rows` 的 byte 下限在数值上确实会互相错位

**File:** `quantlab/dataset/backend.py:777-801`（`_widen_chunked`），`624-626`

**Issue:** scope note 要求确认这两个界不会冲突。它们**不会互相覆盖**（一个定 grid、一个定块大小），
但在 `append_dim_size < APPEND_DIM_CHUNK` 时会**错位**：

- grid chunk = `min(APPEND_DIM_CHUNK, append_dim_size)`；
- `block_rows = max(APPEND_DIM_CHUNK, ...)` ≥ `APPEND_DIM_CHUNK`。

于是 `block_rows` 不再是 chunk 的整数倍，每个块边界都落在 chunk 内部，触发
read-modify-write。实测（`APPEND_DIM_CHUNK=4`、`MAX_WIDEN_BYTES=0`、stated=3、20 行 store）：
grid `(3, 3)`，`block_rows` 4，块边界 4/8/12/16 全部与 3 的倍数错开。
**数据正确**（值逐元素比对通过、新符号列全 NaN），所以这不是数据缺陷；但它正是
`APPEND_DIM_CHUNK` 注释里说要避免的「misaligned with the on-disk chunk grid」，
而现在没有任何断言拦住它。CR-01 的 `max()` 修复会顺带消除这一类错位。

**Fix:** 随 CR-01 一起修；并在 `_widen_block_rows` 或 `_widen_chunked` 里补一句断言/日志：
`block_rows % chunks[0] == 0`。

### IN-05: `append()` 在 caller 已给 `encoding` 时仍会白算一遍编码

**File:** `quantlab/dataset/backend.py:255-260`

`kwargs.setdefault("encoding", self._append_encoding(...))` 的默认值是**先求值再判断**的，
所以调用方自带 `encoding` 时 `_append_encoding` 照样跑一遍并被丢弃；同时这也意味着
调用方自带 `encoding` 会让 `append_dim_size` **静默失效**，而 docstring 没有提这一点。

**Fix:**

```python
if "encoding" not in kwargs:
    kwargs["encoding"] = self._append_encoding(append_dim, append_dim_size=append_dim_size)
elif append_dim_size is not None:
    logger.warning("XrBackend.append: caller-supplied encoding overrides append_dim_size.")
```
