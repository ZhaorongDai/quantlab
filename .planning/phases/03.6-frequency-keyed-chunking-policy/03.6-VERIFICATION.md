## SC-1 裁定(用户明确要求的判断)

**问题:** SC-1 ——「a caller can plan a chunked conversion at `day` granularity and the conversion
writes one window per observed trading day, end to end, to a real Zarr store」—— 在它产出的 store
于本阶段自身等价性检查看不见的维度上结构性退化时,是否算 MET?

**裁定:SC-1 本身 MET;被证伪的是本阶段用来支撑这两级的那句架构论据,而不是 SC-1 的字面契约。
但由此暴露的缺陷严重到必须在 03.6 内修,不建议推到后续工作。**

推理,分三步:

**(一) SC-1 的字面契约确实成立,且我是直接验证的,不是采信 SUMMARY。**
ROADMAP SC-1 的正文只讲梯子的算术契约(五元组、五个分支、`tuple[int, int]` 不变、两条新键的具体
公式与 8807 上界),这一整套我在运行时逐项取值确认过。plan 03.6-01 的 tracer truth 措辞是
「writes one window per observed trading day, end to end, to a real Zarr store」——9 个窗口、
每窗一行三票、whole-range densifier 零次调用、真实 Zarr 落盘、ledger 指纹正确,全部由一条我实际
跑过的具名测试证明。把 SC-1 判为 FAILED 是不诚实的:它写了什么,代码就做到了什么。

**(二) 被证伪的是更强的那句话,而那句话才是删守卫的理由。**
tracer 测试的 docstring 把自己定位成「a finer rung is a data point on an existing axis, not a new
mechanism」的**证明**。我的复现直接否证了这句:

```
DAY-chunked   : 13 个变量全部 (1, 3)
UNCHUNKED     : 13 个变量全部 (9, 3)
YEAR-chunked  : 13 个变量全部 (3, 3)
DAY == UNCHUNKED : False
assert_identical 仍然 PASS(它不比较 encoding)
```

在落盘布局这个维度上,`day` 不是既有轴上的一个数据点——它改变了 store 的物理格网,而证明它「一致」
的那条断言恰好对这个维度失明。所以这两级在写盘侧**确实是新机制**,本阶段是在不知情的情况下发布的。

**(三) 为什么这不能被「caller owns the cost」吸收掉——这是裁定的支点。**
本阶段删守卫的整个正当性建立在一个交换上:库提供梯子,不做策略选择,代价由调用方承担。这个交换
**要求代价被陈述**。我核对了 `03.6-CONTEXT.md:69-79`「Costs accepted, with their owners」,里面
恰好三条:dense-panel 守卫删除(OOM)、`hour` 的 IO 成本、DATA-08 撤回。chunk 格网退化不在其中,
也不在任何 D-xx 里。它从未被摆到开发者面前,所以它不是「已接受成本」,而是**未被发现的后果**。

而且它与那三条**性质不同**:OOM 可以换一级重跑,IO 浪费是单次运行的开销,DATA-08 是能力损失但不
涉及数据。chunk 格网是由**不可逆的 append 写进持久产物**的,唯一补救是删库重建;而 `--chunk` 的
帮助文本对操作者说的代价只有 "more append round trips"。

决定性的一点是:**这条不变式是本仓自己已经声明并已经为姊妹路径修过的。**
`quantlab/dataset/backend.py:414-431` 逐字写着 "**The grid constraint is load-bearing, not
stylistic**",记录了 2026-09-08 的同类实测(100 行块留下 `(100,3)` 而整段路径留下 `(512,3)`),
并加了 `block_rows = max(APPEND_DIM_CHUNK, ...)` 地板,理由明写为「让两种策略在格网上一致」。
分块转换路径没有这个地板。所以这不是我引入的新标准,是仓内已有规则在另一条路径上未被执行,
而本阶段交付的正是触发它的那两级。

**结论与建议:** SC-1 记为 VERIFIED;缺陷单独立项为 gap #1,挂在**阶段目标的 caller-owns-the-cost
一半**上,而不是挂在任何一条 SC 上。建议**在 03.6 内修**而非开后续工作,理由是不可逆性:
每多一次 `--chunk day` / `--chunk hour` 的生产运行,就多一个只能删库重建的 store;而修复面很小
(`_append_encoding` 加一个关键字 + 首写时传整段轴长 + 一条 encoding 断言),与 `_widen_block_rows`
已有的论证同构。若开发者判定为纯性能问题而选择接受,则**接受必须是显式的**:写进 CONTEXT 的已接受
成本清单、写进 `--chunk` 帮助文本与 `example/chunking.md`,并把 tracer 测试改成显式的「已知差异」
pin,不要让 `assert_identical` 继续替一个它看不见的主张背书。

**量级的诚实补注(评审未展开的一点):** `(1, 3)` 是 daily 轴上用 `day` 级这一病态组合的结果;
生产上更现实的组合是 `1m` 轴。按 `_append_encoding` 的 `min(512, 首窗行数)` 公式推导,`1m` 上
`--chunk day` 首窗约 390 行 → chunk 390,`--chunk hour` 首窗为开盘那个不完整钟点约 30 行 →
chunk 30,即约 17 倍于整段路径的 chunk 对象数。这比「1」温和一个量级,但仍是不可逆退化,而且
`--chunk day` 作用在 `1d` store 上的病态路径今天**可达且无任何告警**——本阶段的 tracer 测试本身
就是这条路径。

删库重建。更关键的是,本仓自己已经在 `_widen_block_rows` 里把同一条格网不变式写成
"load-bearing, not stylistic" 并加了地板——分块转换路径没有,这是仓内规则未被一致执行,不是
新标准。而本阶段用来证明「新 rung 与旧 store 一致」的 `assert_identical`,恰好不比较 `encoding`,
即在它唯一可能失败的维度上失明(已复现:encoding 不等而断言 PASS)。

**建议在 03.6 内修**,理由是不可逆性与修复面之小:`_append_encoding` 增加一个 `append_dim_size`
关键字、`from_raw_data_chunked` 首写时传整段轴长、tracer 测试补一条 `encoding["chunks"]` 断言。

「不做决定」不可以——那会让一个已知的不可逆退化继续以「已验证一致」的名义发布。
