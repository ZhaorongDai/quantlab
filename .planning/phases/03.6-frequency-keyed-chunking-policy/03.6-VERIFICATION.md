然后 widen 把它推平成 `3` 和 `1`,**两个数字随 rung 不同**,其中 `(1, 3)` 正是原 gap 报告里
`--chunk day` 那个数字。所以这不是「另一个缺陷」,是同一个缺陷在第三条路径上原样存活。

### 二、按 plan 03.6-05 自己的 must_haves 逐字判定(不用转述)

truth #2 原文(`03.6-05-PLAN.md:22`):

> "The on-disk append-dimension chunk of **a store created by a chunked conversion** is
> `min(XrBackend.APPEND_DIM_CHUNK, len(observed whole-range timestamp axis))` **at EVERY rung**
> — **a property of the store's total extent** …"

主语确实把自己限定在「由分块转换创建的 store」——**而复现 B 的 store 恰好就是这一类**:
它由 `from_raw_data_chunked` 创建,由 `from_raw_data_chunked` 结束,全程没有一次直接的
backend 调用。谓语则是**无条件的**:它是 store 总 extent 的属性。测量结果是 3 与 1,
总 extent 是 9,`min(4, 9) = 4`。谓语在被限定的主语类上失败。

truth #1 原文(`:21`):

> "…a caller that picks a finer rung takes on ONLY the costs this phase stated and accepted …
> and **NOT an irreversible degradation of the store's on-disk chunk grid. The grid is no longer
> a cost of the choice, so it does not need to be a stated one.**"

复现 B 直接否证后半句:选 `day` 的调用方拿到 `1`,选 `year` 的拿到 `3`,Zarr 不可回改。
格网**仍然是选级的代价**,且仍然未被陈述。

按任务给出的判定规则——「若主张的措辞把自己限定在 conversion-created stores,(a) 可能成立;
若它无条件地声称格网是 store 的属性,(b) 成立」——**(b)**。

### 三、为什么不是「一个 gap 从未覆盖过的独立路径」(即为什么不是 (a))

三条理由,按份量排序:

1. **失效模式同构,不是同区域。** 原 gap 的定义性特征不是「首窗口决定格网」这个机制,而是它的
   后果:**格网成了 rung 的属性**。复现 B 的表格显示这个后果原封不动地存在。一个「独立缺陷」
   不会在同一个 fixture、同一条入口、同一组变量上复现出同一张退化表。
2. **`03.6-05` 自己把这条路径考虑进来过,并且做了一个明确的、被记录的决定。**
   `03.6-05-SUMMARY.md` 的 key-decisions 写着「`widen_and_append` 签名刻意不动,关键字借其既有
   `**kwargs` 通过」与「widen 路径保留 block 地板而不改用新关键字」。换言之 widen 路径不是没看见,
   是看见了并判定「它由另一条机制保证」。**那个判定是错的,而且错在一个可检查的地方**:
   `_widen_block_rows` 的地板论证只覆盖 `_widen_chunked`;实测走的 `_widen_whole_store`
   (`:618-619`)既没有字节预算顾虑,也**没有任何地板**,它只是 `data=widened` 地按当时 extent 重钉。
   所以「两条路径用不同机制达成同一格网」这句话,对本次实际发生的那条分支是假的。
3. **本轮把这条错误判定固化成了四处无条件陈述。** `backend.py:189-192`
   「the grid was pinned irreversibly by the creating write and there is nothing left to decide」
   被同一个类的 `widen_symbol_axis` 直接证伪;`:51-57` 的「both paths land on
   `min(APPEND_DIM_CHUNK, total_len)`」漏掉第三条路径。这两段都是**这次 gap-closure 写下的**。
   在一个把 D-18(被证伪的锁定文本必须就地标注)当作纪律、并且刚刚用一整个 plan 去清扫假陈述的
   阶段里,收尾时新增两条假安全陈述,不能记为「已关闭」。

**同时必须说清楚 (a) 有道理的那一半,否则这份裁定不诚实:**
truth #6 逐字枚举的是「建库写不是第 0 次迭代」的两条路径(resume、rebuild),truth #3 说的是
「`--chunk day` 转换与非分块转换产生相同 `encoding['chunks']`」——**这三条都成立,我逐条验过**。
建库写这一半是真修好了,而且修得干净:三向判别(丢 encoding→9 / 旧规则→1 / 新规则→4)让四条新臂
断言的是机制而不是 fixture 巧合,这是很高质量的测试设计。**修复覆盖了原 gap 的大部分面积。**
剩下的是 widen 重写这一条,它在 truth 的措辞里没有被排除,在代码里没有被处理,在测试里没有被覆盖。

### 四、可达性(这决定它是缺陷还是学术问题)

`_resolve_new_listing_strategy`(`base/data.py:1181-1202`):当 raw 在 store 自己的 extent 内
对所有新增 symbol 都没有行时,解析为 `"widen"` —— 这是「真新股上市」的情形,也是 `update()`
的 `_AUTOMATIC` 默认解命中的最常见分支。`_reconcile_new_listings`(`:1285-1289`)随后在
**循环之前**调 `widen_symbol_axis`,不带任何总 extent。

退化只在 **widen 发生时 store 的实际 extent < 建库写陈述的 extent** 时出现,也就是
「store 相对本次转换的计划区间是不完整的」:崩溃/取消后 resume,或重建被回滚。
需要指出的公平之处:对一个**已完整**的 store 做 widen,重写按 extent 重钉的值与建库写钉的值相同,
不产生退化。所以这不是「每次 widen 都坏」,而是「崩溃恢复 + roster 增长这条组合路径上坏」——
而这恰好是 `03.6-05` 自己把 resume 单列为一条 truth 去保护的那条路径。修好的建库写把格网钉对了,
紧接着的 widen 又把它毁掉。

### 五、同源的第二个症状(直接 backend 复现,一并记录)

`widen_data_vars` 的 filler(`:830`)同样拿不到总 extent,于是**同一个 store 内部的变量可以落在
不同格网上**:

```
C) grids after a variable widen : {'close': (4, 2), 'newvar': (3, 2)}
C) stated invariant expects     : both (4, 2)
```

这会打破四条新测试共同断言的 `set(grid.values()) == {单值}` 的单值性前提。根因与 WR-01 相同
(重写路径不知道 store 的最终 extent),修复面也相同,故并入同一条 gap,不单列。
