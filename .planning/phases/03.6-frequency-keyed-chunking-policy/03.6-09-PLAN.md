<objective>
Close WR-04, one of the two robustness defects the developer pulled into scope this round
(`03.6-REVIEW.md` `### WR-04`; listed as `advisory` with
`evidence_status: not independently reproduced` in `03.6-VERIFICATION.md`).

The defect: `BaseDataset._restore_rebuild_asides` (`quantlab/base/data.py:1349-1370`) runs inside
`from_raw_data_chunked`'s `except BaseException: ... raise` handler. Its first move is
`shutil.rmtree(asides["store"], ignore_errors=True)` -- which SILENTLY does nothing when it fails
-- immediately followed by `os.replace(asides["store_aside"], asides["store"])`, which then raises
`OSError`. An exception raised inside an exception handler REPLACES the exception being handled:
the operator sees "Directory not empty", the real failure survives only in `__context__`, and the
store is left in the middle state (partially rebuilt, aside still present) with no clue about what
actually went wrong.

Because the review did not reproduce this independently, the FIRST task here is a failing-first
reproduction. It is a real test that constructs the residue state and goes red on today's code,
before any production line moves. If the condition turns out to be genuinely unreachable, Task 1
says so in writing and the plan downgrades WR-04 to a documented non-defect -- it does not ship a
fix for a condition nobody can produce.

A second, smaller thing rides along because the fix creates it: once the restore can fail without
raising, `rebuild_rolled_back = True` at the cancelled call site becomes a claim the code can no
longer back. The method returns whether it actually restored, and the caller reports that.

This plan runs in Wave 1 in PARALLEL with `03.6-08`. The two share no file: `03.6-08` owns
`quantlab/dataset/backend.py` and `tests/test_chunked_ingest.py`; this plan owns
`quantlab/base/data.py` and a new test module. Plan `03.6-10` (WR-03) depends on BOTH because it
touches both production files.

Purpose: this phase's crash-safety story -- rename-aside, never delete, restore on failure -- is
the reason `on_new_listing="rebuild"` is safe to offer at all. A recovery path that destroys the
diagnosis of the failure it is recovering from is the one kind of bug that costs the most at
exactly the worst moment.

Output: a reproduction that is red today, a fix that makes the original exception survive, a
truthful `rebuild_rolled_back`, and a D-18 annotation explaining the swallow.
</objective>
