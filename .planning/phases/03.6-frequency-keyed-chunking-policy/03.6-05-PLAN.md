<objective>
Close the single gap `03.6-VERIFICATION.md` records. It is not attached to any Success
Criterion; it hangs on the remaining half of the phase goal — *"the caller chooses a rung
by passing it explicitly"* — which presupposes that the cost the caller takes on has been
STATED.

The measured defect: `XrBackend.append()` pins the Zarr on-disk chunk grid exactly once,
on the creating write, from whatever panel is in hand at that moment. In
`BaseDataset.from_raw_data_chunked`'s loop that panel is the FIRST WINDOW, so the store's
permanent append-dimension chunk becomes `min(512, first_window_rows)` instead of
`min(512, whole_range_rows)`. Same raw input, 13 data variables, measured by the verifier
and reproduced independently: unchunked `(9, 3)`, `--chunk year` `(3, 3)`, `--chunk day`
`(1, 3)`. Zarr append is irreversible and the grid is fixed at store creation, so the only
remedy for a store already written this way is delete-and-rebuild.

This is a repo-internal rule not applied consistently, not a new standard.
`XrBackend._widen_block_rows` (`quantlab/dataset/backend.py:411-450`) states the identical
invariant verbatim — *"The grid constraint is load-bearing, not stylistic"* — records the
2026-09-08 measurement behind it, and fixes it for the sibling widen path with
`block_rows = max(APPEND_DIM_CHUNK, (raw // APPEND_DIM_CHUNK) * APPEND_DIM_CHUNK)`,
justified as "making the two strategies agree on the grid without either restating the
arithmetic". The chunked-conversion path has no such floor. `APPEND_DIM_CHUNK`'s own `#:`
comment at `:29-35` already promises the property that is being violated: *"makes the
layout a property of the store rather than of whichever window happened to be written
first."*

Phase 03.6's deliverable is what made this reachable. Before it, the finest rung was
`month`, whose first window normally cleared the 512 floor on its own.

Purpose: the trade this phase made — the library offers the ladder, the caller owns the
cost — only holds while the costs are the stated ones. After this plan, on-disk grid
degradation is not among them, because it no longer happens.

Output: an `append_dim_size` keyword threaded from D-02's once-resolved whole-range axis
down to the one arithmetic expression that decides the grid, and tests that compare
`encoding["chunks"]` so the equivalence claim is made by an assertion that can see it.
</objective>

<correctness_risks>
The five places a naive fix goes wrong, reasoned through against the live code rather than
restated. Each conclusion below is what the tasks implement.

**(1) `_append_encoding` has FOUR call sites, three of which pass `data=` explicitly.**
`_widen_whole_store` (`:542`), `_widen_chunked` (`:596`) and `widen_data_vars`'s filler
(`:754`) pass a panel; `append()` (`:143`) passes nothing and gets `self.data`. A new
keyword must change none of the four. **Resolution: the keyword defaults to `None`, meaning
"use the panel's own append-dim length", which is today's behaviour verbatim.** No existing
call site passes it, so all four produce byte-identical output.
`_widen_block_rows`'s docstring argues that the widen path's grid correctness comes from
its BLOCK FLOOR making `min(APPEND_DIM_CHUNK, first_block_len)` equal
`min(APPEND_DIM_CHUNK, total_len)`; that argument is untouched, because `_widen_chunked`
keeps passing only `data=block`. Task 3 adds one sentence there recording WHY the widen
path keeps its floor rather than switching to the new keyword: the floor also bounds
BYTES (`MAX_WIDEN_BYTES`), which is that path's actual constraint and is not something an
append-dim length can express.

**(2) The non-append dimensions do NOT need the keyword, and the evidence says so.**
`_append_encoding` pins every non-append dim to `max(size, 1)` of the panel in hand. On
the chunked path that panel's symbol axis cannot differ from the whole-range one: D-02
resolves the symbol axis ONCE over the whole range before any window exists
(`quantlab/base/data.py:632`, `symbols, timestamps = self._raw_axes_in_range()`), every
window is materialised on that pinned axis, and the loop asserts it element-count-for-
element-count at `:763-771`, raising rather than appending when `actual != symbols`.
So `panel.sizes["symbol"]` on the store-creating window already equals the whole-range
symbol count. **Resolution: the keyword is append-dim-only. The symbol chunk is covered
anyway because the tests below compare the FULL `chunks` tuple, both components.**

**(3) The store-creating write is not always window zero.** `on_new_listing="rebuild"`
moves the store aside (`_reconcile_new_listings`, `quantlab/base/data.py:646`) so the run
becomes a first write; a resume skips already-recorded windows via `ledger.is_written`, so
the first APPEND of the run is not the first PLANNED window. **Resolution: do not detect
"the first window" in the loop at all. Pass `append_dim_size` on EVERY iteration and let
`append()`'s existing store-existence branch decide whether to use it.** Store existence is
the real condition and `append()` already owns it; a loop-index heuristic would be wrong
under both strategies. Task 2 pins both arms.

**(4) `APPEND_DIM_CHUNK` is a CEILING, not just a floor.** The target is not "a bigger
number" — it is the grid a whole-range write through this same method would have produced,
which is `min(APPEND_DIM_CHUNK, total_len)`. **Resolution: substitute the SIZE and leave
the existing `max(min(self.APPEND_DIM_CHUNK, size), 1)` expression untouched.** A separate
`max(APPEND_DIM_CHUNK, ...)` floor bolted on beside it — the shape `_widen_block_rows`
uses, which is correct for ITS constraint — would lose the ceiling on any range longer
than 512 rows. Task 2's monkeypatched arm (`APPEND_DIM_CHUNK = 4` over a 9-row axis,
expecting 4) is what makes the ceiling an asserted fact rather than an intention.

**(5) The windowing must not move.** The tracer test asserts 9 windows of 1 row each on a
daily axis. **Resolution: the change touches `encoding` only — no planner, no ledger, no
window boundary — and Task 1 keeps every existing windowing assertion in place beside the
new encoding one, in the SAME test, so the two cannot drift apart into separate files.**
</correctness_risks>
