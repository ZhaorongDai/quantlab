# Phase 03.6 Plan 07: Close the Widen-Path Chunk-Grid Gap Summary

`append_dim_size` now reaches all four store-rewriting sites, so a Zarr store's
on-disk chunk grid is `min(APPEND_DIM_CHUNK, whole-range length)` on every path
the store can reach — the `mode="w"` widen rewrite included — and the rung a
caller picks no longer buys an irreversible layout nobody chose.

## What Was Built

Plan `03.6-05` made the store-CREATING write state the whole-range extent and
proved it on four paths. It did not reach the third path: `widen_symbol_axis`
rewrites the whole store with `mode="w"` and re-pins the grid from the extent
*at rewrite time*. That left VERIFICATION truths #17 and #18 FAILED at 16/18.

### The measured defect, and its replacement

At `APPEND_DIM_CHUNK = 4` over a 9-timestamp range, with the store holding only
3 of those rows because the run crashed in window two:

| | pre-plan | post-plan |
|---|---|---|
| `--chunk year`, after `on_new_listing="widen"` | `(3, 3)` | `(4, 3)` |
| `--chunk day`, after `on_new_listing="widen"` | `(1, 3)` | `(4, 3)` |
| after a `widen_and_append` variable widen | `close (4, 2)` beside `newvar (3, 2)` | both `(4, 2)` |
| after a `MAX_WIDEN_BYTES=0` block-by-block widen | `(3, 3)` | `(4, 3)` |

Both pre-plan numbers were reproduced by the RED gate before any production
edit, and `(1, 3)` is the same number the ORIGINAL gap report measured on the
creating write — which is what identifies this as the one defect surviving on a
third path rather than an adjacent new one.

### Why the existing widen tests never caught it

Widening an already-COMPLETE store re-pins to the same value and degrades
nothing. The defect needs a store INCOMPLETE relative to its stated extent —
crash-resume, or a rolled-back rebuild. That is why the new arm builds its store
by hand with `_FailsOnSecondWindow` instead of borrowing `_built_over_ab`, whose
store is complete and would have been green on the pre-fix tree.

## Fixture-Realism Note

Neither widen fixture behaved observably differently under the shrunken
`APPEND_DIM_CHUNK = 4` or the zeroed `MAX_WIDEN_BYTES = 0` than it does at the
real values, and no arm was reshaped around fixture behaviour:

- `APPEND_DIM_CHUNK = 4` changes only the arithmetic's answer, not which branch
  runs; at the real 512 over a 9-row range all three candidate rules collapse
  onto 9 and the arms would not discriminate, which is the whole reason the
  constant is shrunk (the same reasoning `tests/test_symbol_axis_widening.py:412`
  already records).
- `MAX_WIDEN_BYTES = 0` routes to `_widen_chunked` and is the repo's own
  established idiom for reaching that branch. The arm asserts the branch
  actually ran by matching the `"block(s) of"` line only `_widen_chunked`'s
  report emits, rather than trusting the monkeypatch.
- `_widen_block_rows` under the zeroed budget returns `max(4, 0) == 4`, so the
  3-row incomplete store is exactly one block — which is the condition the arm
  is about, not an artefact that hides it.
