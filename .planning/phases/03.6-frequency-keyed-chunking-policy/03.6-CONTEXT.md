# Phase 03.6: Frequency-Keyed Chunking Policy - Context

**Gathered:** 2026-09-12
**Status:** Ready for planning

<domain>
## Phase Boundary

The time-window granularity of a chunked conversion is decided by ONE per-frequency constant
table, `CHUNK_GRANULARITY_BY_FREQUENCY`, rather than resolved at runtime or guessed per
invocation. The RAM guard's REFUSING half is deleted; its ESTIMATING half survives as a value the
caller renders.

**Scope widened by decision during discussion (see D-04):** the developer removed `--chunk`
ENTIRELY rather than demoting it to an override. There is no granularity override at any layer —
not a CLI flag, not a config field, not a keyword parameter. Changing a granularity means editing
the table and committing it.

**OUT of this phase:** tick→Zarr conversion (03.3); `hour` granularity (ROADMAP's own
recommendation is to stop at `day`); `ChunkLedger`'s write amplification (D-12 accepts it);
`ingest_binance_spot.py` joining the conversion entry point (03.5 D-09 keeps it out); any change
to `XrBackend.MAX_WIDEN_BYTES` or `assert_acquisition_volume_fits` — verified during scout that
neither is a RAM refusal (the first is a routing budget that never raises, the second bounds
disk / request count / wall clock), so SC-4's "no code path raises on a RAM budget" does not reach
them.

</domain>

<decisions>
## Implementation Decisions

### The constant table

- **D-01:** `CHUNK_GRANULARITY_BY_FREQUENCY` lives in **`quantlab/base/chunking.py`**, as a
  **module-level constant** (a bare name, exactly as ROADMAP SC-1 writes it), beside
  `TimeChunkPlanner.GRANULARITIES`.

  Why here rather than the two alternatives that were considered and rejected:
  - **`quantlab/enums/data.py`** (beside `RAW_HIVE_KEYS`, the other frequency-keyed table) was
    rejected because SC-1's import-time assertion would force an `enums` → `base.chunking` import.
    `enums/data.py` is currently the one pure-stdlib bottom module and is imported BY `base/`,
    `dataset/` and `acquisition/`; that edge inverts the layering. Splitting the pair — table in
    `enums`, assertion in `chunking` — was also rejected: an import path that touches only `enums`
    would then run no assertion at all, which is not what "asserted AT IMPORT TIME" means.
  - **`UniverseCatalog.CHUNK_GRANULARITY_BY_FREQUENCY`** (beside `BARS_PER_DAY_BY_FREQUENCY`, the
    table it most resembles in shape) was rejected because it pre-decides D-05 the wrong way:
    `quantlab/base/` must not import the acquisition package (the rule 03.5 D-04 states for
    `ConversionResult`), so the Dataset-layer hook could never reach it.

  **VERIFIED, so no new import is needed:** both `BARS_PER_DAY_BY_FREQUENCY: dict[str, int]` and
  `RAW_HIVE_KEYS: dict[str, tuple[str, ...]]` key on **bare `str`**, not on the `Frequency`
  literal. Following that precedent keeps `base/chunking.py`'s documented LEAF property
  (stdlib + pandas/xarray + `quantlab.utils.atomic`, nothing else) intact, untouched and true.

  **NOTE FOR PLAN-CHECKER — do not flag:** a module-level constant sitting next to a class whose
  own `GRANULARITIES` is a class attribute is deliberate, not an oversight. `GRANULARITIES` is a
  fact about the planner ("which windows can I cut"); the table is a POLICY about data ("which
  window does this frequency get"), and a pure time-axis class has no business knowing that
  frequencies exist.
  — **Reversibility:** reversible — one module-level constant with in-repo readers only.

- **D-02:** The import-time validation is a **module-level `if` that raises `ValueError`**, not a
  bare `assert`. The message names the offending key/value and the legal set, in the style
  `TimeChunkPlanner.__init__` already uses. A bare `assert` was rejected because `python -O`
  strips it, which would make SC-1's "asserted AT IMPORT TIME" conditional on how the interpreter
  was launched; a unit-test-only check was rejected because an out-of-repo importer
  (`quantlab-console`) would get no protection at all.

  **No in-repo precedent exists for module-level validation** — `quantlab/utils/file.py:30,35` are
  the only `assert`s in the package and both are inside functions. This is a new idiom; the
  planner should give it a `#:` rationale block rather than letting a future reader wonder.

- **D-03:** A frequency that is absent from the table produces a **custom refusal message** naming
  the frequency and the table — the same shape as 03.5's `dataset_cls=None` refusal that points at
  Phase 03.3. **No `if frequency == "tick"` branch is introduced** (SC-7). Falling back to `year`
  was explicitly rejected: that is precisely the silent guess SC-1 exists to eliminate, and it
  would let a future full-market tick window pass without comment.

### Resolution — CONTRACT CHANGE

- **D-04:** **`--chunk` is REMOVED ENTIRELY. It does not survive as an override.** There is no
  granularity override at any layer: no CLI flag, no `DatasetConfig` field, no keyword parameter
  on `convert()`. The table alone decides. Changing a granularity means editing
  `CHUNK_GRANULARITY_BY_FREQUENCY` and committing it.

  **This FALSIFIES ROADMAP 03.6 Success Criterion 2** ("`--chunk` drops from a required choice to
  an OVERRIDE: absent, it takes the table's value for the frequency; present, it wins").

  **ACTION REQUIRED OUTSIDE THIS DOCUMENT:** ROADMAP 03.6's SC-2 must be **rewritten**, not left
  standing in contradiction — the same handling 03.5 D-06 applied to 03.5's SC-2/SC-3 and that
  03.6's own SC-6 demands for every text this phase falsifies.

  **KNOWN COST, developer-accepted and recorded plainly:** the old refusal's remedy was "pass a
  finer `--chunk`". With both the guard and the flag gone, **an over-sized window has no
  operator-facing lever at all** — the only adjustment is a code change. D-13 and D-16 are what
  keep that honest rather than hidden.
  — **Reversibility:** costly — `convert()`'s signature is read by a second repository
  (`quantlab-console`, its CVT-02), and re-adding the parameter later would have to be threaded
  back through the hook, the entry point and three shells.

- **D-05:** The single lookup lives in an **overridable hook**:
  `BaseDataset._default_chunk_granularity()` raises "this dataset has no chunk policy";
  `MarketDataset` overrides it to return `CHUNK_GRANULARITY_BY_FREQUENCY[self.config.frequency]`.

  **This SUPERSEDES an earlier answer in the same discussion** that put the lookup in
  `registry.convert()`. That answer was given while the obstacle below looked fatal; once it
  dissolved, the same intent — nobody passes a granularity, the table is consulted automatically —
  landed one layer deeper, and `convert()` became a pure pass-through that consults nothing.

  **The obstacle, and why the hook clears it:** `from_raw_data_chunked` is declared on
  `BaseDataset` (`quantlab/base/data.py:542`), while `frequency` is pinned market-only by
  `tests/test_dataset_hierarchy.py:59-65` + `:195` (`MARKET_ONLY_CONFIG_FIELDS`) — a constituent
  panel has no frequency. So the method cannot read `self.config.frequency` through its declared
  type. **VERIFIED during scout: it has no non-market caller either** — every real call site is
  `StockDataset`, `registry.convert()` (`registry.py:568`) or `BaseDataset.update()`
  (`base/data.py:535`); `IndexConstituentDataset` never touches it. The hook therefore expresses a
  fact rather than working around one, and it is the same manoeuvre 03.5 D-08 used to put
  `_raw_data_to_xr_window` abstract on `MarketDataset` while `BaseDataset` kept a base-level answer.

  Two alternatives were considered and rejected: **moving the method down to `MarketDataset`**
  (would drag `update()` down with it, rewrite `tests/test_dataset_hierarchy.py`'s hierarchy
  assertions and `dataset/backend.py:931`'s error text — a structural change larger than this
  phase's goal), and **`getattr(self.config, "frequency", None)`** (a duck-read of a field the
  type does not declare, needing a second branch for the `None` case).

- **D-06:** **`from_raw_data_chunked` loses its `granularity` parameter entirely.** The hook is the
  only source, with no seam left to pass a competing value through. The retired
  `granularity: str = "year"` default was the last hardcoded granularity outside the table, which
  is exactly what SC-1's "single source" forbids.

  **Mechanical scope the planner must carry:** roughly 30 call sites in
  `tests/test_chunked_ingest.py` pass `granularity="year"`, plus
  `tests/test_symbol_coord_encoding.py:263` and several in `tests/test_dataset_update.py`; all
  must drop the argument. Testing a non-default granularity now means monkeypatching the hook or
  the table, and the planner should leave one test doing exactly that so the hook stays exercised.
  — **Reversibility:** costly — ~35 call sites plus a method signature other layers call.

- **D-07:** **`convert()` takes no `granularity` parameter** and passes none. It is a pure
  pass-through with respect to window sizing. `on_new_listing`, `reporter` and `cancel` are
  untouched.
  — **Reversibility:** costly — published signature read by `quantlab-console`.

- **D-08:** `add_chunk_args` (`quantlab/utils/cli.py:255`) **keeps its function name**; only the
  `--chunk` block is deleted, leaving `--on-new-listing`. Its docstring must be rewritten: the
  current text justifies `--on-new-listing` living in this group because it is "a knob on the same
  chunked `--to-zarr` conversion `--chunk` governs", and that justification dies with the flag.
  The derived-`choices` promise for `--on-new-listing` (`BaseDataset.NEW_LISTING_STRATEGIES`)
  stands unchanged.

### Table values and landing `day`

- **D-09:** The table is **`{"1d": "year", "1m": "day"}`**. `tick` is deliberately ABSENT and its
  absence IS the "not wired up yet" answer (SC-7), mirroring `BARS_PER_DAY_BY_FREQUENCY`'s own
  deliberate tick omission.

  `1d → year` is today's behaviour, so this phase changes only WHERE the value comes from, not
  what it is. Sized from `MAX_DENSE_PANEL_BYTES`'s own measurement basis (`us_all` 15,424 symbols
  x 252 trading days x 12 Tiingo EOD variables x float64): **`year` 356 MiB, `quarter` 89 MiB,
  `month` 30 MiB** per window — all far under the 4 GiB reference value, so the choice is not
  memory-forced. `month` (which would align one window to exactly one `RAW_HIVE_KEYS["1d"]` shard)
  was considered and rejected: it changes today's behaviour and multiplies ledger rewrites and
  Zarr appends by ~12 for no memory benefit. `quarter` was rejected as the only option with no
  independent justification at all.

  `1m → day` is forced: at `month` a minute window is a ~10 TB dense panel. At `day` it is
  ROADMAP's ~157 MB and aligns exactly with `RAW_HIVE_KEYS["1m"] = ("date",)`, so a window reads
  one shard and never re-opens it.

- **D-10:** `_period_key` (`quantlab/base/chunking.py:68`) becomes **explicit branches for all four
  granularities with a trailing `raise`**, replacing today's `if year / if quarter / else month`
  fall-through. `day` maps to `(ts.year, ts.dayofyear)`.

  The fall-through is a live trap, not a style question: adding a value to `GRANULARITIES` and
  forgetting `_period_key` currently produces **silent month-sized windows**, while the class
  docstring claims drift between the two planners is "structurally impossible". The trailing
  `raise` is what makes that claim true. (`__init__` already validates membership, so the raise is
  unreachable today — that is the point; it becomes reachable the moment someone edits one of the
  two lists without the other.) A dict-dispatch table was offered and not chosen.

- **D-11:** `plan_calendar`'s `pd.date_range(start, end, freq="D")`
  (`quantlab/base/chunking.py:153`) **keeps `freq="D"` and gains a comment** naming the
  day-resolution assumption. ROADMAP's recommendation to derive `freq` from the granularity now,
  as a cheap compatibility hook, was **declined**: `freq="D"` is exactly correct for every
  granularity down to and including `day`, so there is no defect today, and the only future that
  would break it is `hour` — which the same ROADMAP note recommends against taking. The comment
  is what a future `hour` author must meet.

- **D-12:** **`day` granularity's ledger write amplification is ACCEPTED as a known cost**, not
  fixed and not deferred to a todo. `ChunkLedger.record()` calls `_flush()`, which rewrites the
  ENTIRE sidecar JSON (`indent=2`) per window (`quantlab/base/chunking.py:257-276, 386`). At `day`
  a ten-year `1m` conversion is ~2,500 windows — ~2,500 full rewrites of a JSON that grows to
  ~2,500 entries (O(n²) bytes written), plus ~2,500 Zarr appends instead of ~10.

  Accepted because full-history minute backfill is DATA-V2-01/DATA-V2-02 (v2) and v1 does not
  reach that scale, and because a few hundred MB of ledger churn is noise beside the tens of GB of
  Zarr writes it accompanies. Revisit if minute conversion at production depth is actually run.
