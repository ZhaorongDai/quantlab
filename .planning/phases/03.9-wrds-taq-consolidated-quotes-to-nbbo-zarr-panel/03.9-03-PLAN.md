<objective>
Build the WRDS-shaped pre-flight volume guard (D-16): the REST requests-per-minute model
does not apply to a PostgreSQL pull, so this guard prices a fetch from real `count(*)`
row counts per trading day and refuses above a byte ceiling and a row ceiling unless
`--force-volume` is given.

Purpose: at the calibrated 2024 volumes (AAPL 1.24M rows/day; full market 313M rows/day)
the default 20 GiB ceiling admits only a few days of an S&P 500 pull, so a refusal must
say which shorter date segment WOULD fit (D-24: segmented runs, each guarded).

Output: `quantlab/acquisition/sql_volume.py` (pure arithmetic leaf), the renderer
`print_sql_volume_estimate` in `quantlab/utils/cli.py`, and tests. The count probe that
feeds it is built in plan 04; the CLI wiring in plan 07.
</objective>

<feature>
  <name>SqlVolumeGuard: row/byte ceilings over per-day counts, force contract, segment suggestion</name>
  <files>quantlab/acquisition/sql_volume.py, quantlab/utils/cli.py, tests/test_sql_volume_guard.py</files>
  <behavior>
    Estimate over `rows_by_day={"2024-01-24": 1_243_426, "2024-01-25": 1_100_000}`, `symbols=1`, default knobs:
    rows == 2_343_426; raw_bytes == rows * DEFAULT_BYTES_PER_ROW; trading_days == 2; crossed == [].
    Ceilings: with `max_raw_bytes` set just below the estimate -> ValueError whose message contains "raw-bytes", the estimated GiB, the ceiling, "--force-volume" and a fitting end date "2024-01-24"; with `max_raw_rows` below -> message contains "raw-rows"; both crossed -> both named.
    force=True with both crossed -> returns the estimate, `crossed` lists both, `forced` is True, no raise.
    No day fits at all (first day alone over a ceiling) -> the message says no date segment fits and to narrow the symbol list instead; `fitting_end_date` is None.
    Knobs readable from a kwargs mapping: `SqlVolumeGuard({"max_raw_bytes": ..., "max_raw_rows": ..., "bytes_per_row": ...})`; zero or negative knob -> ValueError (no divide-by-zero, no silent admit).
    Empty `rows_by_day` -> estimate with rows 0 and trading_days 0, admitted.
    Unsorted day keys are ordered ascending before the prefix search.
  </behavior>
  <implementation>See the tasks below.</implementation>
</feature>
