The purpose of this note is to provide detailed analysis and guidance concerning the use of the SAS
procedure PROC SQL when retrieving TAQ data. In particular, it assesses the possibility of record
re-ordering within ties when PROC SQL is used for data that do not have unique sort keys. The current
TAQ data feed lacks unique sort keys. Since TAQ data are ordered by SYMBOL/DATE/TIME, (TIME is
measured only to the whole second), a given SYMBOL can easily have multiple quotes for a single TIME
value. Given the absence of a "tie-breaker", many researchers have simply assumed that the physical
order of quote or trade records for a given TIME are in chronological order. The concern about
unintended re-ordering was originally raised by Prof. Hasbrouck in one of his working papers.

Before delving into details of the analysis performed by WRDS, users should be aware that:

- WRDS has never used PROC SQL in its TAQ database updating procedures (during data updates, TAQ data
  are converted from the NYSE-supplied format to SAS). WRDS does use the PROC SORT procedure from SAS,
  but this procedure is stipulated by SAS as preserving order of ties. Therefore, there is no reason to
  expect data re-ordering. As an additional assurance, WRDS performed multiple random checks scattered
  over the entire taq data history (back to January 1993) confirming in every case that the order of
  quotes/trades within symbol-date-time ties matches the order in the original NYSE-supplied data files.
- Hasbrouck's results show re-ordering only when using an approach (the ORDER BY clause) never
  recommended nor used by WRDS. [...]
- [...] no case of re-ordering has yet been found when using the only WRDS TAQ sample program
  (TAQ3.SAS) that includes PROC SQL.

In order to support these findings, WRDS conducted a number of empirical tests. In particular, we
tested TAQ3.SAS and found that its CREATE TABLE statement does NOT re-order the data, even though this
property is not guaranteed by SAS. But the ORDER BY clause regularly re-orders ties. [...] as a
pro-active measure (PROC SQL behavior can change in a future version), TAQ3.SAS has been removed and
its function is performed by the TAQ_EVENT_WINDOW1 program in /wrds/taq/samples. TAQ_EVENT_WINDOW1
does not use PROC SQL.

More generally, the advisability of whether and how to use PROC SQL when the resulting record order is
important depends on the answer to these two questions:

1. Does a simple table creation in PROC SQL, e.g.

   ```sas
   proc sql; create table MYTABLE as
      select symbol, date, time, bid, ofr from taq.cq_20080602;
   quit;
   ```

   produce a change in record order vs. the source dataset? The empirical answer (tested on samples
   covering over 2 billion TAQ quote records) is NO, even though SAS documentation says order
   preservation is not guaranteed.

2. Does adding an "ORDER BY" clause, e.g.

   ```sas
   proc sql;
       create table MYTABLE as
       select symbol, date, time, bid, ofr from taq.cq_20080602
       order by symbol, date, time;
   quit;
   ```

   change the relative order of "tied records" (i.e. records with the same SYMBOL DATE TIME)? The
   answer is YES, for every one of a battery of tests that used a sample with more than 2 billions of
   records. [...] while this can preserve original order when all the records have unique sort keys,
   it certainly does not preserve original order of tied records (unlike PROC SORT).

[...] Every TAQ quote and trade dataset is indexed by the variable SYMBOL (stock symbol) and also
sorted by SYMBOL (to be more precise, by SYMBOL-TIME) – i.e. each daily dataset is indexed and sorted
by the same variable.

```sas
proc sql;
    create table mydata as select symbol, date, time, ex, bid, ofr
    from taq.cq_20080602
    where symbol in ('IBM','MSFT');
quit;
```

In this case SAS will use the SYMBOL index (if one exists) to access only the records required for
IBM and MSFT. [...] Because the TAQ data are sorted by SYMBOL, each symbol is found in exactly one
unbroken span of consecutive records [...] simple efficiency considerations yield unchanged record
order, as revealed in our tests.

As a complimentary test, we randomly sorted a TAQ dataset, so each symbol had records scattered
throughout, and we built a corresponding index on symbol. We then ran a PROC SQL against it, which
used the index. The resulting table did NOT preserve the order of the input table.

More generally, reordering of WRDS TAQ data does occur when PROC SQL requires two passes of the data -
for instance, when the user adds a GROUP BY or ORDER BY clause [...] Even when the ORDER BY clause
corresponds to the original record order, records with duplicate values of the sort keys (i.e. same
SYMBOL TIME) will likely change order. Another clause that can cause reordering is the "SELECT
DISTINCT" expression.

## Conclusion (verbatim)

If you have used PROC SQL without "ORDER BY" clause to select TAQ quotes or trades on WRDS, it is
virtually certain that no re-ordering within ties occurred. More generally, if a dataset is not
indexed (unlike the TAQ data), or if it indexed by the sorting variable (like the TAQ data), then
output order appears to always match input order, if you avoid ORDER BY, GROUP BY or SELECT DISTINCT.
