**Mapped:** 2026-09-05
**Files analyzed:** 9 create/modify targets (+ tests)
**Analogs found:** 9 / 9 (every target has a real in-repo precedent — this phase invents no new shape)

The single most important finding is in **Section 9 (Convention Conflicts)**:
`base/data.py:Dataset.config`'s setter calls `_reset_symbols()`, which
**reads the zarr store or falls back to `from_raw_data()` — i.e. it triggers a
network fetch/disk read during `__init__`**. A membership dataset derives its
symbol axis from membership intervals, so this path is both wrong and dangerous
for it. Read Section 9 before planning the `BaseDataset` split.

## 2. `base/factor.py` — the precedent extraction (copy this shape exactly)

### 2a. Base-class docstring convention (`base/factor.py:21-33`)

The base states what it holds, what it deliberately excludes, and *why the
exclusion is load-bearing*. Mirror this for `BaseDataset`:

```python
class Factor(ABC):
    """The shared, backend-agnostic factor contract (D-03).

    Everything the model layer needs from a factor lives here: the `config`
    lifecycle, the `XrBackend` storage round-trip (`read`/`save`), the
    `xr.Dataset` feature/label accessors, and the two abstract members
    (`cal`, `_get_factor_names`) each backend implements for itself.

    The base is deliberately free of any KunQuant concept -- no streaming, no
    compiled graph, and no read of the KunQuant-only `mode`/`data_columns`/
    `njobs` config fields. That is what makes a non-KunQuant factor backend
    droppable into `DLConfig.factors` with zero edits to `base/model.py`.
    """
```

### 2b. `__init__` ordering rule — locked by a test (`base/factor.py:35-39`)

```python
    def __init__(self, config: BaseFactorConfig):
        # Ordering is load-bearing: assigning `self.config` fires the property
        # setter below, which runs before `self.data_backend` exists. No
        # setter-reachable method may read the storage backend.
        self.config = config
        self.data_backend = XrBackend()
```

**Critically, `base/data.py:20-22` does the OPPOSITE order:**

```python
    def __init__(self, config: DatasetConfig):
        self.data_backend = XrBackend()
        self.config = config
```

That is intentional and must be preserved — `Dataset`'s setter *does* reach the
backend via `_reset_symbols()`. Do not "harmonize" these two. See Section 9.

### 2c. The overridable seam pattern (`base/factor.py:79-92`)

03-02's answer to "the base's eager default is wrong for one subclass" was a
named hook method, not an `if isinstance` and not a config flag:

```python
def _own_function_sources(cls: type) -> str:
    """Concatenated source of every callable defined DIRECTLY on `cls`. ..."""
    chunks: list[str] = []
    for member in vars(cls).values():
        if inspect.isfunction(member):
            chunks.append(inspect.getsource(member))
        elif isinstance(member, property):
            for accessor in (member.fget, member.fset, member.fdel):
                if accessor is not None:
                    chunks.append(inspect.getsource(accessor))
    return "".join(chunks)
```

## 4. `dataset/backend.py:XrBackend` — the zarr contract the panel must satisfy

`dataset/backend.py:11-50`:

```python
class XrBackend(DataBackend):
    def read(self, path: str, overwrite: bool = False, **kwargs) -> Self:
        if not overwrite and hasattr(self, "data"):
            return self
        if not Path(path).exists():
            raise FileNotFoundError(f"File {path} does not exist.")
        self.data = xr.open_dataset(path, **kwargs)
        return self

    def write(self, path: str, **kwargs) -> Self:
        if not Path(path).exists():
            Path(path).parent.mkdir(parents=True, exist_ok=True)
        kwargs.setdefault("mode", "w")
        self.data.to_zarr(path, **kwargs)
        return self

    def to_internal(self, data: xr.Dataset) -> Self:
        self.data = data
        return self

    def filter_by_date(self, col: str, start_date: str, end_date: str) -> Self:
        self.data = self.data.sel({col: slice(start_date, end_date)})
        return self

    def filter_by_symbol(self, col: str, symbols: tuple[str, ...]) -> Self:
        self.data = self.data.sel({col: list(symbols)})
        return self

    def get_xarray_dataset(self, indexes: Optional[list[str]] = None) -> xr.Dataset:
        return self.data
```

Contract points for the boolean panel:

1. `get_xarray_dataset(["timestamp","symbol"])` **ignores its argument entirely**
   for `XrBackend` — it returns `self.data` as-is. The `["timestamp","symbol"]`
   convention is enforced by *producers*, not by this method. (`PlBackend`'s
   override at line 84-87 does use it, via `set_index`.) So the panel must be
   constructed with dims `timestamp`/`symbol` already correct.
2. `filter_by_date` uses `.sel(timestamp=slice(...))` — requires `timestamp` to
   be a **sorted datetime index coordinate**, or the slice silently returns
   empty/wrong. Sort before writing.
3. `filter_by_symbol` uses `.sel(symbol=[...])` — a symbol in
   `config.symbols` that is absent from the panel raises `KeyError`. Relevant
   because the all-time-union symbol axis (RESEARCH Finding 6) is the thing that
   makes this safe.
4. `read()`'s `if not overwrite and hasattr(self, "data"): return self` —
   a second `read()` is a no-op unless `overwrite=True`. This is why
   `_reset_symbols()`'s `self.read()` is cheap the second time but not the first.
5. `write()` defaults `mode="w"` (full overwrite). `dtype=bool` round-trips
   through zarr fine; no encoding work needed.

Fixture-side confirmation of the same shape (`tests/conftest.py:391-398`):

```python
        dataset = xr.Dataset(
            {
                name: (["timestamp", "symbol"], values)
                for name, values in variables.items()
            },
            coords={"timestamp": timestamps, "symbol": symbol_list},
        )
```

The panel builder should produce exactly this, with a single variable
`is_member` of dtype `bool`.

## 5. `dataset/cleaning.py:clean_market_data` — why `_clean()` must be overridden

`dataset/cleaning.py:165-179`:

```python
def clean_market_data(data: xr.Dataset) -> xr.Dataset:
    """Single entry point called from base/data.py:Dataset.from_raw_data(). ..."""

    data = flag_anomalies(data)

```

`validate_schema` (130-162) hard-raises on missing OHLCV:

```python
REQUIRED_COLUMNS = ("open", "high", "low", "close", "volume")   # line 32

def validate_schema(data, required_columns=REQUIRED_COLUMNS) -> xr.Dataset:
    missing = [col for col in required_columns if col not in data.data_vars]
    if missing:
        raise ValueError(
            f"validate_schema: required column(s) missing from dataset: "
            f"{missing}"
        )
    non_key_columns = [c for c in data.data_vars if c not in required_columns]
    for col in non_key_columns:
        null_count = int(data[col].isnull().sum().item())
        if null_count > 0:
            logger.warning(...)
    return data
```

**Concrete consequence:** a panel whose only data var is `is_member` fails
immediately with
`ValueError: required column(s) missing from dataset: ['open','high','low','close','volume']`.
Even if it passed, `flag_anomalies` (70-127) would append an
`anomaly_flag` variable — via the no-price-columns branch at 88-95 it would be
an all-False array — polluting the panel's `data_vars` with a meaningless second
boolean. Hence `IndexConstituentDataset._clean()` overrides to (at minimum) a
pass-through, ideally to a membership-specific validator (dtype is bool, dims
are exactly `(timestamp, symbol)`, no NaN).

The existing hook docstring already anticipates this (`base/data.py:122-131`):

> "Overridable so a future Dataset subclass whose data isn't OHLCV-shaped
> tabular market data (e.g. unstructured sources like news) is not forced
> through market-specific validation it doesn't apply to."

Also note the module docstring's leaf-purity rule (lines 20-22): "This module is
a leaf: it has zero project-internal imports ... so it can never be the source
of a future import cycle." If a `clean_membership_panel()` is added here, keep
that property.

## 9. Convention Conflicts — READ BEFORE PLANNING

### CONFLICT 1 (blocking design decision): `_reset_symbols()` cannot be inherited as-is

`base/data.py:81-90` (quoted in full in Section 1) does:

```python
    def _reset_symbols(self):
        try:
            self.read()
        except FileNotFoundError:
            logger.warning(...)
            self.from_raw_data()
        symbols = tuple(self._get_symbols())
        self._config.symbols = symbols
```

fired from the config setter whenever `config.symbols is not None`.

For a market dataset this is merely surprising (constructing an object touches
disk). For `IndexConstituentDataset` it is **actively wrong on three counts**:

1. **It re-derives the symbol axis from the store, overwriting the caller's
   request.** `self._config.symbols = tuple(self._get_symbols())` replaces a
   user-supplied 5-ticker list with *every* symbol in the store. For a
   membership panel, the symbol axis is the all-time union derived from
   intervals (RESEARCH Finding 6) — so this either does nothing useful or
   silently discards a legitimate subset request.
2. **The `FileNotFoundError` fallback calls `from_raw_data()`, which for this
   dataset means `_raw_data_to_xr()` → fetcher → HTTP.** Merely constructing
   `SP500ConstituentDataset(config)` on a fresh clone would hit Wikipedia.
   Every test would need the network mock active just to *construct* the object.
   That is a materially worse failure mode than `StockDataset`'s (which only
   reads local parquet), and it directly contradicts the RESEARCH mandate that
   "no test may perform a real network fetch."
3. **It only catches `FileNotFoundError`.** `XrBackend.read` raises exactly that
   (line 20), so a network/parse error from the fallback propagates out of
   `__init__` — an object that cannot be constructed offline at all.

**Recommended resolution (matches the 03-02 precedent exactly):** hoist
`_reset_symbols()` onto `BaseDataset` unchanged, and make it a *named
overridable seam* — the same treatment `_maybe_resolve_factor_names()` got in
`base/factor.py:79-92`, overridden to a no-op in
`base/factor_polars.py`. `IndexConstituentDataset` overrides it to either a
no-op (symbols resolved during `_raw_data_to_xr`) or a read-only variant with no
`from_raw_data()` fallback. Do **not** solve this with an `isinstance` check or
a config boolean flag; 03-02 rejected both.

If the planner instead pushes `_reset_symbols()` down to `MarketDataset`, note
that it is called from the *shared* config setter, so the setter would then have
to be split too — a strictly messier split. The seam is cleaner.

### CONFLICT 2: `__init__` assignment order differs between the two precedents

`base/factor.py:35-39` assigns `config` **first** (with a comment declaring the
ordering load-bearing, and a test `test_factor_init_assigns_config_before_the_
storage_backend` locking it). `base/data.py:20-22` assigns `data_backend`
**first**, because its setter reaches the backend through `_reset_symbols()`.

These are opposite invariants. When writing `BaseDataset`, **keep the
`data_backend`-first order** and add a comment saying so explicitly, or a future
reader will "fix" it to match `Factor` and break `_reset_symbols()`. Consider a
guard test that is the *inverse* of the factor one.

### CONFLICT 3: renaming `Dataset` breaks existing tests and type annotations

- `tests/test_extensibility_contract.py:29` does `from base.data import Dataset`
  and line 83 defines `class FakeDataset(Dataset)` implementing `_raw_data_to_xr`
  / `_to_kunquant` / `_to_nautilus`. If `Dataset` disappears or loses its
  abstract KunQuant/nautilus members, that file must be updated (it should
  subclass `MarketDataset`).
- `base/config.py:7` has `from .data import Dataset` under `TYPE_CHECKING`, and
  `BaseFactorConfig.dataset` is typed `"Dataset"` (line 76). Decide whether the
  factor layer's dataset field is typed against `BaseDataset` or `MarketDataset`
  — KunQuant factors call `dataset.to_kunquant()`, so it is `MarketDataset` in
  practice, but a future constituent-masking consumer would want `BaseDataset`.
- `tests/test_extensibility_contract.py:31-43`'s `CORE_LAYER_FILES` /
  `FORBIDDEN_SUBSTRINGS` purity check does **not** currently include
  `base/data.py`. Adding `base/constituent.py` to `CORE_LAYER_FILES` would be a
  cheap, in-convention win — but be aware `base/constituent.py` legitimately
  needs no market literals, so it should pass as-is.

**Lowest-risk option:** keep the name `Dataset` as an alias for `MarketDataset`
(`Dataset = MarketDataset`) during the split, so `dataset/spot.py`,
`dataset/stock.py`, `base/config.py`, `base/factor.py` and the existing tests
keep working; then re-point them in the same plan and drop the alias. The
planner should decide explicitly rather than discover this mid-execution.

### CONFLICT 4: `DatasetConfig` carries nautilus-only `catalog_path` as a REQUIRED field

`base/config.py:12-15` — `raw_data_dir_path`, `zarr_file_path`, `catalog_path`,
`market`, `frequency` are all positional/required. A constituent dataset has no
catalog and arguably no `raw_data_dir_path` (its "raw data" is an HTTP fetch).
Reusing `DatasetConfig` would force dummy values — the same "meaningless stub"
anti-pattern CONTEXT D-03 is trying to eliminate. This is the argument for
splitting `BaseDatasetConfig` out, mirroring `BaseFactorConfig`.

### CONFLICT 5: `Date.START_DATE = "1900-01-01"` vs `PIT_COVERAGE_START`

The inherited setter defaults `start_date` to 1900-01-01 (`enums/constant.py:5`),
which is 76 years before the S&P's coverage and 107 before NDX's. If the panel
is built over `[config.start_date, config.end_date]` unclamped, it silently
emits an all-False region that *looks like* "nobody was a member," which is
precisely the silent-wrongness RESEARCH Finding 6 warns about. The constituent
config setter must clamp the left edge to the class's `PIT_COVERAGE_START` (or
raise). This is a real behavioural requirement, not a style note.

### Note 6 (not a conflict, but a sequencing hazard, per CONTEXT D-06)

`03-07-PLAN.md` modifies `dataset/stock.py` and `config/__init__.py` against
their pre-03.1 state. Both are touched here. Re-verify `03-07`'s `read_first`
list after this phase lands.
