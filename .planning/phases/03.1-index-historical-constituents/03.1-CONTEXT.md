## D-01 — Scope split: constituents are their own data layer (LOCKED)

数据类，包括纳指和标普的历史成分股变动，日频。成分股数据集包含日期，股票代码"

Two concrete dataset classes, daily frequency, carrying date + ticker. K-line

## D-02 — "纳斯达克指数" means NASDAQ-100 (NDX), not the NASDAQ全市场 (LOCKED)

Asked explicitly because the codebase's existing `nasdaq_all` category means

symbols. The user selected **NASDAQ-100 (NDX)** — ~100 names, ~350 in the
all-time union.

`nasdaq_all` stays as it is. This phase adds a new, third category alongside it.

## D-03 — Abstraction shape: extract `BaseDataset` (LOCKED)

Chosen over a standalone parallel abstraction. Symmetric with what Phase 3's
plan 03-02 did for factors (extract a narrow `Factor(ABC)` so a non-KunQuant
backend does not inherit KunQuant-specific members):

```
base/data.py
  BaseDataset(ABC)                  config lifecycle / read / save /
                                    from_raw_data / _filter / _clean hook /
                                    abstract _raw_data_to_xr()
  MarketDataset(BaseDataset)        abstract _to_kunquant / _to_nautilus
    SpotKlineDataset                (inheritance line changes)
    StockDataset                    (inheritance line changes)

base/constituent.py
  IndexConstituentDataset(BaseDataset)
    SP500ConstituentDataset
    Nasdaq100ConstituentDataset
```

**Why not subclass `Dataset` directly:** `base/data.py:Dataset` declares
`_to_kunquant(data, data_columns)` and `_to_nautilus(data, venue, n_jobs)` as
abstract, and defaults `_clean()` to `clean_market_data()` (OHLCV anomaly
flagging + schema validation). A membership panel has no meaningful
implementation of either abstract method, so direct inheritance would force two
`raise NotImplementedError` stubs — the exact anti-pattern 03-02 just removed
for factors, and the one `dataset/stock.py` still exhibits with its
`raise ValueError("Not finished")` stubs.

The user accepted the blast radius this implies (touching `base/data.py`,
`dataset/spot.py`, `dataset/stock.py` inheritance lines).

## D-04 — Storage: xarray + Zarr boolean panel (LOCKED)

```
<xarray.Dataset>
Dimensions:    (timestamp: N, symbol: M)
Coordinates:
  * timestamp  daily
  * symbol     ticker
Data variables:
    is_member  (timestamp, symbol) bool
```

Chosen over long-format `(date, symbol)` parquet.

**This deliberately diverges from Locked Decision A1 of 02-08-PLAN.md**, which
put `universe.parquet` on PlBackend/parquet on the grounds that it is
reference/metadata rather than pipeline data. The divergence is intentional and
scoped: A1 governs the *interval* reference table, which stays parquet. The
*daily panel* this phase adds is pipeline data — it exists to be consumed by the
factor and model layers as a per-day universe mask — so CLAUDE.md's hard
constraint ("模块间统一使用 xarray（Zarr 落盘）") governs it instead. Do not
"fix" `universe.parquet` to match; both are correct for their own role.

Sizing sanity check: ~1200 symbols x ~12000 days of bool is ~14 MB. Density is
not a concern at this scale.

## D-05 — Scope fence: no K-line downloading in this phase (LOCKED)

The user's original request included downloading all historical daily bars for
these constituents. That work is **explicitly deferred** — it is a separate
concern per D-01, and Phase 2 already ships the machinery for it
(`ingest_tiingo.py --universe ... --as-of-date ...`). Do NOT plan acquisition,
rate-limiting, or resume logic here.

(paid) tier** account, and `base/acquisition.py:79` `download()` is currently a
serial loop with no rate limiting, no retry and no resume — that gap is real but
belongs to the K-line follow-up, not to this phase.
