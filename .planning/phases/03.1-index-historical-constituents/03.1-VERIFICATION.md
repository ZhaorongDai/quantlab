### Hardening Note (advisory, not a gap)

SC-2's "matching `get_symbols_as_of()` exactly" currently holds because two independent
implementations happen to encode the same closed-interval predicate — `_densify()`'s
`(timestamps >= start) & (timestamps <= end)` and `get_symbols_as_of()`'s
`start_date <= as_of & (end_date.is_null() | end_date >= as_of)`. The verifier confirmed
they agree *today* by execution, but **no test in the suite couples them**, so a future
edit to either side would silently break the equivalence with a green suite. The
cross-check the verifier wrote (panel True-set vs `get_symbols_as_of` across the panel's
timestamps) is cheap, offline and fast (~1.8s for both indices) and would be worth keeping
as a permanent regression lock.

One further nuance found while comparing the two: a null `start_date` makes `_densify()`
raise but makes `get_symbols_in_range`/`get_symbols_as_of` silently drop the row (polars
null comparison → filtered out). The panel is the stricter of the two, so this is not a
survivorship hole, but it is a second place the two paths do not agree exactly.

### Gaps Summary

The phase goal — daily point-in-time membership panels for both indices, as `xarray.Dataset`,
Zarr-persisted, survivorship-bias-free, on a shared `BaseDataset` — **is achieved**. Three of
four success criteria verified by execution, including the two that grep alone could not
settle (SC-2's exact-match-with-`get_symbols_as_of` and SC-4's zero-`base/`-edits claim),
both of which the verifier proved by writing and running new code rather than by trusting
the SUMMARYs.

The one gap is narrow but real and observable. SC-3 and DATA-05 both state the guarantee
generically — *a membership query* before coverage start must raise rather than silently
return an incomplete roster. `UniverseCatalog` exposes two membership queries.
`get_symbols_as_of()` raises correctly, registry-driven so a fourth index inherits the
guard. `get_symbols_in_range()` — the query the docs designate for full-window *backfill*,
i.e. exactly the caller that would ask about a multi-decade window — validates the category
token and the ISO date format but never the coverage boundary, and returns silently. The
verifier reproduced both failure shapes: a 1976-censored roster for a 1900–2020 S&P 500
window, and a bare `[]` for a wholly-pre-2007 Nasdaq-100 window. Because `[]` is documented
in this very module as a legitimate answer, the caller has no way to tell "no members" from
"outside coverage."

This is scored a WARNING, not a BLOCKER: the panel — which is what the phase goal and every
downstream masking consumer actually use — is correct, and no downstream code in the tree
currently calls `get_symbols_in_range()` with a pre-coverage window. But the module's own
docstring for that method states the exact principle it fails to apply ("`[]` is a
legitimate answer, so a typo must raise rather than silently ingest nothing"), which reads
as an oversight rather than a scoped decision, and Phase 03.1 is what introduced the second
membership category that now flows through the unguarded path.

**This may be intentional.** 03.1-04-PLAN.md's must-haves deliberately scoped the guard to
`get_symbols_as_of()` ("the explicit-error half of DATA-05"). If the team's reading is that
DATA-05's 显式报错 clause governs only the point-in-time query and that an overlap query is
legitimately answered from whatever coverage exists, add to this file's frontmatter:

```yaml
overrides:
  - must_have: "A membership query before an index's coverage start raises rather than returning a silently incomplete roster"
    reason: "DATA-05's explicit-error clause governs the point-in-time query get_symbols_as_of() only; get_symbols_in_range() is an overlap/backfill query for which a coverage-truncated answer is the intended semantics."
    accepted_by: "{name}"
    accepted_at: "{ISO timestamp}"
```
