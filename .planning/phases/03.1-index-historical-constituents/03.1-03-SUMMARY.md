## Decisions Made

**Calendar-day axis and its downstream join consequence.** The `timestamp` axis is a contiguous `pd.date_range(..., freq="D")` — calendar days, not trading days. A trading-day axis would need a session calendar this repository does not have. The one real consequence, stated in the class docstring and locked by `test_calendar_day_axis_is_contiguous_and_sorted`: a downstream join against OHLCV data, which carries only trading days, must reindex or `.sel()` the panel onto the price panel's timestamps. The weekend and holiday rows carry the last trading day's membership forward.

**Closed-on-both-ends intervals, and the line they match.** A symbol removed with `effective_date` D reads True on D and False on D+1. This is deliberately the same convention as `acquisition/universe.py:UniverseCatalog.get_symbols_as_of`, whose filter is `(pl.col("start_date") <= as_of_date) & (pl.col("end_date").is_null() | (pl.col("end_date") >= as_of_date))`. A divergence here would make the panel and that query disagree by one day at every removal in history, and nothing at runtime would notice — which is why `test_removal_effective_date_is_still_a_membership_day` pins the boolean on exactly `2010-06-15`, `2010-06-14` and `2010-06-16`.

**The two-branch right edge, and why the open branch matters at the live edge.** Let `observed` be the latest date anywhere in the interval table. If ANY interval is still open, `horizon = max(observed, today)`; otherwise `horizon = observed`. The right edge is `min(config.end_date, horizon)`. The today-branch is load-bearing, not a nicety: an open membership is by definition current, so the last change event is only a LOWER BOUND. RESEARCH Finding 2 records the latest real Nasdaq-100 change as 2026-08-04, so a panel stopping at `observed` would end roughly a month short of the present — the phase goal would be met for history and frayed exactly where a universe mask actually gets used. Conversely the `min(...)` is what stops the inherited `Date.END_DATE` ("2100-01-01") from materialising ~45,000 days of fabricated future membership.

**The deliberate warn-on-explicit-request / silent-on-sentinel asymmetry.** One announcement rule, applied to BOTH edges: emit a `logger.warning` naming the requested and resolved dates whenever an edge actually moves AND the pre-move value is not that edge's inherited sentinel (`Date.START_DATE` = "1900-01-01" for the left, `Date.END_DATE` = "2100-01-01" for the right). Both sentinel cases are silent for the identical reason — the caller requested nothing, so warning would fire on every single default construction (`sp500_constituent_config()` with no dates is the common case) and train readers to ignore the log entirely. `test_left_edge_is_clamped_to_the_index_coverage_start` asserts total silence under both sentinels; `..._pre_coverage_start_date_is_clamped_with_a_warning` and `test_right_edge_is_clamped_to_the_observed_horizon_...` are the two tests that force each warning to exist at all.

**The PIT clamp runs at config-assignment time, in a property-setter override.** `IndexConstituentDataset` redefines `config` and calls `BaseDataset.config.fset(self, config)` first (the shared lifecycle fills `name` and the two date defaults the clamp then reads), then `_clamp_coverage_start()`. This makes the clamp assertable on the config object itself (`SP500ConstituentDataset(cfg).config.start_date == "1976-07-01"`) rather than only observable in the panel, and it keeps the inherited `_filter()` consistent with the panel on `read()`.

**`tests/conftest.py` docstring ownership.** This plan owns and fixed the stale docstring at `tests/conftest.py:482-486` (formerly 358-361): `base/data.py:Dataset.config` → `base/data.py:BaseDataset.config`, and "hands the config to a `Dataset`" → "to a `MarketDataset`". The explanation itself is unchanged word for word — it remains the only place in the repository that TEACHES the construction-time-I/O hazard that `_reset_symbols()` is overridden to avoid. 03.1-01 correctly left it alone (`tests/conftest.py` belonged to 03.1-02 in wave 1); this wave-2 plan is the correct owner. ## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `base/constituent.py` imports `enums.constant.Date`, one name beyond the plan's literal import list**

- **Found during:** Task 1
- **Issue:** The plan's `<interfaces>` announcement rule requires comparing the pre-move edge value against the inherited `Date.START_DATE` / `Date.END_DATE` sentinels, but its import list omitted `enums.constant.Date`.
- **Fix:** Added `from enums.constant import Date`, matching `base/data.py`'s own import of the same module. The alternative — hardcoding `"1900-01-01"` / `"2100-01-01"` literals — would silently break if the sentinels ever move.
- **Files modified:** `base/constituent.py`
- **Verification:** All Task 1 acceptance checks pass, including the `'acquisition' not in source` fence, which this import does not affect.
- **Committed in:** `1ac6b7c`

**2. [Rule 1 - Bug] `clean_membership_panel()`'s monotonicity check raised a NumPy `DeprecationWarning`**

- **Found during:** Task 1
- **Issue:** `np.diff(timestamps) > np.timedelta64(0)` compares a `timedelta64[ns]` array against a bare/generic-unit timedelta, which NumPy deprecates and will raise on in a future release.
- **Fix:** Replaced with the dtype-agnostic elementwise `timestamps[:-1] < timestamps[1:]`.
- **Files modified:** `dataset/cleaning.py`
- **Verification:** `uv run pytest tests/test_constituent_panel.py -q` no longer emits the warning; the validation behaviour is unchanged.
- **Committed in:** `1ac6b7c`

### Acceptance criterion adjusted (not weakened)

**3. Task 2's `-k "left_edge or right_edge"` criterion says 3 passed; the actual, correct count is 4**

- **Found during:** Task 2 acceptance verification
- **Issue:** The plan prescribes test 2's name verbatim as `test_open_interval_densifies_true_to_the_right_edge`, which itself matches the `right_edge` selector. Together with the three tests the criterion describes ("the sentinel left-edge clamp and both right-edge branches"), the selector necessarily matches 4, not 3. This is a plan-authoring arithmetic slip, not an implementation defect.
- **Resolution:** Left the plan-prescribed test names intact and recorded the correct count here. Renaming a test purely to satisfy the arithmetic would have been weakening the suite to fit a miscount. All four matched tests pass, and every other Task 2 criterion (`-k removal` → 1, `-k "clamped_with_a_warning or reaching_today"` → 2, module total → 9) matches exactly.
- **Verification:** `uv run pytest tests/test_constituent_panel.py -k "left_edge or right_edge" -q` → `4 passed, 5 deselected`.
