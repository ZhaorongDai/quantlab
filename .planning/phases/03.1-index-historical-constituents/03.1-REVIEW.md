**Reviewed:** 2026-09-07

## Summary

Scope was the 03.1-05 delta: `UniverseCatalog._coverage_start()` /
`_assert_within_coverage()` and the routing of both membership queries through
them, plus the four new `test_universe.py` cases, the new wiring test, and the
two doc updates. `git diff 158a5b0..HEAD` was the unit of review; the wider
`diff_base` was used only for surrounding context.

Against the 03.1-05 `must_haves` the implementation is faithful: the comparison
is a strict `<` (inclusive boundary), `[]` remains a legitimate return for
boundary-free categories, only `start_date` is checked on the interval query,
the boundary is derived from `MEMBERSHIP_FETCHERS` with no category literal in
either query body, and the panel-side clamp asymmetry is documented rather than
"aligned". None of those are reported as findings.

What the delta does **not** hold up against is its own threat model. The guard
it ships is fully bypassable, and I proved the bypass against the live
`data/data/reference/universe.parquet`: `get_symbols_as_of('nasdaq100_constituent',
'20070115')` returns 103 symbols for a date the guard is supposed to refuse.
The whole 03.1-05 premise — "a query date is one somebody actually asked, so a
wrong value is a question, and refusing it is right here" — fails for a class of
input that argparse hands straight through. Three further silent-wrong-answer
surfaces on the same table survive untouched (an inverted window, the
`estimate_dense_panel` family), one load-bearing docstring premise is provably
false against the live table, and one of the two docs updated by this very plan
now misquotes the error message the plan changed.

All 499 tests pass. No finding below is caught by the suite.

## Critical Issues

### CR-01: The new coverage guard is bypassable — `_validate_iso_date` admits non-`YYYY-MM-DD` ISO 8601, and the guard compares lexicographically

**File:** `acquisition/universe.py:1428-1442` (`_validate_iso_date`),
`acquisition/universe.py:1492-1500` (`_assert_within_coverage`), reached from
`:1553-1555` and `:2319-2327`

**Issue:** `_validate_iso_date` gates on `datetime.date.fromisoformat(value)`.
Since Python 3.11 that accepts *any* valid ISO 8601 date, not the
`YYYY-MM-DD` shape its own error message promises — including ISO basic form
(`20070115`) and week dates (`2020-W01-1`). Unlike `BaseDataset._normalize_date`
(`base/data.py`), which re-emits `.isoformat()` precisely because "every
downstream date comparison in this codebase is LEXICOGRAPHIC on these strings",
`_validate_iso_date` validates and discards — the caller's raw string is what
reaches both `date < coverage_start` and the polars filter.

Verified against the live `data/data/reference/universe.parquet`:

| call | expected | actual |
|---|---|---|
| `get_symbols_as_of('nasdaq100_constituent', '20070115')` | raise (2007-01-15 < 2007-02-01) | **103 symbols returned** |
| `get_symbols_in_range('nasdaq100_constituent', '20070101', '2020-01-01')` | raise | **204 symbols returned** |
| `get_symbols_in_range('nasdaq100_constituent', '20100101', '2020-01-01')` | 187 symbols | **184 symbols** (silently wrong roster) |
| `get_symbols_as_of('sp500_constituent', '2020-W01-1')` | raise or 522 | **521 symbols** |

The bypass is arithmetic, not exotic: `"20070101"` vs `"2007-02-01"` compares
`'0'` (0x30) against `'-'` (0x2D) at index 4, so the basic form sorts *after*
every dashed date in the same year and the strict `<` never fires. The dashed
form of the same date raises correctly.

This is reachable from the CLI without any trickery — `utils/cli.py:add_window_args`
declares `--start-date`/`--end-date` as `type=str` with no format constraint, and
`--as-of-date` is the same. So `--start-date 20070101` on a constituent category
resolves a left-censored roster into a multi-year backfill: the exact
DATA-05 failure this plan was written to close, through the guard it added.

`_validate_iso_date` predates the delta, but the delta makes it the sole
precondition of a guard whose docstring claims a one-day-exact boundary, and
this phase's own doctrine ("a wrong value is a question, and refusing it is
right here") does not survive it.

**Fix:** Normalize instead of merely validating, mirroring the pattern already
established one layer over in `base/data.py:_normalize_date`, and use the
normalized value in the guard and the filter:

```python
@staticmethod
def _normalize_iso_date(value: str, field: str) -> str:
    """Validate AND canonicalise to zero-padded YYYY-MM-DD.

    Returning the canonical form is load-bearing, not tidiness:
    `date.fromisoformat` accepts ISO BASIC form ("20070115") and week dates
    ("2020-W01-1") since 3.11, and both compare WRONG against this table's
    dashed strings -- "20070101" sorts AFTER "2007-02-01", so a pre-coverage
    date sails past `_assert_within_coverage`. Same reasoning, and the same
    shape, as `BaseDataset._normalize_date`.
    """
    try:
        return datetime.date.fromisoformat(str(value)).isoformat()
    except (TypeError, ValueError) as exc:
        raise ValueError(
            f"{field} must be an ISO YYYY-MM-DD string, got {value!r}. ..."
        ) from exc

# get_symbols_in_range:
start_date = self._normalize_iso_date(start_date, "start_date")
end_date = self._normalize_iso_date(end_date, "end_date")
self._assert_within_coverage(category, start_date, "start_date")

# get_symbols_as_of:
as_of_date = self._normalize_iso_date(as_of_date, "as_of_date")
self._assert_within_coverage(category, as_of_date, "as_of_date")
```

Apply the same rebinding at `estimate_dense_panel` (`:1634-1635`) and
`:1808-1809`. Add a regression test asserting
`get_symbols_as_of('nasdaq100_constituent', '20070115')` raises — the current
suite would not have caught this.

## Warnings

### WR-01: `get_symbols_in_range` still answers an inverted window with a silent `[]`

**File:** `acquisition/universe.py:1553-1563`

**Issue:** Nothing validates `start_date <= end_date`. Verified against the live
table: `get_symbols_in_range('sp500_constituent', '2020-01-01', '1900-01-01')`
returns `[]`. The coverage guard passes (the left edge is inside coverage), then
the overlap predicate `pl.col("start_date") <= end_date` matches nothing. The
caller gets the module's documented-legitimate `[]` for a window that is not a
window — the precise indistinguishability the delta's own docstring and
`test_get_symbols_in_range_leaves_boundary_free_categories_unguarded` argue is
unacceptable elsewhere. Two-date arguments in the wrong order is a common
mistake, and `resolve_symbols(..., mode="in_range")` feeds these straight from
CLI flags.

**Fix:** Add the ordering check beside the other two validations, and reuse it
in `estimate_dense_panel`, which computes a negative `window_days` for the same
input and floors it to 1 trading day:

```python
if start_date > end_date:
    raise ValueError(
        f"start_date {start_date!r} is after end_date {end_date!r} -- an "
        f"inverted window matches no interval and would return [], which is "
        f"a LEGITIMATE answer here, so the caller could not tell it from "
        f"'no members in this window'."
    )
```

### WR-02: `estimate_dense_panel` runs the same membership-window query and bypasses the shared guard

**File:** `acquisition/universe.py:1634-1657` (and `assert_dense_panel_fits`
`:1738`, `assert_chunked_panel_fits` `:1812`, `assert_acquisition_volume_fits`
`:1990`, which all reach it)

**Issue:** `estimate_dense_panel` validates category and both dates, then applies
a byte-for-byte copy of `get_symbols_in_range`'s overlap predicate (`:1653-1657`
vs `:1558-1562`) — but never calls `_assert_within_coverage`. Verified:
`estimate_dense_panel('sp500_constituent', '1900-01-01', '2020-01-01')` returns
`symbols=766, trading_days=30240` for the identical window
`get_symbols_in_range` now refuses. The delta's stated goal was one contract
rather than two that can drift; there is a third, and it is the one that gates a
real fetch in `ingest_tiingo.py:142`.

Secondary consequence: `test_estimate_dense_panel_reports_a_coherent_density`
(`tests/test_universe.py:1202-1204`) pins
`est["symbols"] == len(catalog.get_symbols_in_range(...))`. That identity is now
unsatisfiable for any pre-coverage window — one side raises. The test passes only
because it uses `us_all`, a boundary-free category.

**Fix:** Route `estimate_dense_panel` through the same helper, so the three
membership-window surfaces share one boundary:

```python
self._validate_iso_date(end_date, "end_date")
self._assert_within_coverage(category, start_date, "start_date")
```

If sizing a pre-coverage window is deliberately allowed (it produces a
30,240-trading-day figure that is nonsense either way), say so explicitly in the
docstring and clamp `start_date` to the coverage start before deriving
`window_days`, rather than leaving the omission silent.

### WR-03: The docstring's load-bearing premise for "raise rather than clamp" is false against the live table

**File:** `acquisition/universe.py:1535-1541`

**Issue:** The new docstring justifies raising over clamping with: "every
membership interval already starts at or after its own coverage start, so
raising `1900-01-01` to `1976-07-01` leaves the overlap predicate's result set
IDENTICAL." Measured against `data/data/reference/universe.parquet`: **74 of 905
`sp500_constituent` rows start before `PIT_COVERAGE_START`**, minimum
`1957-03-04` (PEP, OXY, CL, ADM, GIS, KR, PEG, EXC, ...). They come from
`reconstruct_intervals`'s third branch, `anchor_date_added.get(sym) or
PIT_COVERAGE_START` (`:1022`), where the S&P 500 anchor CSV supplies a real
`Date added` decades before 1976. `nasdaq100_constituent` has 0 such rows only
because its anchor carries no `date_added` at all.

The *conclusion* (raise, not clamp) still happens to hold today, because all 74
are open-ended (`end_date is None`) and therefore overlap either window. But the
stated invariant is wrong, it is stated as fact in a module that treats stated
invariants as contracts, and the only test that pins it
(`tests/test_universe.py:365`, `intervals["start_date"].min() >=
PIT_COVERAGE_START`) covers the Nasdaq-100 alone and would fail if applied to the
S&P 500.

**Fix:** State the actual invariant and the actual reason:

```
Raise rather than clamp, because clamping buys nothing and costs the caller
the signal: intervals that DO start before the coverage start (74 sp500 rows
do, from the anchor's own `date_added`, min 1957-03-04) are all open-ended,
so they overlap the clamped window and the unclamped one alike. Clamping
would hand back the same roster with only a log line to distinguish it ...
```

### WR-05: The registry-driven boundary never validates the one thing registration supplies

**File:** `acquisition/universe.py:1446-1467` (`_coverage_start`), `:543`
(`PIT_COVERAGE_START: str` on the ABC)

**Issue:** `_coverage_start` reads `fetcher_cls.PIT_COVERAGE_START` off every
registered class and feeds it into a lexicographic `<`. Neither the value's shape
nor its presence is checked anywhere:

- A subclass that registers `"2010-1-1"` or `"20100101"` breaks the comparison
  silently and in both directions (`"2010-06-30" < "2010-1-1"` is True), i.e. it
  refuses dates inside coverage and admits dates outside it.
- `PIT_COVERAGE_START` on `IndexMembershipFetcher` (`:543`) is a bare annotation
  with no value, so a subclass that forgets it raises `AttributeError` from
  inside a private helper rather than a message naming the class.

This directly undercuts the delta's headline claim — "a fifth index inherits a
coverage boundary by REGISTRATION, never by someone remembering to add an `if`".
Registration is exactly where the unchecked input enters. Every other data-driven
constant in this module (`MIN_ROSTER_ROWS`, `MIN_ANCHOR_ROWS`,
`EXPECTED_SOURCE_HEADER`) carries a guard; this one does not.

**Fix:** Validate at lookup, where the cost is one line and the message can name
the offender:

```python
coverage_start = {...}.get(category)
if coverage_start is not None:
    try:
        if datetime.date.fromisoformat(coverage_start).isoformat() != coverage_start:
            raise ValueError
    except ValueError:
        raise ValueError(
            f"{category}: PIT_COVERAGE_START must be zero-padded ISO "
            f"YYYY-MM-DD, got {coverage_start!r}. It is compared "
            f"LEXICOGRAPHICALLY against query dates, so a non-canonical "
            f"value admits pre-coverage dates and refuses covered ones."
        ) from None
return coverage_start
```

Plus a registry test asserting every `MEMBERSHIP_FETCHERS` entry defines a
canonical `PIT_COVERAGE_START`, in the idiom of
`test_roster_fetchers_registry_is_disjoint_from_membership_fetchers`.

### WR-06: The four new coverage tests assert only "some `ValueError`"

**File:** `tests/test_universe.py:1089-1090`, `:1108-1111`;
`tests/test_ingest_tiingo_universe_wiring.py:245-246`

**Issue:** `get_symbols_in_range` raises `ValueError` for four distinct reasons
(unknown category, non-ISO `start_date`, non-ISO `end_date`, coverage). The new
tests use bare `pytest.raises(ValueError)` with no `match=`, so they pass on any
of the four — they do not pin that the *coverage* guard is what fired. The
sibling tests written earlier in the same file for the weaker properties
(`test_get_symbols_in_range_rejects_an_unknown_category:1054`,
`..._rejects_a_non_iso_date:1067`) both use `match=`, so this is a step down from
the module's own standard on the assertion that matters most. The wiring test at
`test_ingest_tiingo_universe_wiring.py:245` is the loosest: `resolve_symbols`
raises `ValueError` for a bad `mode` as well.

**Fix:** Match on text only the coverage guard emits — the new `field=` fragment
makes this exact:

```python
with pytest.raises(ValueError, match=r"start_date='1900-01-01' precedes it"):
    catalog.get_symbols_in_range("sp500_constituent", "1900-01-01", "2020-01-01")
```
