**GAP 1 — missing coverage, DATA-05 (RESOLVED).** WR-05: `_coverage_start` reads
`PIT_COVERAGE_START` off every registered class and feeds it into a lexicographic `<`
with nothing checking the value's presence or shape. This is the same failure mode as
CR-01 (fixed in `58d00ab`) at the OTHER entrance: CR-01 closed the QUERY side
(caller-supplied dates, via `_normalize_iso_date`); registration was still unguarded.
Closed by two tests in `tests/test_universe.py`, parametrised over the registry so a
third index inherits the check by being registered:
`test_every_membership_fetcher_declares_a_canonical_iso_coverage_start` (presence +
canonical zero-padded `YYYY-MM-DD`) and
`test_coverage_start_lookup_agrees_with_the_registered_constants` (the lookup actually
consults the registry, and roster categories still resolve to `None`).

Proven fail-first against three deliberately-broken registrations — a subclass that
omits `PIT_COVERAGE_START` (the bare annotation at `acquisition/universe.py:543` means
`getattr` yields `None` rather than raising `AttributeError` from a private helper at
query time), one registering `"2010-1-1"`, and one registering `"20100101"` — all four
assertion bodies failed. No temporary reversal was committed; the proof ran from a
scratch module outside the repo.

**Implementation guard deliberately NOT taken.** WR-05 also proposes a lookup-time
`raise` inside `_coverage_start`. It was weighed and declined here, on two grounds.
First, the auditor's contract is that implementation files stay read-only, and this is a
behaviour change (a new exception on a new input class), not a test. Second, the risk
being guarded is *authoring* risk, not *runtime* risk: `MEMBERSHIP_FETCHERS` is a
class-level tuple of in-repo classes with in-repo constants, so a bad value can only
arrive through a commit — and a registry test fails that commit before it ships, at
registration time, naming the class, which is strictly earlier feedback than a lookup
raise on the first query. The lookup guard remains a legitimate defence-in-depth
improvement (it would also cover a hypothetical externally-registered fetcher) and is
left open for the developer; it is not required for DATA-05 to be verified.
