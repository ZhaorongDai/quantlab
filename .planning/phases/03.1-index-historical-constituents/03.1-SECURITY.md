## Audit Notes

### Note 1 — the one `high` threat's mitigation was incomplete at ship time

`T-03.1-05-01` is the only threat at or above the `high` block threshold, so it alone decides
`threats_open`. It must not be read as "grep found `_assert_within_coverage`, therefore closed."

When plan 03.1-05 shipped (`5273dff`..`15ce278`), the guard was **bypassable**. `_validate_iso_date`
gated on `datetime.date.fromisoformat`, which since Python 3.11 accepts ISO *basic* form
(`20070115`) and week dates (`2020-W01-1`), then **discarded the parsed value** — so the caller's
raw string reached a LEXICOGRAPHIC `<`. `'20070101' < '2007-02-01'` is False (at index 4, `'0'`
0x30 vs `'-'` 0x2D), so a pre-coverage date sailed past the guard and returned a left-censored
roster. Reachable from the CLI without trickery: `add_window_args` declares these flags `type=str`.
Measured against the live table: `get_symbols_in_range('nasdaq100_constituent','20070101','2020-01-01')`
returned 204 symbols where it must raise.

This is precisely the Tampering-on-data-integrity failure the row names — arriving *through* the
control added to prevent it. A grep-depth (L1) classification would have marked it closed and been
wrong.

Closed by `58d00ab`: `_validate_iso_date` → `_normalize_iso_date`, returning
`date.fromisoformat(value).isoformat()`, with all 9 call sites across `acquisition/universe.py` and
`utils/cli.py` rebound, plus 3 fail-first regression locks. Independently re-verified by two agents
against `data/data/reference/universe.parquet`, deliberately including **cross-year basic form**
(`19700101`) and **week dates** (`1976-W01-1`, `2007-W01-1`) — the shapes where the index-4
discriminator does *not* bite and a naive probe passes for the wrong reason. All raise, and the
error text quotes the *normalized* date, which is the observable signature that the parse is no
longer discarded.

`threats_open: 0` here rests on that depth verification, not on the short-circuit's grep.

### Note 2 — two `accept` rows are stale in the conservative direction

`T-03.1-02-05` and `T-03.1-03-04` are registered as `accept` on the rationale that the `User-Agent`
carries "a maintainer contact address". The code no longer does. `acquisition/universe.py:71`:

```python
_CONTACT = os.environ.get("QUANTLAB_CONTACT", "https://github.com/quantlab/quantlab")
```

The developer's personal email was removed and replaced with an env var and a neutral project-URL
default, per CLAUDE.md's env-vars-for-anything-sensitive constraint. The real disposition is
`mitigate`, not `accept`. The register is more conservative than the implementation — harmless in
this direction, but recorded so a future audit does not "discover" a risk that was already removed.

Repo-wide credential check run this audit: no hardcoded API keys remain
(`grep -rniE "api_key\s*=\s*[\"'][A-Za-z0-9]{16,}"` over non-test sources returns nothing). This
matters because CLAUDE.md records a real prior leak of a hardcoded Tiingo key.

### Note 3 — the registration-side entrance of the same failure mode

`T-03.1-05-02` claims the boundary is registry-derived so "a fifth index inherits the guard by
registration." Registration was itself the one unvalidated input: `_coverage_start` read
`PIT_COVERAGE_START` off each registered class into a lexicographic `<` with neither presence nor
shape checked. A non-canonical constant fails silently in **both** directions —
`"2010-06-30" < "2010-1-1"` is True (refuses a covered date) and `"2009-06-30" < "20100101"` is
False (admits an uncovered one).

Same failure mode as Note 1, opposite entrance: Note 1 was the query side (caller-supplied dates),
this is the registration side (fetcher-declared constants). Closed by `525c332`, which locks the
registry contract with two parametrised tests. A lookup-time raise in `_coverage_start` was
deliberately *not* added — a bad value can only arrive via a commit, and a registry test fails that
commit at registration time naming the class, which is strictly earlier feedback than a runtime
raise. The lookup guard remains legitimate defence-in-depth for an externally-registered fetcher and
is left open for the developer.
