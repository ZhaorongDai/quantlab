**NORM-01 — the normalization axis. This is now LOCKED as D-09 in `03-CONTEXT.md`; D-09 is the authority and this section restates it. Read both before touching any factor class.**

The user, who is the domain expert on this project, first corrected an earlier reading that treated the missing `WindowedZScore` wrapper in `Alpha101Stock` as a bug:

> "WindowedZScore是时序策略用的 截面策略用截面Z 值"
> (WindowedZScore is for time-series strategies; cross-sectional strategies use a cross-sectional Z-score.)

and then ruled directly on the market-level question, which is what D-09 records:

> "美股都用截面策略，Alpha158Stock 也不要时序标准化"
> (US equities all use cross-sectional strategies; Alpha158Stock should not have time-series standardization either.)

**Consequence: the matrix is uniform per market.** Both crypto-spot classes apply the rolling time-series z-score; both US-equity classes emit raw values. There is no intra-market asymmetry to reconcile and no open question for the user to answer — D-09 settled it before execution begins.

`my_ops/preprocess.py:WindowedZScore` normalizes each symbol's factor value across that symbol's OWN rolling time window — it is the normalization a single-symbol **time-series** strategy (时序策略) wants. A multi-symbol **cross-sectional** strategy (截面策略) wants a cross-sectional Z-score instead: normalize across SYMBOLS at each timestamp. Presence or absence of the rolling z-score wrapper is therefore a **strategy-type choice, not a market-dependent defect**.

**Consequence for this plan: do NOT add the rolling z-score wrapper to EITHER US-equity class.** Do not add it to `Alpha101Stock` to "align" it with `Alpha101SpotKline`, and do not add it to the new `Alpha158Stock` to mirror `Alpha158SpotKline`. Doing either would silently impose time-series normalization on a deliberately cross-sectional US-equity factor set (D-09). The only genuine `Alpha101Stock` defect is the missing `amount` input.

**D-09 supersedes part of D-01.** D-01's "调用的步骤完全一致" (identical invocation steps across markets) governs the `Alpha158.AllData(...)` wiring, the `build({...})` category dict, the double-`AllData` build and the declared-but-unused `Input(...)` nodes — it does NOT govern the normalization wrapper. `Alpha158Stock` emits `Output(v, k)` directly.

**Scope decision for Phase 3 — document the axis, do not build the cross-sectional op.** Reasoning, recorded so it is reviewable:
- `my_ops/preprocess.py` today contains only time-series composite ops (`WindowedZScore`, `WindowedRobustStandardization`, both `WindowedCompositiveOp` subclasses). No cross-sectional normalization op exists in this project.
- KunQuant upstream already supplies the building blocks (`CrossSectionalOp`, `SimpleCrossSectionalOp`, `Rank`, `Scale`), so the extension point exists without this phase inventing an abstraction.
- Normalization is **already selectable per factor class by construction** — it is just an op wrapped around each `Output(...)` inside that class's own `_get_factor_func()`. No new abstraction is needed to make it selectable, so none is added (QUAL-02: no unnecessary code).
- ARCH-01/ARCH-02 ("架构同时兼容单标的时序策略与多标的截面多因子策略") are Phase 6 requirements, not Phase 3 ones. Building a cross-sectional op now would balloon an already refactor-heavy phase.
- D-09 explicitly defers the cross-sectional op to Phase 6 as well: "this phase emits raw US-equity factor values and leaves normalization to the downstream consumer".
- What this plan DOES deliver: the matrix below written into each class's docstring, plus an automated lock so the per-market split stays intentional-and-recorded rather than silent, plus the final matrix and the Phase-6 deferral written into `03-03-SUMMARY.md`.

| Class | Market | Wrapper applied around each `Output(...)` | Strategy type served |
|---|---|---|---|
| `Alpha101SpotKline` | crypto spot | rolling z-score over `self.config.window` | 时序 / time-series |
