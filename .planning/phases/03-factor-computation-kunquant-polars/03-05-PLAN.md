**Verified blocking discovery (supersedes 03-RESEARCH.md's `[ASSUMED]` Pitfall 3, which guessed the constraint was about `num_stock` being a multiple of 8).** The real constraint is on the SIMD block width, and it is architecture-dependent. `KunQuant/Driver.py:97-112` selects `{"float": 8, "double": 4}` with `simd_len ∈ {256, 512}` on x86_64, and `{"float": 4, "double": 2}` with `simd_len == {128}` on aarch64, then raises `RuntimeError: Blocking length {n} is not supported for {dtype} on {arch}` when the product does not land in `simd_len`. `FactorKunQuant._make_stream()` hardcodes the x86 width, so **`init_stream()`/`cal_stream()` raise immediately on Apple Silicon — this project's own development machine.** Executed and confirmed on 2026-09-05.

**Also resolved empirically:** with the width left unset, a full 20-30 step replay succeeded at `num_stock` of 4, 5, 6, 8 and 16, each returning a correctly-shaped, all-finite output buffer. So `num_stock` does **not** need to be a multiple of 8 for correctness. The smoke test still uses 8 symbols — harmless, and it matches the x86_64 block width so the test exercises the same shape on either architecture.

**Trap verified during planning — `init_stream()` raises `RuntimeError: Cannot find the buffer name` for any declared input the selected outputs do not consume.** `init_stream()` (`base/factor.py:113-129`) loops over every name in `config.data_columns` and every name in `config.factor_names`, calling `queryBufferHandle` on each. KunQuant prunes inputs no reachable `Output(...)` uses, so a `data_columns` list wider than the chosen `factor_names` actually need makes `init_stream()` raise. Measured example: with `factor_names=["KMID","VOLUME0","STD5"]`, the compiled stream module exposes handles for `close`, `open`, `volume` and the three factors, but NOT for `high`, `low` or `amount`. The smoke test must therefore pair `data_columns=["open", "close", "volume"]` with exactly those three factor names. This is a property of the existing code, not a defect to fix here — the production Alpha158 config uses the full factor set, which consumes all six inputs.

**Stream-mode preconditions in the existing code.** `init_stream()` sizes the `StreamContext` from `self.num_symbols`, which `FactorKunQuant` resolves in stream mode as `len(self.config.dataset.config.symbols)` — so the factor's `DatasetConfig` must carry a non-None `symbols` tuple. Set `symbols` on the `DatasetConfig` returned by the `spot_kline_zarr` fixture BEFORE constructing the `SpotKlineDataset`, because `base/data.py:Dataset.config`'s setter calls `_reset_symbols()` (which reads the Zarr) whenever `symbols` is not None — the store must already be on disk, which the fixture guarantees. Also note `FactorKunQuant._auto_filter()` is a deliberate no-op in stream mode; `cal_stream()` writes an integer timestamp coordinate, which a date filter would destroy.

**Verified replay recipe.** Build the per-bar dicts from the real dataset adapter rather than hand-rolling the Binance-to-KunQuant rename: call `factor.config.dataset.to_kunquant(("open", "close", "volume"))` once to get `(input_dict, symbols, timestamps)`, where each `input_dict[col]` is a `[time, symbol]` float32 array. Row `i` of those arrays is the bar for `timestamps[i]`. Pass `np.ascontiguousarray(row.astype(np.float32))` per column into `cal_stream(bar_dict, timestamp_int, list(symbols))`. Use the SAME `Dataset` instance the factor holds so the symbol ordering matches the stream context's.

**Verified output shape.** `getCurrentBuffer(...)` returns a `(num_symbols,)` float32 buffer, which `cal_stream()` wraps with `np.expand_dims(..., axis=0)` into `(1, num_symbols)`. After the final replay step, `factor.get_features()` therefore has `sizes == {"timestamp": 1, "symbol": 8}` with one variable per factor name — `get_features()` reflects only the most recent bar, since each `cal_stream()` replaces the backend's data. Capture intermediate values inside the loop if you need to compare two steps.

**Verified cross-backend combine (the D-03 proof's one real risk, checked on 2026-09-05).** `Alpha158SpotKline.cal().get_features()` and a `FactorPolars`-shaped result built from the same synthetic store both carry `timestamp` as `datetime64[ns]`; the `symbol` coordinate dtype differs (`<U6` from the KunQuant path, `object` from the pandas/polars path) but `xr.combine_by_coords([...])` handles it and returns `{'KMID', 'momentum_5'}` over `{'timestamp': 60, 'symbol': 8}`.
