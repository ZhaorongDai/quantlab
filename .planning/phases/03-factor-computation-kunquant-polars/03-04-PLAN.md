**The seam 03-02 built for this plan.** `Factor` (in `base/factor.py`) already provides `read`, `save`, `get_features`, `get_labels`, `get_config`, `_reset_dataset_config`, `_auto_filter`, `symbols`, `num_symbols`, `num_factors`, `import_path`, `class_name` and the `config` property, and declares `cal()` and `_get_factor_names()` abstract. `Factor._auto_filter`/`symbols`/`num_symbols` deliberately do NOT read `config.mode`, so `PolarsFactorConfig` — which has no `mode` field — works with all of them unmodified. `Factor.config`'s setter calls the overridable `_maybe_resolve_factor_names()` hook; that hook is the seam this plan overrides.

**Why `_maybe_resolve_factor_names()` must become a no-op on `FactorPolars` (03-RESEARCH.md "The `_get_factor_names()` timing split").** The inherited eager default resolves `factor_names` during config assignment, i.e. inside `__init__`. For the Polars path, resolving names means reading the lazyframe schema, which requires `self.config.dataset`'s backend to already hold data — `XrBackend.get_lazyframe()` calls `self.data.to_dataframe()` and raises `AttributeError` if no prior `read()` happened. Keeping the eager default would make merely CONSTRUCTING a factor object trigger a disk read, contradicting D-04's "computation starts at `cal()`". So `FactorPolars` overrides the hook to do nothing and assigns `self.config.factor_names` inside `cal()` instead.

**The resulting, deliberate, narrow caveat (03-RESEARCH.md Pitfall 4).** `FactorPolars._get_factor_names()` and therefore `num_factors` raise until `cal()` or `read()` has populated `config.factor_names`. This is documented, not accidental: `base/model.py` always calls `.cal()`/`.read()` on every factor inside `collect()` before it ever calls `_get_factor_names()` (verified against `base/model.py:115-201`), so no code path exercised by this phase or by Phase 4's model layer as currently written hits it. Record the precondition in `FactorPolars._get_factor_names()`'s own error message and in the class docstring.

**Verified `cal()` chain — executed against this repo's polars 1.44.1 and a synthetic Zarr store on 2026-09-05, producing an `xr.Dataset` with `{'timestamp': 30, 'symbol': 4}` and a single `momentum_5` variable. Do not substitute a different idiom.**
1. `lf = self.config.dataset.read().get_lazyframe()` — `Dataset.read()` returns `self`, and `XrBackend.read()` is a no-op when data is already loaded, so this is safe to call repeatedly.
2. `factor_lf = self._get_factor_lazyframe(lf)` — the subclass hook.
3. `factor_lf.collect_schema().names()`, minus `{"timestamp", "symbol"}`, gives the factor names (D-05). `collect_schema()` is schema-only and does not materialize; it is the correct primitive and replaces the deprecated, more expensive `.columns` property.
4. `factor_lf.collect().to_pandas().set_index(["timestamp", "symbol"])` then `xr.Dataset.from_dataframe(...)` — the exact conversion idiom already used by `dataset/backend.py:PlBackend.get_xarray_dataset()` and by `dataset/stock.py`/`dataset/spot.py`'s `_raw_data_to_xr()`. Do not invent a new one.
5. `self.data_backend.to_internal(ds)` then `self._auto_filter()` then `return self` — mirroring the tail of `FactorKunQuant._to_xarray_dataset()`.

**Laziness of the RAW data load, stated precisely (03-RESEARCH.md Pitfall 5).** `XrBackend.get_lazyframe()` is `pl.from_pandas(self.data.to_dataframe().reset_index()).lazy()` — the underlying materialization is eager on both backends (`FactorKunQuant.cal()` likewise fully reads the dataset via `to_kunquant()`). D-04's guarantee applies to the DERIVED factor computation graph — the expression chain the subclass builds on top of `lf` — not to the raw load. Do not describe it otherwise in docstrings.

**Raw column names the example factor is written against (03-RESEARCH.md Pattern 4).** `Dataset.get_lazyframe()` returns whatever column names the underlying Zarr store holds, un-normalized. Verified for `SpotKlineDataset`: `['timestamp', 'symbol', 'Close', 'High', 'Low', 'Open', 'Quote asset volume', 'Volume']` — Binance Title-Case. `StockDataset` returns lowercase raw plus `adj*` columns instead. There is no `get_lazyframe()` equivalent of `_to_kunquant()`'s per-subclass rename step, and adding one is explicitly out of scope for this phase (03-RESEARCH.md Open Question 2). `Momentum` is therefore written against `SpotKlineDataset`'s Title-Case `Close`, and its docstring must say so and point at that open question.

**Layer conventions to follow (03-PATTERNS.md §8, §9).**
- Fluent returns: `cal()` must be annotated `-> Self` and `return self`, because `base/model.py` chains `.cal().get_features()`.
- Hook naming: `_get_x()` is the subclass hook taking already-materialized input; `get_x()` is the public wrapper. `_get_factor_lazyframe` follows this.
- Concrete factor constructors take the parameter name `factor_config`; the ABC's own `__init__` uses `config`.
- The `_get_labels` refusal idiom used by every feature-only factor class: raise `RuntimeError(f"{__class__.__name__} does not support get_label()")` using the implicit-closure `__class__` form, with `_get_features` returning `data` unchanged. `from typing import NoReturn` is imported for exactly this.
- Timing: wrap the expensive step in `with Timer(f"{self.__class__.__name__}: cal"):` from `utils/timer.py`.
- New Phase-3 code uses English comments with decision-ID references (`# D-05: ...`), unlike the hoisted Chinese in `base/factor.py`.

It must contain no reference to a concrete `Dataset` subclass name and no market literal — `Momentum`'s knowledge that its data is Binance-shaped lives in `factor/momentum.py`, which is not a core-layer file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Subclass-authored Polars expression <-> `FactorPolars.cal()` | User factor logic is arbitrary Polars code executed in-process; `cal()` is where its output shape becomes a pipeline artifact |
| Collected Polars frame <-> `xr.Dataset` pipeline boundary | The conversion point where FACTOR-04's "xarray only between modules" constraint is either upheld or broken |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04-01 | Tampering (contract integrity) | `base/factor_polars.py:FactorPolars.cal` | high | mitigate | If `cal()` returned or persisted a DataFrame instead of an `xr.Dataset`, a plain DataFrame would cross a module boundary and violate the project's hard constraint. Task 3's `test_momentum_cal_returns_xarray_dataset_with_only_factor_columns` asserts the concrete return type and exact variable set; 03-02's `test_public_factor_api_exchanges_only_xarray_datasets` covers the signatures |
| T-03-04-02 | Information Disclosure (data leakage across the contract) | subclass `_get_factor_lazyframe` implementations | medium | mitigate | A hook that forgets its final `select(...)` leaks raw price/volume columns into the persisted factor store as if they were factors. The `sorted(result.data_vars) == ["momentum_5"]` assertion catches exactly this, and the abstract method's docstring states the constraint at the point a new author reads it |
| T-03-04-03 | Denial of Service (unintended eager materialization) | `FactorPolars._get_factor_lazyframe` contract | low | mitigate | A subclass that materializes inside the hook would silently collect the full dataset once per call. The `monkeypatch`-based laziness test makes any such call an immediate hard failure rather than a silent performance cliff |
| T-03-04-SC | Tampering | npm/pip/cargo installs | n/a | accept | Zero new packages installed — `polars>=1.44.1` is already declared in `pyproject.toml` and installed. 03-RESEARCH.md records the Package Legitimacy Audit as "Not applicable"; no `[ASSUMED]`/`[SUS]` package exists, so no legitimacy checkpoint applies |

**Register is deliberately minimal, not omitted:** this plan adds in-process computation over already-local Zarr data with no credential, network call or external integration (03-RESEARCH.md Security Domain).
