# Phase 03.4: Data Source Registry (Operator-Surface Foundation) Verification Report

**Phase Goal:** Every data source quantlab can acquire is described by ONE registered descriptor,
so both quantlab's own code and an out-of-repo operator console enumerate the same sources from the

## Verdict in one paragraph

The registry itself is real, complete and genuinely load-bearing. Five of the six ROADMAP success
criteria are verified behaviourally, not by reading SUMMARY files: a cold subprocess import of
`quantlab.acquisition.registry` alone enumerates both vendors with their capabilities, credential
env var NAMES and acquisition classes; a planted credential value appears in no return, repr or
exception message; the inspector answers with no credentials and pulls in no vendor module at all;
coverage judgement is provably ONE function object; and all three ingest shells reach their vendor
only through the descriptor. The phase also does the thing it claims to do best — three independent
source mutations I introduced were each caught by its own locks (details below).

One success criterion does not hold in substance. `_merge_unattempted_failures` guards the cancel
exit and only the cancel exit, so the DEFAULT quota-abort path destroys the previous run's failure
manifest. I reproduced this with an executing test rather than inferring it from the review. The
phase's own agreement invariant still reads green over the destruction, and the reason it does is
worth more than the bug: the invariant is a tautology.

## The SC-5 judgement call, stated explicitly

I was asked whether SC-5 counts as MET when the agreement invariant holds but the manifest is
factually destroyed on the default quota path. It does not, and here is the reasoning rather than
the score.

**The literal ROADMAP wording of SC-5 survives CR-01.** SC-5 names the *store and watermarks* as
what must stay resumable, and they do — I proved it by re-running after a cancel and observing zero
re-downloaded work. SC-5 names the *result object* as what must name successes and failures, and it
does. SC-5 does not mention `_failures.json` at all. Read strictly as a sentence, SC-5 passes.

**I am not scoring it that way, for three reasons.**

First, the ROADMAP itself assigns the manifest to SC-5. Its plan list reads: *"03.4-05-PLAN.md —
Progress events through a pluggable reporter + a cancel token at the batch boundary, **with the
result object and the failure manifest kept in agreement** (SC-5, D-13, D-16..D-19)"*. The phase
chose SC-5 as the manifest's home. Reading SC-5 narrowly enough to exclude the manifest would be
reading it more narrowly than the phase that wrote it did.

Second, "kept in agreement" was chosen as a *proxy* for "the manifest is a trustworthy operator
record". The proxy passes while the property fails. I verified the destruction and the invariant in
the same test run: `quota_aborted: True`, `cancelled: False`, `result.failures: {}`,
`manifest ON DISK: {}`, and `set(result.failures) == set(manifest): True`. A green invariant sitting
directly on top of a destroyed record is not evidence of correctness — it is evidence that the
invariant was the wrong thing to pin.

Third, and this is the part I think matters most: **the invariant is structurally incapable of
failing.** `_run` assembles the manifest and the result from the same `failures` dict at the same
point, and the code comment at `acquisition.py:1476-1482` says so proudly. No mutation of the
manifest's *contents* can ever break `set(result.failures) == set(manifest)`, because both sides
move together by construction. The phase's D-18 tests are therefore a tautology dressed as a
consistency check. They cannot fail, so their passing carries no information about manifest
correctness. That is why 732 green tests and a careful `_merge_unattempted_failures` for the cancel
path coexist with a wide-open hole on the more common path.

**Blast radius.** `wait_for_quota` defaults to `False`, and quota exhaustion is the *expected*
outcome of the full-market `us_all` backfill this phase exists to support — the 2026-09-06 incident
that motivated the quota handling burned ~10,000 symbols. So this is not an exotic path; it is the
path an operator hits on the job the registry was built for. After it, `SourceInspector.failures()`
— the SC-3 "failure reasons" answer, and the one the out-of-repo console renders — reports a clean
store for one holding un-retried failures. The `waits >= max_waits` exit has the identical hole.

**What makes it a phase-scoped gap rather than a pre-existing one.** The phase *identified* this bug
class, *wrote the fix* (`_merge_unattempted_failures`), *documented why it matters* at length in
that method's own docstring, and then wired it into one of the three exits that need it. The
docstring even asserts the premise that is false: *"That was safe while every run either completed
or quota-aborted, because such a run reaches (or explicitly declines to speak for) every symbol."*
A quota abort does neither — its own log line reads *"{remaining} remain"*.

**Cost to close: small.** Moving the single existing call to immediately before
`_write_failure_manifest` covers every exit path by construction. No new mechanism is needed.

## Gaps Summary

The registry this phase set out to build exists and works. Adding a vendor really is registering a
descriptor: the descriptor carries capabilities, credential names, acquisition class and config
factory; enumeration is complete from a cold import with an empty package `__init__`; and all three
in-repo shells reach their vendor only through it, so the registry has a real consumer here and
cannot rot into a console-only side table. The credential rule is airtight — I tried to leak a
planted value through every return, repr and exception message the registry offers and could not.
Coverage judgement is one function object, proven by mutation rather than by results that agree.
The atomic-write extraction is genuine: one implementation, four callers, and its durability tests
bite when I break them.

Two gaps stand between this and a passing verdict, and they are the same gap seen from two angles.

**The manifest is not durable on the path an operator will actually hit.** `_merge_unattempted_failures`
exists, is correct, is well-documented, and is wired into one of the three exits that need it. The
default quota abort — `wait_for_quota=False`, which is the expected end of the `us_all` backfill this
registry was built to serve — erases the previous run's recorded failures and writes `{}`, the value
the writer's own docstring defines as "the last run was clean". The console then renders a clean
store for one holding un-retried 404s. The fix is to move one existing call; no new mechanism is
needed.

**The phase could not see this, and the reason generalises.** D-18 pinned
`set(result.failures) == set(manifest)` as the consistency check, but `_run` builds both sides from
one dict at one point, so the equality cannot fail no matter what the dict contains. It is an
identity, not a check. Every other lock in this phase pins a *property* and consequently bites when
mutated — I confirmed that four times. This one pins a *construction* and consequently never bites.
When the closure plan lands, the regression test must assert on the manifest's *contents* after a
quota abort, not on its agreement with the result object.

The documentation gap is the same fact reaching the reader. Both the ROADMAP and
`example/acquisition.md` assert that nothing under `quantlab/` reads `_failures.json` and then name
a reader two lines later; this phase added two readers. Plan 07's must-have specified that
contradiction verbatim, so the executor wrote what it was asked to write — the defect is upstream,
in the plan text, and worth noting as a pattern: a factual correction (D-18) was itself made stale
by the same phase that applied it.

Nothing here is deferred to a later phase. Phase 4 is the baseline return-prediction model and
touches none of this.
