Purpose：这是同一形状在本阶段的第 4 次复发。三次修复各自覆盖了大部分实例、漏掉少数，
于是同一份文件里一句陈述与它自己的反面并排站着 —— `quantlab/base/coverage.py` 的
`read_failure_manifest` 摘要行说清单是最近一次 run 的，往下 5 行同一段 docstring 自己说
merge 会把 previous run 的条目折回来。这不是措辞洁癖：`SourceInspector.failures` 是本阶段
目标里「仓库外运维控制台」唯一调用的失败入口，而这句摘要行是**可执行地假**的 ——
`tests/test_acquisition_progress.py` 在 HEAD 上绿着，它断言该方法返回了一个「最近一次 run」
根本没请求过的 `AMZN`。控制台作者照摘要行写出来的任何断言，都会在第二次 run 上炸。

**根因不在扫描机制，在词表来源。** 上一轮的 `manifest_semantics_scan.py` 机制是好的
（7 个 mutation 全部按预期转红，包括跨行中文短语与跨相邻字符串字面量拼接），但它的 11 条
pattern 是把上一版 VERIFICATION 里列的 6 个变体**原样搬过去**的，而那 6 个从来不是穷举。
所以本计划的第一件事不是修文档，而是把验收工具换成**能枚举候选集**的那一类：把 manifest
语义类词与 run-scope 语义类词在归一化文本上求交，列出全部命中句子**逐句判读**。规划阶段
在 HEAD 上实测过这个候选集的规模（准确数字见 Task 1，本文不复述 —— 同一个数字在一份文件里
出现四遍，就是四个各自会过期的副本，而这正是本计划要修的那个毛病）—— 人读一遍不到十分钟，而它一次就找齐了
单词表三轮没找齐的东西。

顺序是这个计划的全部要害，写在这里免得被当成实现细节：
**枚举候选集 → 逐句判读并提交 → 改写 STALE 的句子 → 退役记录留档**。
扩字面量词表是下一份计划（03.4-11）的事，输入只能是本计划落下的退役记录。
反过来做 —— 先想出几条 pattern、再声称覆盖完整 —— 就是前三次漏掉的那个动作。

Output：一个候选集枚举器 + 一份逐句判读账本 + 一份退役记录，以及五处被改写的表述。
